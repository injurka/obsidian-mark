Концепция дериваций

До сих пор мы рассматривали язык Nix как способ описания данных — списков, множеств атрибутов, строк, функций. Теперь мы подходим к тому, *как* Nix использует эти описания для построения реальных программ, библиотек и компонентов системы. Центральную роль в этом процессе играют **деривации (derivations)**.

### Что такое деривация?

Представьте себе очень подробный, точный и неизменный **рецепт** для создания какого-либо программного компонента (пакета, конфигурационного файла, скрипта и т.д.). Этот рецепт содержит абсолютно всё, что нужно знать для его воспроизводимого приготовления:

1.  **Точные ингредиенты:** Какие конкретные версии исходного кода, зависимостей (других пакетов/библиотек), патчей и инструментов для сборки нужны. Важно, что это не просто "библиотека X", а "библиотека X, находящаяся по точному пути `/nix/store/hash-библиотека-X`".
2.  **Инструменты:** Какая программа будет выполнять "приготовление" (например, стандартная командная оболочка `/bin/sh`).
3.  **Пошаговая инструкция:** Детальный скрипт, описывающий все шаги сборки (распаковка исходников, применение патчей, конфигурирование, компиляция, установка).
4.  **Условия приготовления:** На какой архитектуре и операционной системе должна происходить сборка (например, `x86_64-linux` или `aarch64-darwin`).
5.  **Ожидаемый результат:** Как должен называться и где должен располагаться конечный продукт (уникальный путь в `/nix/store`).

Вот эта полная спецификация, этот "рецепт", и есть **деривация** в Nix.

**Ключевые моменты:**

*   **Деривация — это не сам пакет:** Это не скомпилированная программа или библиотека. Это *описание того, как* эту программу или библиотеку получить.
*   **Деривация — это значение в Nix:** В языке Nix деривация представляется как особый тип данных (обычно результат вызова функции `mkDerivation` или подобных).
*   **Деривация хранится в Nix Store:** Когда Nix "инстанциирует" деривацию, он создает специальный текстовый файл с расширением `.drv` в директории `/nix/store`. Например: `/nix/store/agy1wnq3zqv3q5q4n2f9kzzq6a7z9z1j-bash-5.2-p15.drv`. Этот `.drv` файл содержит всю информацию "рецепта" в сериализованном виде. Именно этот `.drv` файл Nix использует для выполнения сборки.
*   **Уникальность и чистота:** Путь к `.drv` файлу (и его содержимое) зависит от *всех* входов, упомянутых в рецепте. Любое изменение в исходниках, зависимостях, скрипте сборки или флагах компиляции приведет к созданию *новой*, другой деривации с другим хешем в имени файла. Это гарантирует, что каждая деривация точно описывает один конкретный процесс сборки.

### Как создаются деривации? Функция `mkDerivation`

Хотя можно было бы вручную описывать все детали деривации, это было бы очень утомительно и подвержено ошибкам. В экосистеме Nix, особенно в репозитории `nixpkgs` (огромной коллекции пакетов Nix), для создания дериваций используется стандартная **встроенная функция** (предоставляемая `nixpkgs`) под названием `mkDerivation`.

`mkDerivation` — это функция Nix, которая принимает на вход **множество атрибутов (attrset)**. Эти атрибуты описывают пакет на более высоком уровне, а `mkDerivation` уже сама генерирует детальный скрипт сборки и все остальные низкоуровневые детали для `.drv` файла.

**Типичные аргументы для `mkDerivation`:**

*   `pname` (или `name`): Название пакета (например, `"bash"`).
*   `version`: Версия пакета (например, `"5.2-p15"`).
*   `src`: Источник пакета. Обычно это результат вызова другой функции, скачивающей исходный код (например, `fetchurl`, `fetchgit`). Этот результат является путем в `/nix/store` к скачанным исходникам.
*   `buildInputs`: Список *других дериваций*, которые необходимы во время сборки пакета (например, компилятор `gcc`, инструмент `make`, библиотеки, от которых зависит пакет). Nix гарантирует, что все зависимости из `buildInputs` будут доступны во время выполнения скрипта сборки.
*   `nativeBuildInputs`: Список дериваций, необходимых для сборки, но только на системе сборки (например, `pkg-config`, `bison`). Актуально при кросс-компиляции.
*   `configureFlags`: Список строк, передаваемых скрипту `configure`.
*   `buildPhase`, `installPhase`, `checkPhase`, `fixupPhase`, etc.: Строки, содержащие shell-скрипты, которые переопределяют или дополняют стандартные фазы сборки (если стандартного поведения недостаточно).
*   `meta`: Множество атрибутов с метаданными о пакете (описание, лицензия, домашняя страница, платформа и т.д.).

**Упрощенный пример (концептуальный):**

```nix
# Это Nix-выражение, описывающее, как собрать пакет 'hello'
let
  pkgs = import <nixpkgs> {}; # Импортируем функции и пакеты из nixpkgs
in
pkgs.stdenv.mkDerivation { # Используем mkDerivation из стандартного окружения nixpkgs
  pname = "hello";
  version = "2.12.1";

  # Указываем, где взять исходный код
  src = pkgs.fetchurl {
    url = "mirror://gnu/hello/hello-2.12.1.tar.gz";
    sha256 = "sha256-hash-goes-here"; # Хеш для проверки целостности
  };

  # Указываем зависимости, необходимые для сборки
  buildInputs = [ pkgs.gettext ];

  # Метаданные (описание, лицензия и т.д.)
  meta = {
    description = "A program that produces a familiar, friendly greeting";
    homepage = "https://www.gnu.org/software/hello/";
    license = pkgs.lib.licenses.gpl3Plus; # Используем стандартные определения лицензий
  };
}
```

**Что происходит, когда Nix вычисляет это выражение?**

1.  Он *не собирает* пакет `hello` немедленно.
2.  Он вычисляет все входные данные для `mkDerivation` (включая скачивание `src`, если его еще нет в `/nix/store`, и вычисление дериваций для `buildInputs`).
3.  Функция `mkDerivation` генерирует полную спецификацию сборки.
4.  Nix создает (или находит в кеше) соответствующий `.drv` файл в `/nix/store`, например `/nix/store/xyz...-hello-2.12.1.drv`.
5.  Результатом всего Nix-выражения является *специальное значение*, представляющее эту деривацию (которое неявно ссылается на путь к `.drv` файлу).

### От деривации (`.drv`) к результату в `/nix/store`

Когда вы просите Nix *собрать* (или "реализовать") деривацию (например, командой `nix-build` или `nix build`), происходит следующее:

1.  Nix читает `.drv` файл.
2.  Он проверяет, существует ли уже в `/nix/store` (или в бинарном кеше) *ожидаемый выходной путь*, указанный внутри `.drv` файла (например, `/nix/store/abc...-hello-2.12.1`).
3.  **Если выходной путь существует (кеш):** Сборка не нужна! Nix просто возвращает этот путь. В этом сила кеширования Nix.
4.  **Если выходного пути нет:**
    *   Nix рекурсивно убеждается, что все *входные деривации* (зависимости из `buildInputs` и т.д.) уже собраны и их результаты доступны в `/nix/store`.
    *   Nix подготавливает изолированное, чистое окружение для сборки (обычно с помощью "песочницы" - sandbox). В этом окружении доступны только явно указанные в деривации зависимости и инструменты. Нет доступа к сети (кроме как для скачивания предопределенных источников) или к неявным файлам хост-системы.
    *   Он запускает указанный в деривации `builder` (обычно `/bin/sh`) и передает ему сгенерированный `mkDerivation` скрипт сборки.
    *   Скрипт выполняется в изолированном окружении.
    *   Если скрипт успешно завершается, его результаты (установленные файлы) помещаются в тот самый *ожидаемый выходной путь* в `/nix/store`, который был предопределен в `.drv` файле.
    *   Nix регистрирует этот путь как "валидный" в своей базе данных.

### Зачем всё это?

Концепция дериваций — это основа для главных преимуществ Nix:

*   **Воспроизводимость:** Поскольку деривация фиксирует *все* входы, сборка одной и той же деривации на разных машинах (той же архитектуры) или в разное время должна давать идентичный результат.
*   **Надежность:** Изолированная среда сборки предотвращает влияние случайных факторов хост-системы на результат.
*   **Кеширование:** Если деривация с точно такими же входами уже была собрана кем-то (например, на официальных серверах NixOS) и ее результат есть в бинарном кеше, вам не нужно собирать ее локально — Nix просто скачает готовый результат.
*   **Атомарность:** Сборка либо полностью успешна и результат помещается в `/nix/store`, либо неудачна и никаких следов в выходном пути не остается.

### Заключение

Деривация (`.drv` файл в `/nix/store`) — это формализованный, неизменяемый рецепт сборки программного компонента, сгенерированный из Nix-выражения (часто с помощью `mkDerivation`). Она содержит все необходимые инструкции, зависимости, инструменты и ожидаемый результат. Реализация деривации — это процесс выполнения этого рецепта в чистой среде для получения выходного артефакта в `/nix/store`. Понимание дериваций критически важно для понимания того, как Nix управляет пакетами и конфигурациями.
