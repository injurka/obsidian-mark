**Цель:** Реализовать основной игровой цикл игрока: выбор карты из руки, определение потенциальной цели (поле, сущность, отсутствие цели), проверку всех условий розыгрыша на сервере (фаза игры, ход игрока, наличие карты в руке, стоимость Эфира, допустимость цели согласно правилам карты и состояния поля), трату Эфира и карты, и, при успешной валидации, выполнение действия карты (спавн сущности, применение эффекта, изменение ландшафта).

**Зачем Нужна Эта Система:**

*   **Основное Взаимодействие:** Розыгрыш карт - это центральное действие, которое игрок совершает в Polye для воздействия на игровое поле и противника.
*   **Игровая Логика:** Эта система объединяет многие предыдущие компоненты (карты, экономика, поле, сущности, эффекты) для реализации правил игры.
*   **Сетевой Поток:** Определяет, как клиентский ввод (клик по карте, клик по полю) преобразуется в серверное действие, валидируется и реплицируется всем игрокам.
*   **Валидация и Безопасность:** Все критически важные проверки (хватает ли ресурсов, допустима ли цель по правилам) должны выполняться на сервере для предотвращения читерства.

**Предпосылки:**

*   **Базовая Сетевая Архитектура (Фаза 1):** Реализованы ключевые C++ классы (`AGameModeBase`, `AGameStateBase`, `APolyePlayerController`, `APolyePlayerStateBase`) с базовой сетевой настройкой (репликация).
*   **Система Данных (Фаза 1):** Определены структуры данных (`FCardDataBase`, `FPolyeEffectConfig`, `FFieldUltConfig`, `EPolyeEffectType`, `EPolyeAttributeType`, и т.д.) и `UDataAsset`ы карт (`UPolyeCardData`). Создан Менеджер Данных (`UPolyeCardManager`), доступный через `UGameInstance`, который может загружать данные карт по `FName CardID`.
*   **Система Сущностей и Эффектов (Фаза 1, 2):** Определены базовые сущности (`ABoardEntityBase`, `AUnit`, `AStructure`) с компонентом `UPolyeEffectManagerComponent`, базовый класс эффекта (`UPolyeGameplayEffectBase`) и его наследники. Система эффектов может применять/удалять экземпляры `UPolyeGameplayEffectBase` и модифицировать атрибуты сущностей.
*   **Игровое Поле (Фаза 2):** Реализовано логическое состояние поля (`FPolyeFieldState::BoardState` в реплицируемом `AGameStateBase`), система идентификации полей (`FieldIndex`, `UPolyeBoardStatics` с расчетом соседей). Базовое визуальное представление (`AGameBoard`, `AFieldTile`) обновляется на основе GameState. `AFieldTile` умеет обрабатывать клики (через трассировку луча в `PlayerController`).
*   **Фаза Активации Полей (Шаг 5):** Реализовано управление фазами в GameMode (`EPolyeMatchPhase`). GameMode знает, когда активна фаза хода игрока (`EPolyeMatchPhase::PlayerTurn`).
*   **Система Ландшафтов (Шаг 6):** Реализована привязка ландшафта к полю (`CurrentLandscapeDataAsset` в `FPolyeFieldState`) и управление эффектом Ульты Ландшафта (`GameState::Apply/RemoveLandscapeUltEffectToField`).
*   **Система Карт (Фаза 3, Пункт 1):** Реализована система управления колодой и рукой игрока (`UPolyeCardGameManagerComponent` на `APolyePlayerStateBase`), включая хранение `HandCardIDs` (реплицируется владельцу), счетчики колоды/сброса (реплицируется всем), и серверную логику добора/сброса карт (`Server_DrawCards`, `Server_DiscardCard`).
*   **Система Эфира (Фаза 3, Пункт 2):** Реализован ресурс Эфир (`CurrentEther`, `MaxEther` в реплицируемом `APolyePlayerStateBase`), серверная логика прироста (`Server_GainEther`), траты (`Server_SpendEther`) и проверки стоимости (`Server_CanAfford`).
*   **Управление Ходами:** `AGameModeBase` (сервер) управляет логикой смены ходов и знает, какой игрок сейчас активен (`AGameStateBase::CurrentActivePlayer`).
*   **Обработка Ввода:** `APolyePlayerController` (клиент) может инициировать запросы на сервер через Server RPC. UI может обрабатывать клики по картам в руке и клики по игровому полю/сущностям.

**Ключевые Компоненты и Их Роли в Этом Пункте:**

*   **UI (Клиенты - Визуал/Ввод):** UMG виджеты отображают руку игрока (`WBP_HandPanel`, `WBP_HandCard`). Позволяют игроку кликнуть по карте в руке, чтобы выбрать ее. Управляют процессом выбора цели, если карта этого требует (подсвечивают допустимые цели на поле/сущностях).
*   **`APolyePlayerController` (Клиент-Владелец и Сервер):** На стороне клиента: регистрирует клик по карте в руке, определяет ее `CardID`. В зависимости от типа карты (из ее данных), либо сразу отправляет Server RPC (если нет цели), либо переходит в **режим выбора цели**. В режиме выбора цели, обрабатывает клик по полю/сущности (используя трассировку луча, `UPolyeBoardStatics`, получение Актера), определяет целевую информацию, и отправляет Server RPC (`Server_RequestPlayCard`) с `CardID` и целевыми данными. На стороне сервера: реализует `Server_RequestPlayCard_Validate` (базовая валидация) и `Server_RequestPlayCard_Implementation`, который делегирует основную игровую логику GameMode. Получает Client RPC от сервера с подтверждением розыгрыша, ошибками (недостаточно Эфира, неверная цель), что обновляет UI.
*   **`AGameModeBase` (Сервер):** Центральный обработчик запросов. Реализует функцию `HandlePlayerPlayCardRequest`, вызываемую из Server RPC PlayerController'а. Выполняет **полную, авторитетную валидацию** розыгрыша карты: правильная фаза, ход игрока, карта в руке, стоимость Эфира, допустимость выбранной цели (или ее отсутствие) согласно типу карты и текущему состоянию GameState. Если все проверки успешны, оркестрирует **выполнение действия карты**, вызывает трату Эфира и удаление карты из руки/колоды.
*   **`APolyePlayerStateBase` (Сервер):** Предоставляет серверные функции для проверки `Server_CanAfford(Cost)` и вычитания `Server_SpendEther(Cost)`. Хранит реплицируемый список `HandCardIDs` (владельцу).
*   **`UPolyeCardGameManagerComponent` (Сервер):** Предоставляет серверную функцию `Server_DiscardCard(CardID)` для удаления карты из руки и перемещения в сброс.
*   **`UPolyeCardManager` (Менеджер Данных):** Используется GameMode (на сервере) для получения статических данных карты (`UPolyeCardData`) по `CardID` (стоимость, тип, параметры эффекта/спавна, ссылка на BP сущности).
*   **`AGameStateBase` (Сервер):** Хранит актуальное состояние доски (`BoardState`) и список сущностей (`EntitiesOnField`). Серверная логика розыгрыша карты (в GameMode или менеджере) будет напрямую изменять или использовать данные в GameState (напр., добавлять сущности в `BoardState[FieldIndex].EntitiesOnField`, изменять `FPolyeFieldState` для смены ландшафта).
*   **`ABoardEntityBase` & Наследники (Сервер):** Классы сущностей, которые будут спавнены (для карт Юнитов/Строений) или будут целью эффектов (для карт Событий/Заклинаний). `EffectManagerComponent` используется для применения эффектов.
*   **`UPolyeBoardStatics` (Утилиты):** Используется GameMode (на сервере) для валидации целевого поля (напр., находится ли FieldIndex в пределах доски, является ли полем игрока/нейтральным). Используется PlayerController (на клиенте) для определения FieldIndex кликнутой плитки.
*   **Система Ландшафтов (Шаг 6):** Логика смены ландшафта и управления его Ультой (`AGameStateBase::Apply/RemoveLandscapeUltEffectToField`) будет вызвана, если разыгрывается карта Изменения Ландшафта.
*   **Система Затухающего Влияния (Шаг 5):** `AGameStateBase::CalculateAndApplyInfluence()` будет вызвана, если розыгрыш карты изменяет состояние поля (напр., спавн Строения с фракцией) или сущностей, которые могут влиять на Ауры. (В текущей модели, спавн/удаление сущности уже вызывает перерасчет влияния).

    *   **Роль:** Если выбранная карта требует цели, PlayerController клиента должен определить, по какому полю или сущности кликнул игрок, и отправить эту информацию на сервер вместе с ID карты.

3.  **Серверная Валидация и Выполнение Действия Карты (в `AGameModeBase` или менеджере):**
    *   **Роль:** `AGameModeBase` (или выделенный менеджер, вызываемый им) - это сердце игровой логики розыгрыша карты. Он получает запрос от PlayerController, выполняет все необходимые проверки и, если они успешны, оркестрирует выполнение действия карты.
    *   **Что Хранить Здесь:** Ничего специфичного для этого шага. Он читает данные из PlayerState, GameState, CardManager, и вызывает функции на PlayerState, Componentах, GameState, других Актерах.
    *   **Что Не Хранить Здесь:** Состояние руки/колоды (в компоненте), значения Эфира (в PlayerState), визуальное представление.
    *   **Действие:** Добавить функцию `HandlePlayerPlayCardRequest` в `AGameModeBase.h`. Реализовать эту функцию в `.cpp`, выполнив следующие шаги (в строгом порядке после базовых проверок RPC):
        *   **Проверка Фазы/Хода:** Убедиться, что сейчас фаза хода игрока и что это ход игрока, отправившего запрос.
        *   **Проверка Карты в Руке:** Убедиться, что карта с таким `CardID` действительно находится в `RequestingPlayer->PlayerState->HandCardIDs`.
        *   **Получение Данных Карты:** Использовать `UPolyeCardManager` для получения `UPolyeCardData` по `CardID`. Проверить, что данные найдены.
        *   **Проверка Стоимости Эфира:** Использовать `PlayerState->Server_CanAfford(CardCost)`.
        *   **Валидация Цели:** **Критически важная логика.** В зависимости от `CardType` из `UPolyeCardData`:
            *   Если карта **не требует цели**: Убедиться, что целевые параметры в RPC (FieldIndex, TargetEntity, Location) являются "пустыми" (INDEX_NONE, nullptr, FVector::ZeroVector или специальные значения).
            *   Если карта требует **цель-поле**: Убедиться, что `TargetFieldIndex` валиден (`UPolyeBoardStatics`), что поле существует в `GameState->BoardState`, что оно допустимо для размещения (напр., поле игрока/нейтральное), что оно не занято, если есть лимит на поле.
            *   Если карта требует **цель-сущность**: Убедиться, что `TargetEntity` валиден, что он существует в мире, что он является допустимым типом сущности (Unit/Structure), что он находится на допустимом поле (напр., на доске).
            *   Если карта требует **цель-локацию**: Валидировать `TargetLocation` (напр., находится ли в пределах доски).
            *   Если карта требует **определенный тип цели** (напр., только вражеский юнит): Проверить `TargetEntity->OwningPlayerState` и тип Актера (Cast к `AUnit`).
        *   Если какая-либо из проверок (фаза, карта в руке, стоимость, цель) **не пройдена**: Отправить Client RPC `Client_NotifyGameplayError` игроку с соответствующим сообщением и прервать выполнение.
        *   **Если все проверки успешны:**
            *   **Трата Эфира:** Вызвать `PlayerState->Server_SpendEther(CardCost)`.
            *   **Удаление Карты из Руки:** Вызвать `PlayerState->GetCardGameManagerComponent()->Server_DiscardCard(CardID)`.
            *   **Выполнение Действия Карты (Оркестрация):** В зависимости от `CardType` из `UPolyeCardData`:
                *   *Unit/Structure:* Получить `TSoftClassPtr<ABoardEntityBase>` (или `AUnit`/`AStructure`) из `UPolyeCardData`. Загрузить класс (`LoadSynchronous` на сервере допустимо для небольших BP классов). `GetWorld()->SpawnActor` по WorldLocation поля (`UPolyeBoardStatics::GetWorldLocationForField(TargetFieldIndex)`). Вызвать `GameState->AddEntityToField(TargetFieldIndex, SpawnedEntity)`. Вызвать `GameState->CalculateAndApplyInfluence()` (появление новой сущности может изменить влияние).
                *   *Event/Ability:* Получить `FPolyeEffectConfig` или список `FPolyeEffectConfig` из `UPolyeCardData`. Определить цели эффекта (TargetEntity, сущности на TargetFieldIndex, все сущности, владелец и т.д.). Для каждой цели-сущности, вызвать `TargetEntity->GetEffectManagerComponent()->ApplyEffect(EffectClass, EffectConfig)` (где `EffectClass` берется из `FPolyeEffectConfig`). Для эффектов на поле или глобальных, вызвать соответствующие функции в GameState или других менеджерах. Вызвать `GameState->CalculateAndApplyInfluence()` если эффект меняет источники влияния.

            *   **Уведомление Клиента:** Отправить Client RPC `Client_NotifyGameplaySuccess` игроку (и, возможно, другим клиентам через Multicast RPC) об успешном розыгрыше (какая карта разыграна, где, на кого).

    *   **Обоснование Реализации:** GameMode (или его менеджер) является единственным местом, где собираются все необходимые данные (состояние игры, состояние игрока, данные карты) для выполнения полной валидации.
