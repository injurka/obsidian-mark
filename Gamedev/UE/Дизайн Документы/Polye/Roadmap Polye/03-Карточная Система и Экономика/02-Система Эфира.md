**Цель:** Реализовать ключевой игровой ресурс "Эфир", который используется для розыгрыша карт и активации способностей. Это включает хранение текущего запаса и максимального лимита Эфира у каждого игрока, реализацию его естественного прироста в начале хода, механизма траты и правила лимита хранения/сгорания.

**Зачем Нужна Эта Система:**

*   **Экономика Игры:** Эфир является основным ресурсом, ограничивающим действия игрока в течение хода и определяющим темп игры.
*   **Стратегическое Планирование:** Управление запасом Эфира, планирование его траты и учет прироста становится важным элементом тактики.
*   **Синхронизация Состояния:** Текущий запас и лимит Эфира каждого игрока должны быть точно синхронизированы между сервером и всеми клиентами для корректного отображения в UI и валидации действий.

**Предпосылки:**

*   **Базовая Сетевая Архитектура (Фаза 1):** Реализованы ключевые C++ классы (`AGameModeBase`, `AGameStateBase`, `APolyePlayerController`, `APolyePlayerStateBase`) с базовой сетевой настройкой (репликация). У игроков корректно создаются и связываются `PlayerController` и `PlayerState`. `APolyePlayerStateBase` настроен на репликацию и `bAlwaysRelevant`.
*   **Система Данных (Фаза 1):** Определены структуры данных (`EPolyeAttributeType` для атрибутов, если Эфир будет атрибутом) и `UDataAsset`ы.
*   **Система Карт (Фаза 3, Пункт 1):** Реализована система управления колодой и рукой игрока (`UPolyeCardGameManagerComponent` на `APolyePlayerStateBase`), хотя напрямую не связана с Эфиром, но использует тот же `PlayerState`.
*   **Управление Ходами:** `AGameModeBase` (сервер) имеет базовую логику управления ходами игроков (начало хода, конец хода, переход хода).
*   **Обработка Действий Игрока:** `APolyePlayerController` (клиент) может инициировать запросы на сервер через Server RPC (например, `Server_RequestPlayCard` - из следующего пункта), и `AGameModeBase` (сервер) обрабатывает эти запросы с валидацией.

**Ключевые Компоненты и Их Роли в Этом Пункте:**

*   **`APolyePlayerStateBase` (Сервер и Клиенты):** Является центральным, реплицируемым хранилищем состояния конкретного игрока. Будет содержать реплицируемые переменные для текущего запаса Эфира (`CurrentEther`) и максимального лимита Эфира (`MaxEther`).
*   **`AGameModeBase` (Сервер):** Управляет ходом матча и логикой смены ходов. В начале хода каждого игрока инициирует **прирост Эфира**. Получает запросы на выполнение действий игрока (напр., розыгрыш карты) и выполняет **валидацию стоимости Эфира** перед их выполнением.
*   **`APolyePlayerController` (Клиент-Владелец):** Отправляет Server RPC на сервер, когда игрок пытается выполнить действие, стоящее Эфир (напр., розыграть карту). Получает Client RPC от сервера с уведомлениями об успешной трате, ошибках недостатка Эфира, начале хода (для прироста Эфира).
*   **UI (Клиенты - Визуал):** Виджеты UMG, управляемые `APolyePlayerController`, отображают текущий запас Эфира и максимальный лимит для игрока-владельца. Обновляются автоматически благодаря репликации свойств в `PlayerState`.

**Шаги Реализации:**

1.  **Реализация Ресурса Эфир в `APolyePlayerStateBase`:**
    *   **Роль:** Хранить актуальные значения Эфира для каждого игрока и синхронизировать их по сети.
    *   **Что Хранить Здесь:** Переменные `int32 CurrentEther` и `int32 MaxEther`.
    *   **Что Не Хранить Здесь:** Логику прироста Эфира (это GameMode), логику траты/валидации (это GameMode/PlayerController), логику, которая *меняет* значения Эфира (это серверные функции в этом же классе, вызываемые из GameMode).
    *   **Действие:** Добавить `UPROPERTY(Replicated)` переменные `CurrentEther` и `MaxEther` в `APolyePlayerStateBase.h`. Реализовать их репликацию в `GetLifetimeReplicatedProps`. Добавить `OnRep` функции (`ReplicatedUsing`) для клиентской реакции (обновление UI). Добавить серверные функции для изменения этих значений (`Server_SetInitialEther`, `Server_GainEther`, `Server_SpendEther`, `Server_CanAfford`).
    *   **Обоснование Реализации:** `APolyePlayerStateBase` - стандартное место для хранения ресурсов игрока. Репликация гарантирует, что эти критически важные данные синхронизированы. `OnRep` функции позволяют UI на клиенте реагировать на изменения. Серверные функции (`Server_...`) выполняют фактические изменения значений Эфира, подчиняясь серверному авторитету.
    *   **Outcome:** `APolyePlayerStateBase` может хранить и реплицировать текущий запас и максимальный лимит Эфира.

    // SERVER ONLY: Устанавливает начальный запас и лимит Эфира
    void APolyePlayerStateBase::Server_SetInitialEther(int32 InitialCurrent, int32 InitialMax)
    {
        // **ВАЖНО: Выполняется ТОЛЬКО на СЕРВЕРЕ.**

    bool APolyePlayerStateBase::Server_SpendEther(int32 Amount)
    {
         // **ВАЖНО: Выполняется ТОЛЬКО на СЕРВЕРЕ.**
         if (!HasAuthority() || Amount < 0) return false;

         // Проверяем, достаточно ли Эфира
         if (CurrentEther >= Amount)
         {
              CurrentEther -= Amount; // Вычитаем стоимость
              UE_LOG(LogTemp, Log, TEXT("Server: Player %s spent %d Ether. New Ether: %d/%d"),
                   GetPlayerName().IsEmpty() ? *GetPlayerName() : *GetPlayerName(), Amount, CurrentEther, MaxEther);
              // Изменение реплицируемой переменной CurrentEther вызовет OnRep_CurrentEther на клиентах.
              // TODO: Возможно, воспроизвести звуковой/визуальный эффект траты Эфира (Multicast RPC)

         {
              // Недостаточно Эфира. Валидация на сервере не пройдена.
              UE_LOG(LogTemp, Warning, TEXT("Server: Player %s tried to spend %d Ether but only has %d. Spend failed."),

         }
    }

3.  **Система Траты Эфира (в `APolyePlayerController` и `AGameModeBase`):**
    *   **Роль:** Позволить игроку инициировать действия, стоящие Эфир, и обеспечить, что стоимость корректно проверяется и вычитается на сервере.
    *   **Что Хранить Здесь:** Ничего специфичного. Логика - это вызовы функций.
    *   **Действие:** В Server RPC, которые игрок отправляет для выполнения платных действий (напр., `Server_RequestPlayCard` из следующего пункта), в их `_Implementation` (на сервере!) получить доступ к `PlayerState` игрока. Использовать `PlayerState->Server_CanAfford(Cost)` для валидации. Если достаточно Эфира, вызвать `PlayerState->Server_SpendEther(Cost)`. Если недостаточно, отправить Client RPC обратно игроку (`Client_NotifyGameplayError`) с сообщением об ошибке.
    *   **Обоснование Реализации:** Серверный авторитет требует, чтобы проверка стоимости и вычет Эфира происходили только на сервере. Server RPC - способ клиента запросить действие. GameMode или менеджер, обрабатывающий RPC, выполняет валидацию и вычет, делегируя изменение значения PlayerState. Client RPC используется для обратной связи клиенту (успех/недостаточно Эфира).
    *   **Outcome:** Реализован механизм серверной проверки стоимости Эфира и его траты при выполнении платных действий.

4.  **Лимит Хранения Эфира и "Сгорание" (в `APolyePlayerStateBase`):**
    *   **Роль:** Определить максимальное количество Эфира, которым может владеть игрок, и что происходит с излишком.
    *   **Что Хранить Здесь:** Переменная `int32 MaxEther`.
    *   **Что Не Хранить Здесь:** Логику, которая *увеличивает* лимит (это может быть от Строений или эффектов), логику, которая *инициирует* прирост (это GameMode).
    *   **Действие:** Логика ограничения запаса Эфира до `MaxEther` должна быть реализована в серверной функции `APolyePlayerStateBase::Server_GainEther`. Прирост выше лимита просто теряется (сгорает).
    *   **Обоснование Реализации:** Логика изменения значения Эфира принадлежит классу, который его хранит (PlayerState), но выполняется только на сервере (`HasAuthority()`). Использование `FMath::Min` - стандартный способ обрезать значение до максимума.
    *   **Outcome:** Прирост Эфира никогда не превышает `MaxEther`, излишек "сгорает".

    **Реализация (в `Core/PolyePlayerStateBase.cpp` - в функции `Server_GainEther`):**

    *   **Что Хранить Здесь:** Ссылки на UI элементы (текстовые поля, индикаторы), возможно, ссылки на PlayerController/PlayerState для чтения данных.
    *   **Что Не Хранить Здесь:** Игровую логику или состояние Эфира.
    *   **Действие:** В UMG виджете игрового экрана добавить текстовые поля или индикаторы для отображения Эфира. **Интеграция и Тестирование:**

*   **Инициализация:** Убедиться, что `AGameModeBase::StartGameSetup` устанавливает правильные начальные значения Эфира для игроков.
*   **Прирост:** Убедиться, что `AGameModeBase` в начале хода игрока вызывает `PlayerState->Server_GainEther` с корректным значением прироста. Проверить, что при приросте Эфир не превышает `MaxEther`.
*   **Трата:** Интегрировать проверки `PlayerState->Server_CanAfford` и вызовы `PlayerState->Server_SpendEther` в логику розыгрыша карт (следующий пункт) и других платных действий. Убедиться, что Server RPC для этих действий сначала проверяет Эфир, и только потом выполняет действие.
*   **UI:** Проверить, что UI корректно отображает Эфир и обновляется при его изменении (прирост, трата).
*   **Сетевое Тестирование:** Запустить игру с двумя клиентами. Убедиться, что Эфир каждого игрока корректно отображается у него самого и синхронизируется (хотя бы число) у противника. Проверить, что трата Эфира одним игроком корректно отображается у обоих.

**Важные Примечания:**

*   **Серверный Авторитет:** Все изменения значений Эфира (`CurrentEther`, `MaxEther`) и проверки стоимости (`Server_CanAfford`, `Server_SpendEther`) должны выполняться ТОЛЬКО на сервере. Нельзя позволять клиенту изменять эти значения напрямую.
*   **UI и Репликация:** UI клиента должен читать реплицированные данные. Прямой Binding в UMG прост, но `OnRep` дает более явный контроль над тем, когда и как обновляется UI.
*   **Атрибуты и GAS (Advanced):** В более сложной игре Эфир может быть реализован как тип Атрибута в Gameplay Ability System (GAS). Тогда `CurrentEther` и `MaxEther` хранились бы в AttributeSet, а прирост и трата Эфира реализовывались бы через `GameplayEffect`ы. Это более мощно и гибко, но требует значительного объема изучения и интеграции GAS. Для MVP, простая реализация в PlayerState достаточна.
*   **Сгорание Эфира:** Текущая реализация "сгорания" просто теряет излишек. Если "сгорание" должно вызывать другие эффекты (напр., наносить урон, давать бонус), эта логика должна быть добавлена в `Server_GainEther` там, где `CurrentEther` обрезается до `MaxEther`.
