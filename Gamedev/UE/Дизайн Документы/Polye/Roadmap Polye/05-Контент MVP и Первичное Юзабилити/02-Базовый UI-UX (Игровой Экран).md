**Цель:** Разработать основной пользовательский интерфейс для игрового матча (HUD - Heads-Up Display), который отображает ключевую информацию для игрока (рука карт, ресурсы, состояние матча) и позволяет ему взаимодействовать с игрой (разыгрывать карты, завершать ход). Реализовать базовую визуальную обратную связь.

**Зачем Нужна Эта Система:**

*   **Взаимодействие с Игроком:** UI - это основной способ, которым игрок управляет игрой и получает информацию о ее состоянии.
*   **Отображение Состояния:** Ключевые данные (рука, Эфир, информация о ходе) должны быть наглядно представлены игроку.
*   **Визуальная Обратная Связь:** Игрок должен понимать, что происходит в ответ на его действия или изменения в игровом мире (подсветка доступных действий, индикаторы статусов).
*   **Тестирование Геймплея:** Для тестирования MVP необходимо иметь возможность видеть и контролировать игру через UI.

**Предпосылки:**

*   **Базовая Сетевая Архитектура (Фаза 1):** Реализованы ключевые C++ классы (`APolyePlayerController` - владеет UI на клиенте, `APolyePlayerStateBase` - хранит реплицируемые данные игрока). `APolyePlayerController` создается для каждого локального игрока.
*   **Система Данных (Фаза 1, 3):** Определены структуры данных (`FCardDataBase`, `FPolyeEffectConfig`) и `UDataAsset`ы карт (`UPolyeCardData`). Создан Менеджер Карт (`UPolyeCardManager`), доступный через `UGameInstance`, который может загружать данные карт (иконка, стоимость, тип) по `FName CardID`. Определены Data Assets для Фракций/Ландшафтов с иконками.
*   **Система Сущностей и Эффектов (Фаза 1, 2, 5, 6):** Определены базовые сущности (`ABoardEntityBase` с `CurrentHP`, `MaxHP`, `Faction`, `OnRep_CurrentHP`). `UPolyeEffectManagerComponent` (с реплицируемым `ActiveEffects` и `OnRep_ActiveEffects`) присоединен к сущностям. Реализованы конкретные эффекты, включая статусные. Есть Placeholder визуал для сущностей и эффектов.
*   **Игровое Поле (Фаза 2):** Визуальные классы `AGameBoard`, `AFieldTile` и их Blueprint наследники (`BP_FieldTile`) существуют и могут отображать базовое состояние (активность, фракция, ландшафт). `BP_FieldTile` имеет Blueprint Implementable Events (`SetFactionVisuals`, `SetLandscapeVisuals`, `SetInfluenceVisuals`, `SetActiveStateVisuals`). `UPolyeBoardStatics` умеет получать `FieldIndex` из World Location (для кликов).
*   **Фаза Активации Полей (Фаза 3, Пункт 2), Система Фракций/Ландшафтов (Фаза 4, Пункт 3, 6):** Реализована фаза активации с UI для выбора фракции/ландшафта (`WBP_FieldActivationOverlay`, `UI_SelectFaction`, `UI_SelectLandscape`, `Server_RequestActivateFieldWithFactionAndLandscape`).
*   **Система Карт (Фаза 3, Пункт 1) и Эфира (Фаза 3, Пункт 2):** Реализована система управления колодой/рукой (`UPolyeCardGameManagerComponent` на `APolyePlayerStateBase`), хранение `HandCardIDs` (реплицируется владельцу, `OnRep_HandCardIDs`), счетчики колоды/сброса. Реализован ресурс Эфир (`CurrentEther`, `MaxEther` в реплицируемом `APolyePlayerStateBase`, `OnRep_CurrentEther`, `OnRep_MaxEther`).
*   **Розыгрыш Карт (Фаза 3.3):** `APolyePlayerController` обрабатывает выбор карты из руки (`UI_SelectCardFromHand`), переход в режим выбора цели, клик по цели и отправку `Server_RequestPlayCard`. GameMode обрабатывает этот RPC с валидацией и выполнением действия. Client RPC `Client_NotifyGameplayError` и `Client_NotifyGameplaySuccess` отправляются обратно игроку.
*   **Система Боя (Фаза 4):** Реализован автоматический боевой цикл. `ABoardEntityBase::TakeDamage` и `Heal` вызывают Multicast RPC для визуализации получения урона/исцеления (`Multicast_PlayReceiveDamageVisuals`, `Multicast_PlayHealVisuals`). `OnDeath` вызывает `Multicast_PlayDeathVisuals`.
*   **Условия Победы/Поражения (Фаза 4.6):** GameMode проверяет условия и вызывает `EndMatch()`. Результат матча может храниться в реплицируемом свойстве `GameState`.

**Ключевые Компоненты и Их Роли в Этом Пункте:**

*   **`WBP_GameplayScreen` (Новый UMG Widget Blueprint):** Основной корневой виджет игрового экрана. Содержит все другие UI элементы (рука, Эфир, кнопка хода, лог). Управляется `APolyePlayerController` клиента.
*   **`WBP_HandPanel` (UMG Widget Blueprint):** Виджет, отображающий руку карт. Содержит панель для виджетов отдельных карт. Обновляется функцией `UpdateHandDisplay`.
*   **`WBP_HandCard` (UMG Widget Blueprint):** Виджет, отображающий одну карту в руке. Показывает арт, стоимость, тип. Обрабатывает клик игрока для выбора карты. Получает данные карты из `CardManager`.
*   **`WBP_EtherDisplay` (UMG Widget Blueprint):** Виджет, отображающий текущий запас и лимит Эфира. Обновляется функцией `UpdateEtherDisplay`.
*   **`WBP_EndTurnButton` (UMG Widget Blueprint):** Виджет кнопки "Завершить Ход". Обрабатывает клик и вызывает функцию в `APolyePlayerController`.
*   **`WBP_ActionLog` (UMG Widget Blueprint):** Виджет для отображения журнала действий. Получает текстовые сообщения о событиях и добавляет их в список.
*   **`WBP_StatusIndicator` (Новый UMG Widget Blueprint):** Виджет для отображения иконки одного статусного эффекта/баффа/дебаффа над сущностью.
*   **`WBP_FloatingText` (Новый UMG Widget Blueprint):** Виджет для отображения плавающих цифр урона/исцеления/Эфира.
*   **`APolyePlayerController` (Клиент):** Владеет `WBP_GameplayScreen`. Создает его, добавляет на экран. Передает в виджеты необходимые данные (ссылку на PlayerState, PlayerController, CardManager). Получает события от виджетов (клик по карте, клик по кнопке). Получает Client RPC от сервера и вызывает соответствующие функции обновления UI. Управляет режимом выбора цели и визуальной обратной связью на доске/сущностях (через вызовы функций на `AFieldTile`/`ABoardEntityBase` BP).
*   **`APolyePlayerStateBase` (Клиент):** Предоставляет реплицированные данные (`HandCardIDs`, `CurrentEther`, `MaxEther`, `CardsInDeckCount`, `CardsInDiscardCount`) для отображения в UI. `OnRep` функции на этих свойствах используются как триггеры для обновления UI.
*   **`AGameStateBase` (Клиент):** Предоставляет реплицированные данные о состоянии матча (`CurrentMatchPhase`, `CurrentActivePlayer`, `MatchOutcome`) для управления видимостью/активностью UI элементов (напр., кнопка "Завершить Ход"). `OnRep` функции могут триггерить UI обновления.
*   **`UPolyeCardManager` (Клиент):** Предоставляет статические данные о картах (арт, стоимость, тип, название) по `FName CardID` для отображения в `WBP_HandCard`.
*   **`UPolyeFactionManager` / `UPolyeLandscapeManager` (Клиент):** Предоставляют статические данные об иконках фракций/ландшафтов/эффектов для отображения в UI или на доске.
*   **`ABoardEntityBase` / `AUnit` / `AStructure` (Клиенты):** Их Blueprint наследники (`BP_Unit`, `BP_Structure`) могут:
    *   Хостить UMG Widget Component для отображения статусных индикаторов (`WBP_StatusIndicator`).
    *   Содержать логику для спавна `WBP_FloatingText` в ответ на Multicast RPC получения урона/исцеления.
    *   Реализовать логику визуальной обратной связи (подсветка) в ответ на вызовы из PlayerController.
*   **`AFieldTile` / `BP_FieldTile` (Клиенты):** Реализует логику визуальной обратной связи (подсветка) в ответ на вызовы из PlayerController.

Эта функция должна очищать текущие виджеты карт, и для каждого `CardID` из списка создавать экземпляр `WBP_HandCard`, вызывать `UpdateCardVisuals` на нем и добавлять в панель.

    *   **Роль:** Визуально отображать активные статусные эффекты/баффы/дебаффы на сущностях и показывать плавающие цифры урона/исцеления/Эфира.

    *   **Что Не Хранить Здесь:** Логику применения эффектов или расчета урона.
    *   **Действие:**
        *   **Статусы:** В Blueprint наследниках сущностей (`BP_Unit`, `BP_Structure`), в ответ на событие `UpdateVisualsBasedOnActiveEffects` (вызывается из `EffectManagerComponent::OnRep_ActiveEffects`), итерировать по списку `ActiveEffects`. Для каждого эффекта, если он является статусным (проверить `EffectType`), создать или обновить дочерний UMG Widget Component, отображающий `WBP_StatusIndicator` с иконкой этого статуса. Удалить виджеты для эффектов, которые больше не активны. Иконки статусов брать из Data Assets (через менеджер).
        *   **Плавающий Текст:** В Blueprint наследниках сущностей (`BP_Unit`, `BP_Structure`), в ответ на Multicast RPC `Multicast_PlayReceiveDamageVisuals` и `Multicast_PlayHealVisuals`, создать экземпляр UMG виджета `WBP_FloatingText` (используя `CreateWidget`), установить в нем текст (количество урона/исцеления), и добавить его в Viewport или в 3D мир над сущностью (используя `WidgetComponent`). Реализовать в `WBP_FloatingText` анимацию движения вверх и исчезновения.
        *   **Плавающий Эфир:** Аналогично, в ответ на Multicast RPC (вызванный из `APolyePlayerStateBase::Server_GainEther` или `Server_SpendEther` на сервере), спавнить `WBP_FloatingText` над сущностью или полем с количеством полученного/потраченного Эфира.
    *   **Обоснование:** UI элементы, привязанные к сущностям в 3D мире (Widget Component), или спавненные временно (Floating Text), являются эффективным способом отображения информации, связанной с конкретными объектами. Они реагируют на репликацию состояния эффектов или на синхронизирующие Multicast RPC.
    *   **Outcome:** Игрок видит иконки активных статусов над сущностями и плавающие цифры урона/исцеления/Эфира во время боя и других событий.

8.  **Подключение UI к Состоянию Игры:**
    *   **Роль:** Гарантировать, что видимость и активность ключевых UI элементов (напр., кнопка "Завершить Ход", панели с картами) зависят от текущей фазы матча и того, чей сейчас ход.
    *   **Что Хранить Здесь:** Логика в UI виджете (`WBP_GameplayScreen`) или `APolyePlayerController`, которая читает состояние игры.
    *   **Что Не Хранить Здесь:** Логику изменения состояния игры.
    *   **Действие:** В `WBP_GameplayScreen` (или в `APolyePlayerController` клиента), получить доступ к `AGameStateBase` (через `GetGameState<APolyeGameStateBase>()`). Читать реплицируемые свойства `CurrentMatchPhase` и `CurrentActivePlayer`.
    *   В `WBP_GameplayScreen`, в функции обновления (вызываемой, напр., в Event Tick или в ответ на `OnRep` GameState), или в `APolyePlayerController` в ответ на `OnRep` GameState:
        *   Если `CurrentMatchPhase` != `EPolyeMatchPhase::PlayerTurn`: Скрыть UI элементы, специфичные для хода игрока (рука карт, кнопка "Завершить Ход"). Показать UI для текущей фазы (напр., `WBP_FieldActivationOverlay` из Фазы 3).
        *   Если `CurrentMatchPhase` == `EPolyeMatchPhase::PlayerTurn`: Показать UI элементы хода игрока.
        *   Если `CurrentMatchPhase` == `EPolyeMatchPhase::GameOver`: Скрыть UI геймплея и показать UI экрана результатов.
        *   Если `CurrentMatchPhase` == `EPolyeMatchPhase::PlayerTurn` И `CurrentActivePlayer` == `GetOwningPlayerState()`: Включить кнопку "Завершить Ход", сделать карты в руке кликабельными.
        *   Иначе (фаза хода, но не наш ход): Выключить кнопку "Завершить Ход", сделать карты некликабельными.
    *   **Обоснование:** UI должен отражать текущее состояние игры, чтобы игрок понимал, какие действия ему доступны. Чтение реплицируемого GameState позволяет UI делать это синхронно у всех игроков.
    *   **Outcome:** UI корректно отображает состояние матча и управляет видимостью/активностью элементов в зависимости от фазы и хода игрока.

**Ключевые Соображения и Тестирование:**

*   **UI и Сеть:** UI клиента ДОЛЖЕН читать состояние игры из реплицированных данных (`PlayerState`, `GameState`). Он НИКОГДА не должен принимать решения об игровой логике или изменять состояние игры сам.
*   **UMG Data Binding vs Manual Update:** Прямой Data Binding в UMG (Вариант А в шаге 3) удобен для простых числовых/текстовых значений. Для более сложного обновления (напр., списка виджетов в руке, или изменения визуала кнопки), лучше использовать явные функции обновления в виджетах, вызываемые из PlayerController в ответ на `OnRep`.
*   **Визуальная Обратная Связь (UX):** Подсветка допустимых целей и индикаторы статусов критически важны для интуитивного геймплея. Реализация подсветки целей на клиенте требует дублирования части серверной логики валидации, но это необходимый компромисс для хорошего UX.
*   **Организация UI:** Разделение UI на мелкие, специализированные виджеты (`WBP_HandCard`, `WBP_EtherDisplay`) упрощает их разработку и управление. Основной виджет (`WBP_GameplayScreen`) служит контейнером.
*   **Data-Driven UI:** Использовать Data Assets (иконки из Card/Faction/Landscape/Effect Data) и Менеджеры Данных для получения ресурсов, необходимых UI для отображения.
*   **Тестирование:**
    *   Тестировать все UI элементы: отображение руки, Эфира, счетчиков колоды/сброса.
    *   Тестировать кликабельность карт в руке и кнопки "Завершить Ход" в зависимости от фазы матча и хода игрока.
    *   Тестировать визуальную обратную связь: подсветка выбранной карты, подсветка допустимых целей, индикаторы статусов на сущностях, плавающие цифры урона/исцеления/Эфира.
    *   Тестировать журнал действий: убедиться, что сообщения появляются корректно.
    *   Тестировать UI фазы активации полей (из предыдущих шагов) в контексте общего игрового экрана.
    *   Тестировать переход UI в состояние "Игра окончена" и отображение экрана результатов.
    *   Проводить сетевое тестирование UI, убедившись, что он корректно отображает синхронизированные данные для всех игроков.
