**Цель:** Создать конкретные игровые данные (характеристики карт, параметры фракций, эффектов, ландшафтов) и простейшие визуальные ассеты/плейсхолдеры, которые позволят протестировать все реализованные к этому моменту системы в рамках одного полного матча MVP.

**Зачем Нужен Этот Контент:**

*   **Проверка Систем:** Реализованные системы (карты, экономика, поле, бой, влияние, ландшафты) являются каркасом. Контент - это "топливо", которое заставляет их работать. Без конкретных карт, фракций, ландшафтов и эффектов невозможно протестировать логику розыгрыша карт, боя, влияния Аур, Ульт полей.
*   **Балансировка (Первичная):** Наличие контента позволяет провести первые тесты баланса - достаточно ли Эфира, сбалансирована ли стоимость карт, сильны ли эффекты.
*   **Визуальное Представление:** Даже простейшие плейсхолдеры делают игру наглядной и позволяют игрокам (тестировщикам) понимать, что происходит на доске.
*   **Основа для Дальнейшего Развития:** Созданный MVP контент послужит основой для разработки полноценного контента в будущем.

**Предпосылки:**

*   **Система Данных (Фаза 1, 3):** Определены все необходимые структуры данных (`USTRUCT`, `UENUM`) для карт (`FCardDataBase`), фракций (`FDecayingInfluenceAuraConfig`), ландшафтов (`FFieldUltConfig`), эффектов (`FPolyeEffectConfig`, `EPolyeEffectType`, `EPolyeAttributeType`). Определены C++ классы для Data Assets (`UPolyeCardData`, `UPolyeFactionData`, `UPolyeLandscapeData`) и Data Tables (`UDataTable`). Создан Менеджер Данных (`UPolyeCardManager`, `UPolyeFactionManager`) для доступа к этим ассетам.
*   **Система Сущностей и Эффектов (Фаза 1, 2, 5, 6):** Определены базовые сущности (`ABoardEntityBase`, `AUnit`, `AStructure`). Создан базовый класс эффекта (`UPolyeGameplayEffectBase`) и, что КРИТИЧНО для этого шага, **реализованы конкретные классы-наследники `UPolyeGameplayEffectBase`** для всех типов эффектов MVP, которые были намечены в Фазе 4.5 (Баффы/Дебаффы атрибутов, Скрытность, Неистовство, Контратака "Ядовитые шипы", Периодический урон, Перегрев). Эти классы умеют модифицировать атрибуты (`ModifyAttributeValue_Implementation`), обрабатывать применение/удаление (`Apply/RemoveEffect_Implementation`), возможно, тик (`TickEffect_Implementation`) или триггеры (`OnDamageReceived_Implementation` и др.).
*   **Системы, Применяющие Эффекты (Фаза 3, 4):** Логика в `AGameStateBase::CalculateAndApplyInfluence` (для Аур), `AGameStateBase::ApplyLandscapeUltEffectToField` (для Ульт), `AGameModeBase::HandlePlayerPlayCardRequest` (для эффектов карт Событий/Заклинаний) вызывает `Entity->GetEffectManagerComponent()->ApplyEffect` с `TSubclassOf<UPolyeGameplayEffectBase>` и `FPolyeEffectConfig`, полученными из Data Assets.
*   **Игровое Поле (Фаза 2):** Визуальные классы `AGameBoard`, `AFieldTile` и их Blueprint наследники (`BP_FieldTile`) существуют и могут отображать базовое состояние (активность, фракция, ландшафт). `BP_FieldTile` имеет Blueprint Implementable Events (`SetFactionVisuals`, `SetLandscapeVisuals`, `SetInfluenceVisuals`) для визуализации этих данных.
*   **Система Розыгрыша Карт (Фаза 3.3):** Логика спавна сущностей из карт Юнитов/Строений в `AGameModeBase::HandlePlayerPlayCardRequest` получает `TSoftClassPtr<ABoardEntityBase>` из `UPolyeCardData` и использует его для спавна Актера.
*   **Система Боя (Фаза 4):** Боевой цикл, расчет урона/исцеления, выбор целей используют атрибуты и эффекты, которые будут определены в этом контенте.

**Ключевые Компоненты и Их Роли в Этом Пункте:**

*   **Data Assets (`UPolyeCardData`, `UPolyeFactionData`, `UPolyeLandscapeData`) & Data Tables (`DT_CardCatalog`) (Content Browser):** Это место, где хранятся все конкретные игровые данные. Гейм-дизайнеры будут работать непосредственно с этими ассетами в редакторе.
*   **Blueprint Классы Наследники Сущностей (`BP_Unit_...`, `BP_Structure_...`) (Content Browser):** Наследуют от C++ классов `AUnit` и `AStructure`. Определяют визуальное представление сущности (Static Mesh, Skeletal Mesh, анимации, материалы, эффекты, коллизия). Ссылки на них хранятся в `UPolyeCardData`.
*   **Blueprint Классы Наследники Эффектов (`BP_Effect_...`) (Content Browser):** Наследуют от C++ класса `UPolyeGameplayEffectBase`. Могут использоваться вместо C++ классов для реализации логики эффекта или для добавления специфической визуальной логики, связанной с эффектом, прямо в Blueprint. Ссылки на них хранятся в Data Assets.
*   **Placeholder Visual Assets (Content Browser):** Простейшие 3D модели, материалы, текстуры, частицы, звуки, которые используются для временного визуального представления игры.
*   **C++ Классы Наследники Эффектов (Code):** Если специфическая логика эффекта слишком сложна для Blueprint или требует C++ (например, прямое взаимодействие с другими системами, сложные расчеты), она реализуется здесь.

**Шаги Реализации:**

1.  **Создание Data Assets и Data Tables для MVP Карт:**
    *   **Роль:** Определить все карты, доступные в MVP, с их уникальными ID, базовыми свойствами и ссылками на более детальные данные или визуал.
    *   **Действие:** В Content Browser, в папке `Content/Data/DataTables/`, открыть или создать `UDataTable` на основе структуры `FCardDataBase` (напр., `DT_CardCatalog`). Добавить строки для каждой из 30-50 MVP карт.
    *   Для каждой строки (карты):
        *   Задать уникальный **Row Name** (это `FName CardID`).
        *   Выбрать `Card Type` (Unit, Structure, Event, Landscape Change).
        *   Выбрать `Faction` (одна из 3 MVP + Neutral).
        *   Задать `EtherCost`.
        *   Написать `CardName` и `CardDescription` (используя FText).
        *   Создать или получить ссылку на Placeholder текстуру для `CardArtwork`.
        *   **Создать соответствующий `UPolyeCardData` Asset:** В папке `Content/Data/DataAssets/Cards/`, создать новый Data Asset на основе C++ класса `UPolyeCardData`. Назвать его соответствующе (напр., `DA_Card_SwampBrotherhood_Unit_Healer`). Заполнить его свойства (CardID, Type, Faction, Name, Description, Cost, Artwork - дублируют DT, но это нормально).
        *   **В `DT_CardCatalog` строке карты:** Указать `DetailedCardDataAsset` на созданный `DA_Card_...` ассет.
    *   **Наполнение `UPolyeCardData` (Детальные Данные и Ссылки):** Открыть каждый созданный `DA_Card_...` ассет.
        *   Если `CardType` = Unit/Structure: Заполнить `BaseHP`, `BaseAttack` (для юнитов), `BasePriority`. **Создать или получить ссылку на Placeholder Blueprint класс сущности:** В папке `Content/Blueprints/Entities/`, создать Blueprint классы, наследующие от `AUnit` или `AStructure` (напр., `BP_Unit_SwampBrotherhood_Healer`). Настроить их визуальное представление (Static Mesh/Skeletal Mesh Placeholder, материал). В `DA_Card_...` указать `UnitBlueprint` или `StructureBlueprint` на этот BP класс.
        *   Если `CardType` = Event/LandscapeChange: Заполнить массив `InstantEffects` (`TArray<FPolyeEffectConfig>`). Для каждого эффекта в массиве:
            *   Выбрать `EffectType` (Enum).
            *   Написать `Description` (FText).
            *   Заполнить `NumericParameters` (`TMap<FName, float>`) с конкретными числами для этого эффекта (напр., {"DamageAmount": 10.0}, {"ModifierValue": 20.0}, {"Duration": 5.0}).
            *   Создать или получить ссылки на Placeholder VFX/SFX для `VFX` и `SFX`.
        *   Если `CardType` = LandscapeChange: Дополнительно указать `LandscapeDataAsset` на соответствующий `UPolyeLandscapeData` ассет (см. шаг 3).
    *   **Обобоснование:** Этот шаг переносит всю статическую информацию о картах из дизайн-документа в редактируемые ассеты Unreal Engine. Data Table обеспечивает быстрый доступ к базовым данным и компактный каталог. Data Assets хранят более сложные и специфичные данные, включая ссылки на другие ассеты (BP, визуал, другие Data Assets).
    *   **Outcome:** Созданы все MVP карты в виде Data Tables и Data Assets, с указанием их характеристик, стоимости, типов и ссылок на другие необходимые ассеты (включая Placeholder BP сущностей и визуал).

2.  **Наполнение Data Assets для MVP Фракций:**
    *   **Роль:** Определить свойства и эффекты, уникальные для каждой из 3 MVP фракций.
    *   **Действие:** В Content Browser, в папке `Content/Data/DataAssets/Factions/`, создать Data Assets на основе C++ класса `UPolyeFactionData` для каждой MVP фракции (напр., `DA_Faction_SwampBrotherhood`, `DA_Faction_CoalChildren`, `DA_Faction_RootGuardians`).
    *   Для каждого ассета фракции:
        *   Выбрать `FactionType` (Enum).
        *   Написать `FactionName` и `FactionDescription` (FText).
        *   Создать или получить ссылку на Placeholder текстуру для `FactionIcon`.
        *   **Настроить Фракционный Бафф (100% поле):** Заполнить `FactionBuff` (`FFactionBuffConfig`). Выбрать `BuffType` (Enum). Написать `Description`. Заполнить `Parameters` (`TMap<FName, float>`). Создать или получить ссылки на Placeholder VFX/SFX. Убедиться, что для этого `BuffType` существует класс `UPolyeGameplayEffectBase` наследник, который умеет применять этот бафф.
        *   **Настроить Ауры Затухающего Влияния:** Заполнить массив `DecayingInfluenceAuras` (`TArray<FDecayingInfluenceAuraConfig>`). Для каждой Ауры, которую испускает эта фракция:
            *   Выбрать `AuraType` (Enum).
            *   Написать `Description`.
            *   **Указать класс эффекта для этой Ауры:** Указать `EffectClass` (`TSubclassOf<UPolyeGameplayEffectBase>`) на соответствующий C++ или Blueprint класс эффекта (напр., `BP_Effect_HealReduction` для Болотников).

В каждом конфиге: выбрать `EffectType` (Enum), заполнить `NumericParameters` с параметрами, соответствующими этой силе (напр., для снижения лечения, разные числа для 50% и 25%). Создать или получить ссылки на Placeholder VFX/SFX для каждой силы, если визуал Ауры меняется с силой. Убедиться, что класс эффекта умеет применять эффект с этими параметрами.

        *   **Указать доступные Ландшафты:** Заполнить массив `AvailableLandscapes` (`TArray<TSoftObjectPtr<const UPolyeLandscapeData>>`), ссылаясь на `UPolyeLandscapeData` ассеты, доступные для этой фракции (см. шаг 3).

    *   **Обоснование:** Data Assets фракций собирают воедино всю информацию, определяющую уникальные механики и эффекты каждой фракции. Это позволяет легко настраивать их в редакторе.
    *   **Outcome:** Созданы Data Assets для MVP фракций с определенными свойствами, баффами, аурами и ссылками на доступные ландшафты.

    *   Для каждого ассета ландшафта:
        *   Выбрать `AssociatedFaction` (к какой фракции относится).
        *   Задать уникальный `LandscapeID` (FName).
        *   Написать `LandscapeName` и `LandscapeDescription` (FText).
        *   Создать или получить ссылку на Placeholder текстуру для `LandscapeIcon`.

Убедиться, что для этого `UltType` существует класс эффекта, который умеет работать с этими параметрами.

    *   **Outcome:** Созданы Data Assets для MVP ландшафтов с определенными свойствами, визуальными ресурсами и Ультой.

4.  **Реализация Специфической Логики Эффектов (Доработка/Проверка):**
    *   **Роль:** Убедиться, что все конкретные эффекты MVP, которые были намечены в Фазе 4.5, действительно реализованы и работают с параметрами, которые будут загружаться из Data Assets.
    *   **Действие:** Просмотреть C++ или Blueprint классы, наследующие от `UPolyeGameplayEffectBase`, созданные в Фазе 4.5 для эффектов MVP (Бафф Атаки, Скрытность, Неистовство, Контратака, Периодический Урон, Перегрев, и т.д.).
    *   Убедиться, что:
        *   Каждый класс переопределяет необходимые виртуальные функции (`Apply`, `Remove`, `Tick`, `ModifyAttributeValue`, триггерные функции).
        *   Логика внутри этих функций корректно читает параметры из унаследованного свойства `EffectConfig.NumericParameters` (по `FName` ключу) и использует их в своих расчетах (напр., урон, значение модификатора, длительность, интервал, порог стеков).
        *   Если эффект является статусным, он корректно применяет/удаляет свой статус (например, через `HasStatusEffect` в `EffectManagerComponent` или путем добавления тега статуса).
        *   Если эффект периодический, его логика в `TickEffect_Implementation` корректно работает (требует, чтобы `UPolyeEffectManagerComponent` вызывал `TickEffect` для этих экземпляров).
        *   Если эффект триггерный (напр., Контратака), его логика в соответствующей виртуальной функции (напр., `OnDamageReceived_Implementation`) корректно срабатывает и выполняет действие.
        *   Если эффект стекирующийся (Перегрев), его логика накопления стеков и срабатывания "взрыва" при пороге корректно реализована и работает с параметрами из `EffectConfig`.
        *   Если для эффекта нужна специфическая визуальная логика в Blueprint, она реализована в BP наследнике, переопределяющем соответствующие Blueprint Implementable Events из `UPolyeGameplayEffectBase` (если они были добавлены).
    *   **Обобоснование:** Data Assets только хранят параметры. Фактическая логика эффекта находится в коде (C++ или BP). Этот шаг - финальная проверка, что код эффектов готов работать с данными, которые будут в Data Assets.
    *   **Outcome:** Реализована или финализирована специфическая логика всех ключевых эффектов MVP.

5.  **Создание Простейших Визуальных Ассетов / Плейсхолдеров:**
    *   **Роль:** Предоставить временное визуальное представление для ключевых элементов игры, чтобы сделать ее наглядной и играбельной.
    *   **Действие:** В Content Browser, создать простые ассеты для использования в Data Assets и Blueprint'ах:
        *   **3D Модели:** Простейшие Static Meshes (кубы, сферы, цилиндры, плоскости) для плиток поля и сущностей (Юнитов, Строений). Для Юнитов, возможно, простейшие Skeletal Meshes или даже просто Static Meshes.
        *   **Материалы:** Простые материалы с разным цветом или базовой текстурой для сущностей, плиток поля. Материалы с параметрами (для изменения цвета/свечения в BP плитки/сущности в ответ на статус/активность/фракцию/ландшафт/ауру).
        *   **Текстуры:** Простейшие иконки (квадраты с символом/буквой) для карт, фракций, ландшафтов, статусов/эффектов.
        *   **Системы Частиц (VFX):** Простейшие эффекты (Niagara или Cascade) для получения урона (красные партиклы), исцеления (зеленые партиклы), смерти (взрыв/дымок), активации поля (свечение), аур (слабое свечение/туман), ульт (более яркий эффект).
        *   **Звуковые Эффекты (SFX):** Простейшие звуки (WAV или Sound Cues) для атаки, получения урона, смерти, розыгрыша карты, получения Эфира, активации поля, срабатывания Ульты.
    *   **Где Использовать:**
        *   В Data Assets карт (`UPolyeCardData`): `CardArtwork`, ссылки на BP сущностей (которые используют Placeholder меши/материалы).
        *   В Data Assets фракций (`UPolyeFactionData`): `FactionIcon`, VFX/SFX для баффа/аур.
        *   В Data Assets ландшафтов (`UPolyeLandscapeData`): `LandscapeIcon`, `FieldMeshOverride`, `FieldMaterialOverride`, VFX/SFX для Ульты.
        *   В Blueprint классах сущностей (`BP_Unit`, `BP_Structure`): Установить Placeholder меши, материалы, компоненты для VFX/SFX. Реализовать логику в BP (в ответ на `OnRep_...` или Multicast RPC) для воспроизведения VFX/SFX.
        *   В Blueprint классе плитки поля (`BP_FieldTile`): Установить Placeholder меш, материал. Реализовать логику в BP (в ответ на `SetFactionVisuals`, `SetLandscapeVisuals`, `SetInfluenceVisuals`) для изменения материала, спавна VFX/SFX, отображения иконок.
    *   **Обоснование:** Этот шаг предоставляет минимально необходимый визуал для игры. Использование плейсхолдеров позволяет фокусироваться на логике и геймплее на ранних этапах, откладывая финальную работу над артом.
    *   **Outcome:** Создан набор простейших визуальных ассетов и настроено их использование в Data Assets и Blueprint'ах для временного представления игровых элементов и эффектов.

**Ключевые Соображения и Тестирование:**

*   **Последовательность:** Этот шаг сильно зависит от завершения предыдущих фаз, особенно Фазы 4.5 (реализация логики эффектов) и Фазы 3 (системы данных). Невозможно заполнить Data Assets, если нет соответствующих структур, классов эффектов или Blueprint классов сущностей, на которые можно ссылаться.
*   **Согласованность Данных:** Убедиться, что ID карт (`FName` в DT и DA), типы фракций/ландшафтов/эффектов (`UENUM`), имена атрибутов (`FName` в NumericParameters) точно совпадают между Data Assets, Data Tables и C++ кодом. Ошибки в именах или типах приведут к тому, что менеджеры не смогут найти данные или классы.
*   **Ссылки на Ассеты:** Тщательно проверить, что все `TSoftObjectPtr` и `TSoftClassPtr` в Data Assets указывают на существующие ассеты в Content Browser. Unreal Editor обычно показывает предупреждения, если ссылка невалидна.
*   **Параметры Эффектов:** Убедиться, что `NumericParameters` в `FPolyeEffectConfig` (в Data Assets) заполнены правильно для каждого эффекта и силы влияния, и что код в `UPolyeGameplayEffectBase` наследниках правильно читает эти параметры по их `FName` ключу.
*   **Визуал vs Логика:** Четко разделять, где происходит логика эффекта (сервер, C++/BP наследники `UPolyeGameplayEffectBase`) и где происходит его визуализация (клиент, `OnRep_ActiveEffects`, Multicast RPC, BP сущностей и плиток).
*   **Тестирование (Сфокусированное):** После создания контента, провести целенаправленное тестирование:
    *   **Тест каждой карты:** Разыграть каждую карту MVP (Юнит, Строение, Событие, Смена Ландшафта), убедиться, что она разыгрывается, стоит Эфир, карта удаляется из руки, и ее базовое действие выполняется (спавн, базовый эффект, смена ландшафта).
    *   **Тест каждой Фракции/Ландшафта:** Активировать поля с каждой MVP фракцией и доступными ландшафтами. Убедиться, что визуал поля меняется. Разместить сущности на полях под влиянием этих Аур/Ульт. Убедиться, что эффекты Аур/Ульт применяются к сущностям и влияют на них (напр., изменение статов, срабатывание триггеров, накопление зарядов).
    *   **Тест каждого типа эффекта MVP:** Убедиться, что каждый конкретный эффект (Бафф Атаки, Скрытность, Перегрев и т.д.) работает согласно дизайну при применении через Ауру, Ульту или карту События.
