**Цель:** Создать визуальное и логическое представление игрового поля 3x5, определить систему идентификации полей, настроить их сетевую синхронизацию и реализовать базовую визуализацию их состояния (активное/неактивное), а также заложить основу для отображения сущностей на поле.

**Зачем Нужна Отдельная Система Поля:**

*   **Структура Игры:** Поле является центральной структурой игры, определяющей пространство для размещения сущностей и применения эффектов. Логическое представление поля необходимо для правил игры (движение, атака, влияние).
*   **Сетевая Синхронизация:** Состояние каждого поля (кто владеет, какие сущности на нем находятся, активно ли оно) должно быть синхронизировано между сервером и всеми клиентами, чтобы игроки видели актуальную картину. `AGameStateBase` - идеальное место для хранения этого реплицируемого состояния.
*   **Визуализация:** Игрокам нужно видеть поле, его состояние и расположенные на нем сущности. Отдельные Актеры для доски и плиток обеспечивают визуальное представление, которое обновляется на основе логического состояния.
*   **Удобство Взаимодействия:** Визуальные плитки поля позволяют игрокам кликать по ним, чтобы выбрать поле для действия (разыграть карту, переместить юнита).

**Ключевые Компоненты Unreal Engine:**

*   **`USTRUCT()` & `FTableRowBase`:** Определяют структуры данных, видимые в UE. `FPolyeFieldState` будет описывать данные одного поля.
*   **`AGameStateBase`:** Центральный Актер (существующий на всех машинах), который хранит и реплицирует общее состояние игры, включая массив структур `FPolyeFieldState` для всей доски.
*   **`AActor`:** Базовый класс для `AGameBoard` (контейнер для визуальной доски) и `AFieldTile` (визуальное представление одной плитки поля). Эти Актеры будут существовать ЛОКАЛЬНО на каждом клиенте для отображения и обработки ввода.
*   **`UPROPERTY(Replicated)` / `DOREPLIFETIME`:** Макросы и функции для настройки репликации свойств между сервером и клиентами.
*   **`UPROPERTY(ReplicatedUsing)`:** Позволяет вызвать функцию на клиенте при получении реплицированного значения свойства.
*   **`UBlueprintFunctionLibrary`:** Статический класс для создания вспомогательных функций, доступных в C++ и Blueprint (например, для преобразования индексов поля в координаты).

**Шаги Реализации:**

1.  **Определение Логической Структуры Поля (USTRUCT `FPolyeFieldState`):**
    *   **Роль:** `FPolyeFieldState` - это структура данных, представляющая логическое состояние *одной* плитки на игровой доске Polye. Она содержит всю информацию об этом поле, которая должна быть известна игровой логике и реплицирована на клиентов.
    *   **Что Хранить Здесь:** Уникальный идентификатор поля (`FieldIndex`), его статус активности (`bIsActive`), изначального владельца (`InitialOwnerPlayerIndex`), текущую фракцию (`CurrentFaction`), ссылку на примененный ландшафт (`CurrentLandscapeDataAsset`), и список сущностей, находящихся на этом поле (`EntitiesOnField`).
    *   **Что Не Хранить Здесь:** Визуальное представление поля (это в `AFieldTile`). Игровую логику, которая *обрабатывает* состояние поля или сущностей на нем.
    *   **Действие:** Расширить файл `Source/Polye/Data/PolyeDataTypes.h`, добавив структуру `FPolyeFieldState`.
    *   **Обоснование Реализации:** Использование `USTRUCT` позволяет сгруппировать связанные данные об одном поле. `UPROPERTY(Replicated)` помечает эти данные для репликации, когда структура является частью реплицируемого Актера (`AGameStateBase`). 2.  **Хранение Состояния Поля в `APolyeGameStateBase`:**
    *   **Роль:** `APolyeGameStateBase` является центральным, авторитетным (на сервере) и реплицируемым (на все клиенты) хранилищем общего состояния игры, включая состояние всей доски.
    *   **Что Хранить Здесь:** Массив структур `FPolyeFieldState` для каждого поля на доске. Список подключенных игроков (`ConnectedPlayers`). Общее состояние матча (номер хода, текущий игрок).
    *   **Что Не Хранить Здесь:** Логику правил игры (это в `GameMode`). Визуальное представление доски (это в `AGameBoard`/`AFieldTile`). Логику конкретных сущностей (это в `ABoardEntityBase`/`AUnit`/`AStructure`).
    *   **Действие:** В классе `APolyeGameStateBase` (в `Source/Polye/Core/PolyeGameStateBase.h`) добавить массив структур `FPolyeFieldState` и реализовать функции для управления этим состоянием на сервере.
    *   **Обоснование Реализации:** Массив `TArray<FPolyeFieldState>` с `UPROPERTY(ReplicatedUsing=OnRep_BoardState)` гарантирует, что любые изменения в состоянии полей на сервере будут отправлены всем клиентам, вызывая `OnRep_BoardState` для обновления визуального представления. `ConnectedPlayers` также реплицируется, позволяя клиентам знать, кто участвует в матче. Серверные функции (`InitializeBoardState`, `UpdateFieldState` и т.д.) обеспечивают, что только сервер может изменять состояние доски.

3.  **Система Идентификации Полей:**
    *   **Роль:** Определить простой и последовательный способ обращения к любому полю на доске (3x5 сетке), а также предоставить вспомогательные функции для преобразования между этим идентификатором (индексом) и мировыми координатами или соседними полями.
    *   **Что Хранить Здесь:** Константы для размеров доски (количество рядов и колонок). Примерные параметры для расчета 3D позиций по индексу.
    *   **Что Не Хранить Здесь:** Состояние поля (это в `GameState`). Визуальные Актеры полей.
    *   **Действие:** Использовать `int32 FieldIndex` (0-14) как уникальный идентификатор поля. Определить логическое расположение этих индексов на сетке 3x5. Создать вспомогательные статические функции для преобразования между индексом, координатами (ряд, колонка) и мировыми координатами.
    *   **Обоснование Реализации:** Использование статического класса-библиотеки (`UBlueprintFunctionLibrary`) делает эти функции легко доступными как в C++, так и в Blueprint из любого места кода. `FieldIndex` - эффективный идентификатор для сетевых RPC и хранения в структурах. Функции преобразования скрывают детали реализации сетки. Функции для соседних полей и полей "через одно" будут активно использоваться системой Затухающего Влияния и логикой движения/атаки.
    *   **Outcome:** Определена система идентификации полей и созданы вспомогательные C++ функции (доступные в Blueprint) для работы с ней.

    void UPolyeBoardStatics::GetCoordsFromIndex(int32 FieldIndex, int32& OutRow, int32& OutColumn)
    {

        {

    {
        TArray<int32> AdjacentIndices;
        int32 Row, Column;
        GetCoordsFromIndex(FieldIndex, Row, Column);

        if (Row == -1) return AdjacentIndices; // Невалидный индекс

        // Смещения для 4 направлений (вверх, вниз, влево, вправо)
        int32 Dr[] = {-1, +1, 0, 0}; // Изменение ряда
        int32 Dc[] = {0, 0, -1, +1}; // Изменение колонки

        // Смещения для 4 диагональных направлений
        int32 DrDiag[] = {-1, -1, +1, +1};
        int32 DcDiag[] = {-1, +1, -1, +1};

        // Проверяем 4 ортогональных соседа
        for (int i = 0; i < 4; ++i)
        {
            int32 NewRow = Row + Dr[i];
            int32 NewColumn = Column + Dc[i];
            int32 NewIndex = GetIndexFromCoords(NewRow, NewColumn);
            if (NewIndex != INDEX_NONE) // Проверяем, что новый индекс валиден (не выходит за границы доски)
            {
                AdjacentIndices.Add(NewIndex);
            }
        }

        // Проверяем 4 диагональных соседа, если нужно
        if (bIncludeDiagonal)
        {
             for (int i = 0; i < 4; ++i)
             {
                  int32 NewRow = Row + DrDiag[i];
                  int32 NewColumn = Column + DcDiag[i];
                  int32 NewIndex = GetIndexFromCoords(NewRow, NewColumn);
                  if (NewIndex != INDEX_NONE)
                  {
                       AdjacentIndices.Add(NewIndex);
                   }
             }
        }

        return AdjacentIndices;
    }

    *   **Роль `AFieldTile`:** Это Актер, представляющий одну визуальную плитку поля в 3D мире. Он спавнится и управляется `AGameBoard`. `AFieldTile` отвечает за отображение визуального состояния *своего* поля (активное/неактивное, фракция, ландшафт) на основе данных, полученных из `AGameBoard`. Он также обрабатывает взаимодействие игрока (клики).
    *   **Что Хранить в `AFieldTile`:** Свой уникальный `FieldIndex`. Ссылки на визуальные компоненты (Static Mesh, материалы).
    *   **Что Не Хранить в `AFieldTile`:** Логическое состояние поля (оно передается из `GameState`). Правила игры. Логику сущностей на поле.
    *   **Действие:** Создать C++ классы `AGameBoard` и `AFieldTile`, наследующие от `AActor`.
    *   **Обоснование Реализации:** `AGameBoard` и `AFieldTile` являются Актерами, но не реплицируются как *игровая логика*. Они спавнятся ЛОКАЛЬНО на каждом клиенте. Их задача - читать реплицированное состояние из `AGameStateBase` и отображать его. `AGameBoard::SpawnFieldTiles` создает нужное количество плиток и располагает их, используя `UPolyeBoardStatics`. `AGameBoard::UpdateVisualsFromGameState` вызывается из `GameState::OnRep_BoardState` и передает обновленные данные каждой плитке. `AFieldTile::UpdateVisuals` и вспомогательные функции изменяют внешний вид плитки. Настройка коллизии на `AFieldTile` позволяет детектировать клики игрока.
    *   **Outcome:** Созданы базовые C++ классы `AGameBoard` и `AFieldTile` для визуального представления доски. Реализован спавн плиток и функции для обновления их внешнего вида на основе состояния из GameState.

    void AGameBoard::SpawnFieldTiles()
    {
         if (!FieldTileClass)
         {
             UE_LOG(LogTemp, Error, TEXT("FieldTileClass is not set on AGameBoard Blueprint! Please set BP_FieldTile."));
             return;
         }

         UWorld* World = GetWorld();
         if (!World) return;

         // Убедимся, что массив плиток пустой перед спавном (если BeginPlay может вызываться несколько раз)
         if (FieldTiles.Num() > 0)
         {
             UE_LOG(LogTemp, Warning, TEXT("FieldTiles already spawned for AGameBoard %s. Skipping redundant spawn."), *GetName());
             return;
         }


         FieldTiles.SetNum(UPolyeBoardStatics::TotalFields); // Инициализируем массив ссылок

         for (int32 i = 0; i < UPolyeBoardStatics::TotalFields; ++i)
         {
              FVector SpawnLocation = UPolyeBoardStatics::GetWorldLocationForField(i);
              // TODO: Возможно, добавить повороты для плиток игроков, если они смотрят в разные стороны

              FActorSpawnParameters SpawnParams;
              SpawnParams.Owner = this; // Владелец - сам AGameBoard Актер
              SpawnParams.Instigator = GetInstigator();
              // Спавним локально, поэтому нет необходимости в RemoteRole/OwnerOnly и т.д.
              SpawnParams.SpawnCollisionHandlingOverride = ESpawnActorCollisionHandlingMethod::AdjustIfPossibleButAlwaysSpawn; // Или другой подходящий метод

              // Спавним Актер плитки поля (выполняется ЛОКАЛЬНО)
              AFieldTile* NewTile = World->SpawnActor<AFieldTile>(FieldTileClass, SpawnLocation, FRotator::ZeroRotator, SpawnParams);
              if (NewTile)
              {
                   FieldTiles[i] = NewTile; // Сохраняем ссылку
                   NewTile->SetFieldIndex(i); // Устанавливаем индекс поля для плитки

                   // TODO: Установить другие начальные параметры плитки, которые не меняются (напр., начальное владение для визуала)

                   //      }
                   // }
              }
              else

    // CLIENT ONLY - Обновление визуального представления плиток
    void AGameBoard::UpdateVisualsFromGameState(const TArray<FPolyeFieldState>& CurrentBoardState)
    {
         // **ВАЖНО: Эта функция вызывается на КЛИЕНТЕ из APolyeGameStateBase::OnRep_BoardState.**

         if (FieldTiles.Num() != CurrentBoardState.Num())
         {
             UE_LOG(LogTemp, Error, TEXT("Mismatch between number of visual tiles (%d) and board state data (%d)! Cannot update visuals."), FieldTiles.Num(), CurrentBoardState.Num());
             return;
         }

         // Проходим по всем плиткам и обновляем их визуал
         for (int32 i = 0; i < CurrentBoardState.Num(); ++i)
         {
             if (FieldTiles[i].IsValid())
             {
                  // Передаем актуальное состояние этого поля визуальной плитке для отображения
                  FieldTiles[i]->UpdateVisuals(CurrentBoardState[i]);
             }
             else
             {
                  UE_LOG(LogTemp, Warning, TEXT("Invalid Field Tile actor found at index %d in FieldTiles array."), i);
             }
         }
         UE_LOG(LogTemp, Log, TEXT("[Client] AGameBoard visuals updated from GameState."));
    }

3.  **Настройка GameMode:** В вашем `APolyeGameModeBase` (или его Blueprint наследнике) убедитесь, что логика инициализации матча (например, в `HandleMatchHasStarted`) вызывает `GameState->InitializeBoardState()`.
4.  **Механика Активации Полей:** В Фазе 2 (пункт 2) мы заложили основу для активации полей. Теперь у вас есть структура `FPolyeFieldState` в `GameState`. В `APolyeGameModeBase` (или менеджере, вызываемом из GameMode) реализуйте логику выбора начальных активных полей и их активации, вызывая `GameState->UpdateFieldState(FieldIndex, NewState)`.
5.  **Обработка Клика по Полю:** В `APolyePlayerController`, реализуйте обработку ввода (клик мыши). Используйте `UPolyeBoardStatics::GetFieldIndexAtLocation` (вызывая ее на клиенте!) для определения, по какому полю кликнул игрок. Затем используйте этот `FieldIndex` в Server RPC (например, `Server_TryPlayCard`, `Server_RequestMoveUnit`) для передачи серверу информации о цели действия.
6.  **Спавн и Отображение Сущностей:** Когда на сервере спавнится `ABoardEntityBase` (например, при розыгрыше карты в Фазе 3), после вызова `Server_InitializeEntity`, вызовите `GameState->AddEntityToField(FieldIndex, NewEntity)`. Это обновит массив `EntitiesOnField` в `GameState` и вызовет `OnRep_BoardState` на клиентах, что приведет к вызову `AFieldTile::UpdateVisuals` и `UpdateEntitiesVisuals` на соответствующей плитке. Логика в `BP_FieldTile::UpdateEntitiesVisuals` или в BP сущностей будет отвечать за правильное позиционирование визуального представления сущности на плитке.

**Важные Примечания:**

*   **Логика vs. Визуал:** Четко разделяйте логическое состояние (в `GameState`) и визуальное представление (в `AGameBoard`/`AFieldTile`/BP сущностей). Сервер управляет логикой. Клиенты читают логику через репликацию и используют ее для обновления визуала.
*   **Локальный Спавн Визуала:** `AGameBoard` и `AFieldTile` являются визуальными Актерами, которые спавнятся ЛОКАЛЬНО на каждом клиенте. Они не должны реплицировать свое положение или другие визуальные свойства, так как их положение фиксировано или вычисляется из `FieldIndex`, а их состояние берется из реплицированного `GameState`.
*   **Доступ к GameState на Клиенте:** Клиентский код (например, `OnRep_BoardState` в GameState, `UpdateVisualsFromGameState` в GameBoard, `UpdateVisuals` в FieldTile) может безопасно читать данные из реплицированного `GameState`.
*   **Асинхронная Загрузка:** Для Landscape Data Asset в `AFieldTile::UpdateVisuals` используется синхронная загрузка (`LoadSynchronous`). Для реальной игры, особенно если ассетов много или они большие, рассмотрите использование асинхронной загрузки через `FStreamableManager`, уведомляя плитку, когда ассет будет готов.
*   **Отладка Репликации:** Используйте консольные команды `Net Debug`, `Net Stat`, `NetProfile` для отладки сетевой репликации. Убедитесь, что BoardState реплицируется правильно и OnRep функции вызываются.
