**Цель:** Спроектировать и реализовать систему, которая позволяет хранить все игровые данные (характеристики карт, параметры фракций, эффектов, ландшафтов и т.д.) во внешних ассетах Unreal Engine (Data Tables, Data Assets) вместо жесткого кодирования в C++ или Blueprint. Это позволит гейм-дизайнерам и контент-менеджерам добавлять/изменять контент и баланс игры без участия программистов, что критически важно для будущих обновлений и итераций баланса.

**Зачем Хранить Данные Вовне (Data-Driven Approach):**

*   **Разделение Ролей:** Гейм-дизайнеры и контент-менеджеры могут изменять параметры игры (стоимость карты, HP юнита, описание эффекта, иконки) без необходимости изменять или компилировать код.
*   **Быстрые Итерации Баланса:** Изменение чисел в таблице или ассете занимает секунды, перезапуск игры — и можно тестировать новый баланс.
*   **Удобство Редактирования:** Unreal Editor предоставляет удобные интерфейсы для работы с Data Tables (табличный вид, импорт/экспорт CSV/JSON) и Data Assets (окно Details).
*   **Поддержка Локализации:** Использование `FText` в структурах данных позволяет легко интегрировать систему локализации Unreal Engine для всех текстовых элементов игры.
*   **Чистота Кода:** Игровая логика становится чище, фокусируясь на *использовании* данных, а не на их *хранении* или жестком кодировании.

**Ключевые Инструменты Unreal Engine:**

*   **`USTRUCT()`:** Определяет структуру данных в C++. Используется как "схема" для Data Tables (`FTableRowBase` наследники) и Data Assets, а также может быть членом других структур или классов. Данные в структурах не могут существовать сами по себе в мире или Content Browser; они должны быть частью Актера, Компонента, UObject, Data Asset или строки в Data Table.
*   **`FTableRowBase`:** Базовая структура, от которой должны наследоваться структуры, используемые в `UDataTable`. Каждая строка в Data Table соответствует одному экземпляру такой структуры.
*   **`UDataTable`:** Ассет в Content Browser, который хранит коллекцию структур данных, унаследованных от `FTableRowBase`. Идеально подходит для хранения однотипных данных, где важен табличный вид (каталог всех карт, баланс всех юнитов, список всех эффектов).
*   **`UDataAsset`:** Ассет в Content Browser, который хранит данные, определенные в C++ классе, наследующем от `UDataAsset`. Подходит для хранения уникальных, более сложных, иерархических данных или данных, которые не вписываются в строгую табличную структуру. Например, полная конфигурация конкретной фракции или детальное описание уникальной карты с ветвящейся логикой эффектов.
*   **`TSoftObjectPtr<T>` / `TSoftClassPtr<T>`:** "Мягкие" ссылки на ассеты (объекты или классы) в Content Browser. В отличие от сильных ссылок (`T*`, `TSubclassOf`), мягкие ссылки не загружают ассет в память автоматически при загрузке Актера/Объекта, который содержит ссылку. Ассет загружается только при явном вызове `.LoadSynchronous()` или через систему асинхронной загрузки (`FStreamableManager`). Это важно для оптимизации памяти.

**Шаги Реализации:**

1.  **Определение Базовых Структур Данных (C++ `USTRUCT()`)**:
    *   **Действие:** В папке `Source/Polye/Core/` или отдельной папке `Data/` (если она будет сильно разрастаться), создать заголовочный файл (например, `PolyeDataTypes.h`). В нем определить структуры данных для каждого типа игровых данных, которые будут храниться вовне.
    *   Каждая структура должна использовать макрос `USTRUCT()` и включать `UPROPERTY()` для каждого поля данных. Используйте подходящие типы данных (`int`, `float`, `FString`, `FText` для локализуемого текста, `TSoftObjectPtr`/`TSoftClassPtr` для ссылок на другие ассеты).
    *   Для структур, которые будут использоваться в `UDataTable`, они должны наследовать от `FTableRowBase`.
    *   **Обоснование:** Определение структур в C++ создает формальные "контракты" для данных. Макрос `USTRUCT()` и `UPROPERTY()` делают эти структуры видимыми и доступными в Unreal Engine (в Data Tables, Data Assets, Blueprint). `FTableRowBase` является обязательным для использования в Data Tables. Использование `FText` вместо `FString` важно для будущей локализации. `TSoftObjectPtr`/`TSoftClassPtr` позволяют ссылаться на ассеты, не загружая их в память сразу, что хорошо для производительности.
    *   **Что Хранить Здесь:** Определения *формата* данных. Какие поля есть у карты, какие параметры у эффекта и т.д.
    *   **Что Не Хранить Здесь:** Сами игровые данные (числа, тексты). Они будут в ассетах. Игровую логику, которая *обрабатывает* эти данные.

2.  **Определение Классов `UDataAsset` (C++)**:
    *   **Действие:** Создать C++ классы, наследующие от `UDataAsset`, для тех типов данных, которые являются более сложными или требуют уникальной конфигурации, выходящей за рамки простой строки в таблице. Например, детальные данные о каждой карте, полная конфигурация фракции или ландшафта.
    *   В каждом классе использовать макрос `UCLASS()` и `UPROPERTY()` для хранения данных. Добавить спецификатор `BlueprintType`, чтобы их можно было использовать в Blueprint.
    *   **Обоснование:** `UDataAsset`ы предоставляют удобный способ редактировать сложные, иерархические данные в редакторе. Каждый ассет является самостоятельным файлом, что хорошо для уникальных объектов. Использование `TSoftClassPtr` позволяет ссылаться на Blueprint классы (например, `BP_Unit_SwampBrotherhood_XYZ`), которые будут спавнены.
    *   **Что Хранить Здесь:** Детальные, специфичные для конкретного объекта (карта, фракция, ландшафт) данные, которые не подходят для плоской структуры Data Table. Ссылки на другие ассеты (модели, материалы, частицы, звуки, Blueprint классы).
    *   **Что Не Хранить Здесь:** Общие балансные параметры, которые одинаковы для многих объектов (их лучше в Data Table). Игровую логику.
    *   **Outcome:** Созданы базовые C++ классы, наследующие от `UDataAsset`, для основных типов игровых данных. Проект скомпилирован.

    #include "CoreMinimal.h"
    #include "Engine/DataAsset.h"
    #include "PolyeDataTypes.h" // Включить наш файл с основными структурами
    #include "PolyeCardData.generated.h"

    // Можно создать наследников (UPolyeUnitCardData, UPolyeStructureCardData и т.д.)
    // если данные сильно различаются между типами карт.
    UCLASS(BlueprintType)
    class POLYE_API UPolyeCardData : public UDataAsset
    {
        GENERATED_BODY()

    public:
        // Базовые свойства (могут дублировать FCardDataBase, но здесь это источник истины для детальных данных)
        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        FName CardID; // Уникальный ID для этой карты (должен совпадать с Row Name в DT)

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        EPolyeCardType CardType = EPolyeCardType::ECT_Unit;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        EPolyeFaction Faction = EPolyeFaction::EF_Neutral;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        FText CardName;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        FText CardDescription;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        int32 EtherCost = 0;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
        TSoftObjectPtr<UTexture2D> CardArtwork;

        // Свойства, специфичные для каждого типа карты.
        // Можно использовать EditCondition или создать наследников UPolyeCardData.
        // С EditCondition все поля видны, но активны только для выбранного CardType.
        // С наследниками - у каждого наследника только свои поля.
        // Для простоты MVP используем EditCondition.

        // --- Для Юнитов/Строений ---
        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Combat Data", meta=(EditCondition="CardType == EPolyeCardType::ECT_Unit || CardType == EPolyeCardType::ECT_Structure"))
        int32 BaseHP = 0;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Combat Data", meta=(EditCondition="CardType == EPolyeCardType::ECT_Unit"))
        int32 BaseAttack = 0;

        UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Combat Data", meta=(EditCondition="CardType == EPolyeCardType::ECT_Unit || CardType == EPolyeCardType::ECT_Structure"))

        // --- Для Событий/Эффектов ---
         UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Effect Data", meta=(EditCondition="CardType == EPolyeCardType::ECT_Event || CardType == EPolyeCardType::ECT_LandscapeChange"))

         UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Landscape Change Data", meta=(EditCondition="CardType == EPolyeCardType::ECT_LandscapeChange"))

3.  **Создание и Наполнение Ассетов в Редакторе (Data Assets & Data Tables):**
    *   **Действие (Data Assets):** В Content Browser, в папке `Content/Data/DataAssets/` (и подпапках `Cards/`, `Factions/`, `Landscapes/`):
        *   Правой кнопкой мыши -> `Miscellaneous -> Data Asset`.
        *   В появившемся окне выбрать созданный вами C++ класс `UPolyeCardData` (или его наследника, если создавали), `UPolyeFactionData`, `UPolyeLandscapeData` и т.д.
        *   Назвать ассеты в соответствии с соглашениями (напр., `DA_Unit_SwampBrotherhood_XYZ`, `DA_Faction_SwampBrotherhood`, `DA_Landscape_MysticSwamp`).
        *   Открыть каждый созданный ассет и заполнить все `UPROPERTY()` поля в окне Details, используя данные из дизайн-документа.
    *   **Действие (Data Tables):** В Content Browser, в папке `Content/Data/DataTables/`:
        *   Правой кнопкой мыши -> `Miscellaneous -> Data Table`.
        *   В появившемся окне выбрать созданную вами C++ структуру `FCardDataBase` (для каталога карт), или другую структуру `FTableRowBase` (для балансных таблиц).
        *   Назвать таблицы в соответствии с соглашениями (напр., `DT_CardCatalog`, `DT_Balance_Units`).
        *   Открыть каждую созданную таблицу. Можно добавить строки вручную или импортировать из CSV/JSON (кнопка Import).
        *   **Для `DT_CardCatalog`:** Каждая строка будет представлять одну карту. **Row Name** (имя строки) будет уникальным ID карты (`FName`). Заполнить поля `FCardDataBase` (CardType, Faction, Cost, Name, Description, Artwork, и ссылку `DetailedCardDataAsset` на соответствующий `DA_CardData`).
        *   **Для `DT_Balance_Units`:** Структура может содержать ID юнита (Row Name), и поля для переопределения базовых характеристик (HP, Attack).
    *   **Обобоснование:** Этот шаг переносит фактические игровые данные из дизайн-документа в редактируемые ассеты UE. Это позволяет дизайнерам менять числа, тексты, иконки, ссылки на другие ассеты (VFX, SFX, BP) прямо в редакторе, без перекомпиляции кода. Создание подпапок (`DataAssets/`, `DataTables/`, `Cards/`, `Factions/` и т.д.) помогает организовать контент.
    *   **Что Делает Дизайнер:** Создает и заполняет эти ассеты, экспортирует/импортирует CSV для массового редактирования.
    *   **Что Не Делает Дизайнер:** Пишет C++ код, меняет логику игры.
    *   **Outcome:** Создан набор ассетов Data Asset и Data Table в Content Browser, содержащих стартовые игровые данные (для MVP).

4.  **Реализация Менеджеров Данных (C++ `UObject` или `USubsystem`)**:
    *   **Действие:** Создать C++ классы (например, в папке `Source/Polye/GameplaySystems/Data/` или `Core/`) ответственные за загрузку и предоставление доступа к этим ассетам данных. Эти менеджеры должны быть доступны из геймплейного кода. Рекомендуется использовать `UGameInstance` или `USubsystem`. `UGameInstance` - хороший вариант для данных, нужных на протяжении всей сессии игры (меню, лобби, матчи), `USubsystem` (UE5+) - более современный и гибкий способ создания глобальных менеджеров. Для MVP, `UGameInstance` вполне подходит.
    *   Создайте классы вроде `UPolyeCardManager`, `UPolyeFactionManager`, `UPolyeLandscapeManager`. Они могут быть простыми `UObject`ами, создаваемыми и управляемыми вашим `APolyeGameInstance`.
    *   Эти классы будут содержать ссылки (`TSoftObjectPtr`) на Data Assets и Data Tables и функции для безопасного доступа к данным.
    *   **Обоснование:** Менеджеры данных инкапсулируют логику доступа к ассетам. Они знают, какие Data Tables и Data Assets существуют и как их загружать/читать. Использование `TSoftObjectPtr` и асинхронной загрузки (через `UAssetManager` и `FStreamableManager` - продвинутая тема, но очень полезная) помогает управлять памятью, загружая ассеты только по требованию. Синхронная загрузка (`LoadSynchronous`) проста, но может вызвать зависания, если грузит большие ассеты, поэтому ее следует использовать осторожно, преимущественно во время загрузки уровней или инициализации.
    *   **Что Делает Менеджер:** Хранит ссылки на Data Tables/Data Assets, предоставляет функции для поиска и загрузки данных (например, "дай мне базовые данные карты с ID X", "дай мне полный Data Asset фракции Y"), кэширует загруженные ассеты для быстрого повторного доступа.
    *   **Что Не Делает Менеджер:** Не содержит саму игровую логику, которая использует данные (например, расчет урона с учетом параметров из Data Asset юнита). Не хранит состояние игры или игрока.
    *   **Outcome:** Созданы C++ классы-менеджеры для доступа к игровым данным. Эти менеджеры могут быть инициализированы и доступны из других частей игры (например, из GameMode, GameState, PlayerState, UI).

    FCardDataBase UPolyeCardManager::GetCardDataBase(FName CardID)
    {
        if (CardCatalogDataTable.IsValid())
        {
            // Get() возвращает указатель, если ассет уже загружен. LoadSynchronous() загрузит его, если нет.
            // Для DT, загруженной при инициализации, Get() достаточно.
            if (UDataTable* LoadedDataTable = CardCatalogDataTable.Get())
            {
                if (const FCardDataBase* Row = LoadedDataTable->FindRow<FCardDataBase>(CardID, TEXT("GetCardDataBase")))
                {
                     return *Row; // Возвращаем копию структуры
                }
            }
        }
        UE_LOG(LogTemp, Error, TEXT("Card Data Base for ID %s not found in Data Table!"), *CardID.ToString());
        return FCardDataBase(); // Вернуть пустую/дефолтную структуру в случае ошибки
    }

    TSoftObjectPtr<UPolyeCardData> UPolyeCardManager::GetCardDataAsset(FName CardID)
    {
        // Находим базовые данные в DT
        FCardDataBase BaseData = GetCardDataBase(CardID);
        // Возвращаем мягкую ссылку на детальный Data Asset из DT
        return BaseData.DetailedCardDataAsset;
    }

    UPolyeCardData* UPolyeCardManager::LoadCardDataAssetSynchronous(FName CardID)
    {
        // Сначала пробуем найти в кэше загруженных ассетов
        if (LoadedCardDataAssets.Contains(CardID) && LoadedCardDataAssets[CardID].IsValid())
        {
             return LoadedCardDataAssets[CardID].Get();
        }

        // Если не в кэше, получаем мягкую ссылку
        TSoftObjectPtr<UPolyeCardData> CardDataAssetPtr = GetCardDataAsset(CardID);

        if (CardDataAssetPtr.IsValid())
        {
            // Синхронно загружаем Data Asset
            UPolyeCardData* LoadedDataAsset = CardDataAssetPtr.LoadSynchronous();
            if (LoadedDataAsset)
            {
                LoadedCardDataAssets.Add(CardID, LoadedDataAsset); // Сохраняем в кэше
                return LoadedDataAsset;
            }
            else
            {
                UE_LOG(LogTemp, Error, TEXT("Failed to load Detailed Card Data Asset for ID %s!"), *CardID.ToString());
            }
        }
        else
        {
             // У этой карты нет Detailed Data Asset, или ссылка невалидна
             UE_LOG(LogTemp, Warning, TEXT("Card ID %s does not have a valid Detailed Card Data Asset reference."), *CardID.ToString());
        }

        return nullptr; // Не удалось загрузить или найти Data Asset
    }

5.  **Интеграция Менеджеров Данных (в GameInstance или USubsystem):**
    *   **Действие:** В вашем `APolyeGameInstance` (наследует от `UGameInstance`, устанавливается в настройках проекта -> Maps & Modes) или создать собственный `UGameInstanceSubsystem` (UE5+), создать экземпляры менеджеров данных и инициализировать их.
    *   `UGameInstance` или `UGameInstanceSubsystem` подходит для данных, которые нужны на протяжении всей игровой сессии (например, каталог карт для редактора колоды, информация о фракциях для лобби, менеджеры, которые предоставляют доступ к этим данным).
    *   **Обоснование:** Инициализация менеджеров в `GameInstance` (или его подсистеме) гарантирует, что они создаются один раз при запуске игры и доступны из любой части кода, которая может получить доступ к GameInstance (`UGameplayStatics::GetGameInstance(GetWorld())` или `GetGameInstance()->GetSubsystem<UMySubsystem>()`). Это централизованный доступ к игровым данным.
    *   **Что Делает GameInstance/Subsystem:** Создает экземпляры менеджеров, хранит на них ссылки, вызывает их функцию инициализации при старте игры, предоставляет геттеры для доступа к менеджерам из других частей игры.
    *   **Что Не Делает GameInstance/Subsystem:** Не содержит саму логику работы с игровыми данными или геймплейную логику.
    *   **Outcome:** Менеджеры данных создаются при запуске игры и хранят ссылки на загруженные ассеты данных, предоставляя функции для доступа к ним из C++ и Blueprint.

**Ключевые Соображения и Лучшие Практики:**

*   **Single Source of Truth:** Все игровые данные должны храниться в Data Assets или Data Tables. Код должен только *читать* эти данные через менеджеры, а не содержать их жестко или дублировать логику их обработки в разных местах.
*   **Сложность Эффектов:** Система эффектов в вашем дизайне очень богатая. Структура `FPolyeEffectConfig` может оказаться недостаточно гибкой для всех эффектов. Рассмотрите возможность использования отдельных `UDataAsset`ов для каждого *типа* эффекта (например, `UDamageEffectDataAsset`, `UStatModifierEffectDataAsset`, `UAuraEffectDataAsset`), каждый со своей специфической структурой данных. Или, если будете использовать Gameplay Ability System (GAS), его `GameplayEffect`ы уже являются мощным инструментом для этого.
*   **Ссылочная Целостность:** Убедитесь, что ссылки между ассетами (`TSoftObjectPtr`) корректны. Инструменты UE могут помочь в этом (Reference Viewer).
*   **Производительность Загрузки:** Остерегайтесь синхронной загрузки больших Data Assets (`LoadSynchronous`) во время геймплея (например, в Tick или в функциях, вызываемых часто). Используйте асинхронную загрузку (`FStreamableManager`) и убедитесь, что критически важные данные загружены заранее (при старте игры или уровня). Менеджеры должны инкапсулировать эту логику загрузки.
*   **Доступ из Blueprint:** Убедитесь, что структуры (`USTRUCT(BlueprintType)`) и функции менеджеров (`UFUNCTION(BlueprintCallable)`) доступны в Blueprint, чтобы гейм-дизайнеры могли легко получать данные.
*   **Валидация Данных:** Реализуйте базовую проверку данных при загрузке (например, в `InitializeManager` или в функциях геттеров), чтобы ловить ошибки в ассетах на ранней стадии (например, отсутствующие ссылки, нулевые значения, где они недопустимы, некорректные параметры в TMap).
*   **Иерархия UDataAsset:** Для сложных типов данных, таких как карты, рассмотрите создание базового класса `UPolyeCardData` и наследование от него (`UPolyeUnitCardData`, `UPolyeStructureCardData`, `UPolyeEventCardData`). Это позволяет каждому типу карты иметь свои уникальные свойства, не захламляя базовый класс и не полагаясь только на `EditCondition`.
