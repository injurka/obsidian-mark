**Цель:** Спроектировать и реализовать систему, которая позволяет хранить все игровые данные (характеристики карт, параметры фракций, эффектов, ландшафтов и т.д.) во внешних ассетах Unreal Engine (Data Tables, Data Assets) вместо жесткого кодирования в C++ или Blueprint. Это позволит гейм-дизайнерам и контент-менеджерам добавлять/изменять контент и баланс игры без участия программистов, что критически важно для будущих обновлений.

**Ключевые Инструменты Unreal Engine:**

*   **`USTRUCT()`:** Определяет структуру данных в C++. Используется как "схема" для Data Tables и может быть членом других USTRUCT/UOBJECT.
*   **`UDataTable`:** Ассет в Content Browser, который хранит коллекцию структур данных (`USTRUCT()` с наследованием от `FTableRowBase`). Отлично подходит для однотипных данных (каталог всех карт, баланс юнитов). Может быть импортирован из CSV или JSON.
*   **`UDataAsset`:** Ассет в Content Browser, который хранит данные, определенные в C++ классе, наследующем от `UDataAsset`. Подходит для хранения уникальных, более сложных или иерархических данных (полная конфигурация фракции, детальное описание уникальной карты).

**Шаги Реализации:**

1.  **Определение Базовых Структур Данных (C++ `USTRUCT`)**:
    *   **Действие:** В папке `Source/Polye/Core/` или отдельной папке `Data/` (если она будет сильно разрастаться), создать заголовочный файл (например, `PolyeDataTypes.h`). В нем определить структуры данных для каждого типа игровых данных, которые будут храниться вовне.
    *   Каждая структура должна использовать макрос `USTRUCT()` и включать `UPROPERTY()` для каждого поля данных. Используйте подходящие типы данных (int, float, FString, FText для локализуемого текста, ссылки на другие ассеты).

Макрос `USTRUCT()` и `UPROPERTY()` делают эти структуры видимыми и доступными в Unreal Engine (в Data Tables, Data Assets, Blueprint). `FTableRowBase` является обязательным для использования в Data Tables. Использование `FText` вместо `FString` важно для будущей локализации. `TSoftObjectPtr` позволяет ссылаться на ассеты, не загружая их в память сразу, что хорошо для производительности.

            FText CardDescription;

            UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")
            int32 EtherCost = 0;

            UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Card Data")

            // Добавить поля, специфичные для каждого типа карты, или создать наследников

3.  **Создание и Наполнение Ассетов в Редакторе (Data Assets & Data Tables):**
    *   **Действие (Data Assets):** В Content Browser, в папке `Content/Data/DataAssets/` (и подпапках `Cards/`, `Factions/`, `Landscapes/`):
        *   Правой кнопкой мыши -> `Miscellaneous -> Data Asset`.
        *   В появившемся окне выбрать созданный вами C++ класс `UPolyeCardData` (или его наследника, если создавали), `UPolyeFactionData`, `UPolyeLandscapeData` и т.д.
        *   Назвать ассеты в соответствии с соглашениями (напр., `DA_Unit_SwampBrotherhood_XYZ`, `DA_Faction_SwampBrotherhood`, `DA_Landscape_MysticSwamp`).
        *   Открыть каждый созданный ассет и заполнить все `UPROPERTY()` поля в окне Details, используя данные из дизайн-документа.
    *   **Действие (Data Tables):** В Content Browser, в папке `Content/Data/DataTables/`:
        *   Правой кнопкой мыши -> `Miscellaneous -> Data Table`.
        *   В появившемся окне выбрать созданную вами C++ структуру `FCardDataBase` (для каталога карт), или другую структуру `FTableRowBase` (для балансных таблиц).
        *   Назвать таблицы в соответствии с соглашениями (напр., `DT_CardCatalog`, `DT_Balance_Units`).
        *   Открыть каждую созданную таблицу. Можно добавить строки вручную или импортировать из CSV/JSON.
        *   **Для `DT_CardCatalog`:** Каждая строка будет представлять одну карту. Row Name может быть уникальным ID карты (FName). Заполнить поля `FCardDataBase` (CardType, Faction, Cost, Name, Description, Artwork, и ссылку `DetailedCardDataAsset` на соответствующий `DA_CardData`).
        *   **Для `DT_Balance_Units`:** Структура может содержать ID юнита (Row Name), и поля для переопределения базовых характеристик (HP, Attack).
        *   **Для `DT_FactionAuraStrength`:** Структура может содержать FName ID Ауры и float проценты влияния по дистанции (или просто хранить эти числа в `UPolyeFactionData`).
    *   **Обоснование:** Этот шаг переносит фактические игровые данные из дизайн-документа в редактируемые ассеты UE. Это позволяет дизайнерам менять числа, тексты, иконки, ссылки на другие ассеты (VFX, SFX, BP) прямо в редакторе, без перекомпиляции кода.
    *   **Outcome:** Создан набор ассетов Data Asset и Data Table в Content Browser, содержащих стартовые игровые данные (для MVP).

4.  **Реализация Менеджеров Данных (C++ `UObject` или `AActor`)**:
    *   **Действие:** Создать C++ классы (например, в папке `Source/Polye/GameplaySystems/Data/` или `Core/`) ответственные за загрузку и предоставление доступа к этим ассетам данных. Эти менеджеры должны быть доступны из геймплейного кода (например, через `UGameInstance`, `AGameStateBase` или как `USubsystem` в UE5). `UGameInstance` - хороший вариант для данных, нужных на протяжении всей сессии игры (меню, лобби, матчи), `AGameStateBase` - для данных специфичных для конкретного матча (например, актуальное состояние поля).
    *   Создайте классы вроде `UPolyeCardManager`, `UPolyeFactionManager`, `UPolyeLandscapeManager`. Они могут быть простыми `UObject`ами, создаваемыми и управляемыми вашим `APolyeGameInstance`.
    *   Эти классы будут содержать ссылки на загруженные Data Assets и Data Tables.
    *   **Пример `UPolyeCardManager`:**
        ```cpp
        // Data/PolyeCardManager.h
        #pragma once

        #include "CoreMinimal.h"
        #include "UObject/NoExportTypes.h"
        #include "Engine/DataTable.h"
        #include "PolyeDataTypes.h" // Включить структуры
        #include "Data/PolyeCardData.h" // Включить UDataAsset карты
        #include "PolyeCardManager.generated.h"

        UCLASS(BlueprintType)
        class POLYE_API UPolyeCardManager : public UObject
        {
             GENERATED_BODY()

        public:
             void InitializeManager(); // Функция инициализации, вызываемая из GameInstance

             // Функция для получения базовых данных карты по ID
             UFUNCTION(BlueprintCallable, Category = "Card Manager")
             FCardDataBase GetCardDataBase(FName CardID);

             // Функция для получения полных данных карты (загружает Data Asset при необходимости)
             UFUNCTION(BlueprintCallable, Category = "Card Manager")
             UPolyeCardData* GetCardData(FName CardID);

             // ... другие функции для работы с коллекцией карт

        protected:
            UPROPERTY(EditAnywhere, Category = "Card Data")
            TSoftObjectPtr<UDataTable> CardCatalogDataTable; // Ссылка на DT_CardCatalog

            // Карта для быстрого доступа к загруженным Data Assets карт по их ID (Row Name в DT)
            UPROPERTY(Transient) // Transient - не сохраняется в ассет
            TMap<FName, TObjectPtr<UPolyeCardData>> LoadedCardDataAssets;

            // Массив ID всех карт (опционально)
            TArray<FName> AllCardIDs;
        };

        // Data/PolyeCardManager.cpp
        #include "Data/PolyeCardManager.h"
        #include "Engine/AssetManager.h" // Для асинхронной загрузки (лучшая практика)
        #include "Engine/StreamableManager.h"

        void UPolyeCardManager::InitializeManager()
        {
            // Загрузить Data Table при старте менеджера (синхронно - она обычно небольшая и нужна рано)
            if (CardCatalogDataTable.IsValid())
            {
                 UDataTable* LoadedDataTable = CardCatalogDataTable.LoadSynchronous();
                 if (LoadedDataTable)
                 {
                     // Можно прочитать все строки тут, чтобы получить список всех CardID
                     TArray<FName> RowNames = LoadedDataTable->GetRowNames();
                     AllCardIDs = RowNames;
                     UE_LOG(LogTemp, Warning, TEXT("Card Catalog Data Table loaded with %d entries."), RowNames.Num());
                 }
            }
            else
            {
                 UE_LOG(LogTemp, Error, TEXT("Card Catalog Data Table reference is invalid!"));
            }
        }

        FCardDataBase UPolyeCardManager::GetCardDataBase(FName CardID)
        {
            if (CardCatalogDataTable.IsValid())
            {
                if (UDataTable* LoadedDataTable = CardCatalogDataTable.Get()) // Использовать Get() если уже загружено
                {
                    if (const FCardDataBase* Row = LoadedDataTable->FindRow<FCardDataBase>(CardID, TEXT("")))
                    {
                         return *Row;
                    }
                }
            }
            UE_LOG(LogTemp, Error, TEXT("Card Data Base for ID %s not found!"), *CardID.ToString());
            return FCardDataBase(); // Вернуть пустую/дефолтную структуру
        }

        UPolyeCardData* UPolyeCardManager::GetCardData(FName CardID)
        {
            // Сначала пробуем найти в уже загруженных ассетах
            if (LoadedCardDataAssets.Contains(CardID) && LoadedCardDataAssets[CardID].IsValid())
            {
                 return LoadedCardDataAssets[CardID].Get();
            }

            // Если не загружен, получаем ссылку из Data Table
            FCardDataBase BaseData = GetCardDataBase(CardID);
            if (BaseData.DetailedCardDataAsset.IsValid())
            {
                // Асинхронно загружаем Data Asset (лучше для больших объемов или редких данных)
                // Или синхронно, если ассет маленький или нужен немедленно (будьте осторожны с синхронной загрузкой в геймплейном коде)
                // Пример синхронной загрузки (для простоты, но не всегда лучшая практика):
                UPolyeCardData* LoadedDataAsset = BaseData.DetailedCardDataAsset.LoadSynchronous();
                if (LoadedDataAsset)
                {
                    LoadedCardDataAssets.Add(CardID, LoadedDataAsset); // Сохраняем в мапе загруженных
                    return LoadedDataAsset;
                }
                else
                {
                    UE_LOG(LogTemp, Error, TEXT("Failed to load Detailed Card Data Asset for ID %s!"), *CardID.ToString());
                }
            }
            else
            {
                 // Карты может не иметь Detailed Data Asset, если все данные в Data Table
                 // В этом случае, возможно, нужно создать временный UObject из BaseData или вернуть null, в зависимости от дизайна
            }

            return nullptr; // Не удалось загрузить или найти Data Asset
        }

        ```
    *   **Обоснование:** Менеджеры данных инкапсулируют логику доступа к ассетам. Они знают, какие Data Tables и Data Assets существуют и как их загружать/читать. Использование `TSoftObjectPtr` и асинхронной загрузки (через `UAssetManager` и `FStreamableManager` - продвинутая тема, но очень полезная) помогает управлять памятью. Синхронная загрузка (`LoadSynchronous`) проста, но может вызвать зависания, если грузит большие ассеты.
    *   **Outcome:** Созданы C++ классы-менеджеры для доступа к игровым данным. Эти менеджеры могут быть инициализированы и доступны из других частей игры (например, из GameMode, GameState, PlayerState, UI).

5.  **Интеграция Менеджеров Данных (в GameInstance или GameState):**
    *   **Действие:** В вашем `APolyeGameInstance` (наследует от `UGameInstance`, устанавливается в настройках проекта -> Maps & Modes) или `APolyeGameStateBase` создать экземпляры менеджеров данных и инициализировать их. `UGameInstance` подходит для данных, которые нужны на протяжении всей игровой сессии (например, каталог карт для редактора колоды, информация о фракциях для лобби). `AGameStateBase` подходит для данных, специфичных для текущего матча, которые нужно реплицировать (например, состояние поля, данные существующих эффектов на поле). Для MVP, возможно, проще начать с GameInstance для всех менеджеров данных.
    *   **Пример в `APolyeGameInstance.h`:**
        ```cpp
        // Core/PolyeGameInstance.h
        #pragma once

        #include "CoreMinimal.h"
        #include "Engine/GameInstance.h"
        #include "Data/PolyeCardManager.h"

        #include "Data/PolyeLandscapeManager.h" // Если создали
        #include "PolyeGameInstance.generated.h"

        UCLASS()
        class POLYE_API UPolyeGameInstance : public UGameInstance
        {
             GENERATED_BODY()

        public:
             virtual void Init() override;
             virtual void Shutdown() override;

             UFUNCTION(BlueprintCallable, Category = "Managers")
             UPolyeCardManager* GetCardManager() const { return CardManager; }

             // Добавить геттеры для других менеджеров

        protected:
             UPROPERTY(EditAnywhere, Category = "Managers")
             TSubclassOf<UPolyeCardManager> CardManagerClass; // Ссылка на класс BP_PolyeCardManager

             UPROPERTY() // UProperty для GC и владения
             TObjectPtr<UPolyeCardManager> CardManager;

             // Добавить свойства для других менеджеров
        };
        ```
    *   **Пример в `APolyeGameInstance.cpp`:**
        ```cpp

            Super::Init();

            // Создаем экземпляры менеджеров данных
            if (CardManagerClass)
            {
                 CardManager = NewObject<UPolyeCardManager>(this, CardManagerClass);
                 if (CardManager)
                 {
                     CardManager->InitializeManager(); // Вызываем нашу функцию инициализации
                 }
            }
             // Инициализировать другие менеджеры
        }

        {
            // Очистка менеджеров, если необходимо
            Super::Shutdown();
        }
        ```
    *   **Обоснование:** Инициализация менеджеров в `GameInstance` гарантирует, что они создаются один раз при запуске игры и доступны из любой части кода, которая может получить доступ к GameInstance (`UGameplayStatics::GetGameInstance(GetWorld())`). Это централизованный доступ к игровым данным.
    *   **Outcome:** Менеджеры данных создаются при запуске игры и хранят ссылки на загруженные ассеты данных, предоставляя функции для доступа к ним из C++ и Blueprint.

**Ключевые Соображения и Лучшие Практики:**

*   **Single Source of Truth:** Все игровые данные должны храниться в Data Assets или Data Tables. Код должен только *читать* эти данные, а не содержать их жестко.
*   **Сложность Эффектов:** Система эффектов в вашем дизайне очень богатая. Структура `FPolyeEffectConfig` может оказаться недостаточно гибкой. Рассмотрите возможность использования отдельных `UDataAsset`ов для каждого *типа* эффекта (например, `UDamageEffectDataAsset`, `UStatModifierEffectDataAsset`, `UAuraEffectDataAsset`), каждый со своей специфической структурой данных. Или, если будете использовать Gameplay Ability System (GAS), его `GameplayEffect`ы уже являются мощным инструментом для этого.
*   **Ссылочная Целостность:** Убедитесь, что ссылки между ассетами (`TSoftObjectPtr`) корректны. Инструменты UE могут помочь в этом (Reference Viewer).
*   **Производительность:** Остерегайтесь синхронной загрузки больших Data Assets (`LoadSynchronous`) во время геймплея. Используйте асинхронную загрузку (`FStreamableManager`) и убедитесь, что критически важные данные загружены заранее (при старте игры или уровня).
*   **Доступ из Blueprint:** Убедитесь, что структуры (`USTRUCT(BlueprintType)`) и функции менеджеров (`UFUNCTION(BlueprintCallable)`) доступны в Blueprint, чтобы гейм-дизайнеры могли легко получать данные.
*   **Валидация Данных:** Реализуйте базовую проверку данных при загрузке (например, в `InitializeManager`), чтобы ловить ошибки в ассетах на ранней стадии (например, отсутствующие ссылки, нулевые значения, где они недопустимы).
