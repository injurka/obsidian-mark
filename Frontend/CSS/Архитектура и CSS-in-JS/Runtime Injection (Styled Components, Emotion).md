# Runtime Injection (Styled Components, Emotion)

## 1. Что такое Runtime CSS-in-JS?

**Runtime CSS-in-JS** — это подход к стилизации, при котором стили пишутся непосредственно внутри JavaScript-файлов (обычно с использованием шаблонных строк или объектов), а их компиляция, хеширование и внедрение в документ происходят непосредственно **в браузере во время выполнения приложения** (runtime).

Наиболее известные представители: **Styled Components** и **Emotion**.

---

## 2. Архитектура и жизненный цикл стилей под капотом

Когда React рендерит компонент со стилями CSS-in-JS, библиотека выполняет следующую цепочку действий:

```text
[React Render] 
      │
      ▼
1. Вычисление динамических пропсов ──> 2. Хеширование стилей ──> 3. Парсинг через Stylis 
                                                                           │
                                                                           ▼
                                                               4. Внедрение в DOM (<style>)
```

1.  **Интерполяция пропсов:** JS выполняет функции внутри шаблонных строк (например, `${props => props.primary ? 'red' : 'blue'}`).
2.  **Хеширование:** Библиотека создает уникальный хэш на основе полученной строки стилей (например, `css-1x8a8sd`). Этот хэш служит именем класса.
3.  **Кэширование:** Библиотека проверяет свой внутренний кэш. Если класс с таким хэшем уже генерировался, шаг парсинга пропускается.
4.  **Парсинг (Stylis):** Строка стилей парсится легковесным CSS-парсером (обычно **Stylis**) для добавления вендорных префиксов и поддержки вложенных правил ( nesting ).
5.  **Внедрение (Injection):**
    *   *В режиме разработки:* Стили вставляются как обычный текстовый контент внутрь тега `<style>`, чтобы разработчик мог редактировать их в DevTools.
    *   *В режиме продакшена:* Используется метод `CSSStyleSheet.insertRule()`. Это самый быстрый способ добавления стилей в обход парсинга DOM браузером, но такие стили нельзя редактировать напрямую в инспекторе.

---

## 3. Преимущества подхода

*   **Динамическая стилизация "из коробки":** Стили меняются декларативно в зависимости от состояния React-компонента через пропсы.
*   **Локальная видимость (Scoping):** Исключены конфликты имен классов, так как каждый компонент получает уникальный сгенерированный хэш.
*   **Автоматический Critical CSS:** На страницу загружаются и применяются стили только тех компонентов, которые рендерятся в данный момент. Стили для остальных страниц не скачиваются.
*   **Удобная темизация:** Использование контекста (через `<ThemeProvider>`) позволяет легко менять темы на лету.

## 4. Проблемы производительности: Почему индустрия отказывается от Runtime?

Несмотря на удобство разработки (DX), рантайм-инъекция создает серьезные проблемы для конечных пользователей (UX):

### 4.1. Накладные расходы на вычисления (Performance Overhead)
Поскольку парсинг и генерация CSS происходят в главном потоке JavaScript, частые обновления пропсов (например, при анимации, скролле или drag-and-drop) заставляют браузер непрерывно выполнять JS-код для генерации стилей. Это приводит к просадке FPS и задержкам ввода (Input Lag).

### 4.2. Частая инвалидация стилей и перерисовка
Каждое новое значение пропса генерирует новый хэш-класс, который вставляется в DOM. Браузер вынужден парсить новое правило и заново пересчитывать стили (Recalculate Styles) для всего DOM-дерева.

### 4.3. Проблемы с Server-Side Rendering (SSR)
Чтобы избежать вспышки нестилизованного контента (FOUC — Flash of Unstyled Content) при первой загрузке, разработчики вынуждены использовать специальные серверные сборщики стилей (Style Sheet Collectors). Они собирают все стили при SSR и вставляют их в `<head>` документа, что усложняет архитектуру и увеличивает размер HTML-документа.

### 4.4. Несовместимость с React Server Components (RSC)
React Server Components рендерятся исключительно на сервере и не отправляют JS-рантайм на клиент. Поскольку Styled Components и Emotion требуют наличия рантайма на клиенте и используют React Context, их **невозможно** использовать внутри серверных компонентов.

## 5. Лучшие практики оптимизации при работе с Runtime CSS-in-JS

Если проект уже написан на Styled Components или Emotion, следуйте этим правилам для минимизации проблем:

1.  **Не используйте пропсы для часто меняющихся значений:**
    *   *Плохо (каждый кадр генерирует новый CSS-класс):*
        ```javascript
        const Box = styled.div`
          transform: translateY(${props => props.offset}px);
        `;
        ```
    *   *Хорошо (класс остается статичным, меняется только CSS-переменная):*
        ```javascript
        const Box = styled.div`
          transform: translateY(var(--offset));
        `;
        // В рендере: <Box style={{ '--offset': `${offset}px` }} />
        ```
2.  **Используйте `shouldForwardProp`:**
    Чтобы кастомные пропсы не улетали в DOM в качестве невалидных HTML-атрибутов (что вызывает варнинги в консоли и нагружает DOM), отфильтровывайте их:
    ```javascript
    const Button = styled('button', {
      shouldForwardProp: (prop) => !['customColor'].includes(prop),
    })`
      color: ${props => props.customColor};
    `;
    ```
