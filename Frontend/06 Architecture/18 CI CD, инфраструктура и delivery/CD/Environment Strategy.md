# Стратегия окружений (Environment Strategy)

Код проходит долгий путь от локального ноутбука разработчика до конечного пользователя. Главная боль — это рассинхронизация: "А у меня локально всё работало!". Стратегия окружений призвана сделать этот путь максимально предсказуемым.

Обычно мы выделяем несколько классических этапов: Local -> Dev -> Staging -> Production. Цель Staging (предпродакшена) — быть *точной* копией Production (те же версии БД, те же настройки серверов, похожий объем данных), чтобы отловить баги интеграции до того, как они затронут реальных клиентов.

```mermaid
graph LR
    A[Local] -->|Push| B(CI Pipeline)
    B -->|Deploy| C[Dev Environment]
    C -->|QA Testing| D[Staging Env]
    D -->|Release| E[Production]
```

**Неочевидные нюансы:**
- **Дрифт конфигураций:** Самая частая проблема, когда на Staging добавили переменную окружения, а на Prod забыли. Использовать IaC для всех окружений обязательно.
- **Стоимость:** Полная копия продакшена для Staging стоит столько же, сколько сам Production. Часто Staging делают "уменьшенным", но это убивает суть нагрузочного тестирования.

**Антипаттерн:**
```bash
# Использование production-базы для локальной разработки
DATABASE_URL=postgres://prod-db.example.com/main_db # НИКОГДА ТАК НЕ ДЕЛАЙТЕ!
```

**Правильно:**
Для каждого окружения свои изолированные ресурсы, ключи и базы данных.
