Случаются ситуации, когда в системе появляются сложные бизнес-операции, которые концептуально не принадлежат ни одной конкретной [[Entity]] или [[Value Object]]. Попытка искусственно запихнуть такую логику внутрь одной из сущностей делает её перегруженной и неестественной.

Доменный сервис (Domain Service) — это объект без собственного состояния (stateless), который благородно берет на себя ответственность за инкапсуляцию такой "беспризорной" бизнес-логики.

**Инженерный пример:**
Представим операцию перевода денег с одного счета на другой. Кто должен стать владельцем этого действия? Счет-отправитель? Счет-получатель?

**Антипаттерн (Искусственная привязка):**
```typescript
class Account {
  // Выглядит странно: счет управляет чужим счетом, нарушая инкапсуляцию
  transferTo(targetAccount: Account, amount: Money) {
    this.withdraw(amount);
    targetAccount.deposit(amount);
  }
}
```

**Правильный подход (Domain Service):**
```typescript
class FundsTransferService {
  // Сервис оркестрирует взаимодействие независимых сущностей
  transfer(source: Account, target: Account, amount: Money) {
    // Здесь могут быть сложные проверки лимитов, комиссий и т.д.
    source.withdraw(amount);
    target.deposit(amount);
  }
}
```

**Границы применимости:**
Очень легко скатиться в антипаттерн "Анемичной модели", начав выносить вообще всю логику в сервисы. В таком случае ваши сущности деградируют до глупых мешков с данными. 

Доменные сервисы должны быть исключением, а не правилом повседневной разработки. Прежде чем создать сервис, проведите мысленный эксперимент: "Можно ли это поведение разместить в одном из участвующих объектов или, возможно, выделить новую сущность для этого процесса?". Создавайте сервис только тогда, когда логика затрагивает координацию нескольких самостоятельных сущностей.
