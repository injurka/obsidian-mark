# Архитектура малого приложения (MVP / Прототип)

## 📖 Что это и какую боль мы решаем

**Архитектура малого приложения** — это подход к разработке проектов, главная цель которых: **максимально быстрый Time-to-Market**. 
Это лендинги, простые админки на 3-4 сущности, промо-сайты, или MVP для проверки гипотезы стартапа.

**Боль:** Часто разработчики начитаются статей про DDD и Clean Architecture и начинают внедрять их в MVP. В итоге стартап умирает, так и не выпустив продукт, потому что команда месяц писала мапперы DTO и абстрактные репозитории для формы "Оставьте email". 
Другая крайность — писать весь код в одном файле `App.js` на 3000 строк.

Задача — найти баланс: писать быстро, но не превратить код в помойку за первые 2 недели.

## ⚙️ Как это работает на практике

Главный принцип малого приложения: **Группировка по типам файлов (Layering by Type)** и **Использование возможностей фреймворка на 100%**.

- **Никаких сложных слоев BLL/DAL**. Данные запрашиваются прямо в компонентах (через хуки вроде SWR или React Query).
- **Минимум глобального стейта.** Используется локальный стейт (`useState`, `ref`). Если нужны глобальные данные (токен авторизации) — используется нативный Context API.
- **Файловая структура:** Плоская и понятная.

### Типичная файловая структура:

```text
src/
├── api/          # Файлы с функциями fetch/axios (без сложных классов)
│   └── users.ts
├── assets/       # Иконки, картинки, шрифты
├── components/   # Переиспользуемые UI-компоненты (Кнопки, Инпуты, Модалки)
├── hooks/        # Общие хуки (useClickOutside, useWindowSize)
├── pages/        # Страницы приложения (роуты)
│   ├── Home.tsx
│   └── Profile.tsx
└── App.tsx       # Корневой компонент, роутинг
```

## 💻 Пример: Как надо (Smart / Dumb Component)

Самый полезный паттерн здесь — разделение на "Умные" (Container) и "Глупые" (Presentational) компоненты.

```tsx
// 🟢 Как надо: Smart-компонент страницы
// Он знает про сеть, про роутинг и данные
function ProfilePage() {
  const { data: user, isLoading } = useQuery('user', fetchUserProfile);

  if (isLoading) return <Spinner />;
  
  return (
    <div className="page">
      <h1>Профиль</h1>
      {/* Передаем данные в "Глупый" компонент */}
      <UserProfileCard user={user} onEdit={() => console.log('edit')} />
    </div>
  );
}

// 🟢 Как надо: Dumb-компонент (UI)
// Ничего не знает про сеть, чисто отрисовывает пропсы
function UserProfileCard({ user, onEdit }) {
  return (
    <div className="card">
      <img src={user.avatar} />
      <h2>{user.name}</h2>
      <button onClick={onEdit}>Редактировать</button>
    </div>
  );
}
```

## ⚠️ Неочевидные нюансы и трейдоффы (Где это ломается)

1. **Момент перехода (Когда нужно переписывать)**
   - Эта архитектура ломается, когда количество страниц (Pages) переваливает за ~10-15 штук, а компоненты из папки `components` начинают импортировать друг друга, создавая цикличные зависимости.
   - **Симптом смерти:** Вы открываете папку `components`, а там 150 файлов. Вы не понимаете, какие из них общие (Кнопки), а какие привязаны к конкретной бизнес-логике (КарточкаТовараСРасчетомСкидки).

2. **Заражение UI бизнес-логикой**
   - В малых приложениях валидация формы часто пишется прямо внутри компонента формы. Пока форма простая — это нормально. Когда в форме появляется 20 полей со сложными зависимостями ("Если выбран чекбокс А, поле Б обязательно, но только для юзеров из региона В") — компонент раздувается до 1000 строк. Это сигнал к переходу на *Архитектуру среднего приложения* (вынесение логики в кастомные хуки или сервисы).

3. **Ошибки с Prop-Drilling**
   - При отсутствии Redux/Zustand разработчики начинают прокидывать пропсы (например, данные текущего пользователя) через 5 уровней вложенности.
   - **Решение для MVP:** Использовать Composition (передачу через `children`) или нативный React Context. Не тащите тяжелые стейт-менеджеры "на всякий случай".
