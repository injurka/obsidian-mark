**Разделение ответственности (Separation of Concerns, SoC)** — это фундаментальный принцип проектирования, который гласит, что программа должна быть разделена на отдельные модули, каждый из которых решает только одну задачу (свою "заботу"). 

Если *Single Responsibility Principle (SRP)* применяется в основном к классам и функциям, то *SoC* — это макро-принцип, применяемый к архитектуре всего приложения.

## 1. Суть концепции и какую боль решаем

**Боль:** "Божественные" модули (God Modules). Когда в одном файле или компоненте смешаны стили, разметка, бизнес-логика, сетевые запросы и аналитика. Такой код невозможно тестировать, переиспользовать, а малейшее изменение в стилях может случайно сломать логику запроса к серверу.

### Оси разделения во Frontend

| Ось разделения | Описание |
|---|---|
| **Технологическое разделение** | HTML (Структура)<br>CSS (Внешний вид)<br>JS (Поведение) |
| **Слоистое разделение** | UI (Отображение)<br>Domain (Бизнес-правила)<br>Data (API / Хранилище) |
| **Функциональное разделение** | Auth (Авторизация)<br>Cart (Корзина)<br>Profile (Профиль) |
*Исторически фронтенд делили по технологиям (файлы `.html`, `.css`, `.js`). Сегодня с приходом React/Vue мы перешли к компонентному и слоистому разделению (где в одном компоненте лежат и разметка, и стили, но они строго разделены по бизнес-задачам).*

## 2. Как это работает на практике

Посмотрим на классический React-компонент, который делает слишком много.

### Антипаттерн: Смешение забот (Mixed Concerns)
Компонент загружает данные, парсит их, фильтрует, управляет состоянием и рендерит сложный UI.

```tsx
// ОШИБКА: Нарушение SoC. Компонент знает всё обо всём.
export function UserDashboard() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);

  // ЗАБОТА 1: Сетевой слой
  useEffect(() => {
    fetch('/api/users')
      .then(res => res.json())
      .then(data => {
        // ЗАБОТА 2: Трансформация данных (Бизнес-логика)
        const activeAdmins = data.filter(u => u.isActive && u.role === 'ADMIN');
        setUsers(activeAdmins);
        setLoading(false);
      });
  }, []);

  // ЗАБОТА 3: UI-рендеринг
  if (loading) return <Spinner />;
  return (
    <div className="dashboard">
      {users.map(u => <div key={u.id}>{u.name}</div>)}
    </div>
  );
}
```

### Решение: Выделение слоев (Layered Concerns)
Мы разделяем код: извлечение данных (Хук/Сервис), бизнес-логику (Чистая функция) и UI (Компонент).

```tsx
// 1. Бизнес-логика (Чистая функция, легко тестировать)
const getActiveAdmins = (users) => users.filter(u => u.isActive && u.role === 'ADMIN');

// 2. Data-слой (Хук, инкапсулирующий сеть)
function useAdminUsers() {
  const { data, isLoading } = useQuery('users', fetchUsers);
  const admins = data ? getActiveAdmins(data) : [];
  return { admins, isLoading };
}

// 3. UI-слой (Только рендеринг)
export function UserDashboard() {
  const { admins, isLoading } = useAdminUsers();

  if (isLoading) return <Spinner />;
  return (
    <div className="dashboard">
      {admins.map(u => <div key={u.id}>{u.name}</div>)}
    </div>
  );
}
```

## 3. Неочевидные нюансы и трейдоффы

*   **Колокация (Colocation):** Принцип SoC часто ошибочно путают с разделением по типам файлов. В начале 2010-х было модно держать все CSS в папке `styles/`, все шаблоны в `templates/`, а все скрипты в `js/`. Это плохой SoC. Правильный SoC (например, в Feature-Sliced Design) группирует связанные сущности (стили, UI, логику) по бизнес-фичам (например, папка `features/auth/`), а не по техническому стеку.
*   **Грань абстракции:** Слишком мелкое разделение ответственности приводит к фрагментации кода. Если для вывода кнопки вам нужно создать 5 файлов (`Button.tsx`, `Button.styles.ts`, `Button.logic.ts`, `Button.types.ts`, `Button.constants.ts`) — вы перегнули палку с SoC.
