# Architecture Decision Records (ADR)

Архитектура — это последовательность решений, принятых в условиях неопределенности. Часто мы понимаем, *как* работает система, но забываем, *почему* она работает именно так. ADR (Architecture Decision Records) — это практика ведения журнала критических архитектурных решений прямо в репозитории проекта, решающая боль "потерянного контекста".

## 1. Зачем нам ADR?

Когда в проект приходит новый разработчик или спустя год команда смотрит на старый код, возникают вопросы:
- "Почему мы используем Redux, а не Zustand?"
- "Зачем здесь самописный кэш, если есть React Query?"
- "Почему мы разделили этот монолит на микрофронтенды именно так?"

Без задокументированной истории ответом чаще всего будет: "Исторически сложилось". ADR позволяет зафиксировать контекст, альтернативы и аргументы на момент принятия решения.

```mermaid

    Problem[Проблема / Потребность] --> Discussion[Обсуждение / RFC]
    Discussion --> Decision[Принятие решения]
    Decision --> ADR[Запись в ADR]
    ADR --> Implementation[Реализация в коде]
    Implementation -.->|Спустя год| ADR
    NewDev[Новый разработчик] -.->|Читает историю| ADR
    
    style ADR fill:#e3f2fd,stroke:#1e88e5,stroke-width:2px,color:#0d47a1
```

## 2. Структура хорошего ADR

Каждый ADR — это короткий markdown-файл (обычно 1-2 страницы). Он всегда содержит следующие разделы (шаблон Майкла Найгарда):

1. **Title (Название):** Короткое, отражающее суть (например, `ADR 001: Использование Zustand для стейт-менеджмента`).
2. **Status (Статус):** Предложено, Принято, Отклонено, Устарело (Superseded).
3. **Context (Контекст):** Какие силы, требования и ограничения привели нас к необходимости принимать решение?
4. **Decision (Решение):** Что именно мы решили сделать (и как).
5. **Consequences (Последствия):** Какие плюсы мы получаем? С какими трейдоффами (минусами) нам придется жить?

### Пример ADR (Как надо)

```markdown
# ADR 004: Переход с Axios на нативный Fetch API

**Статус:** Принято (2024-03-15)

## Контекст
В нашем приложении размер бандла достиг критической отметки. Мы провели аудит и выяснили, что `axios` занимает существенную долю в вендорном чанке. Современные браузеры (и Node.js >= 18) нативно поддерживают `fetch`. Мы не используем специфичные фичи Axios (например, сложные интерсепторы или отмену запросов через CancelToken), за исключением базовых перехватов для авторизации.

## Решение
Мы отказываемся от Axios в пользу нативного `fetch`. Для удобства типизации и обработки ошибок напишем легковесную обертку (`httpClient.ts`), которая будет автоматически добавлять заголовки авторизации и парсить JSON.

## Последствия
**Положительные:**
- Уменьшение размера бандла на ~15 КБ (minified+gzipped).
- Избавление от внешней зависимости.

**Отрицательные:**
- Придется вручную написать логику для таймаутов (через `AbortController`), так как `fetch` не поддерживает их из коробки.
- Необходимость переписать ~40 существующих API-вызовов в инфраструктурном слое.
```

## 3. Где хранить и как управлять?

ADR хранятся в папке `docs/adr/` (или `architecture/decisions/`) прямо в репозитории кода (подход Documentation as Code).
Каждый файл имеет префикс с порядковым номером (например, `0001-use-zustand.md`, `0002-switch-to-vite.md`).

**Как обновлять ADR:**
Архитектурные решения не высечены в камне. Если решение устарело, мы **не удаляем и не переписываем** старый ADR. Мы создаем новый ADR, а в старом меняем статус на "Устарело (Superseded by ADR 005)". Это сохраняет историческую цепочку.

## 4. Границы применимости и трейдоффы

**Когда ADR необходим:**
- Выбор ключевых технологий (фреймворк, стейт-менеджер, роутер).
- Изменение структуры директорий (переход на Feature Sliced Design).
- Правила работы с API (GraphQL vs REST).
- Внедрение новых архитектурных паттернов (Microfrontends).

**Когда ADR — это оверхед (Антипаттерны):**
- *Микроменеджмент в решениях.* Не нужно писать ADR на выбор библиотеки для иконок или на то, как называть переменные (для этого есть Linter и Code Conventions).
- *Подгонка под результат.* ADR пишется ДО или ВО ВРЕМЯ принятия решения. Если вы написали код, а потом задним числом сочиняете ADR для галочки, польза теряется.
- *Слишком длинные простыни.* Если ваш ADR занимает больше двух страниц, вероятно, вы пытаетесь запихнуть в него целую спецификацию или RFC. ADR должен фиксировать *факт* решения и его мотивы, а не детальный план реализации.
