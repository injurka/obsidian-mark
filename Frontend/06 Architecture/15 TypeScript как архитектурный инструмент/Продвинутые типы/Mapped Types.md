# Mapped Types (Отображаемые типы)

## Концепция и проблематика
Часто в архитектуре мы имеем базовую сущность, например, `User`. Но в разных слоях приложения эта сущность видоизменяется: для DTO создания пользователя все поля могут быть обязательными, для DTO обновления — все поля опциональными, а в сторе — все поля только для чтения. Дублировать интерфейсы — значит обречь себя на рассинхронизацию при добавлении нового поля. Mapped Types позволяют алгоритмически создавать новые типы, проходя по ключам существующих.

## Как это работает
```mermaid
graph LR
    A[Base Interface] -->|Iterate keys: K in keyof T| B[Transformation]
    B -->|Add modifier e.g. readonly| C[Mapped Interface]
```

## Примеры

**Антипаттерн:** Дублирование интерфейсов
```typescript
interface User { id: string; name: string; age: number; }
interface ReadonlyUser { readonly id: string; readonly name: string; readonly age: number; }
// Добавили email в User, но забыли добавить в ReadonlyUser
```

**Как надо:** Mapped Types
```typescript
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

type ReadonlyUser = MyReadonly<User>; // Все поля автоматически readonly ✅
```

## Неочевидные нюансы
- **Модификаторы:** Можно не только добавлять, но и удалять модификаторы с помощью минуса. Например, `-readonly` или `-?` сделают поля изменяемыми или обязательными соответственно.
- **Key Remapping (`as`):** Начиная с TS 4.1 можно менять имена ключей "на лету" прямо в процессе маппинга: `[K in keyof T as \`get${Capitalize<string & K>}\`]: () => T[K]`.
- **Проблема производительности:** Сложные маппинги с глубокой рекурсией могут экспоненциально увеличить время проверки типов.
- **Читаемость ошибок:** Когда Mapped Type ломается, TS может выдавать монструозные сообщения об ошибках, где вместо имени интерфейса выводится сырая структура `{ [x: string]: ... }`.
