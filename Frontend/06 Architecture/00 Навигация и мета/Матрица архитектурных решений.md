# Матрица архитектурных решений (Decision Matrix)

Эта таблица содержит сравнение типичных архитектурных выборов во фронтенде, помогая оценить плюсы, минусы и границы применимости каждого подхода.

---

## 🏗️ 1. Способ организации приложений

| Подход | Подходящие условия | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Монолит (SPA / SSR)** | Малые и средние проекты, команды до 10–12 человек. | • Простая сборка и деплой<br>• Единая кодовая база<br>• Легкий рефакторинг | • Плохо масштабируется при росте команд<br>• Долгое время сборки на больших объемах |
| **Монорепозиторий (Nx / Turborepo)** | Средние и крупные проекты, разделяющие общий код (UI Kit, типы) между приложениями. | • Единый источник истины<br>• Легко шарить код<br>• Кэширование сборок и тестов | • Сложная настройка CI/CD<br>• Высокие требования к инфраструктуре сборки |
| **Микрофронтенды (Module Federation)** | Огромные Enterprise-системы, множество независимых команд, разные технологии. | • Независимый релизный цикл<br>• Изоляция ошибок<br>• Автономия команд | • Сложность рантайм-интеграции<br>• Риск дублирования зависимостей в бандле |

---

## 📂 2. Методология структуры проекта

| Методология | Когда использовать | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Flat / Flat-by-type** (`components/`, `hooks/`, `pages/`) | Маленькие проекты, MVP, быстрые прототипы. | • Минимальный порог входа<br>• Высокая скорость на старте | • Превращается в свалку при росте файлов<br>• Размытые границы ответственности |
| **Feature-Sliced Design (FSD)** | Средние и крупные веб-приложения со сложным интерфейсом и частыми изменениями. | • Строгие правила зависимостей<br>• Контролируемые импорты (Public API)<br>• Легко масштабируется | • Высокий порог входа на старте<br>• Избыточность папок для простых фич |
| **Clean Architecture / DDD** | Приложения с тяжелой и независимой от UI бизнес-логикой на клиенте. | • Независимость логики от фреймворка<br>• Максимальная тестируемость модулей | • Написание большого количества оберток (DTO, репозитории, порты) |

## 🖥️ 3. Стратегии рендеринга и доставки UI

| Стратегия | SEO-критичность | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **CSR (Client-Side Rendering)** | Низкая (SaaS, дашборды, личные кабинеты) | • Дешевый хостинг (статический CDN)<br>• Плавный пользовательский опыт (SPA) | • Медленный первый рендер (FCP)<br>• Плохая индексация поисковиками |
| **SSR (Server-Side Rendering)** | Высокая (интернет-магазины, блоги, порталы) | • Быстрый вывод контента на экран<br>• Идеально для SEO | • Требует Node.js сервера<br>• Высокая нагрузка на CPU сервера |
| **SSG / ISR (Static Generation / Revalidation)** | Высокая (статические сайты, документация, витрины товаров) | • Максимальная скорость загрузки<br>• Безопасность и масштабируемость | • Время сборки растет с ростом страниц (для SSG)<br>• Риск отображения устаревших данных (до ревалидации) |
| **Islands Architecture (Astro)** | Высокая (контент-ориентированные сайты с интерактивными вкраплениями) | • Почти нулевой JS на клиенте по умолчанию<br>• Отличный перформанс | • Сложно применять для приложений с единым сложным глобальным стейтом |
