# Выбрасывание паник (Exception-based / throw & try-catch)

## 1. Основная идея

Код пишется так называемым «счастливым путем» (happy path). Мы предполагаем, что всё идет хорошо. Если же на любом этапе возникает проблема (невалидные данные, упала база, нет сети), мы немедленно прерываем выполнение текущей функции с помощью `throw`. Управление прыгает по стеку вызовов вверх до тех пор, пока не встретит первый подходящий блок `try-catch`.

Этот подход реализует принцип **Fail Fast (Быстрый отказ)**: система не пытается работать с испорченными данными, а сразу переходит в режим обработки аварии.

Но если мы просто используем `throw new Error('Что-то сломалось')`, мы теряем важнейшую деталь — **контекст**. Блок `catch` поймает ошибку, но не будет знать, *что именно* произошло, кроме как попытаться распарсить текстовое сообщение (что является ужасной практикой).

Здесь на помощь приходят две техники: кастомные классы и перебрасывание.

## 2. Использование кастомных классов (Custom Error Classes)

Чтобы в месте перехвата (в блоке `catch`) мы могли отличить одну ошибку от другой и принять правильное решение, мы создаем собственные классы ошибок, наследуя их от встроенного класса `Error`.

### Зачем это нужно?
1. **Типизация:** Мы можем проверять тип ошибки через `instanceof`.
2. **Обогащение данными:** В класс можно добавить специфичные поля (например, код HTTP-ответа, список невалидных полей формы).

### Пример реализации:

Создадим несколько классов для разных доменных и инфраструктурных проблем:

```javascript
// Базовая ошибка валидации
class ValidationError extends Error {
  constructor(message, invalidFields = []) {
    super(message);
    this.name = 'ValidationError'; // Переопределяем имя для удобства
    this.invalidFields = invalidFields; // Сохраняем массив проблемных полей
  }
}

// Ошибка сети (инфраструктура)
class NetworkError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.name = 'NetworkError';
    this.statusCode = statusCode; // Сохраняем HTTP статус (например, 404 или 500)
  }
}
```

### Пример использования (генерация и отлов):

```javascript
// Функция, которая может бросить разные исключения
async function fetchAndParseUser(userId) {
  if (!userId) {
    // Выбрасываем доменную ошибку
    throw new ValidationError("ID пользователя обязателен", ["userId"]);
  }

  const response = await fetch(`/api/users/${userId}`);
  
  if (!response.ok) {
    // Выбрасываем инфраструктурную ошибку
    throw new NetworkError("Не удалось получить данные", response.status);
  }

  return await response.json();
}

// Главная функция, которая обрабатывает процесс
async function handleUserLogin(userId) {
  try {
    const user = await fetchAndParseUser(userId);
    console.log("Пользователь загружен:", user);
    
  } catch (error) {
    // МАРШРУТИЗАЦИЯ ОШИБОК (Error Routing)
    
    if (error instanceof ValidationError) {
      // Мы знаем, что это ошибка данных. Подсвечиваем поля в UI.
      console.error("Ошибка формы:", error.invalidFields);
      ui.highlightFields(error.invalidFields);
      
    } else if (error instanceof NetworkError) {
      // Мы знаем, что это проблема сети.
      if (error.statusCode === 404) {
        ui.showMessage("Пользователь не найден");
      } else {
        ui.showMessage("Сервер недоступен, попробуйте позже");
      }
      
    } else {
      // А что делать, если это TypeError (например, опечатка в коде)?
      // Об этом в следующем пункте!
    }
  }
}
```

## 3. Перебрасывание (Rethrow)

В примере выше в самом конце блока `catch` есть ветка `else`. Туда могут попасть непредвиденные системные паники (например, `TypeError: Cannot read properties of undefined`, или `ReferenceError`, или ошибки из сторонних библиотек, о которых мы не знали).

**Главное правило обработки ошибок:** Блок `catch` должен обрабатывать только те ошибки, в которых он "разбирается" (входит в его зону ответственности). 

Если `catch` молча «проглотит» неизвестную ошибку (например, просто сделает `console.log(error)`), приложение продолжит работу в сломанном, непредсказуемом состоянии. Это приведет к фантомным багам.

Чтобы этого избежать, используется паттерн **Rethrow**. Если мы проверили `error` и поняли, что это не наша специфика — мы выбрасываем его дальше, наверх, чтобы с ним разобрался кто-то другой (обычно это глобальный обработчик).

### Пример паттерна Rethrow:

```javascript
async function registerUser(userData) {
  try {
    // Валидируем
    if (userData.age < 18) {
      throw new ValidationError("Пользователь должен быть совершеннолетним", ["age"]);
    }
    
    // Сохраняем в БД (здесь может упасть ошибка базы данных, сети, синтаксиса и т.д.)
    await database.save(userData); 
    
  } catch (error) {
    // Этот catch отвечает только за бизнес-правила валидации!
    if (error instanceof ValidationError) {
      // Обрабатываем ожидаемую ошибку
      return { success: false, reason: error.message };
    }
    
    // 🔴 ПЕРЕБРАСЫВАНИЕ (Rethrow)
    // Мы не знаем, что это за ошибка. Это не валидация.
    // Возможно, отвалилась БД или мы где-то обратились к null.
    // Делегируем её обработчику вышестоящего уровня.
    throw error; 
  }
}
```

### Куда летит переброшенная ошибка?
Она летит вверх по стеку вызовов. В идеальной архитектуре на самом верху (на уровне инициализации приложения или роутера) у вас должен стоять **«Обработчик последней надежды» (Global Error Handler)**.

```javascript
// Где-то на самом высоком уровне приложения (Entry Point)
async function appEntryPoint() {
  try {
    await registerUser({ name: "Ivan", age: 20 }); // Внутри может произойти неведомый сбой
  } catch (error) {
    // Сюда прилетят все "переброшенные" ошибки, которые никто не смог обработать внизу.
    
    // 1. Отправляем в систему мониторинга (Sentry, Datadog)
    logger.logFatalError(error);
    
    // 2. Показываем пользователю глобальный экран "Что-то пошло не так"
    renderCrashScreen();
  }
}
```

## 4. Плюсы и минусы архитектуры на исключениях

### Плюсы:
* **Нативность:** Механизм встроен в язык, его понимают все разработчики (низкий порог входа).
* **Чистота бизнес-кода:** Не нужно писать `if (error) return error;` после каждого вызова функции. Код линейный и читается легко.
* **Fail Fast из коробки:** Программа мгновенно останавливает выполнение "плохого" сценария.

### Минусы:
* **Скрытый поток управления (Hidden control flow):** Сигнатура функции никак не говорит о том, *какие именно* исключения она может выбросить. (В TypeScript исключения в catch всегда имеют тип `any` или `unknown`, их нельзя строго типизировать в сигнатуре). Разработчику приходится лезть в исходный код функции, чтобы понять, что ловить в `catch`.
* **Производительность:** Сборка стек-трейса (stack trace) при каждом `new Error()` — относительно тяжелая операция. Бросать исключения в плотных циклах для банального контроля потока — плохая идея (исключения должны быть *исключительными* ситуациями).
