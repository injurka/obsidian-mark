# Гибридный подход (Сочетание Result-контейнеров и Исключений)

## 1. Основная идея

На сегодняшний день в экосистеме TypeScript (и современных веб-приложениях вообще) гибридный подход — это наиболее прагматичный и популярный архитектурный стандарт. 

Он берет лучшее от двух миров: безопасность и предсказуемость функциональных Result-контейнеров и простоту встроенного механизма исключений (`throw`) для критических сбоев.

В реальном мире не все проблемы равны между собой. Мы делим все нештатные ситуации на две фундаментально разные категории:

1. **Ожидаемые ошибки (Errors):** Это часть бизнес-логики. Неверный пароль, отсутствие сети, товар закончился на складе. Мы *ожидаем*, что это может произойти, и бизнес *знает*, как на это реагировать (показать сообщение, предложить другой товар, повторить запрос).  
   👉 **Инструмент:** `Result`-контейнеры.
2. **Паники (Panics / Defects):** Это баги разработчиков или фатальные отказы инфраструктуры. Опечатка в переменной (`TypeError`), отсутствие критической переменной окружения (`process.env.DB_PASSWORD`), падение физического сервера БД. Мы *не знаем*, как программа может продолжить работу, если сломано само ядро системы.  
   👉 **Инструмент:** Исключения (`throw new Error()`).

**Золотое правило гибридного подхода:** 
> *Используй контейнеры для общения с пользователем и управления логикой. Используй `throw` для спасения системы от работы в сломанном состоянии.*

## 2. Практическая реализация: Изоляция паник

### Пример 1: Когда мы используем `throw` (Паника)
Если при старте приложения мы понимаем, что у нас не задан URL бэкенда — нет смысла пытаться что-то загружать. Это фатальная ошибка конфигурации.

```typescript
function getConfig() {
  const apiUrl = process.env.VITE_API_URL;
  if (!apiUrl) {
    // 🔴 ПАНИКА! Это баг конфигурации (разработчик забыл .env).
    // Нет смысла возвращать Result, приложение просто не сможет работать.
    // Бросаем исключение, чтобы процесс упал/остановился.
    throw new Error("CRITICAL: VITE_API_URL is not defined in environment variables!");
  }
  return apiUrl;
}
```

### Пример 2: Когда мы используем `Result` (Ожидаемая ошибка)
Теперь мы пытаемся загрузить пользователя по сети. Пользователя может не быть в базе (404), или сервер может отвечать слишком долго. Это нормально.

```typescript
// Обертка над fetch, которая превращает ожидаемые сбои сети в Result,
// но пропускает настоящие паники (например, если URL оказался null)
async function fetchUser(userId: string): Promise<Result<User, 'NOT_FOUND' | 'NETWORK_ERROR'>> {
  try {
    const response = await fetch(`/api/users/${userId}`);
    
    if (response.status === 404) {
      return Result.failure('NOT_FOUND'); // 🟢 Ожидаемая проблема
    }
    
    if (!response.ok) {
      return Result.failure('NETWORK_ERROR'); // 🟢 Ожидаемая проблема
    }

    const data = await response.json();
    return Result.success(data);
    
  } catch (error) {
    // Сюда попадут TypeError, AbortError, синтаксические ошибки JSON.parse
    // 🔴 Это паники! Мы не пытаемся их скрыть в Result, мы бросаем их дальше.
    throw error; // Rethrow (Перебрасывание)
  }
}
```

## 3. Бизнес-логика в гибридной архитектуре

Благодаря разделению на ошибки и паники, слой нашей бизнес-логики становится невероятно чистым. Мы работаем только с Result-контейнерами и вообще не пишем `try-catch` в бизнес-слое!

```typescript
async function renderUserDashboard(userId: string) {
  // Мы не используем try-catch здесь. Мы исходим из того,
  // что если случится Паника, управление улетит на глобальный уровень.

  const result = await fetchUser(userId);

  // Обрабатываем ожидаемые бизнес-ошибки
  if (!result.ok) {
    if (result.error === 'NOT_FOUND') {
      ui.renderEmptyState("Пользователь не найден. Зарегистрируйтесь.");
    } else if (result.error === 'NETWORK_ERROR') {
      ui.renderRetryButton("Проблемы с сетью. Попробовать снова?");
    }
    return; // Завершаем выполнение (Fail Fast)
  }

  // Счастливый путь: рендерим дашборд
  ui.renderDashboard(result.value);
}
```

## 4. Глобальный обработчик последней надежды

Но куда деваются ошибки из `throw`? Если панику не поймать, приложение "повиснет" (в браузере) или умрет (в Node.js). 

В гибридной архитектуре обязателен **глобальный перехватчик (Catch-All / Error Boundary)**. Он стоит на самом высоком уровне и ловит то, что пробило все слои защиты.

### Для React-приложения (через ErrorBoundary):
```jsx
// Этот компонент оборачивает всё приложение в index.tsx
class GlobalErrorBoundary extends React.Component {
  componentDidCatch(error, errorInfo) {
    // 1. Записываем панику в систему аналитики (чтобы починить баг)
    Sentry.captureException(error, { extra: errorInfo });
  }

  render() {
    if (this.state.hasError) {
      // 2. Показываем пользователю заглушку вместо "белого экрана смерти"
      return <h1>Упс! В приложении произошел критический сбой. Мы уже чиним!</h1>;
    }
    return this.props.children;
  }
}
```

### Для Node.js (Express бэкенд):
```javascript
// Самый последний middleware в роутере
app.use((err, req, res, next) => {
  // Сюда прилетят все "throw new Error()" из наших контроллеров
  
  logger.error("Критическая паника сервера", err);
  
  // Отдаем клиенту безликий 500 статус, не раскрывая деталей бага
  res.status(500).json({ message: "Внутренняя ошибка сервера" });
});
```

## 5. Плюсы и минусы Гибридного подхода

### Плюсы:
* **Четкое разделение ответственности:** Вы перестаете смешивать логику общения с пользователем («Введи другой пароль») и системные логи (`TypeError at line 42`).
* **Отсутствие замалчивания багов:** Когда разработчики повсеместно используют `try-catch` и возвращают фолбэки (типа `return null`), они часто "проглатывают" реальные баги. В гибридном подходе баги честно взрываются и попадают в мониторинг.
* **Идеально для TypeScript:** Типизируются только те ошибки (`Result`), с которыми разработчик действительно должен работать.Никакого визуального мусора.

### Минусы:
* **Требует строгих договоренностей в команде:** Разработчикам нужно постоянно задавать себе вопрос: *«То, что я сейчас обрабатываю — это ожидаемое поведение системы (Result) или критический сбой (throw)?»*.
* **Нужны адаптеры над базовыми API:** Приходится писать обертки, чтобы укротить стандартные функции JavaScript, которые выбрасывают исключения.
