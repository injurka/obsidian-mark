
Выбор стратегии рендеринга — ключевое решение при проектировании архитектуры веб-приложения (System Design). Оно влияет на скорость загрузки страницы (TTFB, LCP), поисковую оптимизацию (SEO), нагрузку на серверную инфраструктуру и стоимость масштабирования.

---

## 1. Сравнительный анализ стратегий рендеринга

```text
CSR:  [Браузер] ──► (Пустой HTML) ──► (Скачивание JS) ──► (Рендеринг на клиенте) ──► Страница готова
SSR:  [Браузер] ──────────────────(Запрос)──────────────────► [Node.js Сервер] ──► (Рендеринг HTML) ──► Готовый HTML в браузер
SSG:  [Браузер] ──────────────────(Запрос)──────────────────► [CDN (Static File)] ──► Мгновенная отдача готового HTML
```

### 1.1. CSR (Client-Side Rendering)
Классическое Single Page Application (SPA). Сервер отдает пустой HTML-шаблон и тяжелый JS-бандл. Браузер скачивает JS, выполняет его и строит DOM на клиенте.
*   **TTFB (Time to First Byte):** Отличный (сервер отдает статический файл мгновенно).
*   **LCP (Largest Contentful Paint):** Плохой (пользователь долго видит пустой белый экран или лоадер, пока качается и парсится JS).
*   **SEO:** Плохое (поисковые роботы могут не дождаться выполнения JS-скриптов).
*   **Цена хостинга:** Минимальная (все файлы статические, раздаются с дешевого CDN).

### 1.2. SSR (Server-Side Rendering)
При каждом запросе Node.js-сервер собирает данные из API, на ходу рендерит HTML-страницу и отправляет готовую разметку в браузер. Затем происходит процесс гидратации (Hydration) — JS «оживляет» статический HTML.
*   **TTFB:** Зависит от скорости запросов к базе данных и API (может быть долгим).
*   **LCP:** Отличный (браузер сразу получает готовый для чтения текст).
*   **SEO:** Отличное.
*   **Цена хостинга:** Высокая (требуются мощные Node.js серверы, способные обрабатывать пиковую нагрузку запросов).

### 1.3. SSG (Static Site Generation)
Страницы рендерятся в HTML один раз — на этапе сборки проекта (build time).
*   **TTFB / LCP:** Идеальные (HTML-файлы лежат на CDN в кэше и доставляются пользователю мгновенно).
*   **SEO:** Идеальное.
*   **Минус:** Не подходит для динамического контента. Изменение одной буквы на сайте требует полной пересборки всего проекта.

### 1.4. ISR (Incremental Static Regeneration)
Гибридный подход. Мы собираем сайт как статический (SSG), но настраиваем правила регенерации отдельных страниц в фоновом режиме по запросу пользователя (например, не чаще одного раза в 60 секунд).
*   **Плюс:** Дает преимущества SSG (быстрый CDN-ответ) без необходимости полной пересборки сайта при изменении контента в CMS.

## 3. Критерии выбора стратегии (Lead Guideline)

При проектировании архитектуры руководствуйтесь следующей логикой:

1.  **Личный кабинет / Панели управления (Дашборды):**
    *   *Решение:* **CSR**. SEO здесь не требуется, данные закрыты авторизацией. Клиентская маршрутизация обеспечит плавный UX без перезагрузки страниц.
2.  **Лендинги / Промо-страницы / Блоги / Документация:**
    *   *Решение:* **SSG**. Контент меняется редко, важна максимальная скорость загрузки страниц из любой точки мира для конверсии и SEO.
3.  **Крупный E-commerce (Каталоги товаров, карточки):**
    *   *Решение:* **ISR** (или SSR для часто меняющихся цен и остатков). Карточек товаров могут быть миллионы, собирать их через SSG на сборке невозможно (билд займет часы). ISR соберет популярные карточки, а редкие сгенерирует на лету при первом обращении.
4.  **Новостные порталы / Социальные сети (Лента новостей):**
    *   *Решение:* **SSR**. Контент обновляется ежесекундно, пользователи должны видеть только свежие посты.
