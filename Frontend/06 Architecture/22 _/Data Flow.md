
# Архитектура управления состоянием во Frontend-приложениях

Главная проблема масштабных SPA (Single Page Applications) — это хаос в данных. Когда разработчики используют один глобальный стор для всего (данных с сервера, состояния модалок, значений инпутов), приложение быстро становится неподдерживаемым, а производительность падает из-за лишних ререндеров.

**Фундаментальный принцип:** У каждого типа данных должен быть свой владелец, свой жизненный цикл и свой специализированный инструмент.

Давайте детально разберем 7 слоев состояния фронтенда.

---

## 1. Server State (Серверное состояние)
Это данные, истинным владельцем которых является Backend. Фронтенд лишь берет их «в аренду» для отображения. 

**Характеристики:**
*   Данные асинхронны.
*   Они могут быть изменены другими пользователями без вашего ведома.
*   Требуют обработки состояний `loading`, `error`, `success`.

**Почему не Redux?**
Раньше серверные данные хранили в Redux (через Thunk/Saga). Это требовало писать тонны бойлерплейта: экшены для старта загрузки, успеха, ошибки. 
Современный подход — использование **TanStack Query** (или RTK Query / SWR). Они относятся к серверным данным как к **асинхронному кэшу**.

**Детальный пример с мутацией и инвалидацией:**
```typescript
// Чтение (Кэширование, дедупликация, рефетч)
const { data: project, isLoading } = useQuery({
  queryKey: ['projects', projectId],
  queryFn: () => api.projects.get(projectId),
  staleTime: 5 * 60 * 1000, // Данные свежие 5 минут
});

// Запись (Мутация)
const queryClient = useQueryClient();
const mutation = useMutation({
  mutationFn: (newParams) => api.projects.update(projectId, newParams),
  onSuccess: () => {
    // Говорим кэшу: "данные устарели, скачай новые"
    queryClient.invalidateQueries({ queryKey: ['projects', projectId] });
  },
});
```

## 2. Client Domain State (Клиентское доменное состояние)
Это бизнес-данные, которые существуют **только на клиенте** в данный момент времени. Сервер о них еще не знает, либо они нужны для сложной локальной логики.

**Примеры:**
*   Черновик (draft) сложной статьи до нажатия кнопки «Сохранить».
*   Выделенные строки в таблице для массового удаления.
*   Состояние многошаговой корзины.

Здесь вступает в игру **Формула Черновика**:
`Текущий вид = Снапшот с сервера + Локальные изменения (Патчи)`

**Как реализовать (например, через Zustand или Redux Toolkit):**
Вместо того чтобы мутировать исходные данные, мы сохраняем историю команд (Command Pattern). Это позволяет легко сделать Undo/Redo.

```typescript
type Command = { type: 'RENAME'; payload: string } | { type: 'MOVE'; payload: {x: number, y: number} };

interface EditorState {
  originalData: Document; // То, что пришло от TanStack Query
  commands: Command[];    // Локальные шаги пользователя
  addCommand: (cmd: Command) => void;
  undo: () => void;
}
```
Пока пользователь работает, сервер может прислать по WebSocket новую версию `originalData`. Мы просто применяем наши `commands` поверх новых данных, избегая конфликтов.

## 3. UI State (Состояние интерфейса)
Это техническое состояние, никак не связанное с бизнес-логикой. 

**Главное правило UI-стейта:** Держите его как можно ниже по дереву компонентов.
*   Открыт ли конкретный выпадающий список? -> `useState` внутри компонента `Dropdown`.
*   Открыта ли глобальная модалка подтверждения? -> Zustand store или Context.

**Проблема React Context:**
Context часто используют как замену глобальному стору. Но если в Context положить часто меняющиеся данные (например, координаты мыши или текущий скролл), **все компоненты, использующие этот контекст, будут перерисовываться** при каждом изменении.
Для глобального UI-стейта лучше использовать **Zustand** — он позволяет подписываться только на нужные кусочки состояния (селекторы), избегая лишних ререндеров.

## 4. URL State (Состояние в URL)
Самый недооцененный слой. **URL — это тоже Store.**
Если вы можете скопировать ссылку, отправить её коллеге, и он увидит ту же самую картину (те же открытые вкладки, фильтры и сортировку) — значит, ваша архитектура великолепна.

**Что должно жить в URL (Search Params):**
*   Глобальный поиск (`?q=react`).
*   Пагинация (`?page=2`).
*   Фильтры таблицы (`?status=active&sort=date_desc`).

**Как с этим работать:**
Никогда не дублируйте URL State в Redux/Zustand. Ваш компонент должен читать напрямую из роутера.
```typescript
// Пример с React Router
const [searchParams, setSearchParams] = useSearchParams();
const statusFilter = searchParams.get('status') || 'all';

// Смена фильтра - это просто обновление URL
const setStatus = (status) => setSearchParams({ status }); 
```

## 5. Persistent Client State (Персистентное состояние)
Данные, которые должны пережить F5 (обновление страницы) или закрытие браузера.

*   **localStorage:** Синхронный, лимит около 5MB. Идеально для простых настроек (тема, язык, токен).
    *   *Подводный камень:* При SSR (например, Next.js) чтение из localStorage при первом рендере вызовет ошибку гидратации. Нужно читать его внутри `useEffect` или проверять `typeof window !== 'undefined'`.
*   **sessionStorage:** Умирает при закрытии вкладки. Отлично для токенов безопасности, которые не должны жить вечно, или состояния длинной формы.
*   **IndexedDB (через Dexie.js):** Асинхронный, может хранить гигабайты (в зависимости от диска). Идеально для Offline-first приложений, PWA, кэширования больших JSON или файлов.

## 6. Form State (Состояние форм)
Форма — это изолированная экосистема. У нее есть свои концепции: `dirty` (изменена ли), `touched` (нажимал ли пользователь), `errors` (валидация).

**Почему React Hook Form (RHF)?**
Классический контролируемый инпут через `useState` вызывает ререндер компонента при каждом нажатии клавиши. RHF использует *неконтролируемые* компоненты под капотом (через `ref`), обновляя интерфейс только когда нужно показать ошибку.

**Жизненный цикл формы:**
1. RHF получает `defaultValues` из *Server State*.
2. Пользователь печатает (локальный *Form State*).
3. При Submit -> валидация (через Zod).
4. Мутация в TanStack Query -> обновление *Server State*.

## 7. Ephemeral & Renderer State (Короткоживущее состояние)
Это высокочастотные данные (60 FPS), которые убьют производительность React, если пустить их через обычный стейт.

*   Координаты мыши, Scroll, Drag & Drop, Canvas/WebGL.
*   **Инструмент:** `useRef` + нативный DOM API или `requestAnimationFrame`.

```typescript
// Правильно для 60 FPS (не вызывает ререндер React)
const circleRef = useRef<HTMLDivElement>(null);

const onMouseMove = (e) => {
  if (circleRef.current) {
    circleRef.current.style.transform = `translate(${e.clientX}px, ${e.clientY}px)`;
  }
};
```
React вообще не должен знать о промежуточных координатах. Он должен получить только итоговое событие `onDragEnd`, чтобы сохранить новую позицию объекта.

## Data Flow и DTO (Anti-Corruption Layer)
Раздел о DTO (Data Transfer Object) описывает классический паттерн **Антикоррупционный слой (Anti-Corruption Layer)** из Domain-Driven Design (DDD).

Бэкенд часто отдает данные в формате, удобном для базы данных, а не для UI (snake_case, строки вместо дат, странные вложенности).

**Почему мапперы (Mappers) обязательны в энтерпрайзе:**
1. **Изоляция:** Если бэкенд поменяет название поля с `project_id` на `uuid`, вам придется изменить только 1 строку в маппере, а не искать по всем React-компонентам.
2. **Типизация:** Бэкенд возвращает дату как строку `"2026-07-21T19:14:00Z"`. Маппер сразу превращает её в объект `Date`. В компонентах больше не нужно делать `new Date(string)`.

```typescript
// Слой API (только тут мы знаем про DTO)
const fetchProject = async (): Promise<Project> => {
  const dto: ProjectDto = await api.get('/project');
  return mapProjectToDomain(dto); // Превращаем мусор в красивую доменную модель
};
```

## Optimistic Updates (Оптимистичные обновления)
Это магия, которая делает интерфейс «мгновенным» (как лайки в соцсетях или галочки в Todoist).

**Алгоритм (на базе TanStack Query):**
1. Юзер жмет «Лайк».
2. **Сразу** отменяем текущие фоновые запросы (чтобы они не перезаписали наш оптимизм).
3. Делаем бэкап текущего состояния из кэша (Snapshot).
4. Вручную мутируем кэш: `Лайки + 1`. UI мгновенно перерисовывается.
5. Отправляем реальный POST-запрос на сервер.
6. Если сервер ответил ошибкой (например, нет интернета) — **откатываем (Rollback)** кэш к бэкапу из шага 3.
7. В конце (успех или ошибка) в фоне запрашиваем актуальные данные (invalidate).

## Резюме: Главные заповеди архитектора состояния
Если суммировать весь этот подход в короткие правила для код-ревью:

1. **Не дублируй:** Если это есть в URL — не клади в Redux. Если это есть в кэше Query — не копируй в `useState`. Истина должна быть в одной инстанции.
2. **Разделяй Сервер и Клиент:** Никогда не смешивай данные профиля пользователя (с бэкенда) и состояние открытого дропдауна в одном Redux-сторе.
3. **Откладывай синхронизацию:** Не отправляй каждый чих на сервер. Собирай локальные изменения в черновик (Draft), отправляй по кнопке "Save" или `debounce`.
4. **Защищай UI от Бэкенда:** Используй мапперы на границе API, чтобы компоненты работали с идеальным фронтенд-интерфейсом (типами).
5. **Используй правильный инструмент для правильной частоты обновления:** 
   * Редко (тема) -> LocalStorage.
   * Нормально (данные) -> TanStack Query / Zustand.
   * Экстремально быстро (скролл) -> `useRef` + Vanilla JS.
