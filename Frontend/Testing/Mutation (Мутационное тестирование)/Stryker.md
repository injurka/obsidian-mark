# Stryker (Мутационное тестирование)

Покрытие кода тестами (Code Coverage) — обманчивая метрика. 100% покрытие означает лишь то, что интерпретатор зашел на каждую строчку кода во время выполнения тестов, но не гарантирует, что тесты действительно что-то проверяют (в тесте может отсутствовать `expect`, или проверяться не то свойство).

**Мутационное тестирование** оценивает качество самих тестов путем внедрения мелких багов (мутаций) в тестируемый код.

---

## 1. Как это работает: Мутанты, Выжившие и Убитые

Процесс мутационного тестирования делится на этапы:

```text
[Исходный код] ──► 1. Внесение изменений (Мутации) ──► 2. Запуск тестов
                                                            │
                     ┌──────────────────────────────────────┴──────────────────────────────────────┐
                     ▼                                                                             ▼
          [Тесты УПАЛИ] ──► Мутант УБИТ                                                  [Тесты ПРОШЛИ] ──► Мутант ВЫЖИЛ
     (Тесты поймали баг - отлично!)                                                (Тесты пропустили баг - плохо!)
```

1.  **Создание мутантов:** Мутационный фреймворк (Stryker) парсит исходный код в абстрактное синтаксическое дерево (AST) и генерирует множество измененных версий кода (мутантов).
    *   *Оригинал:* `if (age >= 18) { return true; }`
    *   *Мутант 1:* `if (age > 18) { return true; }` (изменение оператора)
    *   *Мутант 2:* `if (age >= 18) { return false; }` (изменение логики)
    *   *Мутант 3:* `if (true) { return true; }` (вырождение условия)
2.  **Прогон тестов:** Stryker запускает ваши существующие тесты (Jest, Vitest) для каждого мутанта отдельно.
3.  **Оценка результата:**
    *   **Мутант убит (Killed):** Как минимум один тест упал. Это идеальный сценарий — значит, ваши тесты реагируют на изменение логики.
    *   **Мутант выжил (Survived):** Все тесты прошли успешно. Это проблема — тесты не заметили внесенный баг. Покрытие этой строки кода бесполезно.

## 2. Настройка Stryker JS

Для JavaScript/TypeScript проектов используется **Stryker Mutator**.

### Установка:
```bash
pnpm add -D @stryker-mutator/core @stryker-mutator/jest-runner
```

### Конфигурация (`stryker.config.json`):
```json
{
  "$schema": "https://schema.stryker-mutator.io/stryker-config.json",
  "mutate": [
    "src/**/*.ts",
    "!src/**/*.spec.ts",
    "!src/main.ts"
  ],
  "testRunner": "jest",
  "jest": {
    "projectType": "custom",
    "configFile": "jest.config.js",
    "enableFindRelatedTests": true
  },
  "reporters": ["html", "clear-text", "progress"],
  "thresholds": {
    "high": 80,
    "low": 60,
    "break": 50
  }
}
```

## 3. Проблема производительности и оптимизация Stryker

Главный минус мутационного тестирования — **огромные временные затраты**. Если у вас 1000 строк кода и Stryker сгенерировал 500 мутантов, ему придется запустить ваш тестовый набор 500 раз.

### Стратегии ускорения:
1.  **Ограничение области мутаций:** Не запускайте Stryker на всем проекте в CI на каждый пуш. Запускайте его только на измененных файлах ( affected ):
    ```bash
    npx stryker run --mutate $(git diff --name-only origin/main | tr '\n' ',')
    ```
2.  **Использование `enableFindRelatedTests`:** Stryker умеет анализировать связи и запускать для проверки мутанта не весь тестовый пакет, а только те файлы тестов, которые импортируют измененный модуль.
3.  **Исключение бойлерплейта:** Исключайте из мутации конфигурационные файлы, файлы деклараций типов (`.d.ts`) и файлы UI-компонентов, где тестируется только верстка. Фокусируйте Stryker на расчете скидок, стейт-менеджерах и валидаторах данных.
