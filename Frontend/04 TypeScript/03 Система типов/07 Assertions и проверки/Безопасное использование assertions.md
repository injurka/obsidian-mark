# Безопасное использование assertions

## Описание

> [!info] 
> Безопасное использование assertions подразумевает минимизацию операторов `as` и `!`, отдавая предпочтение статическому контролю типов, Type Guards и оператору `satisfies`.

Утверждения типов (Type Assertions) нарушают гарантии типобезопасности, так как разработчик заставляет компилятор доверять ему, отключая проверки. Безопасный подход состоит в том, чтобы использовать утверждения только на границах систем (например, при парсинге JSON или работе с DOM), а внутри бизнес-логики применять механизмы сужения типов (Narrowing).

## Примеры использования

```typescript
// ПЛОХО: Использование as маскирует потенциальную ошибку
function processDataBad(data: unknown) {
  const user = data as { name: string };
  console.log(user.name.toUpperCase()); // Упадет в рантайме, если data не объект
}

// ХОРОШО: Использование Type Guard
function isUser(data: any): data is { name: string } {
  return typeof data === "object" && data !== null && "name" in data;
}

function processDataGood(data: unknown) {
  if (isUser(data)) {
    console.log(data.name.toUpperCase()); // Безопасно!
  } else {
    console.log("Invalid user data");
  }
}
```

## Особенности и нюансы

- **Zod и валидаторы**: Для работы с внешними данными (`unknown`, ответы API) вместо `as` рекомендуется использовать библиотеки валидации схем (например, Zod, Yup). Они проверяют данные в рантайме и автоматически выводят строгие типы для TypeScript.
- **Случаи неизбежности**: Существуют ситуации, когда `as` оправдан: работа с legacy кодом, сложные моки в тестах или DOM-API, где TypeScript просто не имеет достаточного контекста (например, `document.querySelector(".my-class")`).
- **Двойное приведение**: Конструкция `expr as unknown as T` является явным "красным флагом", указывающим на то, что вы грубо обходите систему типов. Её следует избегать.
