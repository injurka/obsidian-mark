
Эти два хука отвечают за локальное управление состоянием компонента. Интересный факт: под капотом `useState` на самом деле реализован через `useReducer` (он является его упрощенной версией).

## 1. useState

Самый базовый хук для добавления состояния. Возвращает кортеж `[текущее_состояние, функция_обновления]`.

### Асинхронность и замыкания (Важнейший концепт)
Вызов функции обновления (`setState`) **не меняет состояние мгновенно в текущем выполняемом коде**. Вместо этого React ставит обновление в очередь и планирует новый рендер. Значение переменной состояния остается неизменным до следующего цикла рендера (это называется Snapshot/Снимок состояния).

```jsx
const [count, setCount] = useState(0);

const handleClick = () => {
  setCount(count + 1); 
  console.log(count); // Выведет 0, а не 1! 
  // В текущем замыкании count всё ещё равен 0.
};
```

### Функциональное обновление (Updater Function)
Из-за "асинхронной" природы обновлений, если новое состояние зависит от предыдущего, **нельзя полагаться на переменную из замыкания**, особенно если обновления происходят быстро одно за другим или внутри асинхронных коллбеков (например, `setTimeout`).
Вместо значения передавайте **функцию**, которая принимает предыдущее состояние.

```jsx
// ❌ ПЛОХО: Если вызвать это дважды подряд, count увеличится только на 1
setCount(count + 1);
setCount(count + 1);

// ✅ ХОРОШО: React положит эти функции в очередь и выполнит их последовательно
setCount(prevCount => prevCount + 1);
setCount(prevCount => prevCount + 1); // В итоге count увеличится на 2
```

### Ленивая инициализация (Lazy Initialization)
Если начальное состояние требует тяжелых вычислений (например, парсинг большого JSON, обращения к `localStorage` или сложные математические расчеты), передайте в `useState` функцию, а не само значение. Эта функция выполнится **только один раз** при монтировании компонента.

```jsx
// ❌ ПЛОХО: Вычисление (чтение диска/localStorage) происходит при КАЖДОМ рендере
const [data, setData] = useState(JSON.parse(localStorage.getItem('data')));

// ✅ ХОРОШО: Ленивая инициализация. Функция вызовется только при первом рендере.
const [data, setData] = useState(() => JSON.parse(localStorage.getItem('data')));
```

### Автоматический батчинг (Automatic Batching)
Начиная с React 18, React группирует (batches) несколько обновлений состояния в один ре-рендер для повышения производительности. Это работает везде: в обычных обработчиках, таймаутах, промисах и нативных событиях.

```jsx
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React 18: Вызовет только 1 ре-рендер в конце выполнения коллбека
}, 1000);
```
*Примечание:* Если вам критически важно, чтобы DOM обновился немедленно после изменения состояния (например, чтобы измерить высоту элемента), вы можете отключить батчинг для конкретного блока с помощью `flushSync` из `react-dom`.

### Bailout (Отмена ре-рендера)
React сравнивает новое состояние со старым по ссылке, используя алгоритм `Object.is()`. Если вы передадите в `setState` **точно такое же значение**, которое там уже лежит, React прервет процесс обновления (bailout) и **не будет рендерить компонент и его детей**.

### ⚠️ Edge Case: Иммутабельность и мутация объектов
Из-за сравнения по ссылке (`Object.is()`) вы никогда не должны мутировать объекты и массивы в React напрямую. Если вы измените свойство объекта и передадите тот же объект в сеттер, ссылка останется прежней, и React проигнорирует обновление.

```jsx
const [user, setUser] = useState({ name: 'Alex', age: 25 });

// ❌ ПЛОХО: Изменение существующего объекта (мутация)
const updateBad = () => {
  user.name = 'Bob';
  setUser(user); // Ре-рендера не будет, ссылка та же самая!
};

// ✅ ХОРОШО: Создание нового объекта (Иммутабельность)
const updateGood = () => {
  setUser(prevUser => ({ ...prevUser, name: 'Bob' }));
};
```
*Важно:* Spread-оператор (`...`) делает **поверхностное копирование** (shallow copy). Если у вас глубоко вложенные объекты, необходимо копировать каждый уровень вложенности, либо использовать библиотеки вроде `Immer`.

## 2. useReducer

Хук `useReducer` идеален для **сложной логики состояния**, когда следующее состояние сильно зависит от предыдущего, когда несколько полей состояния обновляются вместе, или когда вы хотите вынести логику обновления за пределы компонента.

```tsx
// 1. Начальное состояние
const initialState = { count: 0, error: null };

// 2. Редьюсер: чистая функция (state, action) => newState
function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { ...state, count: state.count + action.payload, error: null };
    case 'error':
      return { ...state, error: action.payload };
    case 'reset':
      return initialState;
    default:
      throw new Error(`Unknown action type: ${action.type}`);
  }
}

function Counter() {
  // 3. Подключение хука
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    <div>
      <p>Счетчик: {state.count}</p>
      {state.error && <p>Ошибка: {state.error}</p>}
      <button onClick={() => dispatch({ type: 'increment', payload: 1 })}> +1 </button>
      <button onClick={() => dispatch({ type: 'increment', payload: 5 })}> +5 </button>
    </div>
  );
}
```

### Ленивая инициализация в useReducer (Третий аргумент)
Вы также можете лениво инициализировать `useReducer`. Для этого нужно передать **третий аргумент** — функцию инициализации (init). Она получит второй аргумент в качестве параметра.

```javascript
function init(initialCount) {
  return { count: initialCount, history: [] }; // тяжелая сборка начального объекта
}

// init(10) вызовется только при монтировании
const [state, dispatch] = useReducer(reducer, 10, init); 
```

### Когда использовать `useReducer` вместо `useState`?

1. **Сложные объекты состояния и зависимые поля**: Если у вас есть 3-4 независимых `useState`, которые часто обновляются одновременно (например, `isLoading`, `data`, `error` при fetch-запросе), лучше объединить их в один объект состояния через `useReducer`. Это исключает ситуации неконсистентного состояния.
2. **Избежание зависимости от замыканий (Stale Closures)**: Если ваш эффект `useEffect` сильно зависит от состояния, добавление `state` в массив зависимостей вызовет частый перезапуск эффекта. Функция `dispatch` от `useReducer` **гарантированно стабильна** — она никогда не меняется в течение жизни компонента. Вы можете безопасно использовать `dispatch` внутри `useEffect` или передавать в глубокие дочерние компоненты (часто через `Context`), не провоцируя их ре-рендеры и не указывая в массиве зависимостей.
3. **Паттерн "Отправка намерений" (Декларативность)**: В `useState` вы императивно говорите компоненту *"что сделать"* (`setCount(5)`). В `useReducer` вы говорите *"что произошло"* (`dispatch({ type: 'user_clicked' })`). Редьюсер сам берет на себя ответственность решить, как обновить данные. Это делает код компонента чище.
4. **Легкость тестирования**: Функция `reducer` является *чистой функцией* (Pure Function). Она не зависит от React. Вы можете вынести ее в отдельный файл и легко покрыть Unit-тестами, просто передавая начальное состояние и action, проверяя результат на выходе.
