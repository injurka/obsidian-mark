Ниже — более развёрнутая версия темы: не только «что такое `staleTime`», но и **какие данные кладут в кэш, как выбирают ключи, когда инвалидируют и как это выглядит в реальном приложении**.

# TanStack Query: управление серверным состоянием

До появления React Query / TanStack Query серверные данные часто складывали в Redux:

- список товаров;
- профиль пользователя;
- заказы;
- комментарии;
- статусы загрузки;
- ошибки запросов;
- флаги `isLoading`, `isError`;
- ручное обновление данных после мутаций.

Сам Redux не был ошибкой и всё ещё полезен для глобального **клиентского состояния**. Например:

- открыта ли модалка;
- тема приложения;
- состояние сайдбара;
- локальные фильтры, если они не должны жить в URL;
- черновик формы;
- состояние сложного UI.

Но серверные данные имеют другую природу:

1. Они принадлежат серверу, а не браузеру.
2. Они могут устареть.
3. Их нужно повторно загружать.
4. Несколько компонентов могут использовать одни и те же данные.
5. Их нужно обновлять после `POST`, `PATCH`, `DELETE`.
6. Нужно обрабатывать повторные попытки, ошибки, отмену запросов, refetch при возврате на вкладку и т. д.

TanStack Query берёт эти задачи на себя.

> TanStack Query — это не просто удобная обёртка над `fetch` или `axios`.
> Это кэш, менеджер асинхронного серверного состояния и механизм синхронизации UI с сервером.

---

# Что именно хранят в кэше?

В кэше TanStack Query обычно находятся **результаты запросов к API**.

Например, в приложении интернет-магазина:

```ts
['products']
['products', { category: 'electronics', page: 1 }]
['product', productId]
['cart']
['orders']
['order', orderId]
['me']
['users', userId]
['users', userId, 'projects']
```

Внутри кэша хранятся не только сами данные, но и метаданные:

- `data` — результат запроса;
- `error` — ошибка, если запрос завершился неудачно;
- `status` — состояние запроса;
- `fetchStatus` — выполняется ли запрос сейчас;
- время последнего успешного получения данных;
- признак `fresh` / `stale`;
- число компонентов-подписчиков;
- информация о retry и состоянии refetch.

Упрощённо можно представить запись в кэше так:

```ts
{
  queryKey: ['product', 42],
  data: {
    id: 42,
    title: 'Keyboard',
    price: 100
  },
  status: 'success',
  isStale: false,
  updatedAt: 1710000000000
}
```

---

# Query Key — адрес данных в кэше

`queryKey` — это уникальный ключ, по которому TanStack Query понимает:

- какие данные запрашиваются;
- можно ли использовать уже существующий кэш;
- какие запросы нужно инвалидировать;
- какие компоненты должны обновиться.

Пример:

```tsx
useQuery({
  queryKey: ['products', { category, page, sort }],
  queryFn: () => getProducts({ category, page, sort }),
});
```

Если меняется `category`, `page` или `sort`, меняется и `queryKey`. Для TanStack Query это уже другой набор данных, поэтому он выполнит новый запрос или возьмёт соответствующие данные из кэша.

Плохой вариант:

```tsx
queryKey: ['products']
```

если запрос зависит от страницы и фильтров:

```tsx
getProducts({ page, category })
```

В таком случае данные разных страниц могут перезаписывать друг друга в одном кэше.

Правильный вариант:

```tsx
queryKey: ['products', { page, category }]
```

---

# Жизненный цикл данных в TanStack Query

Основной поток выглядит так:

1. Компонент вызывает `useQuery`.
2. TanStack Query ищет данные по `queryKey` в кэше.
3. Если данных нет — выполняется запрос.
4. Если данные есть и они свежие — данные возвращаются без нового запроса.
5. Если данные есть, но устарели — UI может сразу показать старые данные, а библиотека выполнит фоновое обновление.
6. Когда компонент размонтируется, данные не удаляются мгновенно.
7. Через `gcTime` неактивные данные удаляются из памяти.

---

# `staleTime`: как долго данным можно доверять

`staleTime` определяет, как долго данные считаются свежими.

```tsx
useQuery({
  queryKey: ['products'],
  queryFn: getProducts,
  staleTime: 60_000, // 1 минута
});
```

В течение минуты после успешного запроса данные будут `fresh`.

Это означает, что при повторном монтировании компонента TanStack Query может просто отдать кэш и не делать новый запрос.

```text
Получили товары в 12:00:00
staleTime = 1 минута

До 12:01:00 данные fresh.
После 12:01:00 данные stale.
```

Важно: `staleTime` не удаляет данные из кэша. Он только меняет их статус: «этим данным больше нельзя полностью доверять».

Типичные значения:

| Тип данных | Примерный `staleTime` |
|---|---:|
| Данные почти не меняются | 30 минут – несколько часов |
| Справочники стран, категорий | 1 час |
| Профиль текущего пользователя | 5–30 минут |
| Список товаров | 30 секунд – 5 минут |
| Уведомления | 10–30 секунд |
| Биржевые котировки, чат, live-данные | часто нужен polling/WebSocket |

По умолчанию:

```ts
staleTime: 0
```

То есть данные становятся stale практически сразу после получения.

Это не значит, что TanStack Query бесконечно делает запросы. Но при событиях вроде повторного монтирования, возврата фокуса на вкладку или восстановления интернета stale-данные могут быть перезапрошены согласно настройкам.

---

# `gcTime`: как долго хранить неиспользуемый кэш

В TanStack Query v5 используется название `gcTime`. Раньше оно называлось `cacheTime`.

```tsx
useQuery({
  queryKey: ['products'],
  queryFn: getProducts,
  gcTime: 5 * 60 * 1000,
});
```

`gcTime` начинает отсчитываться только тогда, когда запрос становится **неактивным**: ни один компонент больше не использует этот `queryKey`.

Например:

1. Пользователь открыл страницу товаров.
2. Запрос `['products']` выполнился.
3. Пользователь ушёл на страницу профиля.
4. Компонент со списком товаров размонтировался.
5. Запрос стал inactive.
6. TanStack Query ждёт `gcTime`.
7. Если пользователь не вернулся — кэш удаляется.

Если пользователь вернётся до истечения `gcTime`, данные всё ещё могут быть в памяти. Он увидит их сразу, а если они stale — в фоне произойдёт refetch.

Если пользователь вернётся после `gcTime`, кэша уже нет. Понадобится полноценная загрузка, обычно с `isLoading`/skeleton.

По умолчанию:

```ts
gcTime: 5 * 60 * 1000
```

то есть 5 минут.

---

# Разница между `staleTime` и `gcTime`

Это два независимых понятия.

| Настройка | Отвечает на вопрос |
|---|---|
| `staleTime` | Можно ли считать данные актуальными? |
| `gcTime` | Как долго держать неиспользуемые данные в памяти? |

Например:

```tsx
staleTime: 60_000,
gcTime: 10 * 60_000,
```

Значит:

- одну минуту данные считаются свежими;
- после минуты — устаревшими;
- после размонтирования страницы они остаются в кэше до десяти минут;
- если пользователь вернётся через 3 минуты, старые данные будут показаны мгновенно, но затем обновятся в фоне;
- если вернётся через 15 минут, кэш уже удалён, будет новая загрузка.

---

# Stale-While-Revalidate

Один из самых полезных паттернов TanStack Query — **stale-while-revalidate**.

Сценарий:

1. Пользователь уже открывал страницу заказов.
2. Данные остались в кэше.
3. Пользователь вернулся на страницу.
4. Интерфейс мгновенно показывает старые данные.
5. TanStack Query параллельно проверяет сервер.
6. Если сервер вернул изменения — UI обновляется.

Пользователь не видит лишний спиннер и не ждёт ответа сервера для отображения уже известных данных.

```tsx
const { data, isFetching } = useQuery({
  queryKey: ['orders'],
  queryFn: getOrders,
});
```

Здесь полезно различать:

- `isLoading` — первая загрузка, данных ещё нет;
- `isFetching` — сейчас идёт любой запрос, в том числе фоновый refetch.

Например:

```tsx
if (isLoading) {
  return <OrdersSkeleton />;
}

return (
  <>
    {isFetching && <SmallRefreshIndicator />}
    <OrdersList orders={data} />
  </>
);
```

# Инвалидация: как понять, что кэш устарел

Инвалидация — это способ сообщить TanStack Query:

> «Эти данные больше нельзя считать свежими. При следующей возможности нужно запросить их заново».

```tsx
queryClient.invalidateQueries({
  queryKey: ['posts'],
});
```

После этого:

- все запросы с ключами, начинающимися на `['posts']`, будут помечены как stale;
- если такой запрос сейчас используется активным компонентом, он обычно будет перезапрошен в фоне;
- если запрос неактивен, он просто останется stale до следующего использования.

То есть инвалидация не всегда означает «немедленно сделай запрос вообще для всего». Для inactive query она чаще означает: «обнови, когда пользователь снова придёт туда».

---

# Как выбирать, что инвалидировать

Обычно отталкиваются от того, **какие данные изменила мутация**.

## Создание поста

```tsx
POST /posts
```

Новый пост должен появиться в списке постов.

```tsx
onSuccess: () => {
  queryClient.invalidateQueries({
    queryKey: ['posts'],
  });
}
```

Если есть список постов конкретного автора:

```ts
['posts', { authorId }]
```

то ключ `['posts']` инвалидирует и его, потому что это частичное совпадение ключа.

---

## Редактирование поста

```tsx
PATCH /posts/:id
```

Может измениться:

- детальная страница поста;
- список всех постов;
- список постов автора;
- результаты поиска, если изменился заголовок;
- избранное, если пост там присутствует.

Минимальный вариант:

```tsx
onSuccess: (_, variables) => {
  queryClient.invalidateQueries({
    queryKey: ['post', variables.id],
  });

  queryClient.invalidateQueries({
    queryKey: ['posts'],
  });
}
```

---

## Удаление поста

```tsx
DELETE /posts/:id
```

Обычно нужно инвалидировать списки:

```tsx
onSuccess: () => {
  queryClient.invalidateQueries({
    queryKey: ['posts'],
  });
}
```

Детальную запись иногда можно удалить вручную:

```tsx
queryClient.removeQueries({
  queryKey: ['post', postId],
});
```

---

# Инвалидация или ручное обновление кэша?

Есть два основных подхода.

## 1. Инвалидация и refetch

```tsx
onSuccess: () => {
  queryClient.invalidateQueries({
    queryKey: ['todos'],
  });
}
```

Плюсы:

- проще;
- сервер остаётся единственным источником правды;
- меньше риска рассинхронизации;
- удобно, если сервер добавляет поля, сортирует данные, преобразует ответ.

Минусы:

- нужен дополнительный запрос;
- обновление интерфейса не всегда мгновенное.

Это самый безопасный и распространённый вариант.

---

## 2. Ручное обновление кэша через `setQueryData`

```tsx
onSuccess: (updatedTodo) => {
  queryClient.setQueryData(
    ['todo', updatedTodo.id],
    updatedTodo,
  );

  queryClient.setQueryData<Todo[]>(['todos'], (oldTodos = []) =>
    oldTodos.map((todo) =>
      todo.id === updatedTodo.id ? updatedTodo : todo,
    ),
  );
}
```

Плюсы:

- UI обновляется сразу;
- можно избежать дополнительного GET-запроса;
- удобно, если mutation API возвращает полностью обновлённую сущность.

Минусы:

- нужно самостоятельно поддерживать консистентность;
- сложнее при пагинации, фильтрах и нескольких списках;
- легко забыть обновить один из зависимых кэшей.

Практический подход часто такой:

- для простых сценариев — `invalidateQueries`;
- для точечных изменений — `setQueryData`;
- для моментального UX — optimistic update;
- после сложных операций всё равно иногда делают инвалидацию для гарантии консистентности.

---

# Пример: создание поста

Простой и надёжный вариант:

```tsx
function useCreatePost() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (newPost: CreatePostDto) =>
      axios.post('/posts', newPost),

    onSuccess: () => {
      queryClient.invalidateQueries({
        queryKey: ['posts'],
      });
    },
  });
}
```

Использование:

```tsx
const createPost = useCreatePost();

function handleSubmit(values: CreatePostDto) {
  createPost.mutate(values);
}
```

Состояние мутации уже есть в объекте:

```tsx
<button disabled={createPost.isPending}>
  {createPost.isPending ? 'Создание...' : 'Создать пост'}
</button>
```

Не нужно вручную создавать в Redux:

```ts
isCreatingPost: true
createPostError: null
createPostSuccess: false
```

# Зависимые запросы

Зависимые запросы возникают, когда данные второго запроса нельзя получить без результата первого.

Например:

1. Получить пользователя по email.
2. Получить проекты по `user.id`.

```tsx
const userQuery = useQuery({
  queryKey: ['user', email],
  queryFn: () => getUserByEmail(email),
});

const projectsQuery = useQuery({
  queryKey: ['projects', userQuery.data?.id],
  queryFn: () => getProjectsByUser(userQuery.data!.id),
  enabled: Boolean(userQuery.data?.id),
});
```

Пока `user.id` отсутствует:

```ts
enabled: false
```

Запрос проектов не отправится.

После успешного получения пользователя:

```ts
enabled: true
```

TanStack Query сам запустит второй запрос.

Это лучше, чем писать `useEffect`, хранить промежуточный `userId` в `useState` и вручную управлять загрузками.

# Оптимистичные обновления

Оптимистичное обновление нужно, когда UI должен реагировать моментально, не дожидаясь сервера.

Классические примеры:

- лайк;
- добавление товара в корзину;
- отметка задачи как выполненной;
- смена статуса;
- drag-and-drop;
- быстрые переключатели.

Пример с todo:

```tsx
function useToggleTodo() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: ({ id, completed }: { id: string; completed: boolean }) =>
      api.patch(`/todos/${id}`, { completed }),

    onMutate: async ({ id, completed }) => {
      await queryClient.cancelQueries({
        queryKey: ['todos'],
      });

      const previousTodos = queryClient.getQueryData<Todo[]>(['todos']);

      queryClient.setQueryData<Todo[]>(['todos'], (oldTodos = []) =>
        oldTodos.map((todo) =>
          todo.id === id
            ? { ...todo, completed }
            : todo,
        ),
      );

      return { previousTodos };
    },

    onError: (_error, _variables, context) => {
      queryClient.setQueryData(
        ['todos'],
        context?.previousTodos,
      );
    },

    onSettled: () => {
      queryClient.invalidateQueries({
        queryKey: ['todos'],
      });
    },
  });
}
```

Что происходит:

1. `onMutate` запускается до запроса на сервер.
2. Мы отменяем возможный текущий refetch, чтобы он не перезаписал оптимистичные данные.
3. Сохраняем старый кэш для rollback.
4. Мгновенно меняем кэш.
5. UI моментально показывает новый результат.
6. Если сервер ответил ошибкой — откатываем старые данные в `onError`.
7. В `onSettled` перепроверяем данные на сервере.

# Пример архитектуры query keys

В реальном приложении удобно централизовать ключи:

```ts
export const queryKeys = {
  me: ['me'] as const,

  posts: {
    all: ['posts'] as const,
    list: (filters: PostsFilters) =>
      ['posts', 'list', filters] as const,
    detail: (id: string) =>
      ['posts', 'detail', id] as const,
  },

  users: {
    all: ['users'] as const,
    detail: (id: string) =>
      ['users', 'detail', id] as const,
    projects: (id: string) =>
      ['users', 'projects', id] as const,
  },
};
```

Использование:

```tsx
useQuery({
  queryKey: queryKeys.posts.detail(postId),
  queryFn: () => getPost(postId),
});
```

После редактирования:

```tsx
queryClient.invalidateQueries({
  queryKey: queryKeys.posts.detail(postId),
});

queryClient.invalidateQueries({
  queryKey: queryKeys.posts.all,
});
```

Это уменьшает вероятность опечаток и делает стратегию кэширования понятной всей команде.

# Какие данные не стоит хранить в TanStack Query

TanStack Query не заменяет вообще всё состояние приложения.

Не лучший кандидат для Query-кэша:

```ts
isLoginModalOpen
isSidebarCollapsed
selectedTab
theme
formDraft
temporaryInputValue
```

Для этого подходят:

- `useState`;
- `useReducer`;
- Zustand;
- Redux Toolkit;
- Context;
- URL-параметры.

Например, фильтры каталога часто полезно хранить в URL:

```text
/products?category=electronics&page=2&sort=price
```

А уже эти параметры передавать в `queryKey`:

```tsx
useQuery({
  queryKey: ['products', { category, page, sort }],
  queryFn: () => getProducts({ category, page, sort }),
});
```

# Плюсы TanStack Query

## 1. Меньше шаблонного кода

Без TanStack Query обычно приходится писать:

- `useEffect`;
- `useState`;
- `loading`;
- `error`;
- `data`;
- отмену запросов;
- защиту от race condition;
- Redux actions;
- reducers;
- thunks/sagas;
- ручную синхронизацию списка после mutation.

С TanStack Query:

```tsx
const { data, isLoading, isError } = useQuery({
  queryKey: ['products'],
  queryFn: getProducts,
});
```

---

## 2. Дедупликация запросов

Если три компонента одновременно используют:

```tsx
useQuery({
  queryKey: ['me'],
  queryFn: getCurrentUser,
});
```

TanStack Query не обязан делать три одинаковых HTTP-запроса. Компоненты подпишутся на одну query и получат единый результат.

---

## 3. Общий кэш для всего приложения

Если один компонент обновил данные через `setQueryData` или получил новый ответ от сервера, все подписанные компоненты автоматически увидят изменения.

---

## 4. Повторные попытки

Для query TanStack Query по умолчанию может повторять неудачные запросы.

```tsx
useQuery({
  queryKey: ['products'],
  queryFn: getProducts,
  retry: 2,
});
```

Можно контролировать логику:

```tsx
retry: (failureCount, error) => {
  if (error.response?.status === 404) {
    return false;
  }

  return failureCount < 3;
}
```

---

## 5. Обновление при возвращении на вкладку

Если пользователь ушёл с вкладки, а потом вернулся, stale-данные могут автоматически обновиться.

Это особенно полезно для:

- уведомлений;
- заказов;
- админ-панелей;
- данных пользователя;
- списков задач.

Настройка:

```tsx
useQuery({
  queryKey: ['notifications'],
  queryFn: getNotifications,
  refetchOnWindowFocus: true,
});
```

# Минусы и сложности

TanStack Query очень удобен, но не отменяет необходимость думать об архитектуре.

## 1. Нужно проектировать `queryKey`

Неправильный ключ приводит к неправильному кэшу:

- перезаписи данных;
- отображению данных не того пользователя;
- неработающей инвалидации;
- лишним запросам.

---

## 2. Сложность оптимистичных обновлений

Оптимистичные обновления требуют аккуратности:

- нужно сохранить прошлый кэш;
- учитывать rollback;
- отменять активные запросы;
- обновлять несколько связанных списков;
- учитывать пагинацию и фильтры.

Поэтому не нужно использовать optimistic update везде. Если задержка приемлема — проще инвалидировать query после успешной мутации.

---

## 3. Нельзя бездумно ставить большой `staleTime`

Например:

```tsx
staleTime: Infinity
```

подходит для почти неизменяемых справочников, но опасен для часто меняющихся данных. Пользователь может долго видеть старый список заказов или устаревший баланс.

# Типичный ответ на собеседовании

> Мы использовали TanStack Query для хранения и синхронизации серверного состояния: списков, деталей сущностей, профиля пользователя, заказов, товаров и данных, полученных через API.
>
> Для клиентского состояния — модалок, UI-флагов, черновиков форм — использовали локальный state, URL или отдельный state manager.
>
> Для каждого запроса проектировали `queryKey`, включающий все параметры, влияющие на ответ: id, фильтры, страницу, сортировку.
>
> После мутаций инвалидировали связанные query. Например, после создания или удаления поста инвалидировали `['posts']`, а после редактирования — и `['post', id]`, и списки постов.
>
> Если mutation API возвращал актуальную сущность, могли обновить конкретный кэш через `setQueryData`. Для лайков, чекбоксов и корзины использовали optimistic update с rollback в `onError`.
>
> `staleTime` использовали для определения периода актуальности данных, а `gcTime` — для времени хранения неактивных query в памяти. Это позволяло пользователю быстро возвращаться на уже открытые страницы и видеть кэшированные данные без лишних загрузок.

Главная мысль:

> TanStack Query не делает серверные данные «локальными навсегда».
> Он хранит их в кэше, знает, когда они могли устареть, и помогает синхронизировать UI с сервером без ручного управления десятками loading/error/data состояний.
