
**CORS (Cross-Origin Resource Sharing)** — это механизм безопасности браузера, использующий дополнительные HTTP-заголовки, чтобы указать браузеру, имеет ли веб-приложение, запущенное на одном источнике (origin), разрешение на доступ к ресурсам с другого источника. 

В основе CORS лежит ограничение, называемое **Same-Origin Policy (SOP)**. По умолчанию браузер блокирует чтение ответов на кросс-доменные AJAX-запросы, чтобы защитить данные пользователя от кражи вредоносными скриптами. CORS позволяет серверу явно ослабить это правило.

---

## 1. Что такое Origin (Источник)?

Источник определяется комбинацией трех параметров: `Схема (Протокол) + Хост (Домен) + Порт`.

Если мы находимся на странице `http://store.company.com/dir/page.html`, то:
* `http://store.company.com/dir2/other.html` — **Тот же источник** (Успех).
* `https://store.company.com/secure.html` — **Другой источник** (Отличается протокол: https).
* `http://store.company.com:81/dir/etc.html` — **Другой источник** (Отличается порт: 81).
* `http://news.company.com/dir/other.html` — **Другой источник** (Отличается хост: news).

Любое несовпадение делает запрос **кросс-доменным** (cross-origin).

---

## 2. Простые и Сложные запросы

С точки зрения CORS, все запросы делятся на две категории. Это критически важно для понимания логики работы браузера.

### 2.1 Простые запросы (Simple Requests)
Запрос считается «простым» и отправляется на сервер **сразу**, если он удовлетворяет строгим условиям:
1. **Метод:** только `GET`, `HEAD` или `POST`.
2. **Заголовки:** только стандартные (`Accept`, `Accept-Language`, `Content-Language`).
3. **Content-Type** (для POST): только `application/x-www-form-urlencoded`, `multipart/form-data` или `text/plain`.

*Важно:* При простом запросе браузер отправляет его на сервер, сервер его обрабатывает и возвращает ответ. Если в ответе нет разрешающих CORS-заголовков, браузер **заблокирует чтение ответа** в JavaScript (хотя сервер действие уже выполнил).

### 2.2 Сложные запросы (Preflighted Requests)
Если запрос использует методы вроде `PUT`, `DELETE`, `PATCH`, отправляет JSON (`Content-Type: application/json`) или кастомные заголовки (например, `Authorization`), он считается «сложным». 
В этом случае браузер **не отправит реальный запрос сразу**, чтобы не допустить несанкционированного изменения данных на сервере. Вместо этого он инициирует **Preflight** (предварительный запрос).

## 3. Как работает Preflight (Предварительный запрос)

Preflight — это запрос методом `OPTIONS`, который браузер делает автоматически под капотом, чтобы «спросить» сервер: *«Разрешишь ли ты мне выполнить эту операцию?»*

### Шаг 1. Браузер отправляет `OPTIONS`
```http
OPTIONS /api/data HTTP/1.1
Host: api.example.com
Origin: https://my-frontend.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Authorization, Content-Type
```

### Шаг 2. Сервер отвечает разрешениями
Сервер должен ответить статусом `200` или `204` и вернуть заголовки доступа:
```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://my-frontend.com
Access-Control-Allow-Methods: GET, POST, PUT, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400
```
*(Заголовок `Max-Age` кэширует разрешение на указанное время в секундах, чтобы браузер не делал `OPTIONS` перед каждым запросом).*

### Шаг 3. Браузер выполняет основной запрос
Если разрешения получены, браузер отправляет фактический `PUT` запрос. Если сервер отказал (или вернул не те заголовки), основной запрос отменяется, а в консоли появляется ошибка CORS.

## 4. CORS и Учетные данные (Cookies, Authorization)

По умолчанию кросс-доменные запросы `fetch` или `XMLHttpRequest` **не отправляют** куки и HTTP-авторизацию. Чтобы их отправить, на клиенте нужно явно указать флаг `credentials: 'include'`.

Если клиент отправляет запрос с куками, политика CORS резко ужесточается. Сервер обязан вернуть специальный заголовок:
```http
Access-Control-Allow-Credentials: true
```

**Ловушка безопасности (Wildcard restriction):**
Если сервер разрешает `Allow-Credentials: true`, ему **запрещено** отвечать `Access-Control-Allow-Origin: *`. Он обязан указать точный домен (например, `Access-Control-Allow-Origin: https://my-frontend.com`). Это сделано для того, чтобы глобально открытые API случайно не отдали приватные данные пользователя любому сайту.

---

## 5. Главный миф о CORS

**Миф:** CORS защищает сервер от несанкционированных запросов.
**Правда:** CORS защищает **клиента (браузер)** от вредоносных скриптов. 
Сервер может получить кросс-доменный запрос (без Preflight), успешно его выполнить (например, списать деньги), отправить ответ с HTTP 200, но браузер увидит отсутствие заголовка `Access-Control-Allow-Origin` и **не отдаст тело ответа вредоносному коду**. Для защиты от несанкционированного *выполнения* запросов на сервере используется механизм **CSRF-токенов**, а не CORS.

---

## Резюме для самопроверки

1. **Origin:** Состоит из протокола, домена и порта.
2. **SOP:** Политика браузера, блокирующая чтение ответов с других Origin по умолчанию. CORS — это способ настроить исключения для SOP.
3. **Preflight (`OPTIONS`):** Предварительный запрос для проверки прав перед отправкой сложных запросов (PUT, DELETE, JSON).
4. **`Allow-Origin: *`:** Разрешает доступ всем доменам. Запрещено использовать вместе с передачей куки.
5. **CORS работает в браузере.** Инструменты вроде Postman или cURL не соблюдают CORS, так как им не нужно защищать пользователя от выполнения чужого JavaScript-кода.
