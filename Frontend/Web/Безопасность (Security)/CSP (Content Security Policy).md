
**CSP (Политика защиты контента)** — это механизм безопасности (эшелонированная защита или defense-in-depth), встроенный в современные браузеры. Он помогает обнаруживать и блокировать атаки, связанные с внедрением вредоносного контента, в первую очередь — **Cross-Site Scripting (XSS)** и кликджекинг.

Вместо того чтобы полагаться только на фильтрацию пользовательского ввода на сервере, CSP позволяет серверу передать браузеру строгий **«белый список» (allowlist)** доверенных источников. Если ресурс (скрипт, картинка, фрейм) не попадает в этот список, браузер отказывается его загружать или выполнять.

---

## 1. Как применять CSP

Политика задается на стороне сервера через HTTP-заголовок ответа:
```http
Content-Security-Policy: default-src 'self'; script-src https://trusted.com
```

Если нет доступа к серверным заголовкам, CSP можно задать прямо в HTML через мета-тег (однако через мета-теги нельзя использовать некоторые функции, например, отправку отчетов):
```html
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src https://trusted.com">
```

## 2. Анатомия политики и основные директивы

CSP состоит из директив, разделенных точкой с запятой. Если для конкретного типа ресурса (например, `font-src`) директива не указана, браузер будет искать резервную директиву `default-src`.

### Ключевые директивы:
* **`default-src`** — фоллбэк (значение по умолчанию) для большинства других директив. Обычно устанавливают в `'self'`, чтобы разрешить загрузку только с текущего домена.
* **`script-src`** — источники, откуда разрешено выполнять JavaScript.
* **`style-src`** — источники для CSS (включая импорты внутри CSS).
* **`connect-src`** — ограничивает URL, к которым может обращаться JS-код (через `fetch`, `XMLHttpRequest`, `WebSocket`).
* **`img-src`** / **`media-src`** / **`font-src`** — источники для картинок, аудио/видео и веб-шрифтов соответственно.
* **`frame-src`** (или `child-src`) — домены, которые разрешено встраивать через `<iframe>`.
* **`frame-ancestors`** — указывает, кто может встраивать *вашу* страницу в свой `<iframe>` (защита от Clickjacking, современная замена заголовка `X-Frame-Options`).

### Спецзначения (всегда пишутся в кавычках):
* `'self'` — текущий источник (совпадение по протоколу, домену и порту).
* `'none'` — запретить загрузку ресурса отовсюду.
* `*` — разрешить отовсюду (небезопасно).

## 3. Защита от XSS: Проблема Inline-скриптов и `eval`

Самое главное свойство строгого CSP заключается в том, что по умолчанию он **запрещает выполнение любых инлайн-скриптов** и потенциально опасных функций.

Если на сайте настроен базовый `script-src 'self'`, браузер заблокирует:
1. Теги `<script> console.log("hello"); </script>` (код прямо в HTML).
2. Инлайн-обработчики событий: `<button onclick="doSomething()">`.
3. Исполнение строк как кода: `eval("...")`, `setTimeout("...", 10)`, `new Function("...")`.

Именно это убивает XSS-атаки: даже если хакер сможет внедрить `<script src="http://evil.com/xss.js"></script>` или `<img src=x onerror=alert(1)>` в HTML, браузер откажется это выполнять.

### Как разрешить инлайн-скрипты, если они действительно нужны?

Добавлять **`'unsafe-inline'`** в `script-src` — крайне плохая практика, так как это полностью отключает защиту CSP от XSS. Вместо этого используются два безопасных подхода:

**1. Подход с Nonce (Одноразовое число)**
Сервер генерирует случайную криптографически стойкую строку при каждом запросе страницы и передает её в заголовке и в самом теге:
```http
Content-Security-Policy: script-src 'nonce-rAnd0m123'
```
```html
<script nonce="rAnd0m123">
  console.log("Этот скрипт выполнится, так как nonce совпадает");
</script>
```
Хакер не знает `nonce`, поэтому его внедренные скрипты не выполнятся.

**2. Подход с Hash (Хеширование)**
Вы можете вычислить SHA-256 хеш от содержимого вашего инлайн-скрипта и указать его в заголовке.
```http
Content-Security-Policy: script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='
```
Если злоумышленник изменит хотя бы один символ во внедренном коде, хеш не совпадет, и скрипт будет заблокирован.

## 4. Режим мониторинга (Report-Only)

Внедрение CSP на большой старый проект («legacy») может сломать его работу (так как заблокируются легитимные сторонние скрипты или инлайн-стили).

Для безопасного внедрения существует отдельный заголовок — **`Content-Security-Policy-Report-Only`**.
Браузер считывает этот заголовок, проверяет все ресурсы, но **не блокирует** их. Вместо этого он молча отправляет JSON-отчет о нарушениях на указанный вами сервер (через директиву `report-to` или устаревшую `report-uri`).

**Процесс внедрения:**
1. Включаете `Report-Only`.
2. Собираете логи о заблокированных ресурсах на реальных пользователях.
3. Добавляете нужные легитимные домены в политику.
4. Когда логи пустые — меняете заголовок на строгий (блокирующий) `Content-Security-Policy`.

## Резюме для самопроверки

1. **Белый список:** CSP меняет поведение браузера с «разрешено всё» на «запрещено всё, кроме того, что явно разрешено».
2. **`default-src`:** Главная резервная директива. Если не знаете с чего начать, начните с `default-src 'self'`.
3. **Смерть XSS:** CSP по умолчанию блокирует инлайн-скрипты (`<script>...</script>`) и `eval()`.
4. **Nonce и Hashes:** Безопасные способы разрешить выполнение доверенных инлайн-скриптов без использования уязвимого `'unsafe-inline'`.
5. **Report-Only:** Способ обкатать политику CSP на боевом сервере без риска сломать сайт для пользователей.
