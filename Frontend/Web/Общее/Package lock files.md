
**Lock-файл** — это автоматически генерируемый слепок (snapshot) всего графа зависимостей проекта. В отличие от `package.json`, который описывает лишь *желаемые* версии верхнего уровня, lock-файл жестко фиксирует **точные версии, адреса для скачивания и контрольные суммы (хэши)** абсолютно всех пакетов, включая их подзависимости (транзитивные зависимости).

---

## 1. Проблема, которую решают Lock-файлы

В экосистеме Node.js используется семантическое версионирование (SemVer). В `package.json` версии обычно указываются с диапазонами:
* `^1.2.0` (совместимая минорная) — разрешает установку `1.3.0`, `1.9.9`, но не `2.0.0`.
* `~1.2.0` (совместимая патч-версия) — разрешает `1.2.1`, `1.2.9`, но не `1.3.0`.

**Ловушка транзитивных зависимостей:**
Допустим, ваш `package.json` зависит от пакета `A`. Пакет `A` зависит от пакета `B (^2.0.0)`.
Вчера вы сделали `npm install`, и скачалась версия `B@2.0.1`. Сегодня автор пакета `B` выпустил обновление `2.1.0` с багом. Если другой разработчик (или CI-сервер) сегодня выполнит `npm install`, он скачает `B@2.1.0`, и проект сломается. При этом ваш `package.json` **не менялся**.

Lock-файл решает эту проблему: он фиксирует точную установленную версию `B@2.0.1`. Пакетный менеджер скачает именно её, игнорируя новые релизы, пока вы явно не обновите зависимости. Это гарантирует **100% воспроизводимость** среды на любой машине.

## 2. Устройство «под капотом» и Безопасность

Если заглянуть внутрь lock-файла (например, `package-lock.json`), каждая зависимость описывается блоком метаданных:

```json
"node_modules/lodash": {
  "version": "4.17.21",
  "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
  "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg=="
}
```

Что здесь происходит:
1. **`version`:** Точная версия пакета (без кареток `^` и тильд `~`).
2. **`resolved`:** Прямой URL на tarball-архив в реестре (пропуск фазы резолва). Пакетному менеджеру больше не нужно опрашивать сервер: *"Какая версия сейчас последняя для ^4.0.0?"*. Он просто берет ссылку и качает файл, что радикально **ускоряет установку**.
3. **`integrity` (Контрольная сумма):** Это важнейший механизм безопасности. Перед распаковкой пакета менеджер вычисляет SHA-512 хэш скачанного архива и сверяет его со строкой `integrity`. Если злоумышленник взломает npm-реестр и подменит архив (Supply Chain Attack) или произойдет сбой сети, хэши не совпадут, и установка будет прервана с ошибкой.

## 3. Форматы Lock-файлов в экосистеме

* **npm (`package-lock.json`)** — стандарт де-факто, генерируется по умолчанию. Формат JSON.
* **Yarn (`yarn.lock`)** — пионер концепции lock-файлов в JS. В Yarn 1 использовался собственный текстовый формат, в новых версиях — YAML.
* **pnpm (`pnpm-lock.yaml`)** — использует строгий YAML формат. YAML выбран специально для минимизации merge-конфликтов в Git, которые часто возникают в больших JSON-файлах при параллельной работе команд.
* **Bun (`bun.lockb` / `bun.lock`)** — современный сверхбыстрый рантайм использует **бинарный** формат `bun.lockb`. Бинарный формат выбран для максимальной скорости чтения/записи (парсинг JSON занимает время). Однако для удобства просмотра diff-ов в Git, Bun может генерировать текстовый `bun.lock` (или сохранять в формате yarn).

## 4. Строгая установка (CI/CD ловушка)

Многие разработчики по ошибке используют команду `npm install` в конвейерах сборки (CI/CD). Этого делать **нельзя**.

Поведение `npm install` (или `yarn install`):
Если в `package.json` указана версия `^1.0.0`, а в lock-файле `1.0.1`, но в реестре уже есть `1.0.2`, команда `npm install` может решить обновить пакет до `1.0.2` и **перезаписать lock-файл**. Сборка пройдет с версией, которую вы не тестировали локально.

**Правильные команды для CI (Чистая установка):**
* В npm: **`npm ci`** (Clean Install). Она полностью удаляет `node_modules`, читает *только* lock-файл и скачивает пакеты. Если lock-файл расходится с `package.json` — сборка упадет.
* В Yarn: `yarn install --immutable` (для Yarn Berry) или `yarn install --frozen-lockfile` (Yarn 1).
* В pnpm: `pnpm install --frozen-lockfile`.
* В Bun: `bun install --frozen-lockfile`.

## Резюме для самопроверки

1. **Гарантия детерминизма:** Lock-файл устраняет проблему "у меня работает, а на сервере упало", фиксируя всё дерево транзитивных зависимостей.
2. **Безопасность (Integrity):** Хэши (SHA-512) гарантируют, что код, скачанный вами сегодня, побайтово совпадает с кодом, который скачает ваш коллега завтра.
3. **Никаких ручных правок:** Lock-файлы всегда генерируются машиной и **обязательно** коммитятся в систему контроля версий (Git).
4. **CI/CD:** В конвейерах сборки всегда нужно использовать строгие команды установки (`npm ci` / `--frozen-lockfile`), чтобы предотвратить мутацию lock-файла «на лету».
