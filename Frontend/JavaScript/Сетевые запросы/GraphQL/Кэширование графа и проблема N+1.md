# Кэширование графа и проблема N+1 в GraphQL

Разработка на GraphQL предлагает гибкость в получении данных, но налагает серьезную ответственность на архитектуру производительности как на бэкенде (проблема N+1), так и на клиенте (кэширование графа).

---

## 1. Проблема N+1 в GraphQL (Бэкенд)

### 1.1. Суть проблемы
Проблема N+1 возникает из-за специфики выполнения GraphQL-запросов. Каждый резолвер (resolver) в GraphQL-сервере отвечает за получение данных для своего поля и выполняется изолированно.

Рассмотрим классический запрос:
```graphql
query GetPosts {
  posts {       # Возвращает N постов
    title
    author {    # Для каждого поста нужно получить автора
      name
    }
  }
}
```

**Как это выполняется без оптимизации:**
1.  Вызывается резолвер `Query.posts`. Он делает **1 запрос** к базе данных: `SELECT * FROM posts;` (получаем, например, 100 постов).
2.  Для каждого из 100 постов GraphQL-движок запускает резолвер поля `Post.author`.
3.  Каждый резолвер делает отдельный запрос к БД: `SELECT * FROM users WHERE id = post.author_id;`.
*   **Итог:** Мы сделали $1 + 100 = 101$ запрос к базе данных вместо того, чтобы получить всех авторов за один раз. Это мгновенно убивает производительность БД.

---

## 2. Решение проблемы N+1: Паттерн DataLoader

Для решения проблемы N+1 используется инструмент **DataLoader** (разработанный Facebook). Он реализует две ключевые концепции: **Batching (Пакетирование)** и **Caching (Кэширование)**.

```text
Без DataLoader:
Резолвер 1 ──► [Запрос User 1] ──► База Данных
Резолвер 2 ──► [Запрос User 2] ──► База Данных
Резолвер 3 ──► [Запрос User 3] ──► База Данных

С DataLoader (Batching за 1 тик Event Loop):
Резолвер 1 ──┐
Резолвер 2 ──┼─► [DataLoader] ──► [SELECT * WHERE id IN (1, 2, 3)] ──► База Данных
Резолвер 3 ──┘
```

### 2.1. Как работает Batching (Пакетирование)
DataLoader собирает (аккумулирует) все индивидуальные запросы на получение данных по ID в течение одного "тика" (микротаска в Event Loop Node.js). 

Когда выполнение JS-стека прерывается, DataLoader объединяет все собранные ID и вызывает одну батч-функцию (batch load function), которая делает один запрос к БД с оператором `IN`:

```javascript
import DataLoader from 'dataloader';

// 1. Создаем функцию пакетной загрузки
const batchUsers = async (userIds) => {
  // Делаем ОДИН запрос к БД для всех собранных ID
  const users = await db.table('users').whereIn('id', userIds);
  
  // КРИТИЧЕСКИ ВАЖНО: возвращаемый массив должен соответствовать порядку userIds
  return userIds.map(id => users.find(user => user.id === id));
};

// 2. Инициализируем DataLoader в контексте запроса (per-request scope)
const userLoader = new DataLoader(batchUsers);

// 3. Используем в резолвере
const resolvers = {
  Post: {
    author: (post) => userLoader.load(post.authorId), // DataLoader перехватит вызовы и объединит их
  }
};
```

### 2.2. Кэширование в DataLoader
DataLoader кэширует результаты в рамках **одного HTTP-запроса**. Если в разных частях графа запрашивается один и тот же пользователь (например, автор поста №1 и автор комментария №5 — это один человек), DataLoader сделает запрос к БД только один раз, а во второй раз вернет данные из памяти.
> [!WARNING]
> DataLoader **не является** глобальным кэшем приложения. Он должен создаваться заново для каждого входящего HTTP-запроса, иначе пользователи будут видеть кэшированные данные друг друга (угроза безопасности данных).

## 3. Кэширование графа на клиенте (Frontend)

На стороне фронтенда (Apollo Client, Relay, URQL) кэширование делится на два типа: **Document Cache** и **Normalized Cache**.

### 3.1. Document Cache (Кэш документов)
Кэширует весь GraphQL-ответ целиком по ключу, состоящему из строки запроса и его переменных.
*   **Минус:** Если два разных запроса содержат одного и того же пользователя, данные будут продублированы. При изменении данных пользователя в одном месте, во втором месте они останутся старыми.

### 3.2. Normalized Cache (Нормализованный кэш)
Это стандарт для крупных приложений (используется по умолчанию в Apollo и Relay). Он превращает иерархический древовидный ответ GraphQL в плоскую нормализованную базу данных в памяти клиента.

#### Алгоритм нормализации:
1.  **Split (Разделение):** Кэш разбирает ответ GraphQL на отдельные объекты.
2.  **Identify (Идентификация):** Для каждого объекта генерируется уникальный ключ (обычно комбинация `__typename` и поля `id` или `_id`, например: `User:14`).
3.  **Merge (Слияние):** Объект записывается в плоскую карту (Map). Если объект с таким ключом уже был, поля объединяются.
4.  **Replace (Замена ссылками):** Вложенные объекты заменяются ссылками на их ключи (например, `author: { __ref: "User:14" }`).

```text
Исходный древовидный ответ:                     Плоский нормализованный кэш:
{                                              {
  post: {                                        "Post:1": {
    id: 1,                                         id: 1,
    title: "Hello",                                title: "Hello",
    author: { id: 9, name: "Ivan" }  ───►          author: { __ref: "User:9" }
  }                                              },
}                                                "User:9": { id: 9, name: "Ivan" }
                                               }
```

### Преимущество нормализации:
Если мы выполняем мутацию и обновляем имя пользователя (User:9), все компоненты на странице, которые отображают посты этого автора, обновятся **автоматически**, так как все они ссылаются на один и тот же объект `"User:9"` в кэше.

## 4. Сложности и ручное управление кэшем на клиенте

Кэш отлично справляется с автоматическим обновлением существующих объектов по `id`. Но он не может автоматически понять, как мутации влияют на **списки**.

Если мы создаем новый пост, кэш не знает, в какие именно списки (все посты, популярные посты, посты пользователя) его нужно добавить. Разработчик должен описать это вручную.

### Пример ручного обновления списка в Apollo Client:
```javascript
const [createPost] = useMutation(CREATE_POST, {
  update(cache, { data: { createPost } }) {
    // 1. Читаем текущий список постов из кэша
    const data = cache.readQuery({ query: GET_ALL_POSTS });

    if (data) {
      // 2. Записываем обратно в кэш список с добавленным новым постом
      cache.writeQuery({
        query: GET_ALL_POSTS,
        data: {
          posts: [createPost, ...data.posts],
        },
      });
    }
  },
});
```
