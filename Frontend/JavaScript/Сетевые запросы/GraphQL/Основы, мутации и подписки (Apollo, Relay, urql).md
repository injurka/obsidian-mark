# GraphQL: Основы, мутации и подписки (Apollo, Relay, urql)

GraphQL де-факто стал стандартом для построения сложных клиент-серверных приложений с развесистыми структурами данных. Однако выбор клиента и правильное использование его механизмов определяют производительность и стабильность фронтенда.

---

## 1. Сравнение ключевых GraphQL-клиентов

В экосистеме React/TypeScript доминируют три клиента:

| Критерий | Apollo Client | Relay | urql |
| :--- | :--- | :--- | :--- |
| **Вес бандла** | ~30 KB gzipped (Тяжелый) | ~25 KB gzipped (Средний) | **~7 KB gzipped (Легкий)** |
| **Философия** | "Всё из коробки" (Батарейки включены). Быстрый старт. | Декларативность, компиляция, максимальная производительность. | Модульность, простота расширения через Exchanges (мидлвары). |
| **Кэширование** | Нормализованный кэш по умолчанию. | Строго нормализованный кэш, привязанный к схеме. | Документный кэш по умолчанию, нормализация через плагин (`graphCache`). |
| **Сложность** | Низкая/Средняя. | **Высокая** (требует компилятор Relay и строгую структуру фрагментов). | Низкая. |

*   **Apollo Client** выбирают за отличную документацию, экосистему и скорость разработки.
*   **Relay** — выбор для сверхкрупных проектов (уровня Meta) с тысячами компонентов, где важен размер запросов и их автоматическое объединение.
*   **urql** — отличная замена Apollo для небольших и средних приложений, где критичен финальный размер JS-бандла.

## 2. Fragment Colocation: Архитектурный паттерн Relay и Apollo

Один из важнейших паттернов при работе с GraphQL — **Fragment Colocation (Совместное размещение фрагментов)**.

> [!NOTE]
> **Суть паттерна:** Каждый UI-компонент должен объявлять свои требования к данным непосредственно в файле компонента с помощью GraphQL-фрагмента, а не надеяться, что родительский компонент запросит нужные поля.

```text
Родительский запрос (Query) 
  ├── Импортирует фрагмент Компонента А ──► Отрендерить Компонент А (получает ровно свои данные)
  └── Импортирует фрагмент Компонента Б ──► Отрендерить Компонент Б (получает ровно свои данные)
```

### Пример реализации на React:

1.  **Дочерний компонент Аватара (`Avatar.tsx`):**
    ```tsx
    import { gql } from '@apollo/client';
    
    // Объявляем фрагмент. Компонент зависит только от id и avatarUrl
    Avatar.fragments = {
      user: gql`
        fragment Avatar_user on User {
          id
          avatarUrl
          displayName
        }
      `
    };
    
    export function Avatar({ user }: { user: any }) {
      return <img src={user.avatarUrl} alt={user.displayName} />;
    }
    ```

2.  **Родительский компонент списка (`UserList.tsx`):**
    ```tsx
    import { gql, useQuery } from '@apollo/client';
    import { Avatar } from './Avatar';
    
    const GET_USERS = gql`
      query GetUsers {
        users {
          id
          email
          ...Avatar_user # Внедряем фрагмент дочернего компонента
        }
      }
      ${Avatar.fragments.user}
    `;
    ```

**Почему это важно?**
Если вы решите удалить поле `displayName` из компонента `Avatar` или добавить новое поле, вам не придется искать и править родительские query-запросы по всему проекту. Компоненты становятся изолированными и безопасными к рефакторингу.

## 3. Мутации и Оптимистичный UI (Optimistic Updates)

При отправке мутации (например, лайк посту) серверу требуется время (100–500 мс) на обработку запроса. Чтобы интерфейс реагировал мгновенно, используется паттерн **Optimistic UI**. Мы принудительно записываем в кэш ожидаемый успешный ответ до фактического ответа сервера.

### Пример на Apollo Client:
```javascript
const [toggleLike] = useMutation(TOGGLE_LIKE_MUTATION, {
  variables: { postId: '1' },
  
  // Данные, которые мгновенно подставятся в кэш при вызове функции мутации
  optimisticResponse: {
    __typename: 'Mutation',
    toggleLike: {
      __typename: 'Post',
      id: '1',
      isLiked: true, // Мгновенно переключит кнопку лайка в состояние "активно"
      likesCount: 121 // Ожидаемое новое значение счетчика
    }
  }
});
```

Если сервер ответит ошибкой, Apollo автоматически откатит изменения в кэше к предыдущему состоянию, а интерфейс вернется в исходный вид.

## 4. Подписки (Subscriptions) и Real-Time данные

Подписки используются для получения обновлений от сервера в реальном времени (например, новые сообщения в чате, биржевые котировки).

### Архитектура транспорта
В отличие от Queries и Mutations, которые работают по стандартному HTTP (POST-запросы), Subscriptions требуют постоянного двустороннего соединения и работают поверх **WebSockets** (библиотека `graphql-ws`).

```text
КЛИЕНТ                                             СЕРВЕР
  │ ───► HTTP POST [Query / Mutation] ─────────────► │
  │ ◄─── HTTP Response [Data] ────────────────────── │
  │                                                  │
  │ ───► WS Connection Upgrade [Subscription] ──────► │
  │ ◄─── WS Message [Event 1: New Comment] ───────── │ (Пуш от сервера)
  │ ◄─── WS Message [Event 2: New Comment] ───────── │ (Пуш от сервера)
```

### Пример использования подписки с обновлением списка:
```javascript
const { data, loading } = useQuery(GET_COMMENTS_QUERY, {
  variables: { postId },
});

// Подписываемся на новые комментарии и мержим их со старым списком
const subscribeToNewComments = () =>
  subscribeToMore({
    document: COMMENTS_SUBSCRIPTION,
    variables: { postId },
    updateQuery: (prev, { subscriptionData }) => {
      if (!subscriptionData.data) return prev;
      const newComment = subscriptionData.data.commentAdded;
      
      // Возвращаем новый объект состояния кэша
      return Object.assign({}, prev, {
        post: {
          ...prev.post,
          comments: [newComment, ...prev.post.comments]
        }
      });
    }
  });
```
