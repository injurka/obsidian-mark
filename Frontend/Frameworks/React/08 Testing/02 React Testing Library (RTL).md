# React Testing Library (RTL)

RTL — это библиотека для тестирования React-компонентов. Она пришла на смену старым инструментам (типа Enzyme) с одной конкретной философией, которую обожают спрашивать на собеседованиях.

## 1. Философия RTL
> *"The more your tests resemble the way your software is used, the more confidence they can give you."*
> (Чем больше ваши тесты похожи на то, как используется ваше приложение, тем больше уверенности они вам дают).

Это означает, что вы **НЕ ДОЛЖНЫ тестировать детали реализации** (implementation details). 
- Нельзя проверять, равно ли состояние компонента (state) числу 5. 
- Пользователь не знает про стейт, он видит цифру "5" на экране в теге `<span>`. Вот это и надо проверять!

## 2. Кверинг элементов (Поиск элементов на экране)
RTL предоставляет множество функций поиска элементов, и их нужно использовать в строгом порядке приоритета:

1. **`getByRole`** (Самый высокий приоритет!): Ищет по ARIA-ролям (`button`, `textbox`, `heading`). Это убивает двух зайцев: проверяет UI и заставляет вас делать приложение **доступным (Accessible)**.
2. **`getByText`**: Поиск по тексту.
3. **`getByLabelText`**: Поиск инпута по связанному `<label>`.
4. **`getByTestId`** (Самый низкий приоритет): Ищет по атрибуту `data-testid`. Использовать только если другие способы невозможны.

## 3. Разница между `getBy`, `queryBy` и `findBy`
Это классический вопрос на собеседованиях:

- **`getBy...`**: Возвращает элемент. Если не находит — **кидает фатальную ошибку** и тест падает.
- **`queryBy...`**: Возвращает элемент. Если не находит — **возвращает `null`**. 
  *(Edge Case: Идеально подходит для проверок отсутствия элемента!)*
  `expect(screen.queryByText('Ошибка')).not.toBeInTheDocument();`
- **`findBy...`**: Асинхронная версия. Возвращает Промис. Ждет до 1 секунды, пока элемент не появится в DOM. Идеально для элементов, которые появляются после загрузки данных.

## 4. Имитация действий пользователя: `fireEvent` vs `userEvent`
- **`fireEvent` (Устарело):** Просто диспатчит синтетическое DOM-событие.
- **`userEvent` (Стандарт 2026):** Симулирует реальные действия пользователя в браузере. 

**Почему `userEvent` лучше?**
Когда пользователь печатает в инпут "abc", срабатывает не просто событие `change`. Срабатывают: `focus`, `keyDown`, `keyPress`, `input`, `keyUp` — причем для каждой буквы! `userEvent.type()` воссоздает всю эту цепочку, что помогает выявить сложные баги, которые `fireEvent` бы пропустил.

## 5. Что такое `act(...)`?
Когда состояние React обновляется (например, после fetch-запроса), React должен применить изменения к DOM. В среде тестирования это может произойти непредсказуемо. Обертка `act()` гарантирует, что все обновления стейта и рендеры завершены перед тем, как вы начнете проверять `expect()`.

*Примечание:* В современном RTL функции вроде `userEvent` или `findBy` уже оборачивают свои действия в `act()` под капотом, поэтому писать его вручную приходится крайне редко (только для моков таймеров или сторонних подписок).
