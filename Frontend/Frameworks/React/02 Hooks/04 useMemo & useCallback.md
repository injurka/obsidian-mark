
Эти два хука предназначены исключительно для **оптимизации производительности** за счет **Мемоизации** (кэширования результатов). 

> **Важно для 2026 года:** С выходом **React Compiler (ранее React Forget)** в React 19, во многих случаях компилятор автоматически мемоизирует код под капотом, делая ручное написание `useMemo` и `useCallback` избыточным. Тем не менее, понимание этих хуков **обязательно** для прохождения собеседований и поддержки кода, написанного без компилятора.

## 1. useMemo
Кэширует **результат** вычислений. Принимает функцию-вычислитель и массив зависимостей.

### ✅ Когда СТОИТ использовать?
1. **Тяжелые синхронные вычисления**: Сортировка, фильтрация или маппинг больших массивов данных (от сотен элементов), сложные математические операции.
   ```jsx
   // filter и map для 10 000 элементов больше не будут запускаться при каждом вводе текста в другой инпут
   const filteredUsers = useMemo(() => {
     return users.filter(u => u.name.includes(searchQuery)).map(formatUser);
   }, [users, searchQuery]); 
   ```
2. **Сохранение ссылочной идентичности (Referential Equality)**:
   - Когда вы передаете объект или массив пропсом в дочерний компонент, обернутый в `React.memo`.
   - Когда объект или массив используется в качестве зависимости в `useEffect` (без `useMemo` ссылка будет новой при каждом рендере, что вызовет бесконечный цикл или ложные срабатывания эффекта).

### ❌ Когда НЕ СТОИТ использовать?
1. **Дешевые вычисления**: Сложение чисел, конкатенация строк, фильтрация массива из 5-10 элементов. Оверхед на вызов хука `useMemo` и проверку массива зависимостей будет стоить дороже, чем само вычисление.
2. **Если зависимости меняются почти всегда**: Если в массиве зависимостей лежит пропс, который обновляется каждую секунду, мемоизация теряет смысл — React будет пересчитывать значение постоянно, при этом тратя ресурсы еще и на работу самого хука.

## 2. useCallback
Кэширует **саму функцию** между рендерами. По сути, `useCallback(fn, deps)` — это синтаксический сахар для `useMemo(() => fn, deps)`.

### ✅ Когда СТОИТ использовать?
1. **Передача функции в дочерний компонент с `React.memo`**: Если вы передаете колбек в компонент, который оптимизирован для предотвращения лишних рендеров. Без `useCallback` функция будет пересоздаваться каждый раз, и `React.memo` в дочернем компоненте будет считать, что пропсы изменились.
2. **Функция является зависимостью в `useEffect`**: Если вы вызываете функцию внутри эффекта, линтер потребует добавить её в зависимости. Чтобы эффект не срабатывал на каждый рендер, функцию нужно обернуть в `useCallback`.

### ❌ Когда НЕ СТОИТ использовать?
1. **Передача функции в обычные DOM-элементы**: `<button onClick={handleClick}>`, `<input>`, `<div>`. Нативные элементы не используют `React.memo`. Пересоздание функции для них практически ничего не стоит.
2. **Передача в обычные (не мемоизированные) компоненты**: Если дочерний компонент не обернут в `React.memo`, он в любом случае перерисуется при рендере родителя. `useCallback` здесь будет бесполезен.

```jsx
// ❌ ПЛОХО: Оверхед на мемоизацию есть, а пользы нет
const handleClick = useCallback(() => console.log('click'), []); 
return <button onClick={handleClick}>Click me</button>; 
```

## 3. React.memo и кастомная функция сравнения (arePropsEqual)

Многие разработчики злоупотребляют `useCallback` в родительских компонентах, пытаясь угодить дочерним. Но у `React.memo` есть мощный инструмент — **второй аргумент**, который позволяет перехватить логику сравнения пропсов.

По умолчанию `React.memo` делает поверхностное сравнение (shallow compare) через `Object.is`. Но мы можем передать свою функцию `arePropsEqual(prevProps, nextProps)`.

```jsx
const HeavyComponent = React.memo(({ user, onUpdate }) => {
  return <div>{user.name}</div>;
}, (prevProps, nextProps) => {
  // Возвращаем true, если пропсы "равны" и рендер НЕ НУЖЕН.
  // Мы можем игнорировать изменение ссылки на функцию onUpdate!
  return prevProps.user.id === nextProps.user.id; 
});
```

### Когда это полезно?
1. Когда дочерний компонент принимает много функций-колбеков, и чтобы не оборачивать каждую из них в `useCallback` в родителе, проще написать логику сравнения в самом `React.memo`.
2. Когда вам нужно глубокое сравнение (deep compare) сложного объекта, хотя с этим тоже нужно быть осторожным (глубокое сравнение большого объекта может быть медленнее самого рендера).

## 4. Итог: Оверхед мемоизации

Мемоизация **не бесплатна**. У хуков есть свой "налог" на производительность:
1. Вызов самого хука стоит процессорного времени.
2. Проверка массива зависимостей (сравнение `Object.is` для каждого элемента массива) при каждом рендере стоит времени.
3. Хранение закэшированных значений занимает оперативную память (Memory leak overhead).

**✅ Золотое правило:** 
Пишите код **без** `useMemo` и `useCallback`. Добавляйте их только тогда, когда профилировщик (React DevTools Profiler) показывает реальные проблемы с производительностью (зависания интерфейса из-за тяжелых вычислений или каскадные ре-рендеры тяжелых компонентов). Исключение — ссылочные зависимости для `useEffect`, их нужно мемоизировать сразу, чтобы избежать бесконечных циклов.
