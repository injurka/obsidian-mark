
Проектирование монорепозитория требует решения трех ключевых инженерных задач: правильная организация связей между пакетами, версионирование релизов и ускорение времени сборки в CI.

---

## 1. Архитектура разделения кода (Boundary Rules)

В монорепозитории кодовая база делится на:
*   **Apps (Приложения):** Точки входа (Next.js, Vite SPA, Mobile Expo).
*   **Packages / Libs (Библиотеки):** Переиспользуемые модули (`@org/ui`, `@org/api`, `@org/utils`, `@org/types`).

### Проблема хаотичных импортов
Без жестких ограничений разработчики начнут импортировать логику из одного приложения в другое, или UI-библиотека начнет напрямую зависеть от серверных утилит. Это ломает саму идею модульности.

### Решение: Правила зависимостей (Lint Boundaries)
Для контроля импортов используются плагины (например, `@nx/eslint-plugin` или настройки eslint-import-resolver).

Мы делим код на теги (tags) и описываем правила:
*   Компоненты из `Packages/UI` могут импортировать только `Packages/Utils` или `Packages/Design-Tokens`.
*   `Packages/UI` **не имеет права** импортировать логику из папки `Apps/`.
*   Приложения `Apps/Admin` и `Apps/User` **не имеют права** импортировать код друг из друга.

## 2. Кэширование сборок и задач (Task Pipeline)

Кэширование сборщика (например, Turborepo) исключает повторный запуск тяжелых задач, если исходный код файлов не менялся.

### Как устроен хэш кэша сборки:
Перед запуском задачи (например, `pnpm build`) сборщик вычисляет хэш-ключ, который зависит от:
1.  Содержимого всех файлов в пакете (на основе git-хэшей).
2.  Конфигурации внешних зависимостей (из `package.json`).
3.  Переменных окружения (например, `NODE_ENV`, `API_URL`).

Если вычисленный хэш совпадает с хэшем из предыдущего запуска, сборщик пропускает выполнение задачи и мгновенно восстанавливает файлы в папке `dist/` и логи консоли из локального кэша.

### Настройка пайплайна в `turbo.json`:
```json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      // Задача build зависит от выполнения build во всех локальных зависимостях (^build)
      "dependsOn": ["^build"],
      // Сохраняем в кэш результаты папок dist и .next
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "test": {
      // Тесты можно запускать без сборки, но они зависят от локального кода
      "outputs": []
    }
  }
}
```

## 3. Стратегии версионирования и релизов

При публикации пакетов из монорепозитория используются две основные стратегии:

### 3.1. Синхронное (Fixed) версионирование
Все пакеты в монорепозитории имеют одинаковый номер версии (например, `v2.4.1`), даже если изменения коснулись только одного пакета.
*   *Плюсы:* Исключает несовместимость версий внутри экосистемы. Упрощает деплой.
*   *Минусы:* Лишние обновления пакетов без реальных изменений.

### 3.2. Независимое (Independent) версионирование
Каждый пакет версионируется отдельно в соответствии с Semantic Versioning (SemVer).
*   *Плюсы:* Экономия трафика, чистота релизов.
*   *Минусы:* Сложно контролировать совместимость.

### Инструмент для релизов: Changesets
В современных монорепозиториях стандартом стал инструмент **Changesets**.
1. Разработчик вносит изменения в ветку и запускает команду `npx changeset`.
2. Команда просит указать: какие пакеты изменились (minor, major или patch) и написать лог изменений (changelog).
3. Changesets генерирует небольшой временный markdown-файл в репозитории.
4. При слиянии в `main` пайплайн автоматически собирает все markdown-файлы, обновляет `package.json` затронутых пакетов, генерирует общие changelog-файлы и публикует новые версии в npm.
