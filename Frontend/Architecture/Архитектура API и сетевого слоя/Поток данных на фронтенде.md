
Главный принцип управления данными в современном фронтенде — **строгое разделение состояния по его происхождению, владельцу и жизненному циклу.** Мы не складываем всё в один глобальный store, а используем специализированные слои.

#### 1. Транспортный слой и API (API & Network Layer)
Это изолированный слой, который ничего не знает об интерфейсе. Компоненты никогда не делают `fetch` напрямую.
*   **Инструменты:** `axios` (удобен для интерцепторов) или нативный `fetch`.
*   **Ответственность:**
    *   Настройка базового URL, заголовков (CORS, Content-Type).
    *   Обработка авторизации (добавление Access-токена, логика Refresh-токена через интерцепторы).
    *   Единый обработчик сетевых ошибок (например, выкинуть пользователя на логин при 401).
*   **Антихрупкость (Валидация контрактов):** На этом же этапе мы валидируем ответ от сервера через **Zod** (или Yup). Если бэкенд прислал `string` вместо `number`, приложение упадет на уровне API с понятной ошибкой, а не сломает рендер компонента. Здесь же DTO (Data Transfer Object) маппится в удобную для фронтенда доменную модель.

#### 2. Серверное состояние (Server State)
Данные, владельцем которых является бэкенд. Фронтенд берет их «в аренду» для отображения.
*   **Инструменты:** `TanStack Query` (React Query), `RTK Query`, `SWR`, `Apollo`.
*   **Ответственность:**
    *   Кэширование и дедупликация (5 компонентов просят профиль юзера — в сеть уйдет 1 запрос).
    *   Управление статусами (`isLoading`, `isError`, `isFetching`).
    *   Фоновое обновление (refetch on window focus / reconnect).
    *   **Мутации:** отправка POST/PUT/DELETE запросов с последующей инвалидацией кэша.
    *   **Optimistic Updates:** мгновенное обновление UI до получения ответа от сервера (для быстрых лайков/переключателей).

#### 3. Состояние URL (URL / Router State)
Самый надежный источник истины для глобальных параметров представления. Если состоянием можно поделиться ссылкой — оно должно быть в URL.
*   **Что храним:** `?category=books&sort=price_desc&page=2&modal=auth` (фильтры, сортировки, пагинация, открытые сущности).
*   **Плюсы:** Работает навигация "Вперед/Назад" в браузере, можно скинуть ссылку коллеге, сохраняется при обновлении страницы (F5). Данные из URL часто выступают ключами (`queryKey`) для Server State.

#### 4. Состояние форм (Form State)
Эфемерные данные, которые вводит пользователь, пока не нажмет кнопку «Отправить».
*   **Инструменты:** `React Hook Form` (идеален по перформансу) + `Zod` (для валидации).
*   **Ответственность:** Отслеживание изменений (dirty, touched), валидация полей в реальном времени, сбор данных для отправки в API. Формы не должны засорять глобальный стейт или вызывать лишние ререндеры всего приложения.

#### 5. Глобальное клиентское состояние (Global Client/UI State)
Состояние интерфейса, которое нужно в разных частях приложения, но *не привязано к серверу*.
*   **Инструменты:** `Zustand` (легкий), `Redux Toolkit` (для сложной бизнес-логики), `Context API` (только для редко меняющихся данных, вроде DI или тем оформления).
*   **Что храним:** Глобальные UI-настройки (свернут ли сайдбар), тема оформления, стейт аудиоплеера (если он играет сквозь страницы), глобальные нотификации (toasts).

#### 6. Локальное состояние компонентов (Local State)
То, что волнует только один конкретный компонент.
*   **Инструменты:** `useState`, `useReducer`.
*   **Что храним:** Открыт ли конкретный дропдаун, значение инпута для локального поиска, активен ли hover. Состояние должно жить максимально близко к месту использования.

#### 7. Персистентное хранилище и Офлайн (Persistent Data)
Данные, которые должны пережить закрытие вкладки.
*   **Cookies:** Только для серверной сессии и Refresh токенов (строго с флагами `HttpOnly`, `Secure`, `SameSite`, чтобы защититься от XSS и CSRF атак).
*   **localStorage / sessionStorage:** Для нечувствительных мелких данных (выбранный язык интерфейса, флаг "пользователь видел онбординг"). *Никаких Access-токенов в localStorage, если есть риск XSS.*
*   **IndexedDB (Dexie.js):** Для больших объемов данных. Офлайн-кэш для работы без сети (PWA), черновики больших форм, тяжелые справочники, чтобы не гонять их по сети каждый раз.

### Общий поток данных (Data Flow) от начала до конца

Когда пользователь взаимодействует с приложением, данные проходят следующий цикл:

1. **Инициализация:** Компонент монтируется. Он читает **URL State** (какая страница нужна) и **Persistent State** (какая тема оформления стоит).
2. **Запрос:** Компонент передает параметры из URL в кастомный хук (`useUsers(filters)`).
3. **Кэш / Сеть:** TanStack Query проверяет **Server State**. Если данных нет, он дергает функцию из API-слоя.
4. **Валидация:** API-слой получает JSON от сервера, прогоняет через Zod-схему (маппит в DTO) и отдает в TanStack Query.
5. **Рендер:** Данные попадают в компонент, UI обновляется.
6. **Взаимодействие:** Пользователь меняет сортировку. Мы обновляем **URL State**. URL меняется -> меняется `queryKey` -> TanStack Query автоматически делает новый запрос (шаг 3).
7. **Мутация (Форма):** Пользователь редактирует профиль в модалке. Данные крутятся в **Form State** (React Hook Form). Если интернет пропал, автосохранение пишет черновик в **IndexedDB**.
8. **Сохранение:** Пользователь жмет "Отправить". Вызывается API-метод.
9. **Синхронизация:** API-слой отвечает успехом. TanStack Query инвалидирует кэш профиля (`invalidateQueries`). Приложение делает фоновый запрос за свежими данными и обновляет UI.
