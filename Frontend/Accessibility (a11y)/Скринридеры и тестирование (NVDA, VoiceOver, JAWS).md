# Скринридеры и тестирование (NVDA, VoiceOver, JAWS)

## 1. Что такое скринридеры и как они работают?
**Скринридер (экранный диктор)** — это программное обеспечение для невизуального доступа, которое озвучивает текст и элементы интерфейса на экране или выводит их на тактильный дисплей Брайля.

Скринридеры не просто «читают экран» построчно. Они взаимодействуют напрямую с **Accessibility API** операционной системы, которое, в свою очередь, получает дерево доступности (Accessibility Tree) от браузера. 

```text
HTML/CSS ──> Браузер ──> Accessibility Tree ──> Accessibility API (OS) ──> Скринридер ──> Речь / Брайль
```

Если у элемента сломана семантика, скринридер не сможет корректно обработать его и либо проигнорирует элемент, либо объявит его неверно (например, назовет интерактивную ссылку "просто текст").

## 2. Обзор популярных скринридеров

Доля рынка скринридеров распределяется в основном между тремя гигантами:

1. **NVDA (NonVisual Desktop Access)**
   - **Платформа:** Windows.
   - **Лицензия:** Бесплатный, Open-Source.
   - **Специфика:** Самый популярный скринридер среди веб-разработчиков благодаря своей открытости и высокой точности следования веб-стандартам. Обычно тестируется в связке с браузерами Google Chrome или Firefox.
2. **JAWS (Job Access With Speech)**
   - **Платформа:** Windows.
   - **Лицензия:** Платный (коммерческий, лицензия стоит дорого).
   - **Специфика:** Исторический лидер рынка, популярен в корпоративной среде. Имеет много настроек и мощный движок для работы со сложными офисными приложениями.
3. **VoiceOver**
   - **Платформа:** macOS, iOS, iPadOS.
   - **Лицензия:** Встроен в систему (бесплатный).
   - **Специфика:** На macOS отлично работает с Safari и Chrome. На iOS является стандартом мобильной доступности.

## 3. Руководство по тестированию для разработчика (Быстрый старт)

Для эффективного тестирования разработчику не нужно знать все 100+ команд скринридера. Достаточно освоить базовую навигацию.

### Клавиша-модификатор (Screen Reader Key / Caps Lock / Insert)
Большинство команд скринридера требуют зажатия специальной клавиши-модификатора.
*   **NVDA:** `Insert` или `Caps Lock`
*   **VoiceOver (macOS):** `Control + Option` (часто обозначается как `VO`)

### 3.1. Базовые горячие клавиши для тестирования в веб

| Действие | NVDA (Windows) | VoiceOver (macOS) |
| :--- | :--- | :--- |
| **Включение / Выключение** | `Ctrl + Alt + N` (запуск) / `Insert + Q` (выход) | `Cmd + F5` |
| **Приостановить речь** | `Ctrl` | `Control` |
| **Быстрый переход по заголовкам** | `H` | `VO + Command + H` |
| **Переход по кнопкам** | `B` | `VO + Command + J` (элементы управления) |
| **Переход по таблицам** | `T` | `VO + Command + T` |
| **Переход по ориентирам (Landmarks)** | `D` | `VO + Command + N` |
| **Открыть список элементов / Ротор** | `Insert + F7` (Список элементов) | `VO + U` (Ротор доступности) |

### 3.2. Ротор доступности (Accessibility Rotor) — главный инструмент
В VoiceOver (нажмите `VO + U` на странице Safari) открывается **Ротор**. Это меню-колесо, которое позволяет отфильтровать элементы страницы по типам: Заголовки, Ссылки, Формы, Ориентиры.
Если пользователь не хочет читать всю страницу, он открывает Ротор и быстро переходит к нужному разделу. 
> [!TIP]
> Проверьте ваш сайт через Ротор: если там присутствуют ссылки без текста (просто `id="link-1"`), кнопки без подписей или нарушен порядок уровней заголовков (например, после `H1` сразу идет `H4`), ваш интерфейс неудобен для использования.

## 4. Автоматизированное тестирование доступности

Автоматизация помогает отловить до **30-40%** очевидных проблем (отсутствие `alt` у картинок, плохой контраст, отсутствие `lang` у тега `html`).

### 4.1. axe-core (Lighthouse / Cypress / Playwright)
`axe-core` — золотой стандарт автоматизированного тестирования.
В **Playwright** интеграция выглядит следующим образом:

```typescript
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test.describe('Accessibility Testing', () => {
  test('Page should not have any automatically detectable accessibility violations', async ({ page }) => {
    await page.goto('https://your-site.com');

    // Ожидаем полной отрисовки интерактивных элементов
    await page.waitForSelector('main');

    const accessibilityScanResults = await new AxeBuilder({ page }).analyze();

    expect(accessibilityScanResults.violations).toEqual([]);
  });
});
```

### 4.2. Тестирование Accessibility Tree в Playwright напрямую
Современные E2E фреймворки поощряют семантические тесты. Вместо CSS-селекторов используйте запросы по ролям:

```javascript
// Тестирование клика по кнопке с учетом доступного имени (Accessible Name)
await page.getByRole('button', { name: 'Подтвердить заказ' }).click();

// Тестирование состояния раскрытия аккордеона
const accordionButton = page.getByRole('button', { name: 'Подробная информация' });
await expect(accordionButton).toHaveAttribute('aria-expanded', 'false');
await accordionButton.click();
await expect(accordionButton).toHaveAttribute('aria-expanded', 'true');
```

## 5. Флоу ручного тестирования доступности (Best Practices)

1.  **Выключите монитор (Screen Curtain):** Попробуйте зайти на страницу, включить скринридер, закрыть глаза (или использовать функцию Screen Curtain / Занавес экрана) и совершить ключевое действие (например, заказать товар или зарегистрироваться). Это сразу вскроет проблемы с фокусом и нечитаемым контентом.
2.  **Проверка логической последовательности (Focus Order):** Убедитесь, что фокус перемещается слева направо и сверху вниз. Абсолютно позиционированные элементы не должны ломать логику чтения.
3.  **Декоративные элементы:** Картинки-иллюстрации, не несущие смысловой нагрузки, должны иметь пустой атрибут `alt=""` или `role="presentation"`, чтобы скринридер их игнорировал.
