# Dependency Rule (Правило Зависимостей)

В любой слоистой архитектуре сами по себе слои не решают проблему жесткой связности (coupling). Если ваша центральная бизнес-логика напрямую вызывает SQL-базу данных, она намертво привязывается к SQL. Если она дергает функцию из UI-библиотеки, она привязывается к UI. Боль, которую мы пытаемся решить — это "эффект бабочки": изменение схемы ответа от сервера или обновление мажорной версии React заставляет нас переписывать наши самые ценные бизнес-правила.

**Dependency Rule (Правило Зависимостей)** — это фундаментальный закон всего семейства чистых архитектур (включая Hexagonal и Onion). Оно гласит максимально просто: зависимости в исходном коде могут быть направлены **только внутрь**, в сторону более высокоуровневых политик.

Ничто во внутреннем круге не должно ничего знать о том, что находится во внешнем круге. Это означает, что имя функции, класса, переменной или формата данных, объявленных во внешнем слое, ни при каких обстоятельствах не должно упоминаться во внутреннем слое.

### Как это работает на практике

Настоящая проблема возникает тогда, когда внутреннему слою (например, Use Case) нужно пообщаться с внешним (например, запросить данные с сервера). Если Use Case импортирует модуль Axios, он нарушает правило.

Мы решаем эту задачу с помощью **Инверсии Зависимостей (Dependency Inversion)**. Внутренний слой просто определяет интерфейс (контракт), который ему нужен. А внешний слой этот интерфейс реализует. Таким образом, внутренний слой дергает интерфейс, оставаясь в блаженном неведении о том, кто именно выполняет реальную работу. Управление идет изнутри наружу, а зависимости направлены снаружи внутрь.

```typescript
// 🛡️ Внутренний слой (Domain / Use Case) диктует правила
// Он ничего не знает про HTTP или Axios
interface UserRepository {
  findById(id: string): Promise<User>;
}

class GetUserProfileUseCase {
  // Зависит только от интерфейса (абстракции), а не от конкретной реализации
  constructor(private repo: UserRepository) {}
  
  async run(id: string) {
    return await this.repo.findById(id);
  }
}

// 🔌 Внешний слой (Infrastructure) подчиняется правилам внутреннего
// Именно здесь живет инфраструктурный код
class ApiUserRepository implements UserRepository {
  async findById(id: string): Promise<User> {
    const { data } = await axios.get(`/users/${id}`);
    return new User(data); // Возвращаем доменную сущность, а не AxiosResponse
  }
}
```

### Неочевидные нюансы и границы применимости

**Скрытые трейдоффы**: Поддержание правила зависимостей требует железной дисциплины. Разработчикам, особенно в условиях горящих сроков, всегда хочется сэкономить время и просто импортировать утилиту из UI-слоя или тип ответа API напрямую в домен. "Всего один импорт" постепенно разрушает архитектуру. Оверхедом здесь является постоянная необходимость внедрения зависимостей (Dependency Injection) и создания интерфейсов.

Кроме того, структуры данных, пересекающие границы, должны быть простыми и принадлежать внутреннему кругу. Вы не можете передать `AxiosResponse` или `React.SyntheticEvent` внутрь Use Case. Вам придется распаковать их на внешнем слое, смаппить в простые DTO и только потом передать внутрь. Это создает трение.

**Где это ломается**: Прагматизм иногда должен брать верх над чистотой. Например, строгое следование правилу зависимостей для банальных утилит форматирования дат или работы с числами (если вы используете библиотеку вроде `date-fns`) может довести до абсурда. В таких случаях часто принимается осознанное архитектурное решение (Architecture Decision Record) о том, что некоторые стабильные утилиты считаются "частью языка" и могут использоваться везде, не нарушая дух правила.
