В традиционном фронтенде бизнес-логика часто размазана ровным слоем по UI-компонентам, Redux-thunk'ам или безымянным функциям-утилитам. Доменная модель предлагает иной путь — собрать всю суть решаемой проблемы бизнеса в чистые, независимые объекты.

Доменная модель состоит из [[Entity]], [[Value Object]] и объединяющих их [[Aggregate]]. Это классы или чистые функции, которые инкапсулируют данные и строгие правила их изменения. Они ничего не знают о том, что данные пришли по HTTP через Axios, или о том, что их отрендерит React. Это позволяет тестировать самую важную логику обычными юнит-тестами без поднятия окружения браузера.

**Проблема анемичной модели (Anemic Domain Model):**
Часто мы создаем интерфейсы, которые просто копируют структуру JSON от API, а всю смысловую логику выносим наружу:
```typescript
// Антипаттерн: структура данных без поведения
interface Order {
  id: string;
  total: number;
  items: any[];
}
// Логика разбросана по компонентам
function calculateTotal(order: Order) { ... }
```

**Богатая доменная модель (Rich Domain Model):**
В хорошей доменной истории объект сам защищает свои инварианты и предоставляет понятное API для взаимодействия.
```typescript
class Order {
  private items: OrderItem[] = [];

  addItem(item: OrderItem) {
    // Внутри инкапсулировано бизнес-правило
    if (this.items.length >= 10) throw new Error("Maximum cart capacity reached");
    this.items.push(item);
  }

  get total(): Money {
    return this.items.reduce((sum, item) => sum.add(item.price), Money.zero());
  }
}
```

**Оверхед и границы применимости:**
Не все данные на фронтенде заслуживают богатой модели. Если вы просто получаете плоский список новостей для отображения в ленте, писать под это классы — чистой воды овер-инжиниринг. Используйте доменные модели исключительно там, где на стороне клиента принимаются сложные решения, происходит расчет цен, сложная валидация или запутанный многошаговый стейт (например, конструктор тарифа).
