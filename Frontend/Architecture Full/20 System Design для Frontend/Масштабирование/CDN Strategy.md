
CDN (Content Delivery Network / Сеть доставки контента) — это географически распределенная сеть серверов, расположенных близко к конечным пользователям. Правильное кэширование статики на уровне CDN снижает нагрузку на бэкенд-серверы практически до нуля и обеспечивает моментальную загрузку страниц.

---

## 1. Заголовки HTTP-кэширования: Спецификация

Управление кэшированием на CDN происходит с помощью заголовков ответа (Response Headers), отправляемых сервером-источником (Origin).

```text
[Клиент] ──(Запрос)──► [Edge Server CDN] ──(Если miss: запрос к Origin)──► [Сервер-источник (Origin)]
  ▲                         │                                                   │
  │                         ▼ (Сохраняет в кэш на s-maxage секунд)              │
  └─────────◄───────────────┴───────────────────◄───────────────────────────────┘
```

### 1.1. `Cache-Control` Директивы
*   **`public`** — ответ может быть кэширован как браузером пользователя, так и любыми промежуточными прокси/CDN серверами.
*   **`private`** — ответ предназначен только для конкретного пользователя. Браузер может его закэшировать, но **CDN кэшировать его не имеет права** (критично для персональных страниц личного кабинета).
*   **`max-age=<seconds>`** — указывает, сколько секунд браузер может считать ответ свежим.
*   **`s-maxage=<seconds>`** — переопределяет директиву `max-age` **исключительно для CDN/промежуточных серверов**.

### 1.2. Стратегия Cache Busting (Сброс кэша по имени файла)
При сборке современных SPA (Vite/Webpack) все ассеты компилируются с хэшем контента в названии файла (например, `index.d8a8sd.js`). 
Благодаря этому мы можем кэшировать эти файлы навечно:
```http
Cache-Control: public, max-age=31536000, immutable
```
*   `immutable` сообщает браузеру и CDN, что контент этого файла никогда не изменится. Браузер даже не будет делать проверочные запросы `Conditional Requests` (304 Not Modified) к серверу.
*   При выходе новой версии приложения генерируется файл с новым именем `index.999xyz.js`. Ссылка в `index.html` меняется, и пользователи сразу скачивают новый файл, обходя старый кэш.

## 2. Стратегия Stale-While-Revalidate (SWR) на уровне CDN

Директива `stale-while-revalidate` позволяет мгновенно отдавать устаревший контент из кэша, пока CDN в фоновом режиме делает запрос к Origin за свежими данными.

```http
Cache-Control: public, s-maxage=60, stale-while-revalidate=600
```
*   **Первые 60 секунд (`s-maxage`):** Запросы попадают на CDN и мгновенно отдаются как абсолютно свежие.
*   **От 60 до 660 секунд (`stale-while-revalidate`):** Пользователь получает ответ из кэша мгновенно, но CDN видит, что контент устарел, и в фоновом асинхронном режиме делает запрос к нашему серверу для обновления кэша.
*   **После 660 секунд:** Кэш считается полностью недействительным. Следующий пользователь будет ждать ответа от сервера-источника (Origin).

## 3. Сброс кэша по тегам (Cache Tags / Invalidation)

Для динамических страниц (например, страница товара с ценой) SWR-стратегия может быть неприемлема, если цена меняется мгновенно. Вместо этого используется кэширование с инвалидацией по тегам.

1.  Сервер-источник отдает страницу товара и вешает заголовок тега:
    ```http
    Cache-Control: public, s-maxage=31536000
    Cache-Tag: product-105, category-books
    ```
2.  CDN кэширует эту страницу на год.
3.  Когда контент-менеджер меняет цену книги №105 в панели администратора, бэкенд шлет API-запрос к CDN провайдеру (Cloudflare / Fastly) на инвалидацию:
    ```bash
    POST /purge-cache-by-tags
    Headers: Authorization Bearer ...
    Body: { "tags": ["product-105"] }
    ```
4.  CDN мгновенно сбрасывает кэш только для страниц, помеченных тегом `product-105`. Все остальные миллионы страниц каталога остаются в кэше.
