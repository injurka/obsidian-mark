# Кратко

### 1. Framework (Каркас приложения)
В нашем случае фреймворк отвечает **только за UI** (панели, меню, настройки). Он не должен управлять жизненным циклом WebGL-канваса напрямую, чтобы не вызывать лишних ререндеров.

1. **React.js** — Индустриальный стандарт. Огромная экосистема (React Three Fiber, React Flow).
2. **Vue 3 (Composition API)** — Более чистый синтаксис, реактивность на основе Proxy отлично подходит для сложного состояния.
3. **SolidJS** — Синтаксис как у React, но без Virtual DOM. Феноменальная производительность, реактивность на уровне атомов (Signals).
4. **Svelte 4/5** — Компилируемый фреймворк. Нулевой оверхед, идеален для встраиваемых виджетов (на этапе миграции в монорепу).
5. **Angular** — Строгий enterprise-фреймворк. Встроенный DI контейнер.

*Сравнение:* Для CAD производительность UI критична (обновление сотен свойств в панели при выделении объектов). React может тормозить из-за Virtual DOM без жесткой оптимизации (`useMemo`). SolidJS решает это из коробки. Vue 3 предлагает идеальный баланс между скоростью и экосистемой.
🏆 **Лучший выбор для WebCAD:** **React.js** (из-за экосистемы для 3D/диаграмм) или **SolidJS** (если в команде сильные инженеры и важна максимальная скорость UI).
*Интервью-поинт:* «Мы изолируем фреймворк в слое Presentation. Бизнес-логика (ядро фигур) пишется на чистом TypeScript. Если мы выберем React, канвас будет рендериться через refs, минуя React-цикл».

### 2. UI-Kit (Компоненты интерфейса)
CAD-системы требуют высокой плотности информации (desktop-density). Большинство популярных библиотек созданы для мобилок и имеют слишком большие отступы.

1. **shadcn/ui (Radix UI)** — Headless компоненты. Вы копируете код себе в проект (VSA-friendly). Полный контроль над стилями.
2. **Ant Design** — Очень плотный UI, созданный для сложных дашбордов. Огромное количество готовых сложных таблиц и деревьев.
3. **Fluent UI (Microsoft)** — Выглядит как десктопное приложение Windows. Отлично подходит для Ribbon-интерфейсов (как в AutoCAD/Word).
4. **Mantine** — Отличная библиотека для React с мощной системой хуков и кастомизации.
5. **MUI (Material UI)** — Самая популярная, но плоха для CAD (слишком "воздушная", тяжело кастомизировать под плотный дизайн).

*Сравнение:* CAD-интерфейс — это сотни маленьких иконок, выпадающих списков, вложенных деревьев сцены и инспекторов свойств.
🏆 **Лучший выбор для WebCAD:** **shadcn/ui** (в связке с Tailwind). Это позволит создать абсолютно уникальный, компактный интерфейс. Если нужно "дешево и сердито" на старте — **Ant Design** (с включенным compact mode).

---

### 3. 2D Rendering (Чертежи, Скетчи)
Если 2D-режим — это отдельная сущность (например, чертеж профиля перед выдавливанием в 3D).

1. **PixiJS** — Самый быстрый WebGL 2D-движок. Идеален, если нужно рендерить сотни тысяч линий и точек (что типично для DXF импорта).
2. **Konva.js** — Обертка над Canvas 2D API. Легко биндится к React (react-konva). Хорошо для интерактивности, но на 10 000+ объектах умрет.
3. **Fabric.js** — Мощная работа с SVG, группировками и текстом. Архитектура старовата, производительность средняя.
4. **Paper.js** — Движок с мощной встроенной векторной математикой (пересечения кривых Безье). К сожалению, редко обновляется.
5. **Two.js** — Универсальный API (может рендерить в SVG, Canvas, WebGL).

*Сравнение:* Для CAD важна не только отрисовка, но и *Raycasting* (определение, на какую линию кликнул пользователь).
🏆 **Лучший выбор для WebCAD:** **PixiJS**. Так как бэкенд отдает тяжелую геометрию, фронтенд должен без тормозов крутить/зумить десятки тысяч примитивов. Pixi (через WebGL) справится с этим блестяще.
*Альтернативный архитектурный подход:* **Не использовать 2D библиотеку вообще**. Использовать 3D-движок (Three.js) с ортографической камерой. Это унифицирует пайплайн и избавит от необходимости поддерживать два разных рендерера в монорепозитории.

---

### 4. Diagramming (Параметрическое проектирование / Ноды)
Для параметрического CAD часто нужен редактор логики (подобно Grasshopper в Rhino или Geometry Nodes в Blender).

1. **LiteGraph.js** — Рендерит на Canvas. Выдерживает огромные графы. Используется в ComfyUI. UI не засоряет DOM.
2. **React Flow** — Самая популярная React-библиотека. Рендерит ноды как HTML/DOM элементы. Прекрасный DX, но тормозит на сотнях нод.
3. **JointJS** — Старая, но невероятно мощная энтерпрайз-библиотека для сложных схем и коннекторов.
4. **GoJS** — Самая мощная, но проприетарная (платная) библиотека.
5. **Rete.js** — Модульный фреймворк специально для создания node-based редакторов (визуальное программирование).

🏆 **Лучший выбор для WebCAD:** Если ноды — это вспомогательная фича: **React Flow** (очень легко стилизовать под дизайн системы). Если ноды — это основа всего параметрического дерева и их могут быть тысячи: **LiteGraph.js** или **Rete.js**.

---

### 5. 3D Rendering (Визуализация деталей)
Фронтенд только отображает сетку (Mesh) и отправляет координаты кликов на бэк.

1. **Three.js** — Абсолютный монополист. Миллион примеров. Поддерживает все нужные шейдеры, инстансинг, работу с буферами.
2. **React Three Fiber (R3F)** — React-обертка над Three.js. Упрощает управление сценой, но может нарушить вашу Clean Architecture (связывает рендер с React).
3. **Babylon.js** — Движок от Microsoft. Изначально написан на TypeScript. Архитектурно более строгий, чем Three.js (ближе к геймдеву).
4. **PlayCanvas** — Легковесный движок, отличная производительность, но больше заточен под игры.
5. **vtk.js** — Порт научного визуализатора VTK. Идеален для рендеринга сложной математики, сечений, изоповерхностей (популярен в мед. софте и инженерном CAD).

*Сравнение:* Поскольку вы используете строгую архитектуру с абстрактным `CanvasRenderer`, R3F может оказаться "занозой" (он заставляет думать компонентами, а не контроллерами сцены).
🏆 **Лучший выбор для WebCAD:** **Three.js** (чистый) или **Babylon.js**. Вынесение их в отдельный слой-адаптер (`class WebGLRenderer implements CRenderPort`) позволит вашему `Command Sourcing` управлять сценой без оглядки на UI-фреймворк.

---

### 6. State Manager (Управление состояниями)
Нам нужно разделить *Scene Graph* (сотни тысяч объектов), *Compute Cache* (ArrayBuffers от бэкенда) и *UI State* (какая кнопка нажата).

1. **Zustand** — Минималистичный, не требует оборачивать приложение в провайдеры. Можно вызывать вне React (идеально для слоя бизнес-логики/Core).
2. **Redux Toolkit (RTK)** — Стандарт, отличный DevTools. Но для CAD часто слишком многословный. Хранить тяжелый Scene Graph в Redux нельзя — убьет перформанс из-за иммутабельности.
3. **MobX** — Мутабельный стейт-менеджер. Исторически **лучший выбор для сложных CAD** (так как дерево сцены мутабельно по природе, а пересоздавать массив из 100k объектов при каждом сдвиге мыши — самоубийство).
4. **Jotai / Recoil** — Атомарный стейт. Отлично для UI, где независимые компоненты подписаны на независимые кусочки данных.
5. **XState** — Машины состояний.

🏆 **Лучший выбор для WebCAD:**
*   **Для Scene Graph и команд:** **MobX** (мутабельность дает феноменальную скорость при работе с деревьями объектов) ИЛИ самописный EventBus (как вы и планировали в VSA).
*   **Для UI State (активный тул, меню):** **Zustand** (просто, легковесно).
*   *Compute Cache* вообще не должен попадать в State Manager! Он должен лежать в `WeakMap` или локальных переменных WebGL адаптера.

---

### 7. Data Communication / Сетевой слой (Экстра)
Поскольку вычисления делегируются на бэкенд (генерация сеток, булевы операции `A union B`), REST/JSON убьет приложение при первой попытке передать сгенерированную сетку на 50 МБ.

1. **gRPC-Web** — Бинарный протокол. Идеально для типизации контрактов между Frontend и Backend (через `.proto` файлы).
2. **WebSockets (native) + ArrayBuffers** — Передача чистых бинарников. Минимальный оверхед, идеален для стриминга геометрии.
3. **Socket.io** — Удобнее голых вебсокетов, есть fallback, но чуть больше оверхед.
4. **tRPC** — Идеально для монорепы на TypeScript (Bun/Node.js на бэке), типизация "из коробки" без кодогенерации.
5. **WebRTC (Data Channels)** — Peer-to-peer. Используется, если бэкендом выступает десктопное приложение локально или нужно совместное моделирование (Co-op).

🏆 **Лучший выбор для WebCAD:** **WebSockets + Protobuf/FlatBuffers**. JSON использовать для геометрии нельзя. FlatBuffers позволяет фронтенду читать данные из памяти прямо в WebGL буферы (Zero-copy), не парся строки.

---

### Итоговый Stack-срез для вашей архитектуры (Summary)

Если вы закладываете **Evolutionary Architecture**, ваш технологический стек в Фазе 1 должен выглядеть так:

*   **UI Слой:** React + Zustand (для кнопок) + shadcn/ui.
*   **Доменный Слой (Core/Command):** Чистый TypeScript. Паттерн Command, самописный Scene Graph на классах, независимый от React.
*   **Слой Рендеринга (Adapter):** Чистый Three.js (обрабатывает и 2D ортогонально, и 3D). Обернут в интерфейс `IRenderer`.
*   **Слой Сети (Adapter):** WebSockets + FlatBuffers. Обернут в `IComputeClient`.
*   **Инфраструктура:** Vite (позже переезд в Bun Workspaces).

**Совет на интервью (продолжение):**
*"Разделяя UI (React) и ядро (TS + Three.js), мы защищаем себя от классической проблемы Web-приложений — когда бизнес-логика намертво врастает в компоненты. Если завтра нам потребуется запустить ядро вычислений WebCAD в Web Worker'е для предотвращения фризов UI, благодаря Ports & Adapters нам придется переписать ровно ноль строк бизнес-логики — мы просто напишем новый адаптер MessagePortClient".*

## 2. UI-Kit (Компоненты интерфейса)

Проектирование интерфейса для CAD-системы кардинально отличается от создания обычного веб-сайта (интернет-магазина или CRM). В CAD интерфейс ближе к **профессиональному десктопному софту** (как Photoshop, Blender или AutoCAD). 

Главные требования к UI в CAD:
*   **Высокая плотность (High Density):** На экране должны помещаться десятки иконок, параметров и деревьев без лишнего "воздуха" и огромных отступов.
*   **Сложные контролы:** Инпуты со встроенной математикой (ввод `10 + 5/2` прямо в поле), сложные color-picker'ы, аккордеоны.
*   **Всплывающие окна и контекстные меню:** Сотни Tooltip'ов и меню по правому клику (которые не должны тормозить DOM).

Ниже подробный разбор 5 лучших UI-библиотек для сложного инженерного софта, их сравнение и критические архитектурные нюансы.

---

### 1. shadcn/ui (Базируется на Radix UI)
*Современный стандарт. Это не NPM-пакет в классическом понимании. Вы через CLI копируете исходный код компонентов (React + Tailwind) прямо в свой проект.*

*   **Особенности:** Полностью Headless (логика и доступность работают под капотом через Radix UI, а внешний вид полностью ваш).
*   **Плюсы (Идеально для VSA):** Вы **владеете** кодом. Компоненты лежат в папке `src/shared/ui/`. Если через 3 года пакет перестанут поддерживать, ваше приложение не превратится в "тыкву". Легко сделать супер-плотный дизайн, просто поменяв Tailwind-классы отступов (с `p-4` на `p-1`).
*   **Минусы:** Требует хорошего знания Tailwind CSS. Нет готовых сложных "энтерпрайз" компонентов (например, готового древовидного селекта — придется собирать самому).
*   **Вердикт:** 🏆 **Лучший выбор для старта и долгосрочной эволюции.** Не создает вендор-лока (зависимости от чужой библиотеки).

### 2. Blueprint JS (от Palantir)
*Специализированная библиотека, созданная компанией Palantir для работы со сверхплотными массивами данных и сложными десктоп-подобными веб-интерфейсами.*

*   **Особенности:** Дизайн по умолчанию выглядит как строгий инженерный софт.
*   **Плюсы:** Шикарная поддержка управления с клавиатуры (Hotkeys), мощные контекстные меню (Context Menus), деревья (Tree), и сверхбыстрые ползунки (Sliders).
*   **Минусы:** Менее гибкая кастомизация внешнего вида по сравнению с Tailwind. Написана не на самых свежих стандартах (использует свои стили, а не CSS-in-JS или Utility-first).
*   **Вердикт:** Если вам нужно за неделю собрать интерфейс, который сразу выглядит и ведет себя как AutoCAD или SolidWorks, Blueprint — скрытый бриллиант.

### 3. Fluent UI (от Microsoft)
*Официальная дизайн-система Microsoft (используется в Office 365, Teams и AutoCAD Web).*

*   **Особенности:** Построена вокруг концепции Ribbon-интерфейсов (вкладок с инструментами, как в Word) и плотных десктопных панелей.
*   **Плюсы:** 100% покрытие accessibility (доступность). Наличие уникальных сложных компонентов, специально созданных для редакторов. Отлично интегрируется в экосистему, если ваш продукт нацелен на корпоративный сегмент (B2B Windows пользователей).
*   **Минусы:** Очень тяжеловесная. Переопределять стили Microsoft — та еще боль (часто приходится бороться с фреймворком).
*   **Вердикт:** Отлично подходит, если вы делаете клон классического САПР (с ленточным меню сверху), но может быть избыточным для современного "чистого" WebCAD (типа Figma или Onshape).

### 4. Mantine
*Современная, невероятно функциональная библиотека компонентов для React, включающая в себя сотни хуков.*

*   **Особенности:** Имеет всё "из коробки". Отличная система темизации.
*   **Плюсы:** В отличие от shadcn/ui, здесь есть готовые Color Pickers (для цвета деталей), Number Inputs с шагом и ограничениями (критично для геометрии), отличные Scroll Areas. Огромная экономия времени.
*   **Минусы:** Привязывает вас к своему API. Если вы захотите переехать на Bun Workspaces и использовать UI-кит в проекте на Vue или Solid (для вьюера), вы не сможете — Mantine жестко привязан к React.
*   **Вердикт:** Идеальный баланс между скоростью разработки и качеством. Если дедлайны горят — берите Mantine, включайте малые отступы (size="xs") и пишите бизнес-логику.

### 5. Ant Design (AntD)
*Самая популярная Enterprise-библиотека в мире (особенно в Азии), гигантский набор всего.*

*   **Особенности:** Создана для китайских админок, где плотность данных максимальна.
*   **Плюсы:** Есть режим `Compact Mode`, который идеально сжимает UI для CAD. Миллион готовых паттернов (деревья, таблицы, сложные формы настроек с валидацией).
*   **Минусы:** Очень раздувает бандл (размер приложения). Дизайн AntD узнается мгновенно, вашему WebCAD будет сложно придать уникальный "брендовый" вид. Генерирует очень много лишних DOM-узлов.
*   **Вердикт:** Хорош как "черновой" вариант для MVP, но для Фазы 2 (масштабирование) часто становится обузой из-за тяжести.

*(Примечание: Material UI / MUI здесь нет, так как Material Design с его огромными кнопками, тенями и анимациями — это худшее, что можно выбрать для CAD-интерфейса).*

### ⚠️ Архитектурные нюансы UI для WebCAD (Что нужно знать обязательно)

Помимо кнопок и чекбоксов, в CAD есть специфические задачи интерфейса, которые обычные UI-киты не решают. Вам потребуются следующие паттерны и доп. библиотеки:

### 1. Docking / Layout Management (Плавающие панели)
В нормальном CAD пользователь может открепить панель свойств (Properties), перетащить её на второй монитор или прикрепить снизу. CSS Flexbox/Grid этого не умеют.
**Что использовать:**
*   **FlexLayout-React** ИЛИ **rc-dock** — Это библиотеки управления окнами внутри браузера. Они позволяют создавать систему вкладок и док-станций (как в VS Code или Blender).
*   **Важно:** Интеграция такой системы требует, чтобы ваш UI-State (в Zustand) четко знал, какие панели сейчас открыты, а какие свернуты.

### 2. Специфические CAD-Инпуты (Math Inputs)
Инженер никогда не пишет просто "100" в поле длины. Он пишет `100mm`, или `2in`, или `(50 * 2) + 3.14`.
*   Стандартный `<input type="number">` из UI-китов **не подойдет**. Браузер не разрешит ввести туда буквы или математические знаки.
*   **Решение:** Вам придется написать свой оберточный компонент `ValueInput` (на базе обычного `type="text"`), который под капотом использует библиотеку `mathjs` для парсинга формул и конвертации единиц измерения (дюймы в миллиметры) перед отправкой в стор/бэкенд.

### 3. Проблема частых обновлений (React Re-renders)
Представьте: пользователь выделил деталь и начал тянуть её мышкой. Координата `X` в панели свойств (Инспекторе) должна обновляться 60 раз в секунду (от 10.0 до 50.0).
Если вы привяжете это поле ввода к React-состоянию (через Redux или стандартный `useState` в корне панели), вся правая панель с сотней свойств будет перерисовываться 60 раз в секунду. UI умрет.
**Решение:**
*   Использовать паттерн **Uncontrolled Components** с прямым доступом к DOM-узлу через `ref`.
*   Или использовать подписки Zustand на конкретное поле: панель свойств не перерисовывается, обновляется *только один* маленький текстовый узел внутри инпута координаты X.

### 4. Изоляция событий мыши от Canvas (Pointer Events)
Когда пользователь ведет мышкой над UI-панелью, события (scroll, click, drag) не должны "пробивать" UI насквозь и вращать 3D-модель позади панелей.
**Решение:** В вашей архитектуре VSA слой UI должен иметь корневой контейнер с CSS `pointer-events: none` (чтобы клики проходили к канвасу), а все панели из UI-кита (меню, тулбары) должны иметь `pointer-events: auto` + перехватчик `e.stopPropagation()`.

---

### 🏆 Итоговая рекомендация для вашего стека

Учитывая принципы **Evolutionary Architecture** и **Monorepo**, ваш идеальный UI-стек выглядит так:

1.  **База:** **shadcn/ui** + **Tailwind CSS**. Это дает вам Headless-компоненты. В будущем (Фаза 2), при переходе в Bun Workspace, вы легко вынесете папку `ui` в отдельный пакет `@webcad/ui-kit` и сможете использовать эти же компоненты во Viewer-приложении.
2.  **Layout:** **FlexLayout-React** для организации плавающих панелей и вкладок вокруг центрального WebGL-канваса.
3.  **Иконки:** **Lucide React** (идет в паре с shadcn) — чистые, минималистичные "инженерные" иконки.
4.  **Кастомные элементы:** Свои обертки для математических инпутов (`MathInput`) и системы горячих клавиш (библиотека `react-hotkeys-hook`), так как 90% работы в CAD делается шорткатами.

**Аргументация на защите/интервью:**
*"Мы избегаем тяжеловесных UI-фреймворков вроде Material или Ant Design, чтобы не получить 'вендор-лок' и проблемы с производительностью DOM. Используя подход Headless UI (Radix/shadcn), мы полностью контролируем разметку и стили. Это позволяет нам создать сверхплотный интерфейс десктопного уровня, который легко упаковывается в отдельный npm-пакет для будущей монорепы, оставляя бизнес-логику независимой от визуального представления".*

## 3. 2D Rendering (Чертежи, Скетчи)

Чтобы выбрать правильную библиотеку (PixiJS, Konva и др.) для 2D-скетчей и чертежей, нужно понимать, **на какой фундаментальной технологии (API браузера) они работают**. 

Все эти библиотеки — лишь абстракции над тремя базовыми технологиями: **Canvas 2D API**, **WebGL** и новым **WebGPU**. Для CAD-системы выбор между ними критичен, так как чертежи (DXF/DWG) состоят из сотен тысяч примитивов (линий, дуг, точек).

Давайте разберем их под капотом: проблемы, плюсы и минусы именно в контексте инженерного софта.

---

### 1. Canvas 2D API (Используют: Konva.js, Fabric.js, Paper.js)
Это самый старый и простой способ рисования в браузере. Работает на CPU (хотя современные браузеры пытаются аппаратно ускорять некоторые операции, это все равно «бутылочное горлышко»).

**Принцип работы:** Приложение каждый кадр (при зуме или панорамировании) говорит процессору: «нарисуй линию от A до B, нарисуй кривую Безье». 

**Плюсы:**
* **Идеальная математика кривых и текста «из коробки»:** Canvas 2D умеет сам рисовать сплайны, идеальные сглаженные (anti-aliased) линии любой толщины, заливки и системные шрифты.
* **Простота:** Очень легко программировать и отлаживать.
* **Экспорт:** Элементарно конвертируется в растровую картинку (PNG/JPEG) или SVG.

**Минусы и Проблемы (почему это плохо для CAD):**
* **Проблема CPU (Draw Calls):** Если в вашем чертеже 50 000 линий (стандартный план этажа в DXF), CPU должен пройтись по циклу 50 000 раз *каждый кадр* (60 раз в секунду при скролле). Это приводит к жесточайшим тормозам (UI замирает, мышь лагает).
* **Нет контроля над памятью:** Вы не можете управлять тем, как браузер выделяет память под холст.
* **Отсутствие Z-буфера:** Чтобы изменить порядок отрисовки (чтобы одна деталь перекрыла другую), нужно вручную сортировать массив объектов (O(n log n) операция на CPU).

**Вердикт для WebCAD:** Подходит **только** для UI-оверлеев (линейки, сетка, курсоры, размеры) или очень простых скетчей (до 1000 элементов). 

---

### 2. WebGL 1.0 / 2.0 (Используют: PixiJS, Two.js в режиме webgl)
Это низкоуровневый доступ к видеокарте (GPU) через браузер. Основан на старом стандарте OpenGL ES.

**Принцип работы:** Вы один раз загружаете массивы координат (вертексы) в память видеокарты (VRAM), а затем просто говорите GPU: «нарисуй это всё».

**Плюсы:**
* **Феноменальная производительность:** GPU может отрисовать миллионы треугольников за миллисекунды. Чертеж на 100 000 элементов будет летать при 60 FPS.
* **Шейдеры:** Позволяют делать сложную математику прямо во время отрисовки (например, бесконечная сетка на фоне, которая рендерится математически, а не линиями).

**Минусы и Проблемы (головная боль инженеров CAD):**
* **«Проблема толстой линии» (The Line Problem):** WebGL аппаратно умеет рисовать только линии толщиной в 1 пиксель (и то с артефактами в зависимости от ОС). В CAD линии имеют разную толщину (веса). Чтобы нарисовать толстую сглаженную линию в WebGL, её нужно **триангулировать** — то есть превратить одну линию в два прямоугольных треугольника с помощью сложной математики. Библиотеки (как PixiJS) делают это за вас, но это жрет память.
* **Проблема с текстом:** GPU не умеет рендерить шрифты. Чтобы показать размеры на чертеже, текст нужно превращать в текстуры или использовать сложный алгоритм SDF (Signed Distance Fields).
* **Потеря контекста (Context Loss):** Если видеокарта перегружена, браузер может просто «убить» ваш WebGL контекст. Ваше приложение должно уметь перехватывать событие `webglcontextlost` и заново загружать все данные в GPU, иначе пользователь увидит черный экран.

**Вердикт для WebCAD:** Текущий индустриальный стандарт для тяжелых 2D/3D сцен. Но требует мощных библиотек (PixiJS/Three.js), чтобы скрыть всю низкоуровневую грязь.

---

### 3. WebGPU (Будущее и настоящее)
К 2026 году WebGPU стал полноправным стандартом (заменив WebGL) во всех современных браузерах. Это современный API, аналогичный Vulkan, Metal (Apple) и DirectX 12.

**Принцип работы:** Дает фронтенду практически прямой, низкоуровневый доступ к архитектуре современной видеокарты.

**Плюсы:**
* **Многопоточность (Command Buffers):** В отличие от WebGL, который работает строго в главном потоке (Main Thread), в WebGPU вы можете собирать команды на отрисовку чертежа в фоновых Web Workers, вообще не блокируя интерфейс (UI).
* **Вычислительные шейдеры (Compute Shaders) — Убийственная фича для CAD!** WebGPU позволяет использовать видеокарту не только для рисования, но и для математики. *Например:* вычисление пересечений 10 000 линий, триангуляция полигонов или расчет привязок (Snap to Grid/Vertex) можно делать на стороне GPU в сотни раз быстрее, чем на бэкенде или в JavaScript.
* **Минимальный Overhead:** Вызовы отрисовки (Draw calls) практически ничего не стоят для процессора.

**Минусы:**
* **Колоссальная сложность:** Написать "Hello Triangle" на WebGL занимает 50 строк кода. На WebGPU — 300 строк. 
* **Зоопарк библиотек в стадии адаптации:** Сейчас крупные игроки (PixiJS v8+, Three.js WebGPURenderer) уже поддерживают WebGPU, но многие старые или кастомные плагины могут требовать переписывания шейдеров с языка GLSL (WebGL) на WGSL (WebGPU).

**Вердикт для WebCAD:** Это то, на что должна быть нацелена архитектура. 

---

### Как это влияет на архитектуру вашего WebCAD? (Итог для интервью)

Если вы закладываете **Evolutionary Architecture**, вам категорически нельзя жестко привязывать бизнес-логику к одной из этих технологий.

**Плохой подход (Tightly Coupled):**
Создать класс `Line`, который наследуется от `Konva.Line` или `PIXI.Graphics`. Если завтра чертеж вырастет до 1 миллиона полигонов и Konva умрет (Canvas 2D не справится), вам придется переписывать всё ядро приложения.

**Хороший подход (Ports & Adapters):**
Ядро приложения ничего не знает о Canvas или WebGL. У вас есть класс `LineModel (x1, y1, x2, y2)`.
Вы создаете интерфейс `IRenderer`.

1. **Этап MVP:** Вы быстро пишете `Canvas2DRenderer` (на базе Konva/Fabric), чтобы за неделю показать инвесторам работающие скетчи, привязки и выделения.
2. **Этап Роста:** Клиенты загружают тяжелые DXF. Вы выбрасываете Konva, пишете `WebGLRenderer` (на базе PixiJS или Three.js) и подключаете его. Бизнес-логика (ядро фигур, инструменты, Undo/Redo) не меняется ни на одну строчку кода.
3. **Этап Enterprise (Масштабирование):** Вы добавляете `WebGPURenderer`, чтобы перенести часть булевых вычислений 2D-профилей (пересечения, вычитания площадей) с бэкенда прямо в вычислительные шейдеры браузера клиента.

## 5. 3D Rendering (Визуализация деталей)

В архитектуре WebCAD, где математические вычисления (булевы операции, скругления, генерация B-Rep) делегируются бэкенду, роль 3D-движка на фронтенде сводится к трем задачам:
1. Максимально быстро отрендерить полигональную сетку (Mesh) и линии граней (Edges), полученные по сети.
2. Обеспечить навигацию (Орбита, Pan, Zoom).
3. Обеспечить точный выбор (Picking) граней, ребер или вершин для отправки их ID обратно на бэкенд.

Вот подробный разбор 5 лучших 3D-решений для веба, их плюсы/минусы и критические нюансы именно для CAD.

---

### 1. Three.js (Индустриальный стандарт)
Самый популярный 3D-движок. В 2026 году он имеет полноценную поддержку WebGPU `WebGPURenderer` и мощную систему Node-based шейдеров.

*   **Возможности:** Миллионы примеров, поддержка всех форматов, огромная экосистема плагинов (например, `three-mesh-bvh` для сверхбыстрого Raycasting).
*   **Плюсы:** Невероятно гибкий. Вы имеете доступ к низкоуровневым буферам (BufferGeometry), что позволяет напрямую закидывать бинарные данные `Float32Array` от бэкенда прямо в видеокарту (Zero-copy).
*   **Минусы:** Архитектурно это "набор утилит", а не строгий фреймворк. Вам придется самостоятельно писать архитектуру управления сценой, очистку памяти (вызов `.dispose()` для геометрий и материалов — бич Three.js, при утечках памяти вкладка браузера быстро упадет).
*   **Когда использовать:** Универсальный выбор для 90% проектов. Идеально ложится в вашу **VSA-архитектуру** как независимый Адаптер `ThreeJsRenderer`.

### 2. React Three Fiber (R3F)
React-обертка над Three.js. Позволяет писать 3D-сцену декларативно, используя JSX компоненты (`<mesh>`, `<boxGeometry>`).

*   **Возможности:** Вся мощь Three.js + реактивность React. Сотни готовых компонентов из библиотеки `@react-three/drei` (камеры, контроллеры, тени, gizmo-инструменты).
*   **Плюсы:** Невероятная скорость разработки (Developer Experience). Управление сценой берет на себя React.
*   **Минусы (Архитектурная ловушка!):** Для WebCAD с подходом **Clean Architecture** R3F опасен. Он намертво связывает слой рендеринга (WebGL) с UI-фреймворком (React). Если вы захотите вынести вычисления или рендеринг в Web Worker или мигрировать на SolidJS/Vue, вам придется переписать весь код 3D-сцены.
*   **Когда использовать:** Если нужно сделать MVP за 1 месяц и в команде только React-разработчики. Для enterprise-продукта на 10 лет — лучше избегать.

### 3. Babylon.js
Главный конкурент Three.js, разрабатываемый Microsoft. Это полноценный, строгий ООП-фреймворк для 3D.

*   **Возможности:** Изначально написан на TypeScript. Имеет встроенный мощнейший Инспектор Сцены (открывается прямо в браузере), встроенные алгоритмы CSG (булевы операции на клиенте, если нужно), шикарную поддержку WebGPU.
*   **Плюсы:** Строгая архитектура. В отличие от Three.js, Babylon сам заботится о многих вещах (менеджмент памяти, кеширование шейдеров). Идеальная обратная совместимость (код 10-летней давности работает сегодня).
*   **Минусы:** Весит больше, чем Three.js. API может казаться немного перегруженным (очень "энтерпрайзным", в стиле C#/Java).
*   **Когда использовать:** Отличный выбор для сложных инженерных систем, где важны строгие типы, предсказуемость и надежность, а команда предпочитает классический ООП (что отлично стакается с вашим паттерном Command).

### 4. vtk.js (Scientific & Engineering Standard)
JavaScript-порт легендарной C++ библиотеки VTK (Visualization Toolkit), которая используется в медицинском софте, ANSYS, ParaView и тяжелом CAD.

*   **Возможности:** Создана не для игр и красоты, а для инженерии. Умеет рендерить изоповерхности, разрезы (slicing) с 3D-штриховкой, тензоры, огромные облака точек и конечно-элементные сетки (FEA).
*   **Плюсы:** Архитектура заточена под дата-пайплайны (Data Pipeline). Вы загружаете массив данных -> применяете фильтр (например, сечение) -> маппер рисует это на экране.
*   **Минусы:** Сложная кривая обучения. Некрасивый рендер "из коробки" (нет физически корректных материалов - PBR, красивого света).
*   **Когда использовать:** Если ваш WebCAD сфокусирован на CAE (инженерных расчетах, симуляции нагрузок, аэродинамике) или вы работаете с тяжелыми медицинскими сканами (DICOM).

### 5. Filament (Google) / WASM-движки
Filament — это C++ движок от Google, скомпилированный в WebAssembly (WASM) с WebGL/WebGPU бэкендом. 

*   **Возможности:** Выдает **фотореалистичную** картинку непревзойденного качества. Используется для рендера продуктов, где важны блики на металле, стекло, шероховатость пластика.
*   **Плюсы:** Максимальная производительность (WASM) и лучшая реализация PBR (Physically Based Rendering) в вебе.
*   **Минусы:** Очень тяжело интегрировать с интерфейсом браузера. Нет инструментов для CAD-редактирования (выделение точек, рисование осей).
*   **Когда использовать:** Для Viewer-приложений (как вы упоминали в "Фазе 2: web-viewer"), где клиенту нужно показать красивую презентацию готовой детали, а не редактировать её.

---

### ⚠️ Критические нюансы CAD 3D-рендеринга (Что вас спросят на интервью)

Если вы делаете именно **CAD**, а не игру, стандартные подходы 3D-движков не сработают. Вот 4 главные проблемы, которые вам предстоит решить:

### 1. Z-Fighting и точность чисел с плавающей точкой (Jittering)
Видеокарты используют 32-битные числа (`Float32`). Если деталь находится на координатах `X: 100000.001` (в 100 км от нуля сцены, что типично для генпланов в DWG) и вы приблизите камеру к болту на этой детали, вершины начнут дрожать при повороте камеры, а полигоны будут мигать (Z-fighting).
**Решение:**
*   Использовать **Logarithmic Depth Buffer** (Логарифмический Z-буфер) — поддерживается в Three.js/Babylon.js из коробки.
*   Camera Relative Rendering — смещать мир к камере на лету (использовать 64-бит числа на CPU для хранения позиций графа сцены, и 32-бит только для отрисовки относительно камеры).

### 2. Отрисовка ребер (Edge Rendering / Wireframe)
В играх полигоны просто закрашиваются. В CAD пользователь должен видеть четкие черные линии (контуры деталей). Стандартный `wireframe: true` в WebGL рисует сетку из треугольников — это выглядит ужасно. Вам нужны контуры (B-Rep edges).
**Решение:**
Бэкенд должен присылать не только `Mesh` (треугольники), но и массив `Edges` (линии граней). На фронтенде вы рендерите их отдельным проходом с помощью `LineSegments`. Для отрисовки линий с идеальной толщиной в пикселях независимо от зума используются шейдеры (например, `LineMaterial` из Three.js).

### 3. Точный выбор объектов (GPU Raycasting / Color Picking)
Как понять, на какую грань из миллиона кликнул пользователь?
Стандартный Raycasting (пускание луча из камеры в мышь) на CPU при 1 000 000 полигонов заморозит вкладку браузера на секунду.
**Решение (Индустриальный стандарт CAD): GPU Color Picking.**
Когда пользователь кликает, вы мгновенно рендерите сцену в невидимый холст (Offscreen Framebuffer) в памяти, где *каждая деталь/грань закрашена уникальным цветом* (например, ID 125 = цвет #00007D). Затем вы читаете цвет ровно 1 пикселя под курсором мыши. Конвертируете цвет обратно в ID и получаете выбранную деталь за **1 миллисекунду** независимо от тяжести геометрии.

### 4. Zero-Copy Data Pipeline (Бинарные данные)
Никогда не передавайте 3D-модели от вашего бэкенда в виде JSON (например: `[{"x": 1.1, "y": 2.2}]`). JSON парсинг на 50 мегабайт убьет V8 движок браузера (сборщик мусора).
**Решение:** Бэкенд должен сериализовать массивы чисел в бинарники (FlatBuffers/Protobuf). Фронтенд принимает `ArrayBuffer`, создает `Float32Array` и передает его **прямо в память GPU** (в `BufferAttribute` в Three.js), вообще не перебирая массив циклом `for` в JavaScript.

---

### Архитектурный итог для вашего WebCAD:

1.  Создайте абстрактный класс/интерфейс `class AbstractSceneRenderer`.
2.  На этапе **Фазы 1 (VSA)** реализуйте его как `ThreeJsRenderer` на чистом **Three.js** или **Babylon.js** (избегайте R3F для ядра).
3.  Настройте GPU Color Picking для выделения объектов.
4.  Свяжите этот рендерер с вашим глобальным стейтом `Scene Graph` (о котором мы говорили в пункте про MobX) через паттерн **Observer/События**. Когда математическое ядро применяет команду "Отрезать угол", Scene Graph обновляется, рендерер ловит событие, удаляет старый ArrayBuffer из GPU, и загружает новый. UI (React) в этот момент даже не перерисовывается.

## 6. State Manager (Управление состояниями)

Вы задали абсолютно правильный и очень глубокий вопрос. **Да, Zustand тоже иммутабельный**, как и Redux. Он использует строгое равенство (`===`) для определения того, нужно ли перерисовывать компоненты в React.

Почему же тогда Zustand хвалят, а Redux для CAD считают тяжелым, и откуда берется рекомендация использовать MobX? Давайте разберем **анатомию состояний в CAD-системах** и почему классический веб-подход (Redux/React) здесь ломается.

---

### Главный враг CAD — Сборщик мусора (Garbage Collector)

В обычном веб-приложении (например, интернет-магазине) у вас в корзине 20 товаров. Если вы изменяете количество одного товара, иммутабельный стейт-менеджер (Redux, Zustand) заставляет вас **скопировать весь массив корзины** и создать новый объект измененного товара. Для 20 элементов это занимает 0.001 мс.

В CAD-системе у вас **100 000 объектов** в дереве сцены (Scene Graph). 
Пользователь зажимает мышь и тащит деталь. Происходит 60 обновлений координат в секунду (60 FPS). 
Если вы используете иммутабельный стейт (Redux или классический подход в Zustand), вам нужно 60 раз в секунду создавать **новую копию массива из 100 000 элементов**. 
* **Проблема не в скорости копирования**, а в том, что старые массивы каждую секунду скапливаются в памяти. Сборщик мусора браузера (GC) сходит с ума, останавливает выполнение JavaScript (GC Pause), и ваш гладкий 60 FPS интерфейс начинает "дергаться" (фризить).

Именно поэтому **архитектура WebCAD требует жесткого разделения состояний**:

---

### 1. Scene Graph (Граф сцены) — 100к+ объектов
*Здесь хранится геометрия, координаты, иерархия объектов.*

*   **MobX:** 🏆 **Идеальный выбор.** Он **мутабельный**. Если вы хотите изменить X-координату у одного объекта, вы просто пишете `object.x = 10`. MobX (через Proxy) знает, кто конкретно следит за этим полем, и обновляет *только этот* кусочек UI (например, Инспектор свойств), не трогая массив из 100к элементов. Сборщик мусора отдыхает, FPS стабильный.
*   **Самописный ООП стейт (EventBus):** В серьезных CAD (как Figma или Onshape) граф сцены вообще не лежит в стейт-менеджерах. Это просто классы TypeScript (`class Node`), которые мутируются напрямую, а при изменениях они стреляют событиями (`node.emit('change')`), которые слушает рендерер.

### 2. UI State (Состояние интерфейса)
*Здесь хранится то, что не обновляется 60 раз в секунду: открыта ли панель, какой инструмент активен (Линия или Круг), текущая тема (Dark/Light).*

*   **Zustand:** 🏆 **Идеально.** Да, он иммутабельный, но для UI это не проблема. Панели открываются редко. Плюс Zustand позволяет читать стейт *вне React* (в обычных `.ts` файлах бизнес-логики): `useUIStore.getState().activeTool`.
    *   *Секретное оружие Zustand:* У него есть метод `.subscribe()`. Он позволяет подписаться на изменения в обход React-рендера (Transient Updates). Вы можете хранить в нем координаты курсора и напрямую передавать их в WebGL, не вызывая перерендер React-компонентов.
*   **Redux (RTK):** Можно, но избыточно. В CAD каждое действие рождает цепную реакцию (подвинул деталь -> пересчиталась сетка -> обновилось дерево). Redux с его глобальным стором и middleware (Thunk/Saga) делает этот поток данных очень "многословным" (boilerplate).
*   **Jotai / Recoil (Атомарные):** Отличная вещь для UI. Представьте, что каждое свойство в правой панели настроек CAD — это отдельный атом. Изменение одного чекбокса никак не затрагивает соседние. Но засовывать 100к фигур в отдельные атомы — прямой путь к нехватке памяти (Out of Memory).

### 3. State Machines (Инструменты рисования)
*В CAD логика инструмента — это всегда процесс с несколькими шагами. Например, инструмент "Линия": Клик 1 (начало) -> Тянем (предпросмотр) -> Клик 2 (конец).*

*   **XState:** 🏆 **Идеально для сложной логики.** Написание инструментов через обычные `if/else` в Zustand или Redux быстро превращается в спагетти-код (особенно когда добавляются привязки, отмена по ESC, переключение на лету). XState — это конечные автоматы. Вы четко описываете графы переходов инструмента. XState работает абсолютно независимо от React, что идеально ложится в вашу **VSA (Vertical Sliced Architecture)** — логика инструмента инкапсулируется в домене `tools`.

### 4. Compute Cache (Кэш вычислений бэкенда)
*Это сырые ArrayBuffers (бинарные данные), которые присылает бэкенд, например, сгенерированная 3D-сетка для рендера.*

*   **Где это хранить? Ни в одном из вышеперечисленных!** Бинарные данные (меши на сотни мегабайт) убьют любой Redux/Zustand/MobX, если те попытаются сделать их "реактивными" или обернуть в Proxy.
*   Эти данные должны лежать в `WeakMap` или обычных локальных переменных внутри вашего слоя Адаптеров (например, внутри класса `WebGLRenderer`), чтобы их напрямую "кушал" GPU.

---

### Итоговая архитектура состояний для вашего проекта (Summary)

Если вы делаете ставку на **Clean Architecture** и производительность, ваш стек состояний должен выглядеть как **гибрид**:

1.  **Core (Scene & Domain Logic):** Чистый TypeScript + **MobX** (или свой EventBus). Граф сцены живет здесь, он мутабельный. Вы легко меняете координаты тысяч объектов без аллокации (выделения) новой памяти.
2.  **Tools (Инструменты ввода):** **XState** (опционально, можно начать с простых классов состояния), чтобы управлять процессом рисования/выделения.
3.  **UI (React):** **Zustand**. Он выступает "клеем" между вашим ядром (MobX/TS) и React-компонентами интерфейса.
4.  **Network/Compute:** Реактивность отключена (никаких Proxy-оберток), просто передача ссылок на `ArrayBuffer` прямо в WebGL/WebGPU-адаптер.

**Как отвечать на интервью/защите проекта:**
*"Мы сознательно отказываемся от Redux и чистого иммутабельного подхода для дерева сцены, так как при 60 FPS это вызовет лавину Garbage Collection и фризы (проблема аллокации). Мы используем мутабельный подход (MobX или паттерн Observer) для тяжелых графов данных (Scene Graph), а иммутабельный (Zustand/React) оставляем только для 'медленного' UI — панелей, кнопок и настроек. Это позволяет сохранить высокую производительность CAD-ядра, оставляя интерфейс предсказуемым."*

## 7. Data Communication / Сетевой слой (Экстра)

В архитектуре вашего WebCAD сетевой слой — это самое узкое горлышко (bottleneck). Вы делегировали тяжелую математику (выдавливание, булевы операции, генерацию сеток) на бэкенд. 

Это значит, что при каждом изменении (например, скруглении угла) по сети будут летать **сотни мегабайт геометрии**. Если использовать здесь стандартный веб-подход (REST API + JSON), браузер просто зависнет на этапе `JSON.parse()`.

В CAD-системах сетевой слой делится на две независимые части: **Транспорт** (как данные летят) и **Сериализация** (в каком виде они летят). Рассмотрим 5 лучших вариантов для организации связи между UI и расчетным ядром.

---

### Часть 1: Транспорт и Библиотеки связи (5 вариантов)

#### 1. gRPC-Web (Google)
*Индустриальный стандарт для микросервисов и тяжелых вычислений.*

*   **Как работает:** Использует HTTP/2 и строгие контракты (файлы `.proto`). Клиент вызывает методы сервера так, будто это локальные функции.
*   **Плюсы:** Строжайшая типизация. Бинарная передача данных из коробки (Protobuf). Поддерживает **серверный стриминг** (бэкенд может кусками отправлять огромную сетку, и она будет отрисовываться в браузере по мере загрузки).
*   **Минусы:** Настройка инфраструктуры (часто нужен Envoy proxy между браузером и gRPC-сервером).
*   **Вердикт:** Лучший выбор для Enterprise-продуктов с микросервисным бэкендом (например, на C++ или Go).

#### 2. Native WebSockets + ArrayBuffers
*Голые вебсокеты (без Socket.io и прочих оберток).*

*   **Как работает:** Постоянное двунаправленное соединение поверх TCP.
*   **Плюсы:** Минимальный оверхед (заголовок фрейма всего 2-10 байт). Идеально для стриминга чистых бинарных данных (`socket.send(Float32Array)`).
*   **Минусы:** Нет встроенных механизмов "запрос-ответ" (Request-Response) и повторного переподключения. Придется писать свою обертку-адаптер.
*   **Вердикт:** 🏆 **Идеальный выбор для передачи геометрии.** Чисто, быстро, дает полный контроль над памятью.

#### 3. tRPC (TypeScript RPC)
*Современный любимец экосистемы TypeScript.*

*   **Как работает:** Позволяет шарить типы TypeScript напрямую между фронтендом и бэкендом без генерации схем (как в GraphQL или gRPC).
*   **Плюсы:** **Идеально ложится в ваш Bun Workspace (Monorepo)!** Если ваш расчетный бэкенд (или хотя бы его gateway) написан на TS/Bun, вы сможете вызывать серверные ручки с полным автокомплитом прямо в React-компонентах.
*   **Минусы:** Работает поверх HTTP/JSON (по умолчанию), хотя можно настроить парсеры (superjson). Не подходит для передачи мегабайтов полигонов.
*   **Вердикт:** 🏆 **Идеально для передачи Команд (UI -> Backend).** Например, отправить команду "Создать линию". Геометрию в ответ лучше получать другим путем.

#### 4. WebRTC (Data Channels)
*Peer-to-peer протокол, работающий поверх UDP.*

*   **Как работает:** Соединяет браузеры напрямую или браузер с локальным десктопным сервером без задержек.
*   **Плюсы:** UDP не ждет подтверждения доставки пакетов. Если потерялся пакет данных от движения курсора коллеги — не страшно, придет следующий.
*   **Минусы:** Очень сложная настройка (нужны STUN/TURN сервера для пробития NAT).
*   **Вердикт:** Используется только если вы делаете Co-op (совместное моделирование в реальном времени, как в Figma) или если бэкенд крутится на локальной машине пользователя (Desktop App + Web UI).

#### 5. Socket.io / SignalR
*Популярные высокоуровневые обертки над WebSockets.*

*   **Плюсы:** Работают "из коробки", имеют комнаты (Rooms) для совместной работы, автоматическое переподключение, fallback на Long Polling.
*   **Минусы:** Добавляют свои метаданные в пакеты (оверхед). Часто провоцируют разработчиков отправлять JSON-объекты вместо бинарников.
*   **Вердикт:** Хорошо для MVP, но для хардкорного WebGL-рендера хуже, чем Native WebSockets.

---

### Часть 2: Сериализация (В чем передавать данные?) ⚠️ КРИТИЧНО

В WebCAD выбор транспорта менее важен, чем выбор **формата данных**.

1.  **JSON (JavaScript Object Notation)**
    *   *В CAD:* Строго запрещен для геометрии!
    *   *Почему:* Массив `[{x: 1.123456, y: 2.123456, z: 3.0}]` занимает в 5 раз больше места в сети, чем бинарный формат. А главное — когда браузер делает `JSON.parse` строки на 50 МБ, основной поток вкладки "замерзает" на 2-3 секунды.
2.  **Protocol Buffers (Protobuf)**
    *   Отличный формат. Сжимает данные в бинарный вид.
    *   *Минус для CAD:* На клиенте данные нужно *десериализовать* (распаковать). Это создает в памяти тысячи маленьких JavaScript-объектов. Сборщик мусора (GC) потом будет долго их удалять.
3.  🏆 **FlatBuffers (Google) — Индустриальный секрет WebCAD**
    *   *Как работает:* Это бинарный формат, который **вообще не требует десериализации (Zero-copy)**.
    *   *Сценарий:* Бэкенд генерирует 3D-сетку (1 миллион вершин), упаковывает во FlatBuffer. Фронтенд получает `ArrayBuffer` из сети, и **напрямую, по ссылке** передает этот кусок памяти в видеокарту (WebGL `BufferGeometry`). JavaScript даже не пробегается по этим координатам! Затраты времени на процессоре (CPU) — 0 миллисекунд.

---

### ⚠️ Важные архитектурные нюансы (Что нужно знать на защите)

#### 1. CQRS (Command Query Responsibility Segregation) в сети
Для CAD идеален подход, когда вы разделяете Транспорт на два потока (как упоминалось выше):
*   **Команды (Commands) идут через tRPC / HTTP REST.**
    Вы отправляете легкий пакет: `tRPC.extrude.mutate({ faceId: 45, depth: 10 })`. HTTP гарантирует доставку и дает удобную обработку ошибок.
*   **Данные сцены (Queries) возвращаются через WebSocket (Binary) / gRPC stream.**
    Сервер ловит HTTP-запрос, пересчитывает модель и пушит готовый бинарник (FlatBuffers) прямо в активный WebSocket. Ваш `ComputePort` ловит бинарник и отдает его WebGL-адаптеру.

#### 2. Optimistic UI (Оптимистичный интерфейс)
Если булева операция (вырезание отверстия в сложной детали) занимает на бэкенде 2 секунды, пользователь не должен видеть зависший экран.
*   *Нюанс:* Как только юзер отпустил мышку, ваш паттерн **Command** локально рисует легкий "предпросмотр" (например, полупрозрачный красный цилиндр, показывающий, где будет отверстие).
*   В этот момент асинхронно улетает запрос на бэкенд.
*   Когда приходит ответ со сгенерированной сеткой, красный цилиндр исчезает, и отрисовывается реальное отверстие.

#### 3. Cancellable Requests (Отмена тяжелых вычислений)
Пользователь начал тянуть скругление угла мышкой: `r=1`, `r=2`, `r=3`. При 60 кадрах в секунду на сервер улетит 60 тяжелых запросов.
*   *Нюанс:* Сетевой слой должен уметь **отменять** предыдущие запросы (AbortController для HTTP или отправка флага "Cancel" в сокет). Бэкенд должен прерывать математику, если клиент сообщил, что данные уже неактуальны, иначе сервер упадет от перегрузки (OOM - Out of Memory).

---

### Итоговое архитектурное решение (Evolutionary Approach)

Следуя вашим правилам (VSA -> Monorepo) и паттерну Ports & Adapters, сетевой слой реализуется так:

1.  В доменном слое (Core) вы объявляете интерфейс `interface INetworkPort`. Бизнес-логика ничего не знает о вебе.
2.  **MVP (Фаза 1):** Вы пишете адаптер `TrpcClient implements INetworkPort`. И команды, и геометрию гоняете через tRPC (JSON), потому что это быстро сетапится. Да, геометрия будет подтормаживать, но вы проверите гипотезу продукта.
3.  **Масштабирование (Фаза 2):** Вы замечаете, что клиенты жалуются на долгую загрузку тяжелых чертежей. Вы **не трогаете бизнес-логику**. Вы пишете новый адаптер `WebSocketFlatBufferClient implements INetworkPort` и подменяете его в DI-контейнере.
4.  В `packages/@webcad/core` вы выносите общие TS-типы Команд, чтобы и фронт, и Bun-бэкенд импортировали их из одного места.

**Как аргументировать на интервью:**
*"Мы применяем гибридный подход к сети (CQRS). Легковесные команды управления мы проводим через tRPC (в перспективе), чтобы иметь жесткую типизацию в монорепозитории. А для передачи тяжелой геометрии мы закладываем использование WebSockets и бинарной сериализации (в идеале FlatBuffers). Это позволит нам реализовать Zero-Copy Pipeline: данные о вершинах будут попадать из сети прямо в память видеокарты без накладных расходов на парсинг в основном потоке JS".*

## 8. Table

В контексте CAD-систем таблицы — это не просто списки пользователей, как в обычных админках. В WebCAD таблицы выполняют две тяжеловесные роли:
1. **BOM (Bill of Materials) / Спецификации:** Иерархические списки деталей (сборка -> подсборка -> деталь), которые могут содержать тысячи строк.
2. **Параметрические таблицы:** Ввод переменных, формул и массивов данных для генерации геометрии (аналог Excel внутри CAD).

Главная проблема таблиц в вебе — **DOM-узлы**. Если вы попытаетесь отрендерить таблицу на 5000 строк по 10 колонок стандартными `<table><tr><td>`, браузер создаст 50 000 DOM-элементов. Память переполнится, и ваш 3D/WebGL канвас начнет безбожно тормозить, так как браузер делит ресурсы между DOM и GPU.

Решение — **Виртуализация (Windowing)** или **Canvas-рендеринг**. Вот 5 лучших вариантов для WebCAD:

---

### 1. TanStack Table (ex-React Table)
*Индустриальный стандарт для современных веб-приложений. Это "Headless" библиотека — она предоставляет только логику (хуки), а HTML/CSS вы пишете сами.*

*   **Возможности:** Мощнейшая сортировка, группировка, вложенные строки (Tree-data), ресайз колонок.
*   **Плюсы:** Идеально ложится в концепцию `shadcn/ui` и **VSA**. Полный контроль над дизайном. Фреймворк-агностик (есть адаптеры для React, Solid, Vue).
*   **Минусы:** "Из коробки" нет виртуализации (нужно прикручивать отдельную библиотеку `TanStack Virtual`, что требует опыта) и нет готового UI (придется верстать таблицу с нуля).
*   **Ситуация:** Отлично подходит для панелей свойств (Property Inspector) и небольших таблиц настроек.

### 2. AG Grid
*Энтерпрайз-монстр. Самая функциональная таблица в мире веба.*

*   **Возможности:** Виртуализация DOM "из коробки", сводные таблицы, экспорт в Excel, копирование как в Excel, древовидные данные, сложные фильтры.
*   **Плюсы:** Готова к огромным объемам данных. Включил — и она работает. Написана на чистом TS, не привязана жестко к React.
*   **Минусы:** Огромный размер бандла. Но главное: самые нужные для CAD фичи (Tree Data для сборок и сводные таблицы) доступны **только в платной Enterprise-версии**.
*   **Ситуация:** Идеально, если у вас коммерческий B2B продукт с бюджетом и вам нужен мощный редактор спецификаций "как в десктопе".

### 3. Glide Data Grid (Скрытый бриллиант для CAD 💎)
*Эта таблица не использует HTML/DOM для рендеринга ячеек. Она рисует всю таблицу на `<canvas>` (как Google Sheets или Figma).*

*   **Возможности:** Рендеринг миллионов строк при 60 FPS, плавный скроллинг, поддержка курсоров, выделение областей (как в Excel).
*   **Плюсы:** **Нулевой оверхед на DOM!** Это спасение для CAD. Вы можете держать открытой таблицу на 100 000 строк поверх 3D-сцены, и интерфейс не потеряет ни одного кадра.
*   **Минусы:** Сложнее кастомизировать дизайн (так как это Canvas, а не CSS). API сильно отличается от стандартных React-компонентов.
*   **Ситуация:** Однозначный фаворит для ввода тяжелых параметрических массивов (например, таблицы координат профиля крыла, облака точек) или гигантских BOM.

### 4. Handsontable
*Библиотека, созданная специально для имитации Microsoft Excel в браузере.*

*   **Возможности:** Поддержка формул, объединение ячеек, автозаполнение (протягивание за угол ячейки), валидация данных на лету.
*   **Плюсы:** Идеальный UX для инженеров, привыкших работать с параметрами в Excel.
*   **Минусы:** Очень тяжелая. Как и AG Grid, требует платной лицензии для коммерческого использования.
*   **Ситуация:** Если ваш WebCAD сильно завязан на параметрику, формулы и табличный ввод таблиц переменных (Design Tables, как в SolidWorks).

### 5. Tabulator
*Старая, но невероятно мощная Vanilla JS библиотека (с обертками для React/Vue).*

*   **Возможности:** Виртуальный DOM, древовидные структуры, редактирование ячеек, экспорт в PDF/XLSX, форматирование на лету.
*   **Плюсы:** Абсолютно бесплатная (MIT-лицензия). Включает в себя все энтерпрайз-фичи (в том числе деревья для спецификаций), за которые AG Grid просит деньги.
*   **Минусы:** Чуть устаревший дизайн по умолчанию (придется переписывать CSS-тему). Менее "React-way" подход, так как это обертка над чистым JS.
*   **Ситуация:** Если нужен функционал AG Grid Enterprise, но бесплатно, и вы готовы потратить время на интеграцию.

### 🏆 Итоговый выбор для архитектуры WebCAD

Выбор зависит от конкретной фичи, которую вы реализуете:

1.  **Для Инспектора Свойств (Property Grid — справа на экране):**
    Используйте **TanStack Table** + ваши компоненты `shadcn/ui`. Там не бывает больше 50 строк (свойства одной выделенной детали), поэтому виртуализация не нужна, а UI должен быть идеально вписан в дизайн системы.
2.  **Для Спецификаций (BOM / Дерево сборок) и Таблиц параметров (миллионы ячеек):**
    Используйте **Glide Data Grid**. Так как архитектура вашего проекта подразумевает тяжелую работу с WebGL, разгрузить Main Thread и DOM-дерево браузера — критически важно. Рендеринг таблицы спецификаций на канвасе гарантирует, что 3D-рендер не будет тормозить, когда инженер начнет скроллить список из 10 000 деталей.

**Как аргументировать на защите проекта:**
*"Для списков и таблиц мы внедряем паттерн **Virtualization/Windowing**. Мы отказываемся от стандартных UI-библиотек с DOM-таблицами для работы со Спецификациями, так как генерация тысяч HTML-нод остановит работу нашего WebGL/WebGPU рендерера. Для тяжелых дата-сетов мы используем Canvas-based таблицы (Glide Data Grid), что полностью изолирует нагрузку UI от графического ядра."*
