# Архитектура стилизации (CSS Architecture)

В современных фронтенд-приложениях существует множество способов работы со стилями, каждый со своими плюсами и минусами.

## 1. БЭМ (Блок, Элемент, Модификатор)
- **Суть:** Методология именования CSS-классов (например, `button`, `button__icon`, `button--primary`), позволяющая избежать конфликтов имен и писать независимые, переиспользуемые компоненты.
- **Плюсы:** Не требует сборки, работает везде, легко читается.
- **Минусы:** Длинные имена классов, сложно поддерживать в больших командах без строгой дисциплины.

## 2. CSS Modules
- **Суть:** CSS-файлы, в которых все классы локальны по умолчанию (сборщик вроде Webpack/Vite генерирует уникальные хэши имен).
- **Плюсы:** Никаких конфликтов имен классов, нативный CSS, простая интеграция в компонентный подход.
- **Минусы:** Требует сборщика, может приводить к дублированию кода, если не выносить общие стили.

## 3. CSS-in-JS (Styled Components, Emotion)
- **Суть:** Стили пишутся прямо внутри JavaScript/TypeScript файлов.
- **Плюсы:** Динамическая стилизация на основе пропсов (JS-состояния), изоляция стилей, автоматическое удаление неиспользуемых стилей.
- **Минусы:** Хуже производительность в рантайме (стили генерируются на лету), не очень дружит с Server-Side Rendering (SSR/RSC) в новых архитектурах вроде React Server Components.

## 4. Utility-first CSS (Tailwind CSS, UnoCSS)
- **Суть:** Использование маленьких, атомарных классов-утилит (например, `flex`, `text-center`, `p-4`) прямо в HTML/JSX.
- **Плюсы:** Невероятная скорость разработки, отсутствие придумывания имен классов, очень маленький итоговый CSS бандл (благодаря удалению неиспользуемых классов).
- **Минусы:** Грязная разметка (HTML становится перегруженным классами), крутая кривая обучения.

## Архитектура UI-кита и Токены дизайна
Вне зависимости от выбранного подхода, современная архитектура требует создания **Design Tokens** (шрифты, цвета, отступы в виде переменных) и абстрагирования UI-компонентов (Кнопки, Инпуты, Модалки) от бизнес-логики.
