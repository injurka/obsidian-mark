# Workspace Structure (Структура Workspaces)

**Workspace Structure (Структура Workspaces)** — это физическая организация папок и файлов монорепозитория, а также набор конфигурационных файлов, которые объясняют пакетному менеджеру (pnpm, yarn) и системе сборки, где именно лежат пакеты и как они связаны.

## Боль, которую мы решаем

Если просто сложить 20 папок с `package.json` в один корень, npm сойдет с ума. Он создаст 20 разных папок `node_modules`, скачает 20 раз один и тот же React, сожрет всё место на жестком диске диске и сломает систему, когда пакет А захочет импортировать пакет Б. Нам нужен механизм оркестрации — **Workspaces (рабочие пространства)**.

## Как это работает на практике

Де-факто индустриальным стандартом стала следующая структура папок:

- **`apps/`** — конечные приложения. Они являются *потребителями* кода, они собираются в артефакты для деплоя (Docker-образы, статика), но их код никто не импортирует.
- **`packages/`** (или `libs/`) — переиспользуемые библиотеки. Они не деплоятся сами по себе, они служат "донорами" кода для `apps/`.

```text
my-monorepo/
├── pnpm-workspace.yaml   # <-- Главный файл маппинга
├── package.json          # Корневой package.json (линтеры, хаски)
├── apps/
│   ├── web/              # React приложение
│   └── docs/             # Документация (Docusaurus)
└── packages/
    ├── ui-kit/           # Общие компоненты
    ├── eslint-config/    # Общие настройки линтера
    └── core-utils/       # Общая бизнес-логика
```

### Конфигурация Workspace

Чтобы это заработало, например в **pnpm**, в корне репозитория создается файл `pnpm-workspace.yaml`:
```yaml
packages:
  # Говорим pnpm, что всё внутри этих папок — это пакеты монорепозитория
  - 'apps/*'
  - 'packages/*'
```

Когда вы запускаете `pnpm install` в корне, менеджер читает этот файл, обходит все подпапки, анализирует их зависимости и скачивает их в единый гигантский **корневой `node_modules`** (Hoisting). Это экономит гигабайты места и гарантирует, что везде используется одна версия React.

## Неочевидные нюансы и трейдоффы

1. **Root Dependencies vs Package Dependencies:** В монорепе есть два уровня зависимостей. Инструменты (Prettier, ESLint, TypeScript, Turborepo) обычно ставятся в *корневой* `package.json`, так как они общие для всего проекта. А вот специфичные библиотеки (React, Lodash) ставятся строго в `package.json` *конкретного* пакета, чтобы сохранить инкапсуляцию.
2. **Вложенность:** Паттерн `apps/*` работает только на один уровень вглубь. Если у вас сложная структура с подпапками (например, `packages/frontend/ui` и `packages/backend/utils`), нужно использовать паттерн с двойной звездочкой: `packages/**`.
3. **Изоляция:** Разделение на `apps` и `packages` логическое. Пакетный менеджер не знает разницы — для него это всё просто "workspaces". Контроль за тем, чтобы `packages` не импортировали `apps`, лежит на разработчике и линтерах (Dependency Constraints).
