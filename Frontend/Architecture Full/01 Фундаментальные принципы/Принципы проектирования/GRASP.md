
**GRASP (General Responsibility Assignment Software Patterns)** — это набор из 9 шаблонов проектирования, которые помогают разработчику правильно распределить обязанности между классами, функциями и компонентами.

---

## 1. Information Expert (Информационный эксперт)
> Обязанности должны быть возложены на тот объект, который владеет максимумом информации для их выполнения.

В компонентном API это определяет, **где должен лежать стейт (state)**.
*   **Пример:** Если компонент списка товаров должен считать общую сумму корзины, стейт с выбранными товарами должен лежать в корзине (информационном эксперте), а не в каждой индивидуальной карточке товара.

## 2. Creator (Создатель)
> Определяет, кто должен создавать новый экземпляр класса/компонента.

Элемент $A$ должен создавать элемент $B$, если:
*   $A$ содержит или агрегирует $B$ (например, компонент `Table` создает `TableRow` и `TableHeader`).
*   $A$ имеет данные, необходимые для инициализации $B$.

## 3. Controller (Контроллер)
> Отвечает за обработку системных событий.

В современном фронтенде роль контроллеров выполняют **кастомные React-хуки** или **слайсы стейт-менеджеров** (Zustand/Redux).
*   **Принцип:** Компонент разметки (UI view) ловит клик пользователя и сразу передает его в хук-контроллер (`useLoginForm`), который содержит логику валидации, отправки запросов и обработки ошибок. UI-компонент остается чистым и тупым.

## 4. Low Coupling (Слабая зацепление)
> Распределяйте обязанности так, чтобы модули как можно меньше зависели друг от друга.

Если два компонента жестко связаны, изменения в одном из них неизбежно сломают второй.
*   *Решение на фронтенде:* Использовать стандартные интерфейсы данных, избегать глубокой вложенности зависимостей, передавать обработчики кликов как пропсы (`onClick`), а не импортировать логику родителя внутрь ребенка.

## 5. High Cohesion (Высокая связность / Сплоченность)
> Логика внутри модуля должна быть максимально сфокусирована на одной задаче.

Каждая функция, хук или компонент должен решать одну узкую задачу, но делать это качественно. Если в вашем хуке `useAuth` внезапно появляется логика форматирования цен — это признак низкого сцепления. Данную логику нужно вынести в утилитарный хелпер.

## 6. Polymorphism (Полиморфизм)
> Обработка альтернативных поведений на основе типов с помощью полиморфных объектов, а не условий `if/switch`.

В дизайне компонентов это выражается в создании полиморфного API (например, `Button as="a"` или `asChild` паттерн), либо в рендере компонентов по карте типов:

```tsx
// Вместо длинного switch-case:
const COMPONENT_MAP = {
  text: TextField,
  select: SelectField,
  checkbox: CheckboxField
};

function DynamicField({ type, ...props }) {
  const Component = COMPONENT_MAP[type] || DefaultField;
  return <Component {...props} />;
}
```

## 7. Pure Fabrication (Чистая выдумка / Синтетический класс)
> Создание искусственного класса/модуля, который не представляет концепцию предметной области, для обеспечения слабой связанности и высокого сцепления.

*   **Пример:** Логгеры ошибок (Sentry-клиент), API-клиенты (Axios-wrapper), трекеры аналитики. Они не являются частью бизнес-домена приложения, но изолируют внешние API от нашего кода.

## 8. Indirection (Посредник)
> Слабая связанность между объектами достигается за счет введения промежуточного звена.

*   **Пример:** React Context API, паттерн Event Bus (шина событий) или использование адаптеров в чистой архитектуре. UI общается не напрямую с сетевым модулем, а через промежуточный слой Context Provider.

## 9. Protected Variations (Защищенные изменения)
> Изолируйте элементы от изменений других элементов с помощью интерфейсов.

*   **Пример:** Использование TypeScript интерфейсов для API ответов. Если бэкендеры поменяют формат ответа, мы скорректируем только слой десериализации (адаптер), защитив всю остальную логику UI от падений.
