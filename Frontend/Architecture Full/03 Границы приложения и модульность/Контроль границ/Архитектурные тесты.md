# Архитектурные тесты

Архитектурные тесты — это вид автоматизированного тестирования (наравне с Unit и E2E), цель которого — проверить не логику работы кода, а **структуру приложения и соблюдение архитектурных правил**.

## Какую боль решаем?

Обычно архитектура держится на двух столпах: диаграммах в Wiki (которые никто не читает) и памяти тимлида (который уходит в отпуск).
Когда на проект приходит новичок, он не знает правил. Он пишет код так, как привык на прошлом месте работы. 
Например, он решает импортировать UI-компонент "Корзина" прямо в Redux-редьюсер (да, бывает и такое), или использует библиотеку для форматирования дат там, где это запрещено.

Если линтеры (типа `eslint-plugin-boundaries`) справляются с проверкой импортов, то архитектурные тесты могут проверять более сложные инварианты структуры.

## Как это работает на практике

Во фронтенде архитектурные тесты часто пишут с использованием Jest и библиотек для статического анализа (например, `dependency-cruiser` или кастомных скриптов на базе AST). В экосистеме Java есть популярный инструмент `ArchUnit`, во фронтенде его аналоги только набирают силу (например, `ts-arch`).

**Пример архитектурного теста (Псевдокод):**
```typescript
import { Architecture } from 'some-arch-tester';

describe('Frontend Architecture', () => {
  it('Слой UI не должен зависеть от API-клиентов', async () => {
    const rules = Architecture.define()
      .filesIn('src/ui')
      .shouldNotDependOn('src/api');
      
    await rules.check(); // Упадет, если есть нарушение
  });

  it('Все Redux-слайсы должны заканчиваться на *Slice.ts', () => {
    // ... логика проверки нейминга файлов
  });
});
```

## Неочевидные нюансы и трейдоффы

1. **Оверхед на поддержку.** Архитектура меняется. Если вы решили переименовать слой `features` в `domains`, вам придется не только перенести файлы, но и переписать все архитектурные тесты. Часто разработчики просто удаляют падающие тесты, чтобы "не мешали релизу".
2. **Линтер против Тестов.** Во фронтенде граница между архитектурными тестами и плагинами для ESLint очень размыта. В 90% случаев настроить ESLint-правила (например, `no-restricted-imports`) проще и эффективнее, чем писать отдельные Jest-тесты. Тесты нужны только для сложной, многошаговой валидации (например, "в модуле обязательно должен быть файл `index.ts`").
3. **Где применимо:** Enterprise-проекты с жесткой структурой (Feature-Sliced Design, Clean Architecture), над которыми работает много разных команд, и цена архитектурной ошибки крайне высока.
