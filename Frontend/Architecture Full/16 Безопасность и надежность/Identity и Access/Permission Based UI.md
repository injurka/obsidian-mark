# Permission-Based UI

## Суть и решаемая боль
Представьте приложение, где администратор видит кнопку "Удалить пользователя", а обычный менеджер — нет. Боль возникает, когда интерфейс начинает обрастать сотнями проверок вида `if (user.role === 'admin' || user.role === 'superadmin')`. При добавлении новой роли (например, 'moderator', которому тоже можно удалять) приходится искать по всему коду эти `if`-ы и дописывать их. Это нарушает DRY, приводит к багам и утечкам (кнопка видна, когда не должна).

**Permission-Based UI** — это паттерн, при котором фронтенд вообще не проверяет РОЛИ. Он проверяет ПРАВА (разрешения, permissions). Бэкенд вычисляет, что может делать текущий пользователь, и отдает массив прав (например, `['users:read', 'users:delete']`). Фронтенд просто сопоставляет этот массив с элементами интерфейса.

## Как это работает на практике

Архитектура состоит из трех частей:
1. **Точка получения прав:** При логине или загрузке приложения запрашиваем список `permissions`.
2. **Контекст/Стор:** Храним массив в памяти (React Context, Zustand, Redux).
3. **Guard-компоненты:** Обертки вокруг UI-элементов, которые рендерят `children` только если в сторе есть нужное право.

```mermaid
graph TD
    API[Backend API] -->|Отдает: ['article:edit', 'comment:delete']| Store((Permissions Store))
    Store --> Hook(usePermissions)

    end
```

## Примеры кода

**Антипаттерн (Role-based в UI):**
```tsx
const ArticleActions = ({ user }) => {
  // Жесткая привязка к ролям. Больно масштабировать.
  const isManager = user.role === 'manager' || user.role === 'admin';
  
  return (
    <div>
      {isManager && <button>Редактировать</button>}
    </div>
  )
}
```

**Правильное решение (Permission-based через компонент-обертку):**
```tsx
// 1. Создаем переиспользуемый Guard
const Can = ({ perform, children, fallback = null }) => {
  const { permissions } = useAuth(); // Получаем ['article:edit', ...]
  
  if (permissions.includes(perform)) {
    return children;
  }
  return fallback;
};

// 2. Используем в UI. Никакого знания о ролях!
const ArticleActions = () => {
  return (
    <div>
      <Can perform="article:edit">
        <button>Редактировать</button>
      </Can>
      
      <Can perform="article:delete">
        <button className="danger">Удалить</button>
      </Can>
    </div>
  )
}
```

## Неочевидные нюансы и трейдоффы
- **Скрытие UI — это не безопасность:** Если вы скрыли кнопку "Удалить" через Permission-Based UI, злоумышленник всё еще может найти ID кнопки в коде и отправить fetch-запрос в консоли. Бэкенд **всегда** должен дублировать проверку прав на своей стороне.
- **Обновление прав в реальном времени:** Если админ заберет право у пользователя, пока тот сидит в приложении, фронтенд не узнает об этом до обновления страницы (или до `403` ошибки от сервера). Хорошая практика — перехватывать `403` в Axios/Fetch и триггерить рефетч списка прав.
- **Wildcards:** Иногда бэкенд возвращает права со звездочками, например `users:*` (доступ ко всему в модуле users). Фронтенду придется реализовать логику матчинга регулярками (напр. библиотекой типа `casl` или простым сплитом по `:`).
