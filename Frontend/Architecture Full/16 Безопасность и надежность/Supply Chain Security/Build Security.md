# Build Security (Безопасность сборки)

## Суть и решаемая боль
Мы привыкли думать о безопасности в контексте "Хакер ломает наш сервер". Но что, если хакер сломает ваш процесс сборки (Webpack/Vite) и встроит криптомайнер прямо в ваш минифицированный `bundle.js`? Боль заключается в том, что разработчики слепо доверяют инструментам сборки (компиляторам, плагинам, лоадерами), имеющим полный доступ к файловой системе и переменным окружения.

**Build Security** — это концепция защиты пайплайна, в котором исходный код превращается в готовый артефакт. Цель — гарантировать, что то, что мы написали в IDE, в неизменном (без вредоносных инъекций) виде доедет до браузера пользователя.

## Как это работает на практике

Сборщик (Webpack, Rollup, Vite) — это обычный Node.js процесс. Если один из сотен npm-плагинов внутри вашего `webpack.config.js` окажется вредоносным (Malicious Package), он сможет:
1. Украсть `.env` файлы с AWS ключами и отправить их на удаленный сервер.
2. Незаметно дописать код во время трансформации AST (Abstract Syntax Tree) в ваш бандл.

```mermaid

    Source[Source Code] --> Builder{Webpack / Vite}
    Env[.env Secrets] --> Builder
    Malicious[Вредоносный плагин] -.->|Читает .env| Hacker[Сервер Хакера]
    Malicious -.->|Инжектит код| Builder
```

## Примеры кода и подходов

**Антипаттерн (Неконтролируемое чтение окружения):**
```javascript
// webpack.config.js
// Если вы используете плагины, которые "пылесосят" все переменные окружения
// и вшивают их в бандл, вы можете случайно отдать API ключи бэкенда на фронт.
new webpack.EnvironmentPlugin(Object.keys(process.env)) 
```

**Правильное решение (Изоляция и явная передача):**
```javascript
// Vite делает это из коробки: он вшивает в бандл ТОЛЬКО те переменные,
// которые начинаются с префикса VITE_. Остальные (например, ключи БД) в безопасности.
import { defineConfig } from 'vite';

export default defineConfig({
  // Хорошая практика: сканировать бандл на известные уязвимости перед деплоем
  plugins: [react(), myCustomLinter()],
  // Ограничиваем доступ сборщика только к нужным папкам
  server: { fs: { strict: true } }
});
```

## Неочевидные нюансы и границы применимости
- **Reproducible Builds (Воспроизводимые сборки):** Одна из метрик безопасности сборки — это возможность собрать проект на двух разных машинах из одного коммита и получить **побайтово идентичный** результат (одинаковый хэш). Если хэши разные (из-за таймстемпов, разных версий Node или плагинов) — сложнее доказать, что в бандл не вмешались.
- **Риски Postinstall-скриптов:** NPM-пакеты могут выполнять произвольный bash-скрипт при установке. Вредоносный плагин для Babel может украсть ключи еще до того, как вы запустите `npm run build`. Спасает флаг `--ignore-scripts` при установке и использование изоляции (Docker) для сборок.
- **Оверхед:** Защита пайплайна требует настройки жестких политик (например, отключение доступа в интернет для контейнера, в котором крутится Webpack, чтобы он не смог выгрузить украденные ключи). Это сложно и применяется в основном в FinTech и Enterprise.
