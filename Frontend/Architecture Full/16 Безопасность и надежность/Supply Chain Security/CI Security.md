# CI/CD Security (Безопасность пайплайнов)

## Суть и решаемая боль
Continuous Integration (GitHub Actions, GitLab CI) — это сердце разработки. Именно здесь гоняются тесты, собирается бандл и деплоится код. Боль в том, что CI-сервер обладает **абсолютной властью**: у него есть ключи от AWS, токены от NPM и доступы к продакшен-серверам. Если хакер получит доступ к CI — он получит доступ ко всей компании (Supply Chain Attack).

**CI Security** — это набор практик, защищающих процессы автоматизации от утечек секретов, вредоносных пулл-реквестов (PR) и компрометации раннеров (Runners).

## Как это работает на практике

На фронтенде основные векторы атак на CI:
1. Вредоносный PR: Злоумышленник форкает ваш Open Source проект, пишет скрипт воровства секретов в тестах и делает PR. Ваш CI автоматически запускает тесты и отдает секреты хакеру.
2. Утечка токенов в логах: Случайный `console.log(process.env)` в тестах печатает NPM_TOKEN в публичные логи GitHub Actions.

```mermaid
graph TD
    PR[Pull Request от Незнакомца] --> CI{CI Runner}
    CI -->|Запускает npm test| Tests[Unit Tests]
    
    Tests -.->|Пытается прочитать $NPM_TOKEN| Sandbox[Sandbox / Изоляция]
    
    Sandbox -->|Ошибка!| Safe[Секреты не переданы в PR от форков]
    Sandbox -.->|Успех (Антипаттерн)| Pwned[Хакер украл токен]
```

## Примеры кода и политик

**Антипаттерн (Раздача секретов всем подряд):**
```yaml
# .github/workflows/test.yml
on: [pull_request] # Запускается на ЛЮБОЙ PR!

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm install && npm test
        env:
          AWS_ACCESS_KEY: ${{ secrets.AWS_ACCESS_KEY }} # КАТАСТРОФА! Хакер добавит в тесты console.log(process.env.AWS_ACCESS_KEY) в своем PR и украдет ключ!
```

**Правильное решение (Принцип наименьших привилегий в CI):**
```yaml
# .github/workflows/deploy.yml
on:
  push:
    branches: [ main ] # Секреты доступны только при пуше в main (мердж делают только доверенные мейнтейнеры)

# Явно отбираем права у GITHUB_TOKEN (по умолчанию он может пушить код)
permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm ci
      - run: npm run build
      
      # Используем секреты ТОЛЬКО на шаге деплоя, а не глобально
      - name: Deploy to S3
        run: aws s3 sync ./dist s3://my-bucket
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_KEY }}
```

## Неочевидные нюансы и границы применимости
- **OIDC (OpenID Connect) вместо статических ключей:** Хранить долгоживущие AWS-ключи в секретах GitHub — это легаси. Современный подход — использовать OIDC. GitHub и AWS "договариваются" между собой, и AWS выдает временный токен (на 15 минут) конкретному пайплайну. Утекать просто нечему.
- **Маскировка логов:** Современные CI-системы автоматически маскируют секреты в логах (заменяют их на `***`). Но это не спасает, если хакер закодирует секрет в base64 перед выводом в консоль: `console.log(btoa(process.env.SECRET))`.
- **Зависимости в CI (Actions):** Плагин `uses: some-guy/cool-action@master` может измениться в любую секунду. Если автор зальет туда вредоносный код, ваш CI его скачает. Безопасный подход — привязывать экшены к конкретному SHA-хэшу коммита, а не к ветке или тегу: `uses: actions/checkout@a12a30...`.
