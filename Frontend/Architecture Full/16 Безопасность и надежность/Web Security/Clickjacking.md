# Clickjacking (UI Redressing)

Clickjacking (от слов *Click* и *Hijacking*) — это тип атаки, при котором злоумышленник обманом заставляет пользователя кликнуть на элемент невидимой страницы, наложенной поверх видимой. Это классическая история о том, как доверие к визуальному интерфейсу оборачивается катастрофой.

## 🎭 Боль: Иллюзия контроля

Представьте: вы заходите на сайт `free-puppies.com` и видите кнопку «Посмотреть видео со щенком». Но злоумышленник загрузил в невидимом `iframe` поверх этой кнопки страницу вашего банка, где на том же самом месте находится кнопка «Перевести все деньги». Вы кликаете на щенка, а в реальности — подтверждаете перевод, ведь в вашем браузере уже есть активная сессия банка.

## 🛡️ Как мы это решаем на практике

Чтобы защититься от Clickjacking, приложение должно запретить браузеру отображать себя внутри `iframe` на чужих доменах. Для этого исторически использовался заголовок `X-Frame-Options`, а сегодня — директива `frame-ancestors` в Content Security Policy (CSP).

### ❌ Антипаттерн (Защита через JS / Frame Busting)

В эпоху до появления защитных заголовков разработчики пытались бороться с этим с помощью JavaScript, проверяя, не находится ли их сайт во фрейме:

```javascript
// 🚨 ПЛОХО: Frame Busting скрипты легко обойти
if (top !== self) {
  top.location = self.location;
}
```
**Почему это ломается:** Злоумышленник может загрузить `iframe` с атрибутом `sandbox="allow-forms allow-scripts"`, запретив выполнение `top.location`, и ваша JS-защита просто перестанет работать.

### ✅ Правильный подход (HTTP-заголовки)

Современный и надежный способ — сказать самому браузеру, чтобы он блокировал рендеринг:

```http
# Строгий запрет: сайт вообще нельзя открывать во фреймах (Рекомендуется по умолчанию)
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none';

# Разрешить только на том же домене
X-Frame-Options: SAMEORIGIN
Content-Security-Policy: frame-ancestors 'self';

# Разрешить конкретным партнерам (X-Frame-Options так не умеет)
Content-Security-Policy: frame-ancestors https://partner.com https://*.internal-tools.com;
```

## ⚖️ Неочевидные нюансы и трейдоффы

### 1. Конфликты легального встраивания
Если вы разрабатываете B2B-продукт (например, виджет чата, форму оплаты или аналитический дашборд), клиенты *захотят* встраивать вас через `iframe`. В этом случае жесткий `DENY` сломает ваш бизнес.
**Решение:** Вам придется динамически формировать заголовок `CSP: frame-ancestors`, подставляя туда домен конкретного клиента, который запросил виджет.

### 2. `X-Frame-Options` vs `CSP`
`X-Frame-Options` (XFO) устарел, но директива `frame-ancestors` в CSP не поддерживалась в старых браузерах (IE). Сегодня лучшая практика — отправлять **оба заголовка**. Современные браузеры отдадут приоритет CSP и проигнорируют XFO.

### 3. Защита от Drag-and-Drop (Data Theft)
Clickjacking используется не только для кликов. Злоумышленник может заставить пользователя выделить невидимый текст (например, токен сессии на вашей странице) и перетащить его в `input` на своем сайте (Drag-and-Drop). Запрет iframe решает и эту проблему.

### 4. Ограничения SameSite Cookie
С внедрением атрибута `SameSite=Lax` (или `Strict`) для Cookie, Clickjacking стал менее эффективным, так как куки не отправляются в сторонние `iframe`. Однако полагаться только на `SameSite` нельзя: некоторые атаки используют старые сессии (если куки живут долго и выставлены в `None`) или не требуют авторизации (например, накрутка лайков/просмотров). Заголовки CSP обязательны.
