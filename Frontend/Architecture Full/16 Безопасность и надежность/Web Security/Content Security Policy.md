# Content Security Policy (CSP)

Content Security Policy (CSP) — это мощный эшелон глубокой защиты (defense-in-depth), позволяющий владельцам сайта декларативно указать браузеру, какие ресурсы разрешено загружать и выполнять. Это ультимативный инструмент для предотвращения XSS-атак (Cross-Site Scripting) и внедрения вредоносного контента.

## 🩹 Боль: Доверие по умолчанию

Браузер по своей природе наивен. Если он встречает на странице тег `<script src="http://zlo.com/hack.js"></script>`, он скачает его и выполнит, предполагая, что это инициатива разработчика. Если злоумышленник найдет способ внедрить свой скрипт на вашу страницу (например, через уязвимый инпут в комментариях), браузер послушно отдаст этому скрипту ваши куки и доступ к DOM.

CSP решает эту проблему, заменяя модель «доверяю всему, что на странице» на модель **строгого белого списка**.

### Как работает CSP в случае атаки

```mermaid

    participant Server as Наш Сервер
    participant Browser as Браузер пользователя

    Server-->>Browser: Отдает страницу с инжектом

    Browser--xZlo: ❌ БЛОКИРОВКА! (zlo.com нет в белом списке CSP)
    Note right of Browser: Выбрасывает ошибку в консоль:<br/>"Refused to load the script..."
    Browser->>Server: (Опционально) Отправляет отчет о нарушении CSP
```

## 🛠 На практике: От антипаттернов к идеалу

Политика задается через HTTP-заголовок `Content-Security-Policy` (реже — через `<meta>` тег).

### ❌ Антипаттерн: Дырявый CSP (Убивает весь смысл)

Зачастую разработчики, столкнувшись с тем, что CSP ломает их приложение (например, инлайн-стили или скрипты из Google Tag Manager), сдаются и добавляют `unsafe-inline` и `unsafe-eval`. 

```http
# 🚨 ПЛОХО: Этот CSP не защищает от XSS, так как разрешает инлайн-скрипты!
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://*;
```

### ✅ Хорошая практика: Strict CSP на базе Nonce

Современный подход для динамических приложений — использовать криптографические одноразовые токены (Nonce). 

1. Сервер генерирует случайный токен на каждый запрос (например, `r@nd0m123`).
2. Добавляет его в заголовок CSP.
3. Добавляет его атрибутом `nonce="..."` ко всем легальным `<script>`.

```http
# Заголовок
Content-Security-Policy: script-src 'nonce-r@nd0m123' 'strict-dynamic'; object-src 'none'; base-uri 'none';
```

```html
<!-- Браузер выполнит: nonce совпадает -->
<script nonce="r@nd0m123" src="/bundle.js"></script>

<!-- Браузер заблокирует: злоумышленник не знает nonce для текущего запроса -->
<script>alert('Hacked!');</script> 
```
*Директива `'strict-dynamic'` позволяет доверенным скриптам (с nonce) динамически подгружать другие скрипты, что решает проблему с современными бандлерами (Webpack/Vite).*

## ⚖️ Скрытые трейдоффы и границы применимости

### 1. Огромный оверхед на внедрение в legacy
Внедрить строгий CSP в существующий крупный проект, которому 5-10 лет — это ад. Инлайн-стили (`<div style="...">`), инлайн-скрипты (`onclick="..."`), динамические `eval()` внутри старых библиотек — всё это сломается.
* **Как решать:** Использовать заголовок `Content-Security-Policy-Report-Only`. Он не блокирует ресурсы, а только тихо отправляет JSON-отчеты о нарушениях на ваш эндпоинт (например, в Sentry). Вы собираете логи месяц, правите код, и только потом включаете блокировку.

### 2. Проблема со сторонними виджетами (Third-party)
Маркетологи обожают вставлять пиксели трекинга, чаты поддержки и виджеты A/B тестирования. Эти скрипты часто загружают ресурсы с десятков непредсказуемых доменов. 
Попытка поддерживать белый список доменов превратится в бесконечную игру в "кошки-мышки". Именно поэтому переход на архитектуру Strict CSP (`nonce` + `strict-dynamic`) предпочтительнее бесконечных списков доменов.

### 3. SPA (Single Page Applications) и Nonce
Если вы раздаете статический SPA (React/Vue) через CDN (Nginx/S3), вы не можете генерировать `nonce` на лету для каждого запроса, так как `index.html` закеширован.
* **Альтернатива для SPA:** Вместо `nonce` использовать хэши содержимого. При сборке (Webpack) вычисляется SHA-256 хэш от инлайн-скрипта инициализации и вшивается в заголовок CSP. Но для подключаемых `.js` файлов придется полагаться на список доменов.

### 4. Не панацея
CSP не защитит от CSRF-атак, не спасет от утечки данных, если уязвимость позволяет извлечь их внутри доверенного скрипта, и не защитит от DOM XSS (здесь нужен Trusted Types). Это второй эшелон обороны, страховка на случай, если вы всё же пропустили XSS.
