
Создание переиспользуемых компонентов (UI-Kit) требует проектирования понятных, гибких и отказоустойчивых интерфейсов (props). Плохо спроектированный компонент быстро превращается в монолит, обвешанный десятками противоречивых флагов.

---

## 1. Правила хорошего дизайна Props

### 1.1. Плоская структура пропсов (Flat Props)
Избегайте передачи сложных вложенных объектов в пропсы, если компонент рендерит только плоские значения.
*   *Плохо:* `<Card data={{ title: 'Title', image: { url: '...' } }} />` (При изменении структуры объекта API карточка сломается).
*   *Хорошо:* `<Card title="Title" imageUrl="..." />` (Компонент изолирован и понятен).

### 1.2. ПроектируйтеControlled и Uncontrolled состояния
Компоненты ввода (инпуты, табы, аккордеоны) должны поддерживать два режима работы:
1.  **Uncontrolled (неконтролируемый):** компонент сам управляет своим состоянием (удобно для быстрого использования). Передается `defaultValue` или `defaultExpanded`.
2.  **Controlled (контролируемый):** родительский компонент полностью управляет состоянием через пропсы. Передаются `value`/`expanded` и обработчик `onChange`/`onToggle`.

## 2. Паттерны проектирования сложных компонентов

### 2.1. Паттерн Compound Components (Составные компоненты)
Используется, когда группа компонентов должна работать совместно, разделяя общее неявное состояние, но при этом обеспечивая гибкость верстки для разработчика.

**Пример (Select-меню):**
Мы хотим дать разработчику возможность вставлять иконки, разделители или кастомные заголовки внутрь выпадающего списка.

```tsx
// Использование паттерна:
export function App() {
  return (
    <Select defaultValue="ru">
      <Select.Trigger />
      <Select.Content>
        <Select.Option value="ru">Русский</Select.Option>
        <Select.Option value="en">English</Select.Option>
        <Select.Divider />
        <Select.Option value="zh">Chinese</Select.Option>
      </Select.Content>
    </Select>
  );
}
```
*Под капотом:* Компонент `<Select>` создает React Context, хранящий выбранное значение и функцию его изменения. Компоненты `<Select.Option>` и `<Select.Trigger>` общаются с этим контекстом неявно, избавляя разработчика от необходимости прокидывать пропсы вручную.

### 2.2. Паттерн Headless UI (Логика без стилей)
Тенденция современного фронтенда — разделение логики поведения компонента (доступность, клавиатурная навигация, фокус) и его визуального оформления (CSS-стилей).

*   **Как это работает:** Библиотеки (Radix UI, Headless UI, React Aria) предоставляют готовые поведенческие скелеты компонентов с настроенными ARIA-атрибутами и логикой, но без единой строчки CSS.
*   **Плюс:** Разработчик получает 100% доступный по стандартам WCAG элемент (например, модальное окно), но может стилизовать его абсолютно любым способом (Tailwind, CSS-in-JS, CSS Modules), не ведя войну с дефолтными стилями библиотеки (как это часто бывает в Material UI или Ant Design).

## 3. Золотые правила проектирования UI-Kit (Lead Checklist)

*   **Имя пропсов по умолчанию:** Для булевых значений используйте префиксы `is`, `has`, `should` (например, `isDisabled`, `hasIcon`).
*   **События по стандартам:** Названия колбэков событий должны соответствовать нативным стандартам HTML (`onChange`, `onClick`, `onFocus`), а не придумывать свои (`onValueChange`, `onBtnClick`).
*   **Типизация:** Всегда типизируйте пропсы с помощью TypeScript. Если компонент оборачивает нативный HTML-тег, расширяйте его типы:
    ```typescript
    interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
      variant: 'primary' | 'secondary';
    }
    ```
