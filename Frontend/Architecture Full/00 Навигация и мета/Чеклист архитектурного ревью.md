# Чек-лист архитектурного ревью (Code Review Checklist)

Используйте этот чек-лист при проведении кросс-кодового или архитектурного ревью пул-реквестов (PR), чтобы гарантировать соблюдение системных границ и чистоту кода.

---

## 1. Модульные границы и импорты (FSD / Modularity)
* [ ] **Направление зависимостей:** Импортирует ли модуль код только с нижележащих слоев? (Например, `shared` не должен импортировать `entities`, а `entities` не должен зависеть от `features`).
* [ ] **Запрет горизонтальных импортов:** Отсутствуют ли перекрестные импорты между слайсами одного уровня (например, `entities/user` импортирует `entities/product`)?
* [ ] **Использование Public API:** Все ли внешние импорты осуществляются строго через корневой `index.ts` слайса? Глубокие импорты (например, `/entities/product/ui/Card.tsx`) запрещены.
* [ ] **Shared Kernel:** Если есть общий код между модулями, вынесен ли он в `shared` или официально оформлен как Shared Kernel?

## 2. Управление состоянием (State Management)
* [ ] **Локализация стейта:** Находится ли состояние максимально близко к месту его использования? (Не выносится ли локальный UI-стейт дропдауна в глобальный Redux/Zustand?).
* [ ] **Разделение типов стейта:** Разделены ли серверные данные (TanStack Query) и клиентские UI-настройки (Zustand)?
* [ ] **Derived State (Производный стейт):** Вычисляются ли зависимые значения «на лету» (с `useMemo` при необходимости), вместо того чтобы синхронизировать их через эффекты (`useEffect`) в отдельные стейт-переменные?
* [ ] **URL State:** Перенесены ли параметры фильтрации, сортировки, активных табов и пагинации в URL-параметры (`?page=2`) для возможности шаринга ссылки?

## 3. Дизайн компонентов и API (Component & UI Design)
* [ ] **Single Responsibility (SRP):** Не делает ли компонент слишком много? (Например, если компонент рендерит UI и сам делает сетевые запросы, сетевые запросы должны быть вынесены в хук или фасад).
* [ ] **Open/Closed (OCP):** Открыт ли компонент для расширения (через `children`, `slots` или полиморфизм) и закрыт для модификации (без кучи флагов вроде `isAdmin`, `isLink`, `isRedInside`)?
* [ ] **Принцип подстановки Лисков (LSP):** Если это кастомная кнопка/инпут, расширяет ли она стандартные HTML-атрибуты элемента (`React.ButtonHTMLAttributes`) и корректно ли прокидывает их?
* [ ] **Interface Segregation (ISP):** Принимает ли компонент только те пропсы, которые ему действительно нужны (например, `Avatar` принимает `avatarUrl: string`, а не весь объект `user: User`)?
* [ ] **Точки расширения и темы:** Не захардкожены ли цвета, отступы и шрифты? Используются ли дизайн-токены/CSS-переменные?

## 4. Сетевое взаимодействие и отказоустойчивость
* [ ] **Изоляция сетевого слоя:** Вынесены ли эндпоинты и запросы в отдельные API-клиенты или функции? (Прямые вызовы `fetch/axios` в компонентах запрещены).
* [ ] **Валидация контрактов:** Валидируются ли входящие данные от бэкенда на границе сети (например, с помощью Zod-схем), чтобы защитить UI от неожиданных изменений API?
* [ ] **Обработка ошибок:** Добавлены ли границы ошибок (`Error Boundaries`) на уровне роутов или виджетов, чтобы падение одного компонента не ломало все приложение?
* [ ] **Индикация состояний:** Предусмотрены ли состояния загрузки (Skeletons/Spinners), пустых экранов (Empty States) и ошибок (Error States)?

## 5. Производительность (Performance Budget)
* [ ] **Размер бандла:** Не импортируются ли тяжелые библиотеки целиком (например, весь `lodash` вместо конкретных функций)?
* [ ] **Ленивая загрузка (Lazy Loading):** Применяется ли динамический импорт (`React.lazy`, `next/dynamic`) для тяжелых модалок, графиков и некритичных страниц?
* [ ] **Лишние ререндеры:** Защищены ли тяжелые вычисления с помощью `useMemo`/`useCallback`? Правильно ли расставлены ключи `key` в списках?
