
# Tree Shaking и Chunking под капотом

Современные сборщики решают две главные задачи оптимизации:
1. **Tree Shaking:** Выбросить из итогового файла всё, что не используется.
2. **Chunking (Code Splitting):** Разрезать то, что используется, на оптимальные куски, чтобы не заставлять браузер качать всё сразу.

---

## 1. Tree Shaking (Удаление мертвого кода)

Термин «встряхивание дерева» означает: представьте, что ваше приложение — это дерево. Исходный код (ваши `import` и `export`) — это ветви. Мертвый код (неиспользуемые функции) — это сухие листья. Сборщик "трясет" дерево, и сухие листья опадают.

### Как это работает под капотом?

1. **Анализ AST (Abstract Syntax Tree):** Сборщик парсит ваш код и строит граф зависимостей.
2. **Маркировка (Marking):** Он начинает с точки входа (`index.js`) и рекурсивно идет по всем `import`. Каждому импортированному экспорту он ставит метку «используется».
3. **Очистка (Sweeping):** На этапе минификации (обычно этим занимается Terser или esbuild) все экспорты, которые не получили метку, просто вырезаются из финального кода.

### Главное условие: ESM vs CommonJS
Tree Shaking **работает только с ECMAScript Modules (ESM)** — `import` / `export`. 
Почему? Потому что ESM **статичны**. Сборщик может прочитать код и до его выполнения точно знать, что импортируется.

CommonJS (`require()`) **динамичен**.
```javascript
// Сборщик не может предсказать, какой модуль загрузится, 
// поэтому он обязан включить в бандл оба. Tree Shaking невозможен!
const module = require(condition ? './a.js' : './b.js');
```

### Проблема: Side Effects (Побочные эффекты)
Самая частая причина, почему Tree Shaking "ломается" (bailout).
*Побочный эффект* — это код, который выполняет какие-то действия при самом факте его импорта, даже если вы не используете экспортируемые из него функции.
Например: модификация глобального объекта `window`, прототипов (`Array.prototype.customMap = ...`), или импорт CSS.

Если сборщик видит импорт:
```javascript
import { add } from 'lodash-es';
```
Он думает: *"Я могу удалить функцию `subtract`, так как она не импортируется. Но безопасно ли вообще не выполнять файл `subtract.js`? Вдруг он добавляет что-то в `window`?"*
Из-за страха сломать приложение, сборщик оставляет код.

### Решение: Флаг `"sideEffects"` в `package.json`
Чтобы дать сборщику зелёный свет на удаление целых файлов, в `package.json` библиотеки (или вашего проекта) указывается флаг:
```json
{
  "name": "my-ui-kit",
  "sideEffects": false
}
```
`false` означает: *"В этом пакете нет побочных эффектов. Если функция из файла не импортируется, смело удаляй весь файл целиком"*.
*(Если в проекте есть CSS, пишут массив: `"sideEffects": ["*.css", "*.scss"]`, чтобы сборщик не вырезал стили).*

## 2. Chunking (Code Splitting / Разделение кода)

Если Tree Shaking уменьшает общий объем кода, то Chunking управляет тем, **как** этот код доставляется в браузер.

### Как это работает под капотом (Точки разделения)?

Основа чанкинга — **динамический импорт `import()`**. 
Когда парсер сборщика (Webpack/Rollup) идет по AST и встречает статический импорт (`import x from './x'`), он склеивает модули вместе. 
Но когда он встречает динамический импорт:
```javascript
button.addEventListener('click', async () => {
  const { Modal } = await import('./Modal.js');
});
```
Сборщик создает **Split Point (Точку разделения)**:
1. Код файла `Modal.js` и все его локальные зависимости выносятся в отдельный физический файл (например, `chunk-a1b2c.js`).
2. В основном бандле вместо кода `Modal.js` сборщик оставляет мини-рантайм (runtime). Этот рантайм знает, что при вызове функции нужно вставить в `<head>` тег `<script src="/chunk-a1b2c.js"></script>`, дождаться его загрузки, и только потом разрешить (resolve) Promise.

### Виды чанков

1. **Entry Chunk (Входной чанк):** Ваш `main.js`. Содержит рантайм сборщика и логику инициализации приложения.
2. **Async Chunks (Асинхронные чанки):** Файлы, созданные через `import()`. Загружаются по требованию.
3. **Vendor Chunk (Чанк зависимостей):** Код из `node_modules` (React, Vue, lodash). 
   *Зачем выносить vendors?* Код библиотек меняется редко. Если вынести его в отдельный чанк `vendor.[hash].js`, браузер закэширует его на год. При релизе новых фич пользователи скачают только крошечный `app.[hash].js`.

### Дедупликация (Shared Chunks)
Представьте:
*   Страница `/about` асинхронно импортирует библиотеку `Chart.js`.
*   Страница `/dashboard` тоже асинхронно импортирует `Chart.js`.

Если сборщик глупый, он положит код `Chart.js` и в чанк "about", и в чанк "dashboard". Пользователь скачает библиотеку дважды.
**Как сборщик решает это (SplitChunksPlugin в Webpack / manualChunks в Rollup):**
Он анализирует граф зависимостей. Если модуль весит больше определенного лимита (например, > 20kb) и используется в 2+ асинхронных чанках, сборщик выносит его в **третий (общий) чанк**. 
Теперь при переходе на `/about` браузер параллельно скачает `chunk-about.js` и `chunk-shared-chart.js`.

## 3. Золотые правила для Senior-разработчика

Понимание того, как это работает под капотом, диктует строгие архитектурные правила:

1. **Используйте Named Exports, а не Default.**
   ```javascript
   // ПЛОХО (default export): Сборщику трудно вырезать неиспользуемые методы из объекта.
   export default { add, subtract, multiply }; 
   
   // ХОРОШО (named exports): Каждая функция статична, Tree Shaking работает идеально.
   export const add = () => {};
   export const subtract = () => {};
   ```

2. **Не делайте "бочонки" (Barrel files) бездумно.**
   Файл `index.js`, который делает `export * from './a'; export * from './b';`, может сломать Tree Shaking в плохих сборщиках или если не настроен `sideEffects`. Если сомневаетесь — импортируйте напрямую из конкретного файла.

3. **Оптимизируйте размер бандла через Route-Level Splitting.**
   Во Vue Router / React Router компоненты страниц всегда должны оборачиваться в динамический импорт. Ни один пользователь не должен скачивать код личного кабинета, находясь на главной странице.

4. **Анализируйте графы сборок.**
   Регулярно используйте `webpack-bundle-analyzer` или `rollup-plugin-visualizer`. Ищите дублирование кода (например, когда разные пакеты тянут разные версии `lodash`, и они обе попадают в бандл) и следите, чтобы тяжелые библиотеки не попадали в Entry Chunk.
