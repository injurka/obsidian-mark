# Terraform и OpenTofu: Modules

## История и Боль
**Боль:** Копипаст инфраструктуры. Разворачивая пятый проект, вы замечаете, что код VPC, базы данных и EKS-кластера просто копируется из репозитория в репозиторий. При обновлении стандартов безопасности приходится править код в 10 местах.
**Решение:** Модули. Инкапсуляция логики и ресурсов в переиспользуемые блоки. Вы пишете код один раз, задаете переменные на вход и получаете готовый кусок инфраструктуры на выходе.

## Примеры
**Определение модуля (структура):**
```bash
tree modules/vpc
modules/vpc
├── main.tf
├── variables.tf
└── outputs.tf
```

**Вызов модуля (HCL):**
```hcl
module "vpc" {
  source = "git::https://github.com/company/terraform-modules.git//vpc?ref=v1.2.0"
  
  vpc_name = "prod-vpc"
  cidr     = "10.0.0.0/16"
  azs      = ["eu-central-1a", "eu-central-1b"]
}
```

## Day 2 Operations
1. **Версионирование модулей:** Всегда используйте теги версий (Git tags) при вызове модулей (`?ref=v1.2.0`). Это гарантирует иммутабельность.
2. **Тестирование модулей:** Используйте `terratest` (Go) или `tflint` для проверки контрактов модулей до их релиза.
3. **Обновление модулей:** При обновлении мажорной версии модуля, внимательно читайте changelog, планируйте `terraform plan` и будьте готовы к `moved` блокам, чтобы ресурсы не пересоздались.

## Антипаттерны
- **Модуль-бог (God Module):** Модуль, который создает "сразу всё" (VPC, базу, кластер, кэш). Их невозможно переиспользовать и очень сложно поддерживать. Разделяйте логику.
- **Хардкод значений:** Зашивание конкретных ID сетей или AMI внутри модуля вместо использования `variables.tf` или `data` сорсов.
- **Вложенность больше 2-х уровней:** Module A вызывает Module B, который вызывает Module C. Отладка и передача переменных превращается в ад.
