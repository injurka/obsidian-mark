# GitOps: Инфраструктура как код в динамике

## Какую боль мы решаем?
Представьте классическую пятницу: разработчик закинул фичу, DevOps запустил деплой через Jenkins, но продакшен упал. Выясняется, что кто-то пару недель назад руками поправил `ConfigMap` прямо в кластере («чтобы быстро починить баг»), и теперь конфигурации разошлись. Это называется *configuration drift* (дрейф конфигурации). Добавьте сюда отсутствие прозрачного аудита (кто и когда изменил инфраструктуру?), рутинные ручные деплои и страх перед релизами — это типичная боль классического подхода. 

GitOps решает эту проблему радикально: **Git становится единственным источником правды (Single Source of Truth).** Если изменения нет в Git — его нет в кластере.

## Как это работает?
GitOps строится на паттерне *Pull*, а не *Push*. Вместо того чтобы CI/CD сервер имел полные права на кластер и «пушил» туда изменения, внутри кластера работает специальный программный агент (например, Argo CD или Flux). Он непрерывно опрашивает Git-репозиторий и, если видит расхождения между желаемым состоянием (в Git) и фактическим (в кластере), автоматически приводит кластер к нужному виду (Reconciliation Loop).

## Примеры конфигурации и Best Practices

**Best Practice:** Использование манифестов, описывающих само приложение в парадигме GitOps.
Пример `Application` манифеста для Argo CD:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: 'https://github.com/my-org/gitops-repo.git'
    targetRevision: HEAD
    path: apps/frontend/overlays/production
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: production
  syncPolicy:
    automated:
      prune: true     # Авто-удаление ресурсов, которых больше нет в Git
      selfHeal: true  # Авто-восстановление, если кто-то руками изменит ресурс в кластере
```

**Антипаттерн:** Хранение секретов в открытом виде в Git. 
GitOps обязывает хранить все в Git, но хардкодить пароли от БД в репозиторий — прямой путь к утечке. 
*Решение:* Использование Sealed Secrets (Bitnami) или SOPS (Mozilla) совместно с AWS KMS/HashiCorp Vault. В Git лежат только зашифрованные блобы, которые расшифровываются уже внутри кластера.

## Неочевидные нюансы и Day 2 Operations

*   **Tradeoffs и Оверхед:** Внедрение GitOps требует дополнительного кластера для инструментов или усложняет существующий. Поддержка ArgoCD/Flux — это тоже работа (обновления, бэкапы, настройка RBAC).
*   **Управление состоянием (State):** GitOps идеально подходит для stateless-приложений. Для баз данных (stateful) автоматический синк может быть опасен: удаление манифеста в Git приведет к удалению БД и потере данных. Для баз часто отключают `prune` или управляют ими вне GitOps (например, через Terraform с защитой от удаления).
*   **Где отстреливает ногу:** Разделение CI и CD. Часто новички пытаются писать манифесты прямо из CI-пайплайна в тот же репозиторий с кодом приложения. Это приводит к бесконечным циклам коммитов и раздуванию истории. Правильный подход — держать инфраструктурные манифесты в *отдельном* репозитории от исходного кода.
*   **Границы применимости:** Если у вас один VPS-сервер и пара Docker-контейнеров, GitOps — это овер-инжиниринг. Для таких задач отлично подойдет обычный bash-скрипт или простой GitHub Actions CI/CD (Push модель). GitOps раскрывает свой потенциал в динамических средах вроде Kubernetes.
