# Keepalived и VRRP: Отказоустойчивость и плавающие IP

## 📖 История: Боль и Решение

**Боль:** Вы настроили мощный и быстрый Nginx или HAProxy для балансировки трафика на ваши бекенды. Но теперь сам этот балансировщик стал единой точкой отказа (Single Point of Failure, SPOF). Если сервер с Nginx падает, падает весь проект, несмотря на то, что за ним стоят десятки живых бекендов, потому что DNS запись указывает на один конкретный IP-адрес мертвого сервера.

**Решение:** **Keepalived**, использующий протокол **VRRP** (Virtual Router Redundancy Protocol). Он позволяет создать "плавающий" виртуальный IP-адрес (VIP), который делят между собой два или более сервера. Если основной сервер (Master) выходит из строя, резервный (Backup) замечает отсутствие heartbeat-сигналов и мгновенно перехватывает VIP на себя. Клиенты не замечают сбоя, так как IP-адрес остается прежним.

## 🛠 Примеры (Конфигурация Keepalived)

Конфигурация состоит из двух частей: проверка состояния локального сервиса (Nginx/HAProxy) и сама настройка VRRP.

```conf
# /etc/keepalived/keepalived.conf на MASTER сервере

# Скрипт для проверки, жив ли балансировщик
vrrp_script chk_haproxy {
    script "killall -0 haproxy" # Или "pidof haproxy", проверяем процесс
    interval 2                  # Запускать каждые 2 секунды
    weight -20                  # Если скрипт упал, уменьшаем приоритет на 20 (100 -> 80)
}

vrrp_instance VI_1 {
    state MASTER                # На втором сервере будет BACKUP
    interface eth0              # Сетевой интерфейс для VIP
    virtual_router_id 51        # Одинаковый ID для всех узлов кластера
    priority 100                # На втором сервере ставим меньше, например 90
    advert_int 1                # Интервал рассылки VRRP пакетов

    authentication {
        auth_type PASS
        auth_pass SecretP@ss    # Пароль для взаимодействия нод
    }

    virtual_ipaddress {
        10.0.0.100/24 dev eth0  # Тот самый плавающий VIP
    }

    track_script {
        chk_haproxy             # Привязываем скрипт проверки
    }
}
```

## 🚀 Day 2 Operations (Жизнь после деплоя)

* **Мониторинг переключений:** Настройте отправку алертов при смене состояния (Master -> Backup и наоборот). Keepalived поддерживает блок `notify`, куда можно передать bash-скрипт (например, для отправки сообщения в Slack/Telegram). Частые переключения ("флаппинг") — признак проблем с сетью.
* **Настройка `nopreempt`:** Если Master упал, VIP перешел на Backup. Когда Master поднимается, он (из-за высокого приоритета) сразу заберет VIP обратно. Это вызывает двойной разрыв соединений. Использование параметра `nopreempt` на Master'е (тогда он должен стартовать в состоянии BACKUP) позволяет избежать обратного переключения, если текущий узел стабилен.
* **Отладка сети:** VRRP использует Multicast (обычно 224.0.0.18). Убедитесь, что ваши коммутаторы и firewall (iptables/ufw) разрешают прохождение протокола VRRP (протокол IP номер 112, не путать с TCP/UDP портом 112).

## 💀 Антипаттерны

1. **Split-Brain (Раздвоение мозга):** Случается, если сетевая связность между Master и Backup обрывается, но оба имеют доступ в основную сеть. Оба считают, что другой мертв, и оба поднимают VIP. Возникают конфликты IP-адресов. **Решение:** использовать дополнительные проверки, например, пинговать шлюз по умолчанию или арбитражный сервер в скрипте проверки.
2. **Отсутствие проверки полезной нагрузки (Healthcheck):** Использование Keepalived без `vrrp_script`. Если Nginx/HAProxy завис или упал, но сам сервер жив и Keepalived работает, переключения не произойдет. Трафик будет уходить в никуда. Обязательно проверяйте состояние проксирующего сервиса!
3. **Использование Keepalived в облаках (AWS, GCP, Azure):** VRRP строится на L2-широковещании (ARP spoofing, Multicast). Большинство публичных облаков блокируют нестандартный L2/Multicast трафик и запрещают самостоятельное переназначение IP-адресов на интерфейсах. В облаках для отказоустойчивости следует использовать нативные балансировщики (AWS ELB) или сервисы Elastic IP/Floating IP, управляемые через API облака.
