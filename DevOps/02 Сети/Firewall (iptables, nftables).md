# Firewall в Linux: от iptables к nftables

## Проблема: Боль и спагетти-сети
Исторически для управления трафиком в Linux использовался `iptables`. Это надежный, но морально устаревший инструмент. Главная боль DevOps-инженера при работе с `iptables` — линейная структура правил. Когда кластер разрастается, количество цепочек и правил превращается в нечитаемое спагетти. Одно неверное правило DROP в начале цепочки, и половина сервисов ложится без внятных причин. Добавьте к этому отсутствие атомарных транзакций при обновлении правил — и перезагрузка фаервола превращается в русскую рулетку, когда на долю секунды сервер остается либо полностью открытым, либо полностью недоступным.

Ответом на эту боль стал `nftables` — современный подсистема ядра, пришедшая на замену `iptables`. Она предлагает структурированный синтаксис, атомарные применения конфигураций и лучшую производительность за счет объединения маршрутизации, фильтрации и NAT в единую логику.

## Как это работает
В основе обоих инструментов лежит фреймворк Netfilter, встроенный в ядро Linux. Он перехватывает сетевые пакеты на разных этапах их пути (хуках).

```mermaid
graph TD
    A[Входящий пакет] --> B{PREROUTING<br/>(NAT, Mangle)}
    B --> C{Решение о маршрутизации}
    C -- Локальный процесс --> D[INPUT]
    C -- Транзит --> E[FORWARD]
    D --> F((Локальный<br/>Процесс))
    F --> G[OUTPUT]
    E --> H{POSTROUTING<br/>(SNAT, Masquerade)}
    G --> H
    H --> I[Исходящий пакет]
```

## Примеры из практики

### Старая школа: iptables
Проброс порта (NAT) и разрешение трафика выглядели так:
```bash
# Разрешаем входящий SSH
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
# Проброс порта 80 на 8080
iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080
```

### Новый подход: nftables
В `nftables` конфигурация описывается декларативно и применяется атомарно:
```yaml
# /etc/nftables.conf
flush ruleset

table inet filter {
    chain input {
        type filter hook input priority 0; policy drop;
        
        # Разрешаем established/related соединения
        ct state established,related accept
        
        # Разрешаем loopback
        iif "lo" accept
        
        # Разрешаем SSH
        tcp dport 22 accept
    }
}
```
Применение: `nft -f /etc/nftables.conf`

## Day 2 Operations (Эксплуатация)

1. **Атомарные изменения**: В production конфигурации `nftables` следует применять только через файлы с командой `flush ruleset` в начале. Это гарантирует, что старые правила удаляются, а новые применяются единой транзакцией, не разрывая текущие сессии.
2. **Отладка (Где отстреливает ногу)**: Главная проблема — асимметричный роутинг и сброс пакетов по `ct state invalid`. Если пакет дропается, используйте логирование (TRACING) в nftables:
   ```bash
   nft add rule inet filter input tcp dport 80 meta nftrace set 1
   ```
   И смотрите в `nft monitor trace`.
3. **Совместимость с Docker/K8s**: Многие оркестраторы (например, Docker) все еще активно используют `iptables` под капотом, манипулируя таблицей NAT. Использование чистого `nftables` на таких хостах требует осторожности и настройки iptables-nft (прослойки совместимости).
