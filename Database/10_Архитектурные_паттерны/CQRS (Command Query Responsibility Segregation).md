# CQRS (Command Query Responsibility Segregation)

Архитектурный паттерн, суть которого заключается в строгом разделении операций чтения (Queries) и операций записи/изменения (Commands).

## Особенности
В традиционной CRUD (Create, Read, Update, Delete) архитектуре мы используем одну и ту же модель данных (и часто одну БД) для чтения и записи. В CQRS они разделяются:
- **Command (Запись)**: Выполняет бизнес-логику, валидацию и изменяет состояние системы. Ничего не возвращает (кроме статуса или ID).
- **Query (Чтение)**: Просто возвращает данные (DTO), не изменяя состояние. Часто использует денормализованные представления данных, оптимизированные специально для конкретных экранов UI.

## Варианты реализации
1. **На уровне кода**: Разные классы/сервисы для команд и запросов, но работают с одной базой данных.
2. **На уровне БД**: Разные базы данных (или реплики) для записи и чтения. База для чтения синхронизируется асинхронно через брокер сообщений (Event Bus), что приводит к согласованности в конечном счете (Eventual Consistency).

## Плюсы и минусы
- **Плюсы**: Независимое масштабирование чтения и записи (обычно чтения в разы больше); оптимизированные модели для UI без сложных JOIN; упрощение сложной бизнес-логики.
- **Минусы**: Значительное усложнение архитектуры; Eventual Consistency (пользователь может сохранить данные, но они не сразу появятся на экране чтения).
