# Базовое объяснение CRP

Существует 6 этапов CRP
Последовательность этих шагов, необходимая для первого отображения страницы, называется «Критический путь рендеринга»

| №   | Описание                | Задача             |
| --- | ----------------------- | ------------------ |
| 1   | построение DOM-дерева   | DOM                |
| 2   | построение CSSOM-дерева | CCSOM              |
| 3   | запуск JavaScript       | JavaScript         |
| 4   | создание Render-дерева  | Render DOM + CSSOM |
| 5   | генерация раскладки     | Layout             |
| 6   | отрисовка               | Paint              |

![[crp.png]]

## 1. Построение DOM-дерева

DOM (объектная модель документа) дерево это объект, представляющий полностью разобранную HTML-страницу. Начиная с корневого элемента `<html>`, узлы создаются для каждого элемента/текста на странице. Элементы, вложенные в другие элементы, представлены в виде дочерних узлов, и каждый узел содержит полный набор атрибутов для этого элемента. Например, элемент `<a>` будет иметь атрибут `href`, связанный с узлом.

Хорошая новость, касательно HTML, заключается в том, что он может быть исполнен по частям. Документ не должен быть загружен полностью для того, чтобы контент начал появляться на странице. Однако, другие ресурсы, такие как CSS и JavaScript, могут блокировать отрисовку страницы.

![[dom.webp]]
Пока браузер парсит документ и строит DOM, он натыкается на элементы типа [`<img>`](https://doka.guide/html/img/), [`<link>`](https://doka.guide/html/link/), [`<script>`](https://doka.guide/html/script/), которые содержат ссылки на другие ресурсы.

Если ресурс _неблокирующий_ (например, изображение), браузер запрашивает его параллельно с парсингом оставшейся части документа. _Блокирующие_ ресурсы (например, скрипты) приостанавливают обработку до своей полной загрузки.

Мы можем указывать браузеру, как именно ему следует запрашивать некоторые ресурсы, например, скрипты. Это может быть полезно, когда в скрипте мы собираемся работать с элементами, которые находятся в разметке после тега `<script>`:

## 2. Построение CSSOM-дерева

CSSOM (объектная модель CSS) — это объект, представляющий стили, связанные с DOM. Он выглядит так же как DOM, но с соответствующими стилями для каждого узла. Не имеет значения были ли стили объявлены явно или наследуются.
В файле style.css, подключающемся в ранее упомянутом документе, мы имеем следующий набор стилей:

CSS считается «блокирующим обработку ресурсом». Это значит, что Render-дерево не может быть построено без полного первоначального разбора CSS.
В отличии от HTML, CSS не может быть использован по частям в силу своей каскадной природы. Стили, описанные в документе ниже, могут переопределять и изменять стили, определённые ранее. Так что если мы начнём использовать CSS-стили до того, как будет разобрана таблица стилей, мы можем столкнуться с ситуацией, когда стили будут применяться неверно. Это означает, что для перехода к следующему шагу, необходимо полностью разобрать CSS.

CSS-файлы блокируют рендер только если они применяются. `<link rel="stylesheet"> `может принимать медиа-атрибут, в котором мы можем указать любое медиавыражение, к которому будут относиться вложенные внутрь стили. Если, например, мы имеем таблицу стилей с медиа-атрибутом orientation:landscape, а мы просматриваем страницу в портретном режиме, то этот ресурс не будет считаться блокирующим обработку.

Благодаря оптимизациям (например, сканеру предзагрузки) стили могут не блокировать чтение HTML, но они точно блокируют выполнение JavaScript, потому что в JS могут использоваться CSS-селекторы для выборки элементов.

![[cssom.webp]]

## 3. Запуск JavaScript

JavaScript является блокирующим ресурсом для парсера. Это означает, что JavaScript блокирует разбор самого HTML-документа.

Когда парсер доходит до тега `<script>` (не важно внутренний он или внешний), он останавливается, забирает файл (если он внешний) и запускает его. Вот почему, если мы имеем JavaScript-файл, который ссылается на элементы документа, мы обязательно должны поместить его после их появления.

JavaScript можно загружать асинхронно, указав атрибут `async`, для того, чтобы избежать блокировки парсера.

## 4. Создание Render-дерева

Render-дерево — это совокупность DOM и CSSOM. Это дерево, которое даёт представление о том, что в конечном итоге будет отображено на странице. Это означает, что оно захватывает только видимый контент и не включает, например, элементы, которые были скрыты с помощью CSS-правила `display: none`.

## 5. Генерация раскладки layout

Раскладка — это то, что определяет размер видимой области документа (viewport), которая обеспечивает контекст для стилей CSS, зависимых от него, например, проценты или единицы вьюпорта.

Размер вьюпорта определяется метатэгом, находящемся в `<head>` документа или, если тэг не представлен, будет использовано стандартное значение вьюпорта шириною в 980 пикселей.

Например, наиболее частым значением для этого метатэга является размер, соответствующий с шириной устройства.
```html
<meta name="viewport" content="width=device-width,initial-scale=1">
```

Если пользователь посещает веб-страницу с устройства, ширина которого, например 1000 пикселей, то размеры будут опираться на это значение. Половина видимой области будет равна 500 пикселей, 10 процентов — 100 пикселей, и так далее.

Важно помнить, что Layout построен на поточной модели компоновки. Это значит, что если элементы не влияют на расположение и размеры других элементов, то их положение и размеры можно просчитать за один подход.

Именно поэтому при вёрстке макетов рекомендуется «находиться в потоке» — чтобы браузеру не приходилось несколько раз пересчитывать один и тот же элемент, так страница отрисовывается быстрее.

### Глобальный и инкрементальный Layout

_Глобальный Layout_ — это процесс просчёта всего дерева полностью, то есть каждого элемента. _Инкрементальный_ — просчитывает только часть.

Глобальный Layout запускается, например, при изменении размера окна, потому что браузеру требуется подогнать всю страницу под новый размер экрана. Это **очень** дорогой процесс.

Инкрементальный Layout запускает пересчёт только «грязных» элементов.
#### «Грязные» элементы

Это те элементы, которые были изменены, и их дочерние элементы.

Если мы как-то поменяли блок, то браузер перерисует его и его детей, потому что их положение и размеры могут зависеть от родителя.

![[dirty.webp]]
Дальше браузер приступает к, собственно, отрисовке.

## 6 Отрисовка paint

Наконец, на шаге отрисовки, видимый контент страницы может быть преобразован в пиксели, чтобы появиться на экране.

Время, которое займет этот этап, зависит как от величины DOM, так и от того, какие стили применяются. Некоторые стили требуют больше усилий, чтобы быть применёнными, чем другие. Например, сложное градиентное фоновое изображение потребует больше времени, чем простой сплошной цвет на фоне.

Отрисовка тоже бывает _глобальной_ и _инкрементальной_. Чтобы понять, какую часть вьюпорта надо перерисовать, браузер делит весь вьюпорт на прямоугольные участки. Логика тут та же, как и в Layout — если изменения ограничены одним участком, то пометится «грязным» и перерисуется лишь он.

Отрисовка — это _самый_ дорогой процесс из всех, что мы уже перечислили.

### Порядок отрисовки

Порядок отрисовки связан со стековым контекстом.
В общих чертах, отрисовка начинается с заднего плана и постепенно переходит к переднему:

- `background-color`;
- `background-image`;
- `border`;
- `children`;
- `outline`.

### CPU и композитинг

И Layout, и Paint работают за счёт _CPU (central process unit)_, поэтому относительно медленные. Плавные анимации при таком раскладе невероятно дорогие.

Для плавных анимаций в браузерах предусмотрен композитинг (Compositing).

_Композитинг_ — это разделение содержимого страницы на «слои», которые браузер будет перерисовывать. Эти слои друг от друга не зависят, из-за чего изменение элемента в одном слое не затрагивает элементы из других слоёв, и перерисовывать их становится не нужно.

Именно из-за разнесения элементов по разным композиционным слоям свойство `transform` не так сильно нагружает браузер. Поэтому чтобы анимации не тормозили, их рекомендуется делать с применением `transform` и `opacity`.

![[layers.webp]]

Применение таких свойств, как, например, `transform`, «выносит» элемент на отдельный композитный слой, где положение элемента не зависит от других и не влияет на них.

> Чтобы узнать, вызывает ли конкретное CSS-свойство композитинг и перерисовку в браузере, воспользуйтесь инструментом «[CSS Triggers](https://csstriggers.com)».

### Перерисовка, Reflow (relayout) и Repaint

Процесс отрисовки — циклический. Браузер перерисовывает экран каждый раз, когда на странице происходят какие-то изменения.

Если, например, в DOM-дереве добавился новый узел, или изменился текст, то браузер построит новое дерево рендеринга и запустит вычисление позиции и отрисовку заново.

Один цикл обновления — это animation frame.

Зная «расписание отрисовки» браузера, мы можем «предупредить» его, что хотим запустить какую-то анимацию на каждый новый фрейм. Это можно сделать с помощью `requestAnimationFrame()`.

```js
const animate = () => {
  // Код анимации
}
```

Эта функция запускает новый кадр анимации: обновляет какое-то свойство или перерисовывает canvas.

Если мы хотим добиться плавной анимации, используя функцию выше, мы должны обеспечить в среднем 60 обновлений экрана за секунду (60 fps — frames per second).

Это можно сделать топорно, через интервал:
```js
// 60 раз в 1000 миллисекунд, приблизительно 16 мс.
const intervalMS = 1000 / 60
setInterval(animate, intervalMS)
```

Либо использовать `window.requestAnimationFrame()`:

```js
window.requestAnimationFrame(animate)
```

Интервалы не всегда запускаются в нужный момент. [`setInterval()`](https://doka.guide/js/setinterval/) не учитывает, на какой стадии отрисовки находится страница, и в итоге кадры отрисовки могут быть рваными или дёрганными.

С интервалом анимация может быть рваной, потому что перерисовка может быть запущена в неподходящее время.

А если вкладка была неактивна, то интервал может «попытаться догнать время», и несколько кадров запустятся разом:

![[reflow.webp]]

С `requestAnimationFrame()` анимация плавнее, потому что браузер знает, что в следующем фрейме надо запустить новый кадр анимации.

Она не гарантирует, что анимация будет запущена строго раз в 16 мс, но значение будет достаточно близким.

![[reflow-2.webp]]

> [!NOTE] Полезное
> Для динамики всегда используйте [`transform`](https://doka.guide/css/transform/) и [`opacity`](https://doka.guide/css/opacity/), избегайте изменения остальных свойств (типа `left`, `top`, [`margin`](https://doka.guide/css/margin/), [`background`](https://doka.guide/css/background/) и так далее).
>
> Таким образом вы дадите браузеру возможность оптимизировать отрисовку, отчего страница станет отзывчивее.
>
> Для анимаций, которые необходимо перерисовывать на каждый фрейм, используйте `requestAnimationFrame()`.
> 
> Это сделает тяжёлую анимацию менее рваной.

# Альтернативное объяснение CRP

Критический путь рендеринга (CRP) представляет собой последовательность шагов, которые веб-браузер выполняет для преобразования HTML, CSS и JavaScript кода в визуальное представление веб-страницы на экране пользователя. Этот процесс имеет основополагающее значение для того, как пользователи воспринимают веб-сайты, напрямую влияя на ощущаемую производительность и удобство использования. Понимание и оптимизация CRP являются ключевыми факторами для обеспечения быстрой загрузки страниц, что, в свою очередь, приводит к улучшению пользовательского опыта, снижению показателей отказов и потенциально повышению рейтинга в поисковых системах.

Процесс CRP начинается с момента, когда браузер получает HTML-документ, и продолжается до тех пор, пока страница не начинает отображаться на экране. Для этого браузеру необходим не только сам HTML-документ, но и все критически важные ресурсы, необходимые для его рендеринга. К таким ресурсам обычно относятся CSS, который определяет внешний вид страницы, и JavaScript, который может изменять структуру (DOM) и стиль (CSSOM) страницы. Последовательность шагов, которые браузер предпринимает для выполнения этой первоначальной отрисовки, и называется критическим путем рендеринга.

Оптимизация CRP имеет первостепенное значение для достижения высокой производительности веб-сайта. Задержки в первоначальном рендеринге могут привести к разочарованию пользователей и увеличению вероятности того, что они покинут сайт. Более того, оптимизированный CRP не только сокращает время до первой отрисовки, но и обеспечивает плавные повторные отрисовки и перекомпоновки, необходимые для быстрой работы интерактивных веб-приложений. Понимание CRP позволяет разработчикам принимать обоснованные решения о том, как структурировать свои веб-страницы и доставлять ресурсы, чтобы обеспечить максимально быструю и эффективную отрисовку.

## Шесть этапов критического пути рендеринга

Процесс критического пути рендеринга можно разбить на шесть основных этапов, которые браузер выполняет последовательно для отображения веб-страницы:

1. **Конструирование DOM-дерева (Document Object Model).**
2. **Конструирование CSSOM-дерева (CSS Object Model).**
3. **Выполнение JavaScript.**
4. **Создание дерева рендеринга.**
5. **Генерация макета (компоновка).**
6. **Отрисовка (рисование).**

Хотя некоторые источники могут детализировать этот процесс на большее количество шагов, включая композицию и физическое рисование пикселей на экране, эти шесть этапов представляют собой ядро CRP и обеспечивают четкую структуру для понимания процесса рендеринга. Важно отметить, что выполнение JavaScript на определенном этапе подчеркивает его способность изменять DOM и CSSOM, влияя тем самым на последующие этапы CRP.

**Таблица 1: Шесть этапов критического пути рендеринга**

| **Этап**                      | **Описание**                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Конструирование DOM-дерева    | Браузер анализирует HTML-разметку и создает объектное представление структуры документа в виде дерева элементов HTML.                                           |
| Конструирование CSSOM-дерева  | Браузер анализирует CSS (как встроенный, так и внешний) и создает объектное представление стилей, применяемых к элементам HTML.                                 |
| Выполнение JavaScript         | Браузер выполняет любой JavaScript-код, который может изменять DOM и CSSOM, потенциально вызывая дальнейшие процессы рендеринга.                                |
| Создание дерева рендеринга    | Браузер объединяет DOM и CSSOM для создания дерева рендеринга, которое включает только видимые элементы DOM с их соответствующими стилями.                      |
| Генерация макета (компоновка) | Браузер вычисляет точный размер и положение каждого элемента в дереве рендеринга в пределах области просмотра, определяя, где они будут отображаться на экране. |
| Отрисовка (рисование)         | Браузер проходит по дереву рендеринга и рисует визуальное представление каждого элемента (текст, изображения, цвета и т. д.) на экране в виде пикселей.         |

## Подробное описание каждого этапа CRP**

- **Этап 1: Конструирование DOM-дерева**
    
    Первым шагом в CRP является конструирование объектной модели документа (DOM). Когда браузер получает HTML-документ, он начинает его анализ. Этот процесс является инкрементным, то есть браузер начинает обработку HTML, как только получает первые части документа. HTML-парсер преобразует полученные байты в символы, затем символы в токены, которые идентифицируют различные части HTML-разметки, такие как теги, атрибуты и текстовое содержимое. Затем эти токены преобразуются в DOM-узлы, которые организуются в иерархическую древовидную структуру, известную как DOM-дерево. Корневым элементом этого дерева является элемент `<html>`, а все остальные элементы HTML становятся его дочерними узлами, отражая вложенность HTML-документа. Каждый узел DOM содержит всю соответствующую информацию об HTML-элементе, представленную с помощью токенов.
    
    Инкрементный характер построения DOM позволяет браузеру начинать обработку HTML и обнаруживать внешние ресурсы, такие как CSS и JavaScript, на ранних этапах загрузки страницы 1. Это способствует более быстрой отрисовке, поскольку браузер может начать загрузку этих ресурсов параллельно с дальнейшим анализом HTML. Иерархическая структура DOM-дерева имеет решающее значение для последующих этапов CRP, так как она определяет, как применяются CSS-стили и как рассчитывается макет страницы 1.
    
- **Этап 2: Конструирование CSSOM-дерева**
    
    Параллельно с построением DOM-дерева, или сразу после его завершения, браузер сталкивается с CSS-правилами, которые могут быть встроены в HTML-документ с помощью тегов `<style>` или подключены как внешние файлы `.css` с помощью тегов `<link>`. Браузер анализирует этот CSS для построения объектной модели CSS (CSSOM). Подобно DOM, CSSOM представляет собой объектное представление CSS-правил, применяемых к документу. Он включает в себя стили, явно определенные разработчиком, а также стили, унаследованные от родительских элементов или являющиеся стилями браузера по умолчанию. CSS-парсер идентифицирует допустимые токены в CSS и преобразует их в узлы CSSOM, которые также организуются в древовидную структуру. В отличие от HTML, построение CSSOM обычно не является инкрементным; браузер блокирует рендеринг страницы до тех пор, пока не будет получен и обработан весь CSS. Это связано с каскадным характером CSS, где более поздние правила могут переопределять более ранние, поэтому браузеру необходимо знать окончательный набор стилей перед началом рендеринга. Таким образом, CSS считается блокирующим отрисовку ресурсом.
    
    Неинкрементный характер построения CSSOM и его блокирующее поведение подчеркивают решающую роль CSS в определении визуального представления веб-страницы. Браузеру необходимо полностью обработать все CSS-правила, чтобы обеспечить правильное применение стилей перед началом рендеринга. Это имеет важные последствия для оптимизации производительности, поскольку большие или неоптимизированные CSS-файлы могут значительно задержать первоначальную отрисовку страницы.
    
- **Этап 3: Выполнение JavaScript**
    
    Когда HTML-парсер встречает тег `<script>` в HTML-документе, он обычно приостанавливает анализ HTML и загружает (если это внешний скрипт, указанный атрибутом `src`) и выполняет JavaScript-код. По умолчанию JavaScript является ресурсом, блокирующим парсер, что означает, что он может задержать построение DOM. Выполнение JavaScript может затем дополнительно повлиять на процесс рендеринга, напрямую манипулируя DOM и CSSOM. Например, JavaScript может добавлять, удалять или изменять HTML-элементы, изменять CSS-стили или даже запускать анимацию и другие визуальные эффекты. Эти изменения могут затем потребовать дальнейшей обработки браузером, такой как перерасчет стилей, макета (перекомпоновка) и перерисовка.
    
    Поведение JavaScript по умолчанию, блокирующее парсер, может существенно повлиять на CRP, задерживая построение DOM. Это заставляет разработчиков стратегически размещать теги `<script>` в своем HTML (например, перед закрывающим тегом `</body>`) или использовать атрибуты `async` и `defer` для контроля над тем, когда JavaScript загружается и выполняется, минимизируя его блокирующий эффект на первоначальный рендеринг. JavaScript часто ждет завершения построения CSSOM перед выполнением, поскольку он может зависеть от стилей, применяемых к элементам.
    
- **Этап 4: Создание дерева рендеринга**
    
    После того как браузер построил как DOM-дерево, так и CSSOM-дерево, он объединяет эти две структуры данных для создания дерева рендеринга. Дерево рендеринга представляет собой визуальное представление веб-страницы, которая будет фактически отображаться на экране. Оно включает в себя только те элементы DOM, которые предназначены для отображения, вместе с их соответствующими стилями. Для каждого видимого узла в DOM браузер находит соответствующие правила CSSOM и применяет их Элементы, которые не являются видимыми (например, элементы внутри раздела `<head>`, который обычно содержит метаданные, а не видимое содержимое, или элементы, к которым применено CSS-свойство `display: none;`), исключаются из дерева рендеринга, как и любые их потомки. Это гарантирует, что браузер обрабатывает и отображает только то содержимое, которое пользователь фактически увидит.
    
    Дерево рендеринга служит важнейшим промежуточным шагом в процессе рендеринга, эффективно объединяя содержимое HTML (из DOM) с информацией о стилях CSS (из CSSOM) в единую структуру, представляющую то, что будет визуально представлено пользователю. Исключение невидимых элементов из дерева рендеринга является важной оптимизацией, которая помогает повысить производительность рендеринга.
    
- **Этап 5: Генерация макета (компоновка)**
    
    После построения дерева рендеринга браузер переходит к этапу макета, также часто называемому компоновкой или "reflow". На этом этапе браузер вычисляет точный размер и положение каждого элемента в дереве рендеринга в области просмотра (видимой области окна браузера). Это включает определение ширины и высоты каждого элемента, а также его координат относительно других элементов на странице. Процесс компоновки учитывает различные факторы, включая размер области просмотра, свойства CSS box model (такие как ширина, высота, отступы, поля и границы) и схему позиционирования, применяемую к каждому элементу (например, static, relative, absolute, fixed). Этот этап имеет решающее значение для обеспечения правильного визуального расположения веб-страницы.
    
    Этап макета является сложным процессом, который может быть ресурсоемким, особенно на сложных страницах с большим количеством элементов. Важно отметить, что макет - это не только одноразовый процесс, происходящий при первоначальной загрузке страницы. Он может быть запущен повторно всякий раз, когда происходят изменения, влияющие на геометрию страницы, такие как изменение размера окна браузера, изменение содержимого элемента или динамическое изменение стилей, влияющих на размер или положение элемента. Эти последующие вычисления макета (перекомпоновки) могут негативно сказаться на производительности, поэтому минимизация ненужных перекомпоновок является важным аспектом оптимизации производительности веб-сайта.
    
- **Этап 6: Отрисовка (рисование)**
    
    Последним этапом в критическом пути рендеринга является отрисовка, которую иногда называют рисованием или растеризацией. На этом шаге браузер проходит по дереву рендеринга и преобразует каждый узел в фактические пиксели на экране. Это включает в себя рисование визуального представления каждого элемента, включая его текстовое содержимое, цвета, изображения, границы, тени и другие визуальные стили. Для первоначальной загрузки страницы необходимо отрисовать всю область просмотра. Однако для последующих обновлений или взаимодействий, которые вызывают изменения во внешнем виде страницы, браузер оптимизирован для повторной отрисовки только тех областей экрана, которые были затронуты, а не всей области просмотра. Этот процесс известен как "перерисовка" и помогает повысить производительность, избегая ненужных операций рисования.
    
    Этап отрисовки является завершающим шагом в процессе визуального отображения веб-страницы пользователю. Именно здесь все предшествующие вычисления и приготовления преобразуются в фактические пиксели, формирующие визуальный опыт пользователя на сайте. Оптимизация этого этапа, хотя он обычно является быстрым, все же важна для обеспечения плавной анимации и взаимодействия.
    

## Последовательный поток критического пути рендеринга

Выполнение шести этапов CRP следует определенной последовательности, хотя этот процесс может быть итеративным, особенно когда JavaScript изменяет DOM или CSSOM. Общий поток выглядит следующим образом:

1. **Конструирование DOM-дерева:** Браузер анализирует HTML и строит DOM-дерево инкрементно.
2. **Конструирование CSSOM-дерева:** Браузер анализирует CSS и строит CSSOM-дерево. Это обычно происходит параллельно с построением DOM, но обычно завершается после полного анализа HTML, поскольку CSS является ресурсом, блокирующим отрисовку.
3. **Выполнение JavaScript:** Когда парсер встречает тег `<script>` (без атрибутов `async` или `defer`), он приостанавливает построение DOM для загрузки и выполнения JavaScript. JavaScript может затем изменять DOM и CSSOM.
4. **Создание дерева рендеринга:** Как только DOM и CSSOM становятся доступны, браузер объединяет их для создания дерева рендеринга, которое включает только видимые элементы с их примененными стилями.
5. **Генерация макета:** Браузер вычисляет размер и положение каждого элемента в дереве рендеринга в пределах области просмотра.
6. **Отрисовка:** Браузер проходит по дереву рендеринга и рисует визуальное представление макета на экране в виде пикселей.

Последовательный характер CRP означает, что задержки на любом одном этапе могут напрямую повлиять на общее время рендеринга. Например, большой HTML-документ потребует больше времени для анализа и построения DOM, что задержит построение CSSOM и все последующие шаги. Понимание этой последовательности помогает разработчикам выявлять критические узкие места в процессе рендеринга и приоритизировать усилия по оптимизации на тех этапах, которые оказывают наиболее значительное влияние на время до первой отрисовки.

Существуют также зависимости и взаимодействия между различными этапами. Дерево рендеринга зависит от построения как DOM, так и CSSOM. Этап макета требует завершения дерева рендеринга, поскольку он вычисляет размер и положение каждого элемента в этом дереве. Этап отрисовки зависит от результатов этапа макета, так как ему необходимо знать точное положение и размеры каждого элемента для их рисования на экране. JavaScript может взаимодействовать с DOM и CSSOM и изменять их, что может привести к повторному созданию дерева рендеринга, повторному вычислению макета и повторной отрисовке затронутых областей. CSS может влиять на выполнение JavaScript, поскольку скрипты могут зависеть от доступности CSSOM. Эти взаимосвязи подчеркивают, что оптимизация более ранних этапов может иметь положительный каскадный эффект на более поздние этапы, что делает целостный подход к оптимизации CRP наиболее эффективным.

**5. Важность оптимизации критического пути рендеринга**

Оптимизация CRP напрямую влияет на время первоначальной загрузки страницы и ощущаемую производительность. Сокращение времени, необходимого браузеру для выполнения шагов, необходимых для отрисовки первоначального вида веб-страницы, приводит к более быстрому времени до первой отрисовки (TTFR). Это имеет решающее значение для первого впечатления пользователя от веб-сайта. Быстрая первоначальная отрисовка обеспечивает немедленную визуальную обратную связь, создавая впечатление, что веб-сайт быстро реагирует, даже если другие ресурсы все еще загружаются в фоновом режиме.

Более того, оптимизация CRP значительно улучшает пользовательский опыт за счет сокращения задержек при загрузке. Длинный CRP может привести к заметной задержке перед тем, как пользователь увидит какое-либо содержимое на экране, что приводит к разочарованию и увеличению вероятности того, что он покинет сайт. Минимизируя эти задержки, разработчики могут обеспечить более плавный и приятный опыт для своих пользователей.

Оптимизация CRP также играет важную роль в обеспечении плавного взаимодействия и предотвращении узких мест в производительности. Эффективная первоначальная отрисовка позволяет браузеру лучше справляться с последующими взаимодействиями и анимацией, избегая таких проблем, как "jank" (визуальные рывки или прерывистые движения) или задержки. Хорошо оптимизированный CRP помогает браузеру поддерживать стабильную частоту кадров, что приводит к более плавному и привлекательному пользовательскому опыту.

Наконец, CRP напрямую связан с ключевыми показателями производительности веб-сайта, такими как First Contentful Paint (FCP) и Time to Interactive (TTI). FCP измеряет время с момента запроса пользователем страницы до момента, когда на экране отображается первый элемент контента (текст, изображение, canvas или SVG). TTI измеряет время с момента начала загрузки страницы до момента, когда ее основные интерактивные компоненты становятся надежно интерактивными. Оптимизация CRP часто является необходимым условием для улучшения этих показателей. Более быстрые значения FCP и TTI указывают на более высокую производительность веб-сайта и лучший пользовательский опыт, что также может положительно сказаться на рейтинге в поисковых системах.

## Анализ и оптимизация критического пути рендеринга

- **Анализ CRP**
    
    Современные веб-браузеры предоставляют мощные инструменты разработчика, которые позволяют анализировать критический путь рендеринга веб-страницы. Вкладка "Производительность" (ранее "Timeline" в некоторых браузерах) особенно полезна для визуализации последовательности событий, происходящих во время загрузки страницы. Эта вкладка обычно отображает временную шкалу, показывающую, когда браузер запрашивал различные ресурсы, сколько времени потребовалось для их загрузки и сколько времени было потрачено на различных этапах процесса рендеринга, включая построение DOM, построение CSSOM, выполнение JavaScript, макет и отрисовку. Изучая эту временную шкалу, разработчики могут выявлять узкие места и понимать, какие ресурсы загружаются или обрабатываются дольше всего, что дает ценную информацию для оптимизации. Эти инструменты позволяют увидеть, какие именно ресурсы блокируют рендеринг и сколько времени занимает каждый этап, что позволяет сосредоточить усилия на наиболее важных областях.
    
    Важным шагом в анализе CRP является определение того, какие ресурсы считаются "критическими" для первоначального рендеринга страницы, и выявление любых из этих ресурсов, которые вызывают значительные задержки (узкие места). Критические ресурсы обычно включают сам HTML-документ, CSS, блокирующий отрисовку (обычно находящийся в разделе `<head>`), и JavaScript, блокирующий парсер (также часто размещаемый в разделе `<head>`). Изучая сетевые запросы в инструментах разработчика браузера и анализируя временную шкалу рендеринга, разработчики могут идентифицировать эти критические ресурсы и увидеть, сколько времени занимает их загрузка и обработка. Любой ресурс, который значительно задерживает процесс рендеринга, считается узким местом и должен быть приоритетным для оптимизации. На длину критического пути также влияют размер документа, количество запросов, устройство пользователя и применяемые стили.
    
- **Методы оптимизации**
    
    Одним из наиболее эффективных способов оптимизации CRP является минимизация количества критических ресурсов (CSS и JavaScript). Это может включать определение того, какие CSS и JavaScript файлы абсолютно необходимы для отображения содержимого над сгибом, и откладывание загрузки любых некритических ресурсов до завершения первоначальной отрисовки. Такие методы, как разделение кода в JavaScript и тщательная организация CSS, могут помочь в достижении этой цели.
    
    Даже если ресурс считается критическим для первоначального рендеринга, уменьшение размера его файла может значительно сократить время загрузки и, следовательно, сократить CRP. Для минимизации объема этих критических ресурсов можно использовать такие методы, как минификация (удаление ненужных символов, таких как пробелы и комментарии, из кода CSS и JavaScript) и сжатие (использование алгоритмов, таких как Gzip или Brotli, для уменьшения размера передаваемых данных).
    
    Порядок загрузки критических ресурсов также может существенно повлиять на CRP. Часто бывает полезно обеспечить первоочередную загрузку ресурсов, необходимых для отображения содержимого над сгибом. Такие методы, как встраивание критически важного CSS и использование атрибута `<link rel="preload">`, могут помочь приоритизировать загрузку важных ресурсов, позволяя браузеру обнаруживать и загружать их на более ранних этапах процесса рендеринга.
    
    Встраивание критически важного CSS предполагает включение минимального набора CSS-правил, необходимых для отображения содержимого над сгибом, непосредственно в раздел `<head>` HTML-документа с помощью тегов `<style>`. Это устраняет необходимость в дополнительном HTTP-запросе для получения внешнего CSS-файла, что позволяет браузеру гораздо быстрее отображать видимую часть страницы. Оставшийся некритический CSS может быть загружен асинхронно или отложен.
    
    Код JavaScript, который не является существенным для первоначального рендеринга страницы, может быть отложен или загружен асинхронно с помощью атрибутов `defer` и `async` в тегах `<script>`. Атрибут `defer` сообщает браузеру о необходимости загрузить скрипт без блокировки анализа HTML и выполнить его только после полного анализа HTML-документа. Атрибут `async` также загружает скрипт без блокировки анализа, но выполняет его, как только он становится доступен, что может произойти до полного анализа HTML. Выбор между `defer` и `async` зависит от того, полагается ли скрипт на полностью построенный DOM или на другие скрипты.
    
    Использование подсказок браузера, таких как `preload`, `prefetch` и `preconnect`, также может принести значительную пользу производительности. `<link rel="preload">` сообщает браузеру о необходимости как можно раньше получить ресурс, поскольку он критически важен для текущей страницы. `<link rel="prefetch">` указывает, что ресурс может понадобиться для будущей навигации и может быть получен в фоновом режиме, когда браузер простаивает. `<link rel="preconnect">` позволяет браузеру установить раннее соединение с сервером, что может быть особенно полезно для ресурсов, размещенных на другом домене, таких как шрифты с CDN.
    
    Наконец, оптимизация структуры DOM также может улучшить CRP. Сложное или чрезмерно большое DOM-дерево может негативно сказаться на производительности, поскольку браузеру необходимо проходить и обрабатывать все узлы в процессе рендеринга. Оптимизация структуры DOM путем удаления ненужных элементов, упрощения иерархии и использования эффективной HTML-разметки может привести к более быстрому построению DOM и повысить производительность последующих этапов, таких как макет и отрисовка.
    

## Заключение

Критический путь рендеринга является фундаментальным процессом, определяющим производительность веб-сайтов и пользовательский опыт. Понимание шести этапов CRP, их последовательности и взаимозависимостей имеет решающее значение для разработчиков, стремящихся оптимизировать время загрузки своих страниц. Минимизируя количество критических ресурсов, оптимизируя их размер, контролируя порядок их загрузки и используя такие методы, как встраивание критически важного CSS и асинхронная загрузка JavaScript, разработчики могут значительно сократить CRP и обеспечить более быструю и плавную работу своих веб-сайтов. Постоянный анализ CRP с помощью инструментов разработчика браузера и применение соответствующих методов оптимизации являются неотъемлемой частью создания высокопроизводительных веб-приложений, которые обеспечивают превосходный пользовательский опыт.
